本参考规定 Product Proposal 的判断质量与完整结构。它不预设具体产品、行业、技术方案或商业模式。所有结论都要从当前项目材料、PM 已确认判断和可核实证据重新推导。

## 一、完成标准

Product Proposal 是产品级投入与方向决策文档。读者看完应能回答：

- 哪个问题值得现在解决；
- 先服务谁，他们当前如何处理；
- 产品通过什么机制改变结果；
- 为什么是产品机会，而不是一次性交付或功能补丁；
- 产品负责什么，不负责什么；
- 为什么需要关键技术；AI 产品为什么必须使用 AI；
- 有哪些现实替代方案，为什么仍值得投入；
- 产品价值如何被观察和验证；
- MVP 用最小投入证明什么，什么结果会停止投入；
- design 下一步要把哪个结果设计成可建造方案。

“完整”指这些判断全部有结论、证据等级或验证方式，不等于固定字数。简单产品可以短写，但不能删除关键判断；不适用的项要写明“不适用”及理由。

以下产物都不能代替完整 Proposal：

- 只有一句定位和功能列表的产品介绍；
- 只列市场规模与竞品的研究报告；
- 只描述页面和流程的 PRD；
- 只列风险和问题、不做推荐的诊断稿；
- 只写愿景、没有 MVP 证伪门的战略叙事；
- 只记录相对旧方向变化的 delta 文档。

## 二、证据纪律

### 2.1 三档证据

每个会改变产品方向的判断，在后台标注一档证据：

| 档位 | 定义 | 写法 |
|---|---|---|
| 已确认事实 | 项目真相源、真实产品、PM 明确决定、一手客户材料或可靠数据可直接支持 | 作为当前事实陈述，并能指出来源 |
| 有依据的推断 | 多条事实共同支持，但尚未被真实使用或结果验证 | 写“当前判断是”，同时说明依据和限制 |
| 待验证假设 | 产品方向依赖它，但当前没有足够证据 | 明确标为假设，并放入 MVP 或调研验证 |

不得把竞品官网没写某项能力解释为竞品没有；不得把访谈中的兴趣解释为付费意愿；不得用行业趋势替代当前产品的用户证据；不得虚构业务基线、财务收益或成功阈值。

### 2.2 现状替代比竞品标签更重要

先回答用户现在如何凑合：人工流程、表格、会议、外包服务、通用工具、既有系统，或直接放弃。这个现状替代决定迁移成本和产品必须明显优于什么。

竞品研究只在会改变产品定义、边界、购买理由或 MVP 时展开。研究时对齐同一个用户任务，并记录来源和观察日期；功能名相似不代表解决了同一问题。

### 2.3 危险前提与反例

至少写出一个最危险前提：它一旦不成立，当前产品回答或 MVP 就应该改变。

推荐句式：

```text
最危险前提：<当前方向依赖的关键假设>。
若 <可观察的反例> 出现，方向应改为 <收缩、换用户、换机制或停止>。
验证方式：<在投入扩大前如何获得证据>。
```

危险前提不能只写“技术可能失败”或“市场竞争激烈”。它应具体到用户是否改变行为、价值链是否闭合、关键数据是否可得、责任方是否愿意承担新动作，或产品是否真的需要 AI。

## 三、产品判断顺序

### 3.1 先定要支持的决定

先写一句：

```text
这份 Proposal 要支持的决定是：是否以 <产品回答> 服务 <目标用户与场景>，并先投入 <MVP> 验证 <关键主张>。
```

Proposal 可以支持立项、方向重判、MVP 投入或停止投入，但一份文档只保留一个主要决定。不要把“对外怎么介绍”和“产品是否成立”混成同一个目的。

### 3.2 问题、原因和后果分开

- **表层现象**：用户看到或抱怨什么；
- **结构原因**：为什么现有产品或流程持续产生这个问题；
- **业务后果**：用户做错、做慢、放弃或承担什么成本；
- **机会条件**：什么变化让新产品回答现在可行。

如果产品只改善一个低频小动作，应先判断它是不是模块需求，而不是产品级 Proposal。

### 3.3 用户按责任而不是画像标签定义

至少区分：

- 谁为结果负责；
- 谁直接使用产品；
- 谁提供输入或协同；
- 谁购买或批准投入；
- 谁影响准入、安全、数据或合规。

同一个人可以承担多个责任。只保留与产品成立、使用或购买有关的角色，不为表格完整硬造角色。

用户描述必须具体到“在什么触发时刻，需要做什么判断或动作”。“企业用户”“管理者”“年轻人”都不够具体。

### 3.4 产品回答先讲机制，再讲功能

产品回答应解释：用户的工作方式将如何变化，哪些信息、判断或动作从谁转移给谁，产品如何形成稳定结果。

推荐顺序：

1. 用户从什么入口或事件开始；
2. 产品怎样理解或组织必要输入；
3. 产品提供什么关键判断、能力或协作；
4. 用户据此采取什么行动；
5. 结果如何反馈并影响下一次使用。

随后再归纳三至七个关键能力。能力必须来自端到端体验，不从页面菜单、技术组件或竞品清单倒推。

### 3.5 产品边界要能排除错误投入

同时写清：

- 产品直接负责的结果；
- 需要用户、外部系统或服务方承担的工作；
- MVP 暂不覆盖的内容；
- 长期也不应成为本产品职责的内容。

边界不是“后续再做”的功能列表，而是防止产品变成另一种产品的责任划分。

### 3.6 价值必须形成因果链

通用价值链：

```text
产品能力
→ 用户判断或行为变化
→ 可观察的任务 / 业务结果
→ 用户、组织或商业价值
```

按产品类型选择终点：

- 个人产品：时间、焦虑、习惯、完成率、健康或生活结果；
- 企业产品：收入、成本、交付、回款、风险、资源利用和组织能力；
- 开发者或平台产品：交付速度、可靠性、认知负担、维护成本、采用与留存；
- 公共或非营利产品：覆盖、公平性、服务质量、资源利用和社会结果。

“提效”“更智能”“准确率更高”“活跃度提升”通常只是中间指标。需要继续说明它为什么会改变真实结果。

## 四、通用 Proposal 结构

### 文档头

```markdown
# <产品名> Product Proposal

> 版本：vN
> Proposal ID：<slug>-vN
> 状态：待确认 | 当前 | 已被 `<新版本路径>` 取代
> 日期：YYYY-MM-DD
> 取代：无 | `<旧版本路径>`
> 支持的决定：<一句话>
> 证据截至：YYYY-MM-DD
```

### 0. 决策摘要与产品主张

让不了解细节的决策者快速判断是否值得继续读。必须包含：

- 一句话定位；
- 目标用户和关键场景；
- 核心问题及其后果；
- 产品机制与职责边界；
- 预期价值；
- MVP 建议；
- 最危险前提。

一句话定位优先使用：

```text
面向 <具体用户>，在 <触发场景> 下，帮助他们从 <现状方式> 转为 <新的判断或行动方式>，从而获得 <可观察结果> 的 <产品类型>。
```

不要把“AI 驱动”“一站式”“全链路”当作产品主张。

### 1. 产品成立的核心判断

写三至五条可证伪判断，说明产品建立在哪些用户、市场、技术或工作方式变化之上。每条判断回答：

- 什么事实或信号支持它；
- 它如何影响后续取舍；
- 什么证据会推翻它。

同时写产品原则。原则必须能排除某种产品做法，不能只是“简单、专业、智能”。

### 2. 用户、场景、问题与现状替代

写清结果负责人、直接用户、协同角色、购买者和准入影响者。围绕一个主场景连续说明：

- 触发条件和当前目标；
- 用户现有做法；
- 表层问题、结构原因和实际后果；
- 为什么现有替代仍不足；
- 用户需要改变什么行为或责任。

辅助场景只保留能证明产品可扩展、或会改变核心边界的场景。

### 3. 产品回答与职责边界

说明产品怎样改变用户完成目标的方式，而不是罗列页面。至少包含：

- 核心机制；
- 产品负责的输入、判断、协作或结果；
- 人、外部系统、服务和当前产品之间的责任；
- 明确非目标；
- 必要的核心业务概念。

技术对象只有在业务概念清楚后才能命名。

### 4. 必要能力与 AI 角色

先给非 AI 基线：传统软件、规则、搜索、分析和人工分别能解决什么。然后判断哪些任务需要更强能力。

AI 产品必须说明：

- AI 具体承担哪个任务，为什么确定性方案不足；
- 输入、输出、不确定性和评价方式；
- 哪些工作自动完成，哪些由人确认、校准或审批；
- AI 出错如何被发现、限制和恢复；
- 模型、当前产品、运行环境和外部系统各自负责什么。

非 AI 产品保留本节，写明关键能力为什么可以由确定性软件或人工流程可靠完成，以及为什么不引入 AI。

### 5. 替代方案、竞争判断与产品机会

至少比较：现状人工方案、相邻产品或服务、直接竞品，以及“不采取行动”。每类只回答：

- 已解决什么用户任务；
- 成立条件与限制；
- 当前产品应学习什么；
- 哪些做法不适合当前目标；
- 仍需验证的机会是什么。

不能证明独占空白时，机会写成待验证的产品范式、工作方式、用户切口或交付方式变化，不声称“竞品做不到”。

### 6. 端到端产品体验与关键能力

从用户的业务目标开始，描述一次完整体验：触发、准备输入、关键判断、主要动作、结果反馈、异常处理和完成状态。

再列关键能力：

| 关键能力 | 主要用户 | 解决的问题 | 输入与结果 | 产品边界 | MVP 状态 |
|---|---|---|---|---|---|

这张表是产品级能力地图，不写字段、按钮、页面层级、接口或验收细则。具体信息模型和交互交给 design。

### 7. 产品价值、因果链与指标

分别说明直接用户价值和整体产品价值。每条价值都沿“能力—行为—结果—最终价值”展开，并区分：

- 领先指标：MVP 周期内较早可观察；
- 滞后指标：需要更长时间才能确认；
- 归因方式：如何避免把外部变化当成产品贡献；
- 成立条件：对哪些用户、场景和时间范围有效。

没有基线时先定义取数与对照方法，不虚构百分比或金额。

### 8. MVP 范围、完整案例与决策门

先写一句 MVP 核心假设，再写：

- 唯一主用户和主场景；
- 必须覆盖的最小能力；
- 必须存在的外部依赖；
- 明确不做；
- 一次端到端 Case Rundown；
- 产品、质量、行为和结果指标；
- 继续投入、调整方向、停止投入的条件。

MVP 是最小价值闭环，不是最少页面或最少功能。只验证技术可行性、模型准确率或功能完成度，不足以证明产品成立。

### 9. 演进条件与长期方向

只写建立在 MVP 结果上的演进。每个阶段包含：

- 扩展哪个用户、场景、能力或市场；
- 上一阶段必须先证明什么；
- 价值如何扩大；
- 哪些边界继续保持；
- 什么信号会让这一阶段不启动。

愿景不是功能愿望池，也不进入 `TODO.md`。

### 10. 下游交接摘要

严格使用第七节的固定结构，不自行改成模块规格。

## 五、企业产品与 AI 产品专项检查

这些是通用结构上的专项检查，不额外增加一套 Proposal 模板。

### 5.1 企业产品

企业产品额外检查：

- 直接用户、结果负责人、购买者、IT / 安全 / 合规准入者是否分清；
- 产品价值是否从员工动作连接到经营结果，再谨慎连接到财务结果；
- 部署、数据、权限、审计和采购要求是否会改变产品边界；
- 产品是否把咨询交付中的一次性工作误写成标准能力；
- MVP 是否在一个真实企业场景里验证使用和结果，而非只完成演示。

企业价值可以参考：收入质量、毛利、交付成本、回款、现金流、风险损失、费用率、资源利用和组织能力。只选择当前业务真正关心且可以建立因果链的指标。

### 5.2 AI 产品

AI 必要性只在具体任务上成立。适合 AI 的常见信号包括：需要理解非结构化信息、处理模糊性与例外、组合多类证据、持续感知变化、生成可校准建议，或从反馈中改进判断。

以下工作优先用确定性软件：身份与权限校验、金额计算、固定状态迁移、不可变审计、明确规则和高风险硬约束。AI 可以辅助解释或发现异常，但不能冒充最终真相源。

若产品包含 Agent，额外回答：

- 它是等待人发起，还是在明确目标下持续工作；
- 可以观察、建议、执行到什么程度；
- 哪些动作必须由人批准；
- 运行记录、反馈和结果如何进入评价；
- 当前产品是否提供 Agent Runtime；若不提供，下游运行责任在哪里；
- 产品如何避免“Agent 更聪明”成为终点，而没有用户行动和结果变化。

## 六、MVP Case Rundown

Case Rundown 必须来自当前产品的真实体验，不套固定平台步骤。至少覆盖：

1. **触发**：谁在什么时刻遇到目标问题；
2. **输入**：产品需要哪些信息或前置条件；
3. **产品工作**：核心机制如何产生判断、能力或协作；
4. **人或系统行动**：谁根据结果做什么；
5. **异常与控制**：信息不足、失败、不确定或高风险时如何处理；
6. **结果**：用户任务或业务状态发生什么变化；
7. **测量**：领先指标如何采集，滞后结果如何继续追踪；
8. **决策**：什么证据支持继续、调整或停止投入。

以下链条至少闭合一次：

```text
更好的能力或判断
→ 用户采取有效行动
→ 可观察结果发生变化
→ 证明或推翻产品主张
```

## 七、下游交接摘要

Proposal 末尾固定使用：

```markdown
## 10. 下游交接摘要

- **第一个 design 目标**：<一个可建造结果，不写文件路径>
- **主用户与触发时刻**：<谁在什么时候开始这项任务>
- **要闭合的核心任务**：<用户最终完成什么判断或动作>
- **必须保持的产品回答**：<不能在模块设计中被改写的核心机制>
- **必须保持的产品边界**：<当前产品明确不承担什么>
- **MVP 必须证明**：<从能力 / 判断到行动与结果的证据链>
- **仍待验证的假设**：<design 可带着验证，但不能伪装成已确认事实>
- **design 需要收敛**：<对象、动作、状态、权限、页面、异常路径中的真实未知项>
```

交接摘要只给 design 起点，不提前写信息模型、页面层级、字段、状态机、权限矩阵或验收步骤。若这些已经在现有模块规格中确认，可以引用路径，不在 Proposal 复制。

## 八、版本与索引

### 8.1 文件名与状态

- 第一个版本：`docs/proposals/<slug>-v1.md`；
- 后续产品方向变化：`<slug>-v2.md`、`<slug>-v3.md`；
- 同一时刻只能有一个“当前”版本；
- 已定稿正文不原地重写；新版本完整重述当前有效产品定义；
- 旧版本只改状态头，保留正文作为历史坐标。

`slug` 使用稳定、短、与产品或方向主题一致的英文 kebab 名；版本变化时不换 slug。产品名正式变化时，新版本可换 slug，但索引必须保留取代关系。

### 8.2 INDEX.md

首次创建时使用：

```markdown
# Product Proposal 索引

> 当前产品级方向以状态为“当前”的 Proposal 为准；历史版本只用于追溯为什么变化。

| 文档 | 版本 | 状态 | 取代 | 决策日期 | 下游起点 |
|---|---|---|---|---|---|
| [`<slug>-v1.md`](<slug>-v1.md) | v1 | 当前 | 无 | YYYY-MM-DD | `<第一个 design 目标>` |
```

方向修订时，先把旧行改为“已取代”，再新增“当前”行。索引、旧文档状态头、新文档和 `PRODUCT.md` 必须在同一提交里更新。

## 九、PRODUCT.md 同步边界

Proposal 与 `PRODUCT.md` 不是两份相同正文：

## 十、全文质检

### 10.1 完整性

- [ ] 开篇能在短时间内讲清用户、问题、产品机制、边界、价值与 MVP。
- [ ] 核心判断可被证伪，不是口号。
- [ ] 用户具体到责任、场景和触发时刻。
- [ ] 问题、结构原因和业务后果没有混写。
- [ ] 产品回答先讲工作方式变化，再讲能力。
- [ ] 每项关键能力都能追溯到用户问题和端到端体验。
- [ ] MVP Case 能从触发走到行动、结果和决策门。
- [ ] 下游交接摘要完整，但没有提前代替 design。

### 10.2 证据与取舍

- [ ] 事实、推断、假设可区分。
- [ ] 竞品和市场判断有来源与日期，或明确待验证。
- [ ] 至少有一个真实现状替代和一个被放弃方向。
- [ ] 最危险前提、反例和验证方式明确。
- [ ] 没有虚构客户证据、市场空白、业务基线或财务收益。

### 10.3 价值与 AI

- [ ] 价值链从产品能力连接到用户行动和最终结果。
- [ ] 领先指标、滞后指标和归因边界分清。
- [ ] AI 产品针对具体任务证明 AI 必要性。
- [ ] 确定性规则没有被错误交给 AI。
- [ ] 人、模型、当前产品、运行环境和外部系统的责任清楚。

### 10.4 一致性与版本

- [ ] 摘要、正文、能力、MVP 和愿景使用同一用户、问题与边界。
- [ ] 新方向使用完整新版本，不是旧版 delta。
- [ ] 旧版本状态、索引和新版本取代关系一致。
- [ ] `PRODUCT.md` 只同步确认的稳定基线。
- [ ] Proposal、索引、旧版本状态、`PRODUCT.md` 和 `.pm-workflow/proposal.json` 进入同一个原子提交。
