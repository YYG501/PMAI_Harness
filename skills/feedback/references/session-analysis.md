# 当前会话分析规则（/pmai-feedback）

本文件用于把原始会话变成可验证的问题判断。目标不是总结聊天，而是找到“已确认依据与实际协作行为之间的差异”。

## 一、完整读取覆盖账本

开始分析前记录：

- 原始文件总行数；
- `session_meta`、用户消息、助手消息、工具调用、工具结果和压缩 / 恢复事件数量；
- 已读取的连续行号范围；
- active 会话初读后新增的尾部范围。

从第一条记录连续读到 EOF。一次输出过大时缩小块，不允许用关键词搜索替代全文读取。关键词只能用于全文读完后的回查。

覆盖完成的判据：所有原始行都进入过读取范围；任何截断块都已用更小范围重新读取；最终 Prompt 生成前已补读 active 尾部。

## 二、两类问题

### 1. 与已确认设计不一致

检查：

- AI 是否推翻或忽略 PM 已明确选择；
- 页面、对象、动作、状态、权限、字段、术语是否偏离当前 `spec.md` / `decisions.md` / `PRODUCT-RULES.md` / `DESIGN.md`；
- 原型或代码是否被当成真相源，反过来覆盖最终目标规格；
- 已被 supersede 的旧决定是否仍在支配回答；
- 推断、问句、草稿或工具输出是否被写成已确认事实；
- 实现是否超出批准目标范围或原型实现深度。

### 2. PM 使用体验卡点

检查：

- 已有答案仍被重复询问；
- 机械项、可逆偏好或内部选择被推给 PM；
- PM 被迫理解 Skill 路由、worktree、合同、hash、工具重试或日志流水；
- AI 选择了错误入口，或让 PM 手工串联本应自动完成的内部能力；
- 小改重复运行重型检查，等待与风险不成比例；
- 工具失败后只直播错误，没有给出最直接恢复路径；
- AI 在 PM 第一次说“不合理”后仍继续补表层方案；
- 阶段结果、下一步或是否可以刷新查看表达不清；
- 同一结论在会话中反复漂移，PM 需要多次纠正。

## 三、根因归属

每个 finding 只选一个主归属，必要时补一个次归属：

| 归属 | 判据 | 框架仓处理 |
|---|---|---|
| `consumer_project` | 当前项目设计、规格、代码或数据自身的问题 | 留在消费仓处理，不改 PMAI |
| `execution_gap` | 当前 Skill 已明确要求，但本轮 agent 没执行 | 查为什么没被读取 / 触发 / 强制，不重复堆同义文案 |
| `skill_gap` | 公开 Skill 的职责、门禁、问法或输出合同确实缺失 / 含混 | 修改正确 Skill 或 reference，并补回归 |
| `framework_contract_gap` | 只写 prose 不够，需要脚本、状态合同、hook 或机器门禁 | 修改共享 helper / contract / hook 和测试 |
| `host_runtime_limit` | 宿主没有会话 ID、工具能力、权限或稳定接口 | 明确宿主限制与可验证的 fallback，不伪装支持 |
| `insufficient_evidence` | 会话或当前文件不足以证明根因 | 作为待核项，不进入框架改造结论 |

## 四、对账纪律

框架反馈不是照单全收。每条必须完成：

1. 读当前有效 Skill 主文件及全部 required references；
2. 查现状是否已经覆盖；
3. 已覆盖则判断是执行偏差还是门禁不足；
4. 部分覆盖写清剩余 gap；
5. 未覆盖时判断正确归属，不能把跨 Skill 问题硬塞给最先被提到的 Skill；
6. 给出什么证据会推翻当前根因判断。

不要让 PM 先说“是哪个 Skill 的问题”。会话分析负责归位。

## 五、严重度

- `blocking`：会让 PM 得到错误产品结论、覆盖已确认决定、产生不可逆错误动作，或无法继续主线。
- `high`：稳定造成返工、错误路由、长时间等待或重复 PM 决策。
- `medium`：明显增加理解成本或操作步骤，但有直接绕行办法。
- `low`：局部表达和轻微摩擦，不值得单独改框架时应留在消费仓。

严重度不等于是否改框架。低频但破坏真相源的问题可能是 blocking；高频文案抱怨也可能只是项目特有。

## 六、反模式

- 只摘 PM 的负面句子，没有对照依据；
- 把所有工具报错都算 PMAI 缺陷；
- 看到 Skill 已写规则就判“框架没问题”，忽略规则为何稳定未执行；
- 为每个 finding 新增一条 prose，造成 Skill 文档膨胀；
- 把一次性项目偏好写成跨项目默认规则；
- 没读完整会话却声称“完整复盘”。
