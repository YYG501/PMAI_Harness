# 当前会话分析规则（/pmai-feedback）

本文件用于把原始会话变成可验证的问题判断。目标不是总结聊天，而是找到“已确认依据与实际协作行为之间的差异”。

## 一、固定证据边界

开始分析前记录定位器返回的：

- `snapshot_end_line`；
- `snapshot_end_bytes`；
- `snapshot_captured_at`；
- 会话当时是 active 还是 archived。

这些值共同定义本次只读证据快照。任何模式都不得读取边界后的记录。active 会话不补读尾部；feedback 自己产生的 commentary、工具调用、工具结果和压缩事件不属于本次待复盘行为。执行期间 PM 新发来的消息直接从当前宿主上下文接收，不靠重新扫描原始文件。

## 二、默认模式：聚焦复盘

目标是解释 PM 当前指出的问题，不是为整段聊天制作审计账本。按以下顺序读取：

1. 以 PM 当前反馈句和它明确指向的行为为起点；
2. 读取该行为前后的用户 / 助手消息，以及产生该行为所依赖的工具调用与结果；
3. 按会话中实际引用的 Skill、脚本、状态和文件定向扩展；
4. 对照直接相关的当前真相源；
5. 根因与归属已经可验证后停止。

可以用结构化解析或关键词定位触发点和证据候选，但最终 finding 必须回读实际对话和工具证据，不能只凭命中词下结论。不要默认展开无关 system / developer 文本、附件全文、网页全文或大段工具输出。

默认复盘以 3–5 分钟内给出可交接结论为产品目标。这不是草率输出的硬超时；接近该范围仍无法归因时，立即按下一节判断是否升级，而不是继续无边界扩读。

### 停止条件

同时满足以下条件就停止扩展：

- PM 指出的行为已经被准确还原；
- 实际行为与直接相关的当前规则 / 真相源已经对账；
- 主根因、归属和可推翻条件已经明确；
- 已有一个可以交给框架仓验证的直接改进方向。

相邻问题、顺手发现和完整性焦虑都不是继续扩展的理由。

## 三、完整审计升级条件

只有以下任一条件成立，才升级为 `full_audit`，读取第 1 行到 `snapshot_end_line` 的完整固定快照：

- PM 明确要求完整审计整段会话；
- 聚焦证据与当前真相源、状态合同或彼此之间发生实质冲突；
- 涉及未经授权的不可逆动作、真相源覆盖或跨阶段状态漂移，且局部证据无法还原因果链；
- 相关行为跨越多段不连续上下文，定向扩展后仍无法判断根因归属；
- 聚焦读取后仍存在会改变结论的关键证据缺口。

升级时必须先说明具体原因，并在最终输出与框架交接 Prompt 中写明 `analysis_mode: full_audit` 和 `upgrade_reason`。没有命中条件时保持 `analysis_mode: focused`。

完整审计只覆盖固定快照，不追读 active 尾部。输出过大时缩小块并补齐截断范围；关键词只能用于回查，不能替代完整覆盖。

## 四、两类问题

### 1. 与已确认设计不一致

检查：

- AI 是否推翻或忽略 PM 已明确选择；
- 页面、对象、动作、状态、权限、字段、术语是否偏离当前 `spec.md` / `decisions.md` / `PRODUCT-RULES.md` / `DESIGN.md`；
- 原型或代码是否被当成真相源，反过来覆盖最终目标规格；
- 已被 supersede 的旧决定是否仍在支配回答；
- 推断、问句、草稿或工具输出是否被写成已确认事实；
- 实现是否超出批准目标范围或原型实现深度。

### 2. PM 使用体验卡点

检查：

- 已有答案仍被重复询问；
- 机械项、可逆偏好或内部选择被推给 PM；
- PM 被迫理解 Skill 路由、worktree、合同、hash、工具重试或日志流水；
- AI 选择了错误入口，或让 PM 手工串联本应自动完成的内部能力；
- 小改重复运行重型检查，等待与风险不成比例；
- 工具失败后只直播错误，没有给出最直接恢复路径；
- AI 在 PM 第一次说“不合理”后仍继续补表层方案；
- 阶段结果、下一步或是否可以刷新查看表达不清；
- 同一结论在会话中反复漂移，PM 需要多次纠正。

## 五、根因归属

每个 finding 只选一个主归属，必要时补一个次归属：

| 归属 | 判据 | 框架仓处理 |
|---|---|---|
| `consumer_project` | 当前项目设计、规格、代码或数据自身的问题 | 留在消费仓处理，不改 PMAI |
| `execution_gap` | 当前 Skill 已明确要求，但本轮 agent 没执行 | 查为什么没被读取 / 触发 / 强制，不重复堆同义文案 |
| `skill_gap` | 公开 Skill 的职责、门禁、问法或输出合同确实缺失 / 含混 | 修改正确 Skill 或 reference，并补回归 |
| `framework_contract_gap` | 只写 prose 不够，需要脚本、状态合同、hook 或机器门禁 | 修改共享 helper / contract / hook 和测试 |
| `host_runtime_limit` | 宿主没有会话 ID、工具能力、权限或稳定接口 | 明确宿主限制与可验证的 fallback，不伪装支持 |
| `insufficient_evidence` | 会话或当前文件不足以证明根因 | 作为待核项，不进入框架改造结论 |

## 六、对账纪律

框架反馈不是照单全收。每条必须完成：

1. 读当前有效 Skill 主文件及全部 required references；
2. 查现状是否已经覆盖；
3. 已覆盖则判断是执行偏差还是门禁不足；
4. 部分覆盖写清剩余 gap；
5. 未覆盖时判断正确归属，不能把跨 Skill 问题硬塞给最先被提到的 Skill；
6. 给出什么证据会推翻当前根因判断。

不要让 PM 先说“是哪个 Skill 的问题”。会话分析负责归位。

## 七、严重度

- `blocking`：会让 PM 得到错误产品结论、覆盖已确认决定、产生不可逆错误动作，或无法继续主线。
- `high`：稳定造成返工、错误路由、长时间等待或重复 PM 决策。
- `medium`：明显增加理解成本或操作步骤，但有直接绕行办法。
- `low`：局部表达和轻微摩擦，不值得单独改框架时应留在消费仓。

严重度不等于是否改框架。低频但破坏真相源的问题可能是 blocking；高频文案抱怨也可能只是项目特有。

## 八、反模式

- 只摘 PM 的负面句子，没有对照依据；
- 把所有工具报错都算 PMAI 缺陷；
- 看到 Skill 已写规则就判“框架没问题”，忽略规则为何稳定未执行；
- 为每个 finding 新增一条 prose，造成 Skill 文档膨胀；
- 把一次性项目偏好写成跨项目默认规则；
- 没读完整会话却声称“完整复盘”。
- 聚焦证据已经足够，仍因“可能还有问题”不断扩大读取范围；
- 对 active 会话追读 feedback 自己新增的尾部；
- 没有命中升级条件却执行完整审计。
