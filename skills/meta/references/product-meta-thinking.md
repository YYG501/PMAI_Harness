# 产品判断模型（/pmai-meta）

`/pmai-meta` 的核心方法论不是外部方法拼装，也不是一套展示给 PM 的步骤清单。

> **产品元思考 = 用追问和压测，把表层诉求建成产品判断模型。**

PM 说“不合理 / 只是复述 / 没新思路 / 帮我深想 / 设计一下”时，AI 不能急着给深度分析或局部补丁。它要先把含混讨论整理成一个可以拍板的模型，再让 PM 在模型级分路里选择。

产品判断模型固定由五个部件组成：

1. **判断句**：这轮到底在判断什么。
2. **地基账本**：事实、约束、真相源、假设分别是什么。
3. **判断标准**：这轮按什么更高标准判断对错。
4. **模型轴**：问题真正卡在哪个轴上。
5. **分路**：2-3 个模型级 alternatives，PM 拍板后只保留唯一下一步。

如果五个部件缺失，不要硬写最终结论。继续一题一问补模型，或把缺口明确列为未验证假设。

---

## 一、判断句

判断句把 PM 的表层诉求改写成可拍板问题。

句式：

```text
这轮要判断的是：是否 / 如何 / 何时 <做某件事>，以便 <谁> 做出 <哪个判断或动作>。
```

判断句必须回答：

- 这轮到底在判断“要不要做”“怎么分”“该不该改”“谁负责”“哪边是真相源”，还是“这段表达是否成立”？
- 这个判断要改变谁的哪个业务判断？
- 如果这轮判断错了，用户或 PM 会做出什么错误动作？

不合格判断句：

- “优化待办体验。”
- “让文案更高级。”
- “设计一个 lark sync skill。”

合格判断句：

- “判断状态变化类事项是否仍归入待确认，以及如何避免用户把确认已知误解成业务审批。”
- “判断 PMAI 缺的是新的飞书编辑能力，还是先判定真相源和同步方向的文档同步入口。”
- “判断这份介绍材料是否应该从功能清单改成买方决策材料。”

---

## 二、地基账本

地基账本区分“已经站住的东西”和“还只是 PM / AI 的想当然”。它主要由 **第一性原理** 和先读真相源补齐。

必须分四栏：

- **事实**：从文件、代码、规格、PM 已确认回答里读到的客观内容。
- **约束**：改了以后整件事会不成立的限制，例如真相源、业务责任、用户动作、技术边界、时间和资源。
- **真相源**：本轮最终以哪个文件、页面、系统、PM 决策或线上状态为准。
- **假设**：没有证据但当前方案依赖它成立的判断。

PMAI 原有方法如何进入：

- **第一性原理** → 建地基账本：拆事实、约束、假设，再从约束重推。
- **多视角压测** → 检查账本有没有漏掉反方、证据、风险和可执行性。

产品想法路径可吸收 gstack / office-hours 的素材来补账本：

- **需求证据**：用户付钱、反复使用、改流程，还是只是口头兴趣。
- **现状对手**：没有它时用户怎么凑合，真正被替代的是谁。
- **具体用户**：哪个角色、哪个时刻、要做哪个判断。
- **观察意外**：看过真实用户之后，哪个事实和原想象不一样。
- **未来适配**：6 个月或 3 年后，这个需求会更必要还是更边缘。

workflow 决策路径必须先读相关 skill、references、README、CHANGELOG、tests。能从文件查到的，不问 PM。

---

## 三、判断标准

判断标准回答：这轮不是按“看起来更顺”判断，而是按什么更高标准判断。

PMAI 原有方法如何进入：

- **升维 / 换高度** → 找判断标准。

常见判断标准：

| 低层问题 | 更高判断标准 |
|---|---|
| 按钮、标签、列表怎么叫 | 用户到底在确认、审批、采纳、已知，还是查看 |
| 页面信息怎么摆 | 这页服务谁的哪个判断 |
| 文档怎么写 | 读者要不要相信、能不能转述、会不会行动 |
| workflow 要不要新增 skill | 缺的是入口、门禁、执行能力、成文能力、证据能力，还是真相源判断 |
| 功能要不要做 | 机会成本、可逆性、最小验证、现状对手强度 |

升维 / 换高度不是把话说大。它必须降回判断标准：按这个标准，哪些方案会被排除，哪些方案才有资格进入分路。

---

## 四、模型轴

模型轴回答：问题真正卡在哪个轴上。表层方案前必须先分模型轴，否则大概率是在症状上打补丁。

常见模型轴：

| 模型轴 | 问什么 |
|---|---|
| 对象 | 到底讨论哪个业务对象、文档对象或 workflow 对象？ |
| 责任 | 谁必须处理，谁只是知道？ |
| 状态 | 业务状态会不会变化？ |
| 统计 | 它该不该进入数量、待办、提醒、完成率或验收口径？ |
| 动作语义 | 点击表示同意、采纳、审批、确认已知、查看，还是忽略？ |
| 真相源 | 最终版本、权威口径、同步方向或记录位置是谁？ |
| 验证路径 | 现在该做、先验证、先不做，还是交给另一个 skill？ |
| 判断标准 | PM / 用户到底要基于它做什么判断？ |

PMAI 原有方法如何进入：

- **UI 信息 / 任务 / 判断层** → 页面类问题的模型轴判断。先问这页服务谁的哪个判断，再反推信息、任务、动作和布局。
- **第一性原理** → 判断哪些轴是真约束，哪些只是习惯分类。

如果 PM 只给了一个短答或只选了一个方向，不能马上收束。必须追问一次具体后果：这个轴判错后，用户会误解什么，哪个状态 / 统计 / 真相源会被污染，或哪个业务动作会出错。

---

## 五、分路

分路是 2-3 个模型级 alternatives。它们不能只是文案、按钮、标签或布局差异，而要在模型轴、判断标准、验证路径或真相源上有差异。

每个分路必须包含：

- 模型级方向。
- 成立条件。
- 代价。
- 被排除时的理由。

常见分路：

- **做小**：只做最小能验证判断的版本。
- **换对象**：先服务更窄角色或更痛场景。
- **换页面重心**：从信息展示改成判断、行动或风险控制。
- **改模型**：改分类、统计口径、动作语义、真相源或责任边界。
- **调用现有**：已有 skill / 页面 / 文档能解决，不新增入口。
- **改现有**：现有边界对，但门禁、流程、测试或表达不足。
- **新建入口**：现有能力都太底层，确实缺上层决策入口。
- **先验证**：先拿材料、原型、人工流程或用户行为验证前提。
- **先不做**：记录触发条件，避免伪需求进入 build。

PMAI 原有方法如何进入：

- **多视角压测** → 压测分路是否漏掉真相源、用户、业务目标、产品逻辑、证据、表达、完整性、可执行性、风险和反方。

## 六、来源如何被消化

外部来源只能被消化成模型动作，不允许成为 `/pmai-meta` 的主结构层或前台品牌。

### PMAI 原有方法

- **第一性原理**：服务地基账本，拆事实、约束、假设并重推。
- **升维 / 换高度**：服务判断标准，找更高一层的取舍口径。
- **多视角压测**：服务模型和分路压测，找盲区、根因和反方。
- **UI 信息 / 任务 / 判断层**：服务页面类问题的模型轴判断。

### gstack / office-hours

只作为产品想法路径的素材来源：

- 需求证据
- 现状对手
- 具体用户
- 最小切口
- 观察意外
- 未来适配

这些素材用于补地基账本、判断标准和分路，不把 office-hours 当 PMAI 主品牌，也不 runtime 调 gstack。

### grill

只作为补齐模型字段的问法纪律：

- 一题一问。
- 沿依赖决策树问：先拍对象、责任、真相源、判断标准，再谈按钮、布局、文案。
- 每题给推荐默认答案。
- PM 短答、抽象答、只选项时追问具体后果。
- 能从文件、代码、skill、真相源查到的不问 PM。
- Alternatives 后停住让 PM 选。

这些纪律的作用是把模型字段问完整，不是把 `/pmai-meta` 变成 grillme 复刻。

## 七、输出合同

最终输出固定围绕产品判断模型：

```text
## 本轮判断
<判断句>

## 地基账本
- 事实：
- 约束：
- 真相源：
- 假设：

## 判断标准
<这轮按什么标准判断>

## 卡住的模型轴
<对象 / 责任 / 状态 / 统计 / 动作语义 / 真相源 / 验证路径>

## 可选分路
- A：<模型级方向>，成立条件 / 代价
- B：<模型级方向>，成立条件 / 代价
- C：<可选>

## PM 已选
<方向>

## 下一步
<唯一 skill 或明确停住>
```

如果 PM 尚未选择分路，停在可选分路，不输出“PM 已选”和“下一步”的最终结论。可以给推荐默认答案，但必须等 PM 拍。

`/pmai-meta` 不生成长期产品文档。会诊结论需要成文、设计、规格或构建时，交给 `/pmai-design`、`/pmai-doc-writing`、`/pmai-spec-writing`、`/pmai-build` 或 `/pmai-skill-improve`。
