# 问题对焦方法（/pmai-meta）

本文件是 `/pmai-meta` 的主方法源。它吸收深度访谈、反方挑战和带资料追问这类方法的有效部分，但不照搬外部 skill，也不把外部概念当成 PMAI 的命名。核心不是“多问几个问题”，而是把低质量讨论拉回一个清晰的问题模型。

---

## 一、基本纪律

1. **先读再问**：能从项目资料、模块文档、PM 本轮材料里查到的，不问 PM。只有答案会改变判断且资料里没有，才问。
2. **一题一问**：每次只问一个问题，问完等待。多个问题一起问会让 PM 只能挑容易的答，真正的冲突被掩盖。
3. **推荐默认答案**：每题都给一个“我建议先按 X 理解”的默认答案，让 PM 能快速接受、修正或否定。
4. **业务语言提问**：问题里不要出现 lens、stage、toolbox、模式、agent 类型、第一性原理流程等内部词。PM 讲工作、判断、代价、对象；AI 内部翻译成方法论。
5. **追问表层答案**：第一答通常是礼貌、抽象或旧认知。只要还停在“用户 / 提效 / 更清楚 / 更智能 / 应该有”，必须追一次。
6. **先挑战前提，再给方向**：任何推荐前都要点名最危险前提，并说明什么证据会推翻它。
7. **Alternatives 必须出现**：至少 2 个可比较方向。没有替代方向，就不是判断，只是附和。
8. **Coverage Check 后再收束**：输出前确认“有没有没问到但会改变判断的点”。没确认，不做最终结论。
9. **降回下一步**：结束时必须指向 `/pmai-design`、`/pmai-doc-writing`、`/pmai-spec-writing`、`/pmai-build` 或停住，不停在高空讨论。

---

## 二、会话类型与问法

### 1. 新想法 / 方向不清

目标是判断“这件事是否值得进入设计”，而不是马上完善方案。

优先问：

- 现在没有它，PM 或用户怎么凑合？
- 最痛的是哪一步，还是哪类判断最容易错？
- 如果只解决一半，先解决哪一半最值？
- 不做这件事，产品会继续丢什么上下文或判断能力？

### 2. PM 说方案不对

目标是停止补丁，回到根因。

先说一句：

```text
我先不继续修这个方案。现在的问题更像是：我们还没确认它到底服务哪个判断，继续加字段/提示只会补丁化。
```

然后问一个能拆根因的问题，例如：

- 你觉得它“不对”，更像是目标错了、对象错了、页面重心错了，还是概念边界错了？我建议先怀疑页面重心。
- 如果这版完全不改 UI，只改判断逻辑，你最希望它先变准哪件事？

### 3. 已有稿子 / 方案 / 页面

目标是判断“根上是否成立”，不是只改局部。

先压测三件事：

- 它服务的判断是否明确。
- 它依赖的前提是否已确认。
- 它有没有至少一个合理替代方向。

如果缺的是材料证据，继续读资料；如果缺的是 PM 判断，转入一题一问。

### 4. 只是表达高级感

目标不是写标题，而是确定表达服务哪个判断。

先问：

- 这句话要改变谁的第一眼印象？
- 你希望对方看完后做什么判断：要不要试、值不值得投、该不该继续看，还是相信这事不是玩具？

然后才调用 `词表与句式.md` 做表达校验。

## 三、六类 Forcing Questions

按场景智能选择，不机械全问。

1. **现状对手**：现在没有它，PM / 用户怎么凑合？
2. **判断对象**：这轮到底要改变谁的哪个判断？
3. **危险前提**：哪个前提如果错了，整个方案就不成立？
4. **最小版本**：最小值得做的版本是什么？
5. **机会成本**：不做 / 晚做会损失什么，做了会挤掉什么？
6. **Pre-mortem**：6 个月后它失败，最可能败在哪里？

好问题的标准：答案会改变方向、范围、页面重心、是否继续、或下游 skill 的输入。

坏问题的标准：答案只会让 PM 重复“更好、更清楚、更智能、更方便”。

---

## 四、追问规则

必须追问的信号：

- **抽象用户**：只说“用户 / 销售 / 管理者”，没有具体场景。
- **泛泛价值**：提效、闭环、智能化、更清楚，但没有具体判断或代价。
- **旧范式**：只是把旧流程搬进新页面，没有问为什么必须这样。
- **矛盾**：既说不是待办，又要求它进待办数量；既说轻量，又要求强确认。
- **回避**：PM 对某个风险答得特别短，或只讲 UI 不讲判断。
- **缺证据**：关键结论来自“感觉应该有”。

追问方式：

- 不问“为什么？”这种容易让人防御的问题。
- 用“什么让你这么判断？”、“如果 X 不成立，我们还会这么做吗？”、“哪个具体场景会证明它值得做？”。
- 追问一次后仍然抽象，就把抽象项列入“未验证前提”，不要假装已确认。

---

## 五、Premise Challenge

推荐方向前必须写出：

```text
这轮最危险的前提是：<一句话>。
如果 <证据或情况> 成立，那我们现在的方向就该改。
```

常见危险前提：

- PM 以为用户会主动处理，但其实只是想知道发生了什么。
- AI 以为多一个类型能解决混乱，但混乱来自数量统计口径。
- 页面以为核心是“展示更多信息”，但用户其实是在做“投不投 / 先做哪个 / 该不该停”的判断。
- 文案以为要更高级，其实是要让对方相信它能进入真实工作流。

---

## 六、Alternatives

至少给 2 个方向，常用形态：

| 方向 | 适用情况 |
|---|---|
| 做小 | 前提不稳，先验证最小判断 |
| 换对象 | 服务错了角色或场景 |
| 换页面重心 | 信息展示、任务执行、判断决策混在一起 |
| 先验证 | 缺材料、缺用户行为、缺现状证据 |
| 先不做 | 价值不够、机会成本过高、容易污染主流程 |

输出时说明推荐方向和被排除方向。PM 没拍前，不把某个方向写成最终方案。

---

## 七、Coverage Check

最终输出前必须问：

```text
我感觉关键问题已经覆盖了。还有没有一个没问到、但会改变判断的点？
```

PM 如果补充新点，回到对应问题继续问。PM 确认没有，再收束。

---

## 八、Escape Hatch

问题对焦不是每次都完整跑。

- 如果 PM 明确不想深挖，说“先直接做”，最多再问 1 个最高风险问题，然后回到下游 skill。
- 如果问题明显是小改，直接说“这个不用问题对焦，直接改更对”。
- 如果已有资料已经回答问题，不要为了仪式继续问。
- 如果连续追问两次仍没有新信息，把缺口写成未验证前提，不继续消耗 PM。

---

## 九、最终输出模板

```text
## 本轮判断
<真问题 / 判断标准 / 根因>

## 推荐方向
<方向 + 为什么>

## 被排除方向
- <方向>：<为什么先不走>

## 仍需 PM 拍板
- <问题，如无则写“无”>

## 下一步
<回到哪个 skill 或明确停住>
```

模板只在收束时使用。访谈过程中不要提前输出完整结论。
