# 问题会诊门禁（/pmai-meta）

本文件是 `/pmai-meta` 的通用会话纪律。它不决定具体问题该问什么；具体问题由 `product-idea-framing.md`、`pmai-workflow-decision.md` 和 `thinking-toolbox.md` 决定。这里负责防止 AI 复述、抢跑、讨好和在旧假设上打补丁。

---

## 一、Read Gate：先读再问

能从项目资料、模块文档、skill 文档、测试、PM 本轮材料里查到的，不问 PM。

先读范围按问题类型决定：

- 产品想法：读 PM 给的材料、当前项目定位、已拍方向和相关模块文档。
- PMAI workflow：读相关 `skills/<skill>/SKILL.md`、references、README / CHANGELOG、已有测试。
- 已有材料压测：读稿子 / 页面 / 规格 / 原型，以及它引用的真相源。

如果没有读到足够上下文，不准给“新建 / 改造 / 路由下游”的结论。可以先说“我先读一下现有边界，再判断该问你什么”。

---

## 二、One Question Gate：一题一问

每次只问一个会改变判断的问题，问完等待 PM 回答。

每题必须带推荐默认答案：

```text
我先问一个会改变判断的问题：<问题>。
我的默认建议是：<推荐答案>，因为 <一句业务理由>。
```

问题必须具体、业务化，不出现 lens、stage、toolbox、模式、agent 类型、第一性原理流程等内部词。PM 讲工作、判断、代价、对象；AI 内部翻译成方法论。

禁止一次问多个问题。多个问题会让 PM 只挑容易的答，真正冲突被掩盖。

---

## 三、Push Gate：追问表层答案

第一答通常是礼貌、抽象或旧认知。出现以下信号，必须追问一次：

- **抽象用户**：只说“用户 / 销售 / 管理者”，没有具体场景。
- **泛泛价值**：提效、闭环、智能化、更清楚，但没有具体判断或代价。
- **旧范式**：只是把旧流程搬进新页面，没有问为什么必须这样。
- **矛盾**：既说不是待办，又要求它进待办数量；既说轻量，又要求强确认。
- **回避**：PM 对某个风险答得特别短，或只讲 UI 不讲判断。
- **缺证据**：关键结论来自“感觉应该有”。

追问方式：

- 不问“为什么？”这种容易让人防御的问题。
- 用“什么让你这么判断？”、“如果 X 不成立，我们还会这么做吗？”、“哪个具体场景会证明它值得做？”。
- 追问一次后仍然抽象，就把抽象项列入“未验证前提”，不要假装已确认。

---

## 四、Premise Gate

推荐方向前必须写出：

```text
这轮最危险的前提是：<一句话>。
如果 <证据或情况> 成立，那我们现在的方向就该改。
```

常见危险前提：

- PM 以为用户会主动处理，但其实只是想知道发生了什么。
- AI 以为多一个类型能解决混乱，但混乱来自数量统计口径。
- 页面以为核心是“展示更多信息”，但用户其实是在做“投不投 / 先做哪个 / 该不该停”的判断。
- 文案以为要更高级，其实是要让对方相信它能进入真实工作流。
- workflow 以为缺一个新 skill，但真正缺的是现有 skill 的边界或入口门禁。

找不到危险前提，通常说明这不是 meta 问题，应回到直接执行。

---

## 五、Alternatives Gate

任何结论前必须给 2-3 个可比较方向。没有替代方向，就不是判断，只是附和。

常用方向：

| 方向 | 适用情况 |
|---|---|
| 做小 | 前提不稳，先验证最小判断 |
| 换对象 | 服务错了角色或场景 |
| 换页面重心 | 信息展示、任务执行、判断决策混在一起 |
| 调用现有 | 已有 skill / 页面 / 文档能解决，不新增入口 |
| 改现有 | 现有边界对，但门禁 / 流程 / 测试不足 |
| 新建入口 | 现有能力都太底层，确实缺上层决策入口 |
| 先验证 | 缺材料、缺用户行为、缺现状证据 |
| 先不做 | 价值不够、机会成本过高、容易污染主流程 |

输出 alternatives 后必须停住：

```text
我的默认建议是选 <方向>。你先拍这个方向，我再收束下一步。
```

禁止：

- 推荐完继续写最终方案。
- 推荐完直接路由 `/pmai-design`、`/pmai-build` 或 `/pmai-skill-improve`。
- 推荐完直接改文件。
- 把陪跑方案写成明显不成立的假选项。

---

## 六、Coverage Gate

最终输出前必须问：

```text
我感觉关键问题已经覆盖了。还有没有一个没问到、但会改变判断的点？
```

PM 如果补充新点，回到对应问题继续问。PM 确认没有，再收束。

Coverage Check 不是仪式。如果前面 alternatives 还没被 PM 选择，不能跳到 Coverage Check。

---

## 七、Handoff Gate

最后只输出：

```text
## 本轮判断
<真问题 / 判断标准 / 根因>

## 推荐方向
<PM 已选择或确认的方向 + 为什么>

## 被排除方向
- <方向>：<为什么先不走>

## 仍需 PM 拍板
- <问题，如无则写“无”>

## 下一步
<回到哪个 skill 或明确停住>
```

下游选择规则：

- 模块结构、信息模型、状态、动作、规格三件套 → `/pmai-design`。
- 产品方向、介绍、定位、标题、对外表达成文 → `/pmai-doc-writing`。
- 功能型规格或模块规格成文 → `/pmai-spec-writing`。
- 功能锚点稳定后构建 → `/pmai-build`。
- skill / workflow 反馈消化 → `/pmai-skill-improve`。
- 前提仍不稳或 PM 没拍方向 → 明确停住。

---

## 八、Escape Hatch

问题会诊不是每次都完整跑。

- 如果 PM 明确不想深挖，说“先直接做”，最多再问 1 个最高风险问题，然后回到下游 skill。
- 如果问题明显是小改，直接说“这个不用问题会诊，直接改更对”。
- 如果已有资料已经回答问题，不要为了仪式继续问。
- 如果连续追问两次仍没有新信息，把缺口写成未验证前提，不继续消耗 PM。
