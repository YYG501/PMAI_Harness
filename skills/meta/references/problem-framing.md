# 判断模型问法纪律（/pmai-meta）

本文件不是 `/pmai-meta` 的核心方法论。核心方法论在 `product-meta-thinking.md`，产物是**产品判断模型**。

本文件只负责补齐模型字段时的问法纪律：防止 AI 复述、讨好、抢跑、在旧假设上打补丁，或把 PM 的短答直接整理成结论。

产品判断模型缺哪个部件，就问哪个部件；不要为了流程完整机械全问。

---

## 一、Read Gate：先读再问

能从项目资料、模块文档、skill 文档、代码、测试、PM 本轮材料里查到的，不问 PM。

先读范围按问题类型决定：

- 产品想法：读 PM 给的材料、当前项目定位、已拍方向和相关模块文档。
- PMAI workflow：读相关 `skills/<skill>/SKILL.md`、references、README / CHANGELOG、已有测试。
- 已有材料压测：读稿子 / 页面 / 规格 / 原型，以及它引用的真相源。

如果没有读到足够上下文，不准给“新建 / 改造 / 路由下游”的结论。可以先说“我先读一下现有边界，再判断该问你什么”。

---

## 二、One Question Gate：一题一问

每次只问一个会改变判断的问题，问完等待 PM 回答。

每题必须带推荐默认答案：

```text
我先问一个会改变判断的问题：<问题>。
我的默认建议是：<推荐答案>，因为 <一句业务理由>。
```

问题必须具体、业务化，不出现 lens、stage、toolbox、模式、agent 类型、第一性原理流程等内部词。PM 讲工作、判断、代价、对象；AI 内部翻译成模型字段。

禁止一次问多个问题。多个问题会让 PM 只挑容易的答，真正冲突被掩盖。

---

## 三、依赖决策树 Gate

沿依赖决策树问，先拍上游模型字段，再谈表层方案。

顺序通常是：

1. **判断句**：这轮到底要改变谁的哪个判断？
2. **对象 / 责任**：讨论哪个对象？谁必须处理，谁只是知道？
3. **真相源 / 状态**：业务状态会不会变？最终以谁为准？
4. **判断标准**：按什么更高标准判断方案好坏？
5. **动作语义 / 统计**：点击动作代表什么？是否进入数量或完成率？
6. **验证路径**：现在做、先验证、先不做，还是交给另一个 skill？
7. **表层方案**：按钮、布局、标签、文案、页面结构。

如果对象、责任、真相源或判断标准没拍清，就不要直接给按钮、布局、文案或 skill 名。

---

## 四、Push Gate：短答追后果

第一答通常是礼貌、抽象或旧认知。PM 短答、抽象答、只选项不解释时，必须追问一次具体后果。

出现以下信号，必须追问：

- **抽象用户**：只说“用户 / 销售 / 管理者”，没有具体场景。
- **泛泛价值**：提效、闭环、智能化、更清楚，但没有具体判断或代价。
- **旧范式**：只是把旧流程搬进新页面，没有问为什么必须这样。
- **矛盾**：既说不是待办，又要求它进待办数量；既说轻量，又要求强确认。
- **回避**：PM 对某个风险答得特别短，或只讲 UI 不讲判断。
- **缺证据**：关键结论来自“感觉应该有”。

追问方式：

- 不问“为什么？”这种容易让人防御的问题。
- 问具体后果：“如果这个方向错了，用户会做出什么错误动作？”“哪个统计、状态或真相源会被污染？”“什么场景会证明它值得做？”
- 追问一次后仍然抽象，就把抽象项列入“未验证假设”，不要假装已确认。

---

## 五、Premise Gate

推荐方向前必须写出：

```text
这轮最危险的前提是：<一句话>。
如果 <证据或情况> 成立，那我们现在的方向就该改。
```

常见危险前提：

- PM 以为用户会主动处理，但其实只是想知道发生了什么。
- AI 以为多一个类型能解决混乱，但混乱来自数量统计口径。
- 页面以为核心是“展示更多信息”，但用户其实是在做“投不投 / 先做哪个 / 该不该停”的判断。
- 文案以为要更高级，其实是要让对方相信它能进入真实工作流。
- workflow 以为缺一个新 skill，但真正缺的是现有 skill 的边界或入口门禁。

找不到危险前提，通常说明这不是 meta 问题，应回到直接执行。

---

## 六、Alternatives Gate

先判断是否存在真实产品模型岔路。只有两个方向会改变对象、责任、状态、统计、动作语义、权限、真相源、页面任务、成功标准或验证路径时，才必须给 2-3 个可比较方向。没有真实岔路时，直接给推荐并返回 design；不要为了形式凑陪跑方案。

常用方向：

| 方向 | 适用情况 |
|---|---|
| 做小 | 前提不稳，先验证最小判断 |
| 换对象 | 服务错了角色或场景 |
| 换页面重心 | 信息展示、任务执行、判断决策混在一起 |
| 改模型 | 分类、统计口径、动作语义、真相源或责任边界错了 |
| 调用现有 | 已有 skill / 页面 / 文档能解决，不新增入口 |
| 改现有 | 现有边界对，但门禁 / 流程 / 测试不足 |
| 新建入口 | 现有能力都太底层，确实缺上层决策入口 |
| 先验证 | 缺材料、缺用户行为、缺现状证据 |
| 先不做 | 价值不够、机会成本过高、容易污染主流程 |

存在真实岔路时，输出 alternatives 后必须停住：

```text
我的默认建议是选 <方向>。你先拍这个方向，我再收束下一步。
```

禁止：

- 推荐完继续写最终方案。
- 推荐完直接路由 `/pmai-design`、`/pmai-build` 或 `/pmai-skill-improve`。
- 推荐完直接改文件。
- 把陪跑方案写成明显不成立的假选项。

---

## 七、Coverage Check

收束前由 AI 在后台检查判断句、事实 / 约束 / 真相源 / 假设、危险前提、反例、代价和返回 design 的动作是否齐全。只有确实存在一个 PM 才能回答、且会改变产品模型的缺口时才提问；禁止固定问“还有没有没覆盖的点”。

---

## 八、Handoff Gate

最后只输出产品判断模型：

```text
## 本轮判断
<判断句>

## 地基账本
- 事实：
- 约束：
- 真相源：
- 假设：

## 判断标准
<这轮按什么标准判断>

## 卡住的模型轴
<对象 / 责任 / 状态 / 统计 / 动作语义 / 真相源 / 验证路径>

## 可选分路
- A：<模型级方向>，成立条件 / 代价
- B：<模型级方向>，成立条件 / 代价
- C：<可选>

## PM 已选
<方向>

## 下一步
<唯一 skill 或明确停住>
```

下游选择规则：

- 模块结构、信息模型、状态、动作、规格三件套 → `/pmai-design`。
- 产品方向、介绍、定位、标题、对外表达成文 → `/pmai-doc-writing`。
- 功能型规格或模块规格成文 → `/pmai-spec-writing`。
- 功能锚点稳定后构建 → `/pmai-build`。
- skill / workflow 反馈消化 → `/pmai-skill-improve`。
- 存在真实模型岔路且 PM 没拍方向 → 明确停住；没有真实岔路时给推荐并返回 design。

---

## 九、Escape Hatch

产品元思考不是每次都完整跑。

- 如果 PM 明确不想深挖，说“先直接做”，最多再问 1 个最高风险问题，然后回到下游 skill。
- 如果问题明显是小改，直接说“这个不用 meta，直接改更对”。
- 如果已有资料已经回答问题，不要为了仪式继续问。
- 如果连续追问两次仍没有新信息，把缺口写成未验证假设，不继续消耗 PM。
