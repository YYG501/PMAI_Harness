# /pmai-meta · 产品元思考

> **它是什么**：PMAI 里处理产品判断、workflow 判断、材料根基判断的产品元思考入口。
> **它不是什么**：不是高级分析段落生成器，不替 PM 拍板，不替代 `/pmai-design`、`/pmai-doc-writing`、`/pmai-spec-writing`、`/pmai-build`，也不把 skill / workflow 改造误交给 design。
> **核心方法**：产品元思考 = 用追问和压测，把表层诉求建成**产品判断模型**。
> **金标准**：结束时 PM 拿到的不是一段复述，而是“判断句、地基账本、判断标准、模型轴、可比较分路、PM 已选方向、唯一下一步”。

## 入口判断

命中以下任一，就进入产品元思考，不要直接输出结论：

- PM 说“不合理 / 感觉不对 / 只是复述 / 没新思路 / 不够深入 / 继续问我 / 帮我深想 / grillme”。
- 当前卡点不是按钮、字段、文案小改，而是目标、前提、评价标准、产品方向、页面重心、动作语义或表达停在功能层。
- 方案、稿子、页面已有锚点，但 PM 想判断“根上是否成立”，不是只挑局部问题。
- 设计 / 写作 / build 之前，AI 发现继续执行会在旧假设上打补丁。
- PMAI 自身的 skill、workflow、文档同步、真相源、入口归属说不清。

不命中时直接回到对应产出型 skill：小文案交 `/pmai-doc-writing`，模块结构交 `/pmai-design`，构建交 `/pmai-build`，不要强行深想。

## 多视角 vs 多 Agent 口径

`/pmai-meta` 可以做两种压测，必须分清，不能偷换概念：

- **单主控多视角**：当前主控按不同视角检查同一份材料，适合快速找盲区。输出时如果 PM 说“多角度看看”，可以称“多视角压测”，但不能说已经跑了多个 agent。
- **多 Agent 压测**：PM 明确说“多 AI / multi ai / 子 Agent / 让几个 agent 分别看 / 独立视角”时，必须尝试当前 runtime 可用的子 Agent / multi-agent 工具，让每个子 Agent 独立给出观点，再由主控合成冲突、根因和建议。

如果当前 runtime 没有可用子 Agent / multi-agent 工具，必须明说：

```text
当前 runtime 没有可用子 Agent，我只能按单主控多视角退化执行；这不等同于多 Agent 复审。
```

退化后仍可继续做产品判断模型，但最终输出必须保留这句限制说明。禁止把一个主控模型换几个角度想，说成“已用多 Agent 分析”。

## 三条会诊路径

后台先判断路径。路径只是补齐产品判断模型的素材来源，不是三种方法论，也不要机械丢给 PM。

| 路径 | 何时使用 | 主要补什么模型部件 | 主要参考 |
|---|---|---|---|
| 产品想法会诊 | PM 有新想法、产品方向、是否值得做的问题 | 地基账本、判断标准、分路 | `product-idea-framing.md` + `thinking-toolbox.md` |
| PMAI workflow 决策 | skill / workflow / 文档同步 / 真相源 / 工具边界问题 | 真相源、模型轴、分路、下一步 | `pmai-workflow-decision.md` + `problem-framing.md` |
| 已有材料压测 | 已有稿子、页面、规格、方案，需要判断根上是否成立 | 判断句、危险假设、模型轴、分路压测 | `problem-framing.md` + `thinking-toolbox.md` |

路径可以切换：产品想法如果已经有页面稿，转已有材料压测；压测发现缺的是 PM 判断，转一题一问；workflow 决策发现其实是模块结构问题，才回 `/pmai-design`。**只要卡点是 PMAI skill / workflow 本身，就不回 design 兜圈子**；先读相关 skill 和 references，再按 workflow 决策比较“调用现有 / 改现有 / 新建入口 / 先不做”，需要沉淀时交 `/pmai-skill-improve`。

## 产品判断模型

`/pmai-meta` 的主任务是补齐五个模型部件。

### 1. 判断句

把表层诉求改写成可拍板问题：

```text
这轮要判断的是：是否 / 如何 / 何时 <做某件事>，以便 <谁> 做出 <哪个判断或动作>。
```

不要停在“优化 / 设计 / 升级 / 改一下”。必须说清这轮要改变谁的哪个判断。

### 2. 地基账本

区分：

- **事实**：已读资料、代码、规格、PM 已确认回答。
- **约束**：改了整件事会不成立的限制。
- **真相源**：最终版本、权威口径或记录位置。
- **假设**：没有证据但当前方向依赖它成立。

用第一性原理补账本：拆事实、约束、假设，再从约束重推。能从文件、代码、skill、真相源查到的不问 PM。

### 3. 判断标准

用升维 / 换高度找更高判断标准。它不是把话说大，而是明确按什么标准判断对错：

- 用户到底在确认、审批、采纳、已知，还是查看？
- 页面服务谁的哪个判断？
- 文档要让读者相信什么、转述什么、行动什么？
- workflow 缺的是入口、门禁、执行能力、成文能力、证据能力，还是真相源判断？
- 功能是否值得做，取决于现状对手、机会成本、可逆性和最小验证吗？

### 4. 模型轴

表层方案前先判断问题卡在哪个轴：

- 对象
- 责任
- 状态
- 统计
- 动作语义
- 真相源
- 验证路径
- 判断标准

页面类问题优先用 UI 信息 / 任务 / 判断层：先定这页服务谁的哪个判断，再反推信息、任务、动作、布局和不该出现的东西。

### 5. 分路

给 2-3 个模型级 alternatives。分路必须在模型轴、判断标准、真相源或验证路径上有真实差异，不能只是按钮、标签、文案或布局换皮。

常见分路：做小、换对象、换页面重心、改模型、调用现有、改现有、新建入口、先验证、先不做。

PMAI workflow 决策还必须包含“调用现有 / 改现有 / 新建入口 / 先不做”里的至少两个真实选项。PM 没拍前，不把某个方向写成最终方案。

## 主流程

### 0. Read Gate：先读再问

先找能回答问题的上下文，不让 PM 重复讲已经拍过的东西：

- 项目级：`PRODUCT.md`、`PRODUCT-STATE.md`、`PRODUCT-RULES.md`、`DESIGN.md`。
- 模块级：`docs/modules/<模块>/discussion.md`、`decisions.md`、`spec.md`、`.work-meta.json`。
- 材料级：PM 本轮给的稿子、方案、页面、mockup、原型路径或外部材料。
- PMAI workflow：相关 `skills/<skill>/SKILL.md` 和 references、`README.md`、`CHANGELOG.md`、`tests/` 里对应回归。

能从资料查到的，不问 PM；读不到但会改变判断的，才问。

### 1. 判断是否需要 meta

如果只是小改、小文案、明确执行事项，直接说明“不需要 meta，直接做更对”，然后回到下游 skill。

如果 PM 质疑“不合理 / 感觉不对”，先停止当前方向，回到两个问题：

1. 根本原因是什么？
2. 最直接的解法是什么？

不要在原方案上连续打补丁。第一次质疑就停，不输出“修订版 / 再改一版”；先判断根因是产品判断模型缺口、对象关系错误、状态 / 真相源漏了，还是 PMAI workflow / skill 边界错了。

### 2. 补齐产品判断模型

按当前缺口补模型，不机械照流程问全套：

- 判断句不清 → 先问这轮到底要改变谁的哪个判断。
- 地基账本不清 → 先读真相源；读不到再问事实、约束或假设。
- 判断标准不清 → 用升维 / 换高度找更高判断标准。
- 模型轴不清 → 先分对象、责任、状态、统计、动作语义、真相源、验证路径。
- 分路不清 → 用多视角压测找 2-3 个模型级 alternatives。
- PM 要求多 AI / 子 Agent → 先尝试多 Agent 压测；不可用时声明“单主控多视角退化执行”。

### 3. 不足处一题一问

每次只问一个会改变判断的问题，带推荐默认答案：

```text
我先问一个会改变判断的问题：<问题>。
我的默认建议是：<答案>，因为 <一句业务理由>。
```

沿依赖决策树问：先拍对象、责任、真相源、判断标准，再谈按钮、布局、文案。

PM 短答、抽象答、只选项不解释时，必须追问一次具体后果：

- 如果这个方向错了，用户会做出什么错误动作？
- 哪个业务判断会被误导？
- 哪个统计、状态或真相源会被污染？
- 做了会挤掉什么，不做 / 晚做会损失什么？

追问一次后仍然抽象，就把缺口列入“未验证假设”，不要假装已确认。

### 4. Premise Gate

给方向前，必须点名一个最危险前提：

```text
这轮最危险的前提是：<一句话>。
如果 <证据或情况> 成立，那我们现在的方向就该改。
```

如果找不到危险前提，通常说明这不是 meta 问题，应回到直接执行。

### 5. Alternatives Gate

任何结论前必须给 2-3 个可比较方向。方向必须是模型级差异，不只是按钮、标签、文案、布局差异。

**硬门禁**：Alternatives 输出后必须停住让 PM 选。可以给推荐默认答案，但不能推荐完继续写最终结论、不能直接路由下游、不能直接改文件。

### 6. Coverage Gate

输出最终结论前问：

```text
我感觉关键问题已经覆盖了。还有没有一个没问到、但会改变判断的点？
```

PM 说有，就继续补模型；PM 说没有，再收束。

### 7. Handoff Gate

最后只输出产品判断模型：

```text
## 本轮判断
<判断句>

## 地基账本
- 事实：
- 约束：
- 真相源：
- 假设：

## 判断标准
<这轮按什么标准判断>

## 卡住的模型轴
<对象 / 责任 / 状态 / 统计 / 动作语义 / 真相源 / 验证路径>

## 可选分路
- A：<模型级方向>，成立条件 / 代价
- B：<模型级方向>，成立条件 / 代价
- C：<可选>

## PM 已选
<方向>

## 下一步
<唯一 skill 或明确停住>
```

如果 PM 尚未选择分路，停在“可选分路”，不写最终“PM 已选 / 下一步”。

不要输出空泛总结，不生成长期产品文档。文档成文仍交给 `/pmai-design`、`/pmai-doc-writing` 或 `/pmai-spec-writing`；skill 反馈消化交给 `/pmai-skill-improve`。

## 与其它 skill 的边界

- `/pmai-design`：负责模块结构、信息模型、状态、动作、规格三件套。Meta 只负责把产品判断模型想清楚；只有产品模块结构问题才回 design。
- `/pmai-doc-writing`：负责产品方向、介绍、定位、标题、对外表达成文。Meta 只给重定位结论、判断标准、“从 A 到 B”和反对的旧范式。
- `/pmai-spec-writing`：负责功能型规格文档和模块规格成文。Meta 可以做已有材料压测，但不写完整 PRD。
- `/pmai-build`：只在功能锚点稳定后执行。Meta 可以帮判断锚点稳不稳，但不进入默认 build 门。
- `/pmai-skill-improve`：负责把 PM 对 skill 的反馈消化进 SKILL.md / references / tests / feedback archive。Meta 只判断“该改哪个 skill / 是否该新建 / 是否该先不做”。

一句话：Meta 让“这轮到底判断什么、凭什么判断、卡在哪个模型轴、有哪些模型级分路”变清楚；下游 skill 才把它写成文档、规格、原型或 skill 改造。

## 反模式

- PM 说“不合理”，AI 继续在原方案上加字段、加提示、加解释。
- 没问 PM 关键判断，就输出一段“本质是……”的分析。
- 把 Office Hours、grillme 或 gstack 当成要直接调用的 runtime，而不是吸收到 PMAI 的模型构建动作里。
- 用 Office Hours 或 grillme 作为 `/pmai-meta` 的主品牌，盖过 PMAI 自己的产品元思考。
- 只给一个推荐方向，没有替代方向和被排除方向。
- Alternatives 后没有停住，推荐完就继续写最终方案或路由下游。
- workflow / skill 边界问题没读现有 skill，就建议新建 skill。
- 把 skill / workflow 改造误交给 `/pmai-design`。
- 用“升维 / 第一性原理 / 多视角”当固定章节标题给 PM 看；这些是内部工具，不是前台模板。
- 把 PM 的话整理得更顺，但没有新增判断、前提挑战或下一步落点。
- 把产品元思考产物写成长期文档，越过 design / doc-writing / spec-writing / skill-improve。
