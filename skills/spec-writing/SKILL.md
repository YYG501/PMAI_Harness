# /pmai-spec-writing · 规格文档成文器（模块规格 + 功能型规格文档）

## 入口护栏

执行本 skill 前先运行：

```bash
source "${PMAI_HOME:-$HOME/.pmai}/scripts/skill-preamble.sh"
```

如果输出 `PMAI_PROJECT_INITIALIZED: 0`，停止本 skill，只引导 PM 先发 `/pmai-init-project`。初始化或已有代码接入完成前，不要读取项目底座或生成/改写规格文档。

> **PM 答题规则（M4）**：所有 AskUserQuestion 调用按 `_shared/pm-view/askuser-rules.md` §1 四条硬规则走（空答 STOP / 没拿到答案禁止落盘 PM 视图文档 / runtime 退化保留 wait / 多决策拆开顺序问）。**Runtime 兜底**：本 skill 各门写的都是 picker 形态；runtime 不支持时 AI 按 §1.3 自动退化为编号列表，仍 wait。

## What This Skill Produces

spec-writing 是**统一规格成文器**，负责把已经拍板的信息写成模块 `spec.md` 或功能型规格文档，并集中把关结构、语言风格和 lint。它的核心模型是：**先判断文档目标，再选择 preset、规格模块和功能需求写法**。PRD 只是功能型规格文档的一种 preset，4 列功能表只是特定写法，不是模块 `spec.md` 或所有功能需求的默认格式。

它覆盖四种文档目标：

| 文档类型 | 何时写 | 产物路径 | 用途 |
|---|---|---|---|
| **模块规格** | `/pmai-design` 探索 + 设计拍板后；或 `/pmai-build-close` 收尾发现规格需要按最终结果修订时 | `docs/modules/<模块>/spec.md` | build 的权威契约；写产品行为、规则、字段口径、验收路径 |
| **功能型规格文档** | `/pmai-build-close` 收尾时 PM 按需选择；或 PM 手动要求功能需求 / 功能描述 / 功能规格 / 功能评审稿 | `docs/modules/<按内容命名>.md` | 给研发、业务、评审或后续 build 使用的功能方案；文件名按实际内容定 |
| **PRD 体例** | PM 明确要 PRD、研发评审稿、权限矩阵、完整交付说明，或当前工作需要完整评审结构 | `docs/modules/<按内容命名>.md` | 功能型规格文档的完整 preset；保留 PRD 章节、§六 4 列功能表、PRD lint 和原型覆盖范围表 |
| **既有规格补差** | PM 已有 PRD / 功能需求 / 规格，要求整体优化结构、内容、文风 | 原文件同路径覆盖或 PM 指定路径 | 修已有文档，不重做设计 |

本 skill **只负责模块 `spec.md` / 功能型规格文档成文，不负责替 PM 或 `/pmai-design` 重新做产品决策，也不负责生成 `discussion.md` / `decisions.md`**。`discussion.md` / `decisions.md` 是输入、证据和留痕位置；如果写作时发现信息结构没想清、范围没拍板、规则互相矛盾，必须停下把问题交回 `/pmai-design`、`/pmai-build-close` 或 PM 确认，不能在写作阶段补拍脑袋决策。

功能型规格文档可以选择不同章节模板：PRD 体例是其中最完整的一套章节模板；功能需求 / 功能规格 / 功能评审稿可以选更轻的章节组合。默认落 `docs/modules/` 根目录，文件名按内容取，比如 `批量审核-PRD.md`、`权限模型-功能规格.md`、`组织角色数据范围-联动评审稿.md`。它是**反向合成**，不是「把代码翻译成文档」，更**不从 mock 原型随手的实现反推业务规则**：

- **结构 / 字段 / 交互** ← 最终原型（`prototype/`）+ 模块规格（`docs/modules/<模块>/spec.md`）
- **业务规则 / 权限语义 / 审批口径** ← 模块 `spec.md` + `decisions.md`

**铁律（真系统口径）**：哪怕这版原型是 mock 壳，PRD 也按**真实系统口径**写 —— 需求、业务规则、权限语义都面向生产系统，绝不从 mock 原型的临时实现反推。权限 / 审批这类「为什么」规则代码本来就反映不出来，从模块规格和决策记录锁定。

当功能型规格文档采用 PRD / 评审稿体例时，内含**原型覆盖范围表**：列出本次模块工作覆盖了哪些功能 / 页面、哪些仍是 mock 占位 / 未覆盖（见下方 PRD 体例 preset「§九 附件」+ 步骤 2 原型覆盖范围表）。

## When To Use（四类文档目标）

spec-writing 不是 PRD / spec 两套模式，而是一套规格写作流程。先判**文档目标**，再选**章节模板**，最后按触发方式确定输入和落点。

### 目标 A — 模块规格生成/修改（由 `/pmai-design` 或 `/pmai-build-close` 调用）

- **触发**：
  - `/pmai-design` 完成探索与设计，PM 已拍板模块身份、信息模型、关键规则、呈现方向。
  - `/pmai-build-close` 收尾时，最终原型/验收结论要求修订模块规格。
- **输入**：`discussion.md` 中已收敛的探索结论 + `decisions.md` 中已拍板决策 + PM 确认的 mock/原型线索 + 项目底座；由 `/pmai-build-close` 调用时，还要读最终 `prototype/` 与验收结论。
- **产物**：`docs/modules/<模块>/spec.md`。
- **边界**：只生成/修改 `spec.md`；不写 `discussion.md` / `decisions.md`。发现未决问题就停止落盘，交回调用方继续问清。

### 目标 B — 功能型规格文档（由 `/pmai-build-close` 或 PM 手动调用）

- **触发**：`/pmai-build-close` 收尾时，PM 选择「当前工作要出一份 PRD / 功能需求 / 功能规格 / 功能评审稿」；或 PM 手动要求跨模块 / 专题规格文档。**不是每次工作都必跑**，避免文档税。
- **输入**：涉及模块的 `spec.md` / `decisions.md` + 最终 `prototype/` + `PRODUCT-STATE.md` + `PRODUCT.md` + `PRODUCT-RULES.md`。
- **产物**：`docs/modules/<按内容命名>.md`，文件名按实际内容取，不固定叫 `prd.md` / `spec.md`。
- **章节模板**：按需要选择版本信息、变更日志、名词解释、背景、范围、关键规则、功能需求、字段口径、状态分类、流程、权限矩阵、验收标准、非功能要求、附件等规格模块；PRD 体例才使用完整章节模板。
- **功能需求写法**：先走「功能需求写法选择器」，规则收口用分组规则，状态分类用定义 + 条件表，流程用叙述，字段多用字段表，权限用矩阵，CRUD / PRD §六才默认 4 列功能表。
- **确认门**：只有选择 PRD 体例或 4 列功能表 preset 时，才走 P2.5 二级 / 三级拆分确认门；最终成品确认归 `/pmai-build-close` 的收尾确认。原型覆盖范围表和 §六原型节只属于 PRD 体例，不随 4 列表格 preset 自动触发。

### 目标 C — PRD 体例（功能型规格文档的完整 preset）

- **触发**：PM 明确说「写 PRD」「研发评审稿」「需要完整 PRD 结构」，或当前工作需要完整评审材料、权限矩阵、原型覆盖范围表。
- **输入**：同目标 B，但必须把最终原型结构、相关模块 `spec.md` / `decisions.md`、`PRODUCT-STATE.md` 和 `PRODUCT-RULES.md` 对齐清楚。
- **产物**：仍是功能型规格文档，不固定文件名；可以叫 `xxx-PRD.md`，也可以按 PM 指定命名。
- **preset**：摘要、版本信息、变更日志、名词解释、需求分析、用户与场景、§六功能需求、验收、非功能、附件；身份 / 权限类按需追加数据权限范围和角色权限清单。
- **功能需求写法**：默认使用 4 列功能表 + 二级 / 三级拆分；P2.5 PM 确认门和 `check-prd-hierarchy.py` 只绑定本 preset 或显式选择 4 列功能表的场景。

### 目标 D — 既有规格补差（PM 手动 `/pmai-spec-writing`）

- **触发**：PM 已有 PRD、功能需求、功能描述、功能规格、功能评审稿或模块 `spec.md`，要求「看这个文件」「整体优化结构 / 内容 / 文风」「补某节」「规范一下语言」「按我们的结构重写」。
- **输入**：现有文档 + 补差范围相关的模块 `spec.md` / `decisions.md` / 项目底座。
- **产物**：原文件同路径覆盖或 PM 指定路径。
- **边界**：可以重组结构、补齐已知内容、统一语言；发现产品口径未拍板时停下问，不自行新增规则。纯文风收口可调用 `/pmai-humanize`，但不要让 humanize 接管结构和内容判断。

## 步骤 0 · 开场确认（仅 PM 手动调用时走）

> **由 `/pmai-design` 或 `/pmai-build-close` 调用时跳过本步骤。**调用方已经确定文档目标、模块和默认路径。

PM 手动调用时，AI 第一件事是确认文档目标。AI 调 AskUserQuestion 三连（按 `_shared/pm-view/askuser-rules.md §1.4` 多决策拆开顺序问）：

**第一题：写哪类文档？**
- `question`: "这次要写哪类文档？"
- `options`:
  - `label`: `模块规格`
    `description`: `生成或修改 docs/modules/<模块>/spec.md`
  - `label`: `PRD`
    `description`: `基于当前模块工作生成完整 PRD，落 docs/modules/<按内容命名>.md`
  - `label`: `功能型规格文档`
    `description`: `功能需求 / 功能描述 / 功能规格 / 功能评审稿，回答时告诉我覆盖范围`
  - `label`: `补差`
    `description`: `已有 PRD 或规格，整体优化结构、内容、文风`

**第二题（PM 答完第一题后问）：产物路径？**
- `question`: "文档产物放哪？"
- `options`:
  - `label`: `默认路径`
    `description`: `模块规格 → docs/modules/<模块>/spec.md；功能型规格文档 → docs/modules/<按内容命名>.md；补差 → 原文件覆盖`
  - `label`: `我指定`
    `description`: `优先贴仓内相对路径；仓外文件才贴完整路径`

**第三题（PM 答完前两题后问）：输入清单确认？**

AI 先在 prose 里列出按"输入推荐表"对应场景的推荐输入清单，然后调 AskUserQuestion：
- `question`: "我准备读这些文件，要加 / 减吗？"
- `options`:
  - `label`: `用推荐清单`
    `description`: `按 AI 列的清单读`
  - `label`: `加减文件`
    `description`: `说哪些要加 / 减`

**输入推荐表（手动调用）**：

| 场景 | 推荐输入 |
|---|---|
| 模块规格 | `/pmai-design` 已收敛的 discussion/decisions + PRODUCT-STATE.md + PRODUCT.md + PRODUCT-RULES.md + docs/modules/INDEX.md + 已确认 mock/原型线索；如是 `/pmai-build-close` 收尾修订，还要读最终 prototype/ 与验收结论 |
| 功能型规格文档（当前工作） | 最终 prototype/ + PRODUCT-STATE.md + PRODUCT.md + PRODUCT-RULES.md + docs/modules/INDEX.md + 涉及模块的 docs/modules/<模块>/spec.md / decisions.md |
| 功能型规格文档（PM 指定模块清单 X/Y/Z） | PRODUCT-STATE.md + PRODUCT.md + PRODUCT-RULES.md + docs/modules/INDEX.md + docs/modules/X/spec.md + docs/modules/Y/spec.md + docs/modules/Z/spec.md |
| 既有规格补差 | 现有 PRD/spec + 补差范围相关的 module spec / decisions 子集 |

三题答完后进入实际写作（步骤 1）。

**禁止**：
- 当 PM 在 prompt 里明确说「覆盖 X/Y 模块」或「不绑定当前工作」时仍按当前工作流程跑（要识别跨模块功能型规格文档，跳过无关旧工作上下文必读）
- 推荐清单僵化（PM 选跨模块功能型规格文档后仍读无关模块或旧工作上下文）
- 把「优化文档」当成重新设计：未获 PM 确认不得新增产品规则、改范围、改模块归属

## Required Inputs

### 模块规格目标（目标 A）

`/pmai-design` 调用时，输入已经来自同一模块的 `discussion.md` / `decisions.md`。`/pmai-build-close` 调用时，输入还包括最终原型、验收结论和收尾对账结果。本 skill 要做的是把已确认内容写成或修订 `spec.md`，不再展开 PRD §六重组，也不生成 `discussion.md` / `decisions.md`。

- 🟢 本模块 `discussion.md`（探索结论 + 设计讨论收敛稿）
- 🟢 本模块 `decisions.md`（已拍板决策、否过方案、术语定名）
- 🟢 `PRODUCT-STATE.md`（产品现状，避免规格写成和当前产品脱节）
- 🟢 `PRODUCT.md`（项目定位 / 用户画像 / 业务术语表）
- 🟢 `PRODUCT-RULES.md`（跨功能产品行为规则）
- 🟢 `docs/modules/INDEX.md`
- 🟡 已确认的 mock / 原型线索；由 `/pmai-build-close` 调用时读最终 `prototype/` 与验收结论（只作为规格修订 evidence；规格不嵌 ASCII、不描述像素布局）
- ❌ 任何 `.engineering.md`

### 功能型规格文档目标（目标 B）

沉淀阶段原型已建完 —— 反向合成多源拼齐：**结构 / 字段 / 交互**看最终原型 + 模块规格，**业务规则 / 权限语义**看模块 `spec.md` 与 `decisions.md`。

- 🟢 最终 `prototype/`（栈内建好的主原型）— **结构 / 字段 / 交互的来源**：实际页面 / 弹窗 / 字段 / 按钮按它落 §六与原型节。遵守 `input-flow.md` §9.3.1 原型读取强约束（>500 行禁整文件 Read，按目录 / 入口选读）。**只取结构，不从 mock 实现反推业务规则**（真系统口径铁律）。
- 🟢 `PRODUCT-STATE.md`（产品现状，项目底座核心 — 已落地的产品全貌 / 主原型当前状态；PRD 要和产品现状一致，不重复造口径）
- 🟢 `PRODUCT.md`（项目定位 / 用户画像 / 业务术语表 / 技术栈）
- 🟢 `PRODUCT-RULES.md`（如存在 — **全文读**，跨功能产品行为规则；PRD 一次写对、不违背常驻规则。）
- 🟢 `docs/modules/INDEX.md` + `docs/modules/<本次工作涉及模块>/spec.md` / `decisions.md`（如目录存在）
- ❌ `DESIGN.md`（视觉规范，归 build 阶段读；PRD 写需求方案不写像素颜色，DESIGN.md 在本 skill 只作**反向边界提示**用，不作正向源材料 —— 见 §六「原型」节 / §六 lint 视觉细节越界）
- ❌ 任何 `.engineering.md`

### 跨模块功能型规格文档 / 既有文档补差目标（目标 B/D）

按步骤 0 与 PM 对话确认的清单读入，参考上方「输入推荐表」。不绑定当前工作时，不读无关旧工作上下文。

特别遵守：
- 手动调用如读 `prototype/`（跨模块功能型规格文档评审已落地模块时有原型），遵守 `input-flow.md` §9.3.1 原型读取强约束（>500 行禁整文件 Read）

## Workflow

> 模块规格目标走 S1-S5；功能型规格文档目标走 P0.5-P3.8；PRD 体例只是功能型规格文档流程内的完整 preset；既有规格补差目标走 C1-C5。PM 手动调用先走步骤 0，`/pmai-design` 和 `/pmai-build-close` 调用时跳过步骤 0。

### C1-C5 · 既有规格补差流程（目标 D）

PM 给了既有文档并要求"整体优化结构、内容、文风"时，按三层处理，**不要把它降级成 `/pmai-humanize` 纯润色**：

| 层级 | 谁负责 | 处理方式 |
|---|---|---|
| 结构 | `/pmai-spec-writing` | 重排章节、合并重复段、把功能需求改成可评审结构 |
| 内容 | `/pmai-spec-writing` | 基于模块 `spec.md` / `decisions.md` / 项目底座补已知事实；无依据就问 PM |
| 文风 | `/pmai-humanize` 规则 | 最后一遍去 AI 味、去黑话、改顺句子 |

C1. **判文档类型**：确认它是功能型规格文档。若其实是产品方向 / 产品介绍 / 一页纸 / 汇报材料，停止本 skill，转 `/pmai-doc-writing`。

C2. **读原文 + 读最小真相源**：先读原文，再按涉及范围读 `docs/INDEX.md`、`docs/modules/INDEX.md`、相关模块 `spec.md` / `decisions.md`、`PRODUCT-STATE.md`、`PRODUCT.md`、`PRODUCT-RULES.md`。不整仓乱读。

C3. **先出改稿计划**：用 3 段给 PM 看清楚要改什么：
- 结构问题：章节顺序、重复、缺少功能需求 / 验收 / 边界等。
- 内容问题：缺事实、缺规则、与模块规格冲突、引用过期口径。
- 文风问题：AI 腔、黑话、啰嗦、无法执行的泛词。

PM 已明确说"直接改"时可跳过确认；否则等 PM 确认改稿方向后落盘。

C4. **重写 / 覆盖**：在原路径覆盖或写到 PM 指定路径。允许重排结构和补齐已知内容，但禁止新增未拍板的产品规则；遇到缺口用 TODO / 待 PM 确认标注，不把猜测写成事实。

C5. **收口**：PRD 体例文档跑 P3.5 lint；所有文档目标最后按 `/pmai-humanize` 的表达层规则做一遍文字收口。若文档落在 `docs/modules/<按内容命名>.md`，同步更新 `docs/modules/INDEX.md`。

### attachments AI 接管 hook（trigger 0 — 任何步骤期间生效；手动独立调用不启）

**模块规格目标 / 绑定当前工作的功能型规格文档目标启用 trigger 0**；**不绑定当前工作的跨模块功能型规格文档 / 既有规格补差目标默认不启**（不一定绑定当前模块状态 → 不写 `.work-meta.json`）。

PM 在 chat 任何位置自然描述 "我有 X 在 ~/Downloads/foo.pdf，重点 Y" → AI first-principle 识别（chat 含绝对路径 + 描述材料）→ 调 helper：

```python
from _lib.attachments import copy_attachment

# 模块规格目标
result = copy_attachment(work_dir, Path("~/Downloads/foo.pdf"),
                        stage_prefix="spec", hint="Y 重点",
                        input_category="interviews")

# 绑定当前工作的功能型规格文档目标
result = copy_attachment(work_dir, Path("~/Downloads/foo.pdf"),
                        stage_prefix="prd", hint="Y 重点",
                        input_category="interviews")
```

stage_prefix 按文档目标取值：模块规格目标用 `"spec"`，绑定当前工作的功能型规格文档目标用 `"prd"`。`input_category` 由 caller 按 PM 描述 / 材料内容判断（完整类别表见 `_shared/pm-view/attachments-upload.md`）。chat 一行确认 `已归档到「访谈材料」（docs/inputs/interviews/<spec|prd>-foo.pdf），Y 重点。继续。`（禁 cp / 绝对路径全文 / 字段名等工程黑话）。

异常 catch：
- `FileNotFoundError` → "路径不可读：<src>。"
- `SensitivePathError` → "路径含敏感关键词，拒纳：<src>。"
- `FileSizeError` → "文件 X MB 超 50MB 上限。"

**trigger 2 fallback**：写模块 `spec.md` / 功能型规格文档前扫 `docs/inputs/*/`，`is_seen(work_dir, filename)` 判定（真相源 `.work-meta.json:attachments_seen`，非引用 section）。

**引用 section 渲染**：写模块 `spec.md` / 功能型规格文档时 `list_attachments_seen(work_dir)` 按 `registered_at` 升序渲染到文档物理末尾 `## 参考材料` section。

**单一真相源**：`skills/_shared/pm-view/attachments-upload.md`（完整 prose / 替换 / 删除 / batch / 失败兜底）。

### S1-S5 · 模块规格生成/修改流程（目标 A）

S1. **核对结论已收敛**：确认 `discussion.md` 里没有未回答问题，`decisions.md` 已记录关键拍板；由 `/pmai-build-close` 调用时，同时确认最终原型/验收结论没有新的未决产品问题。若还有未决问题，停止写 `spec.md`，交回调用方。

S2. **抽取规格骨架**：从 `discussion.md` / `decisions.md` 提炼模块定位、功能清单、信息模型、业务规则、页面 / 交互口径、验收路径、边界与非目标。章节顺序按 `_shared/pm-view/section-order.md` 的 `spec.md` 约束。

S3. **写入 / 更新 `spec.md`**：按 `docs/modules/<模块>/spec.md` 就地成文。新模块新建；重做模块升版本号 + 变更日志，正文只写最终事实，旧口径的为什么留在 `decisions.md`。**变更说明必须简要**：每条一句，通常 20 字内、最多不超过 30 字；只写"改了什么"，不写原因、过程、背景，复杂理由放 `decisions.md`。

S4. **语言把关（先锚定金标准，再守禁用清单）**：
- **第一步，锚定语体**：动笔前读 `references/few-shots.md` 顶部「大白话模块 spec 金标准」一节——那里的**6 条可检验风格卡 + 待办实例 + 语体转换反例表**就是模块 spec 的目标语体。模块 spec **学待办那种大白话讲法，不套 PRD 的 L1–L6 重型指纹**（套了就会写成"咨询报告 / 方法论白皮书"腔，PM 还得逐句改回来）。`references/few-shots.md` 下半部的真系统 PRD 样例**只在采用 PRD 体例时参照，模块 spec 不模仿**。
- **第二步，硬守**：8 类禁用清单；L6 术语锁定；L1 轻版（先结论、短句、动作先行）；不写代码路径 / 字段名 / reducer / hook 等工程词；不嵌原型 ASCII，不写像素和颜色。
- **方法论 / 算法类模块**（如 ROI 测算）：天生需要公式和口径，公式以**纯文本**保留即可，但同样去掉 `Σ × ÷ ≥` 符号堆砌、`→ ✘ ✅ ⚠️` 装饰、中英混杂和版本叙事——语言整体收到大白话（风格卡第 3 条）。

S5. **规格自检（机械关口 + 冷读语体，PM 看到前先扫干净）**：
- **机械关口（必跑）**：写完 `spec.md` 后跑下面这段 grep，把可机械检测的语体违规扫出来；命中即对照风格卡逐处改，改完复跑到无命中（方法论 spec 里 `×`、命名公式等可能是合理算式 —— 逐条人工判断，是装饰就改、是必要算式就留）。

  ```bash
  SPEC="docs/modules/<模块>/spec.md"   # 替换为实际路径
  echo "── 版本/迭代叙事（正文不留，改去变更日志）──"
  grep -nE 'V[0-9]+(\.[0-9]+)?[^|]*基础上|沉淀回规格|重做|老版|新版|上一版|第[一二三四五六七八九]版' "$SPEC"
  echo "── 文件路径直引（改成产品功能名 / 本规格 §X）──"
  grep -nE '[A-Za-z0-9_./-]+/[A-Za-z0-9_./-]+\.(md|tsx?|jsx?|py|json)|docs/|prototype/|src/' "$SPEC"
  echo "── 中英混杂（给中文产品词）──"
  grep -nE 'business case|Payback|NPV|IRR|POC|SaaS|CRUD|\breview\b|\bscope\b|\bprompt\b|double-?count' "$SPEC"
  echo "── 数学符号 / 流程装饰（公式改大白话，删装饰）──"
  grep -nE 'Σ|≥|≤|⊆|⊊|✘|✅|⚠️|→ ' "$SPEC"
  ```

- **冷读语体（必做）**：通读一遍自问——"这读起来像待办那种**大白话产品规格**，还是像**咨询报告 / 方法论白皮书**？"。若后者，标出最像白皮书的 2–3 处，对照风格卡 6 条改。**打磨文字可直接调 `/pmai-humanize <spec 路径>`** 当统一引擎（按"简要易懂 / 规格平实"语气跑改写 + 二次自审）；也可派 subagent 冷读：给它风格卡 6 条 + 待办实例，让它只回答"像哪一类、哪几处不像大白话"。
- **结构 / 4 问自检**：对照 `skills/spec-writing/references/writing-rules.md`「规格 4 问自检」和 `skills/_shared/pm-view/checklist.md`；发现结构问题回调用方补拍，发现表达问题直接修文。
- **多视角冷读（可选）**：PM 明确想在定稿前找盲区、对齐 truth source、或让几个 agent 分别看时，可跑 `/pmai-meta <spec 或功能型规格文档路径>` 的已有材料压测。它只产出产品判断模型、问题诊断和改法方向，不替代本 skill 的成文职责，也不作为默认定稿门。

模块规格目标到这里结束，不进入下方 PRD §六重组和原型覆盖表流程。

### P0.5 · 项目级文档强制 echo（绑定当前工作的功能型规格文档目标必跑；不依赖 LLM 自觉 Read）

PRD 漏读 / 浅读项目级文档（PRODUCT-STATE / PRODUCT.md / PRODUCT-RULES.md / modules INDEX）是 LLM 自觉 Read tool 触发不稳的典型踩坑。本子步骤用 Bash `cat` 把项目级文档无条件 echo 到 transcript，**保证内容进入 working context** —— 比依赖 Read tool 自觉触发硬。冗余于上方「Required Inputs」prose 列表也无害。

**绑定当前工作的功能型规格文档目标：必跑本步骤**（`/pmai-build-close` 调用时已确定当前工作和默认路径 → 直接进 P0.5）。
**跨模块功能型规格文档 / 既有规格补差目标**：步骤 0 已与 PM 对齐清单 / PM 在线会立刻拦漏读，本步骤可省。

最终 `prototype/`（结构 / 字段 / 交互来源）按 `input-flow.md` §9.3.1 强约束选读，不在本步全文 echo（原型代码量大，全文 echo 会污染 context；步骤 2 派生 §六时按目录 / 入口选读）。

```bash
SOURCES=(
  "$REPO_ROOT/PRODUCT-STATE.md"
  "$REPO_ROOT/PRODUCT.md"
  "$REPO_ROOT/PRODUCT-RULES.md"
  "$REPO_ROOT/docs/modules/INDEX.md"
)

for f in "${SOURCES[@]}"; do
  if [ -n "$f" ] && [ -f "$f" ]; then
    echo "════════════════════════════════════════════════════════════════"
    echo "FORCE READ: $f"
    echo "════════════════════════════════════════════════════════════════"
    cat "$f"
    echo "════════════════════════════════════════════════════════════════"
    echo "END $f"
    echo "════════════════════════════════════════════════════════════════"
  else
    echo "ℹ️  $f 不存在或未解析，跳过"
  fi
done
```

涉及模块的 `docs/modules/<模块>/spec.md` 在**P1.5** echo（要等 P1 识别完本次工作涉及哪些模块；不能在 P0.5 机械列出，会污染 context）。

本步骤只保证内容到位，不做 echo 后语义校验（语义校验靠 LLM 在步骤 1 拆决策 / 步骤 2 派生 §六时自然消化）。

P1. **识别涉及模块 + 拆决策**（基于 P0.5 已 echo 的内容）——从 `docs/modules/INDEX.md`、当前 `.work-meta.json`、本次改动与 PM 说明识别模块清单，落到 `MODULES` 变量供 P1.5 使用；从模块 `decisions.md` 拆出「已确认决策」和「待补口径」。有待补口径则先编号提问 PM，确认后再写功能型规格文档。**需求方案从模块 spec / decisions + 最终原型的结构反向拼** —— 真系统口径，不从 mock 实现反推规则。

P1.5. **涉及模块 spec 强制 echo**（绑定当前工作的功能型规格文档目标必跑；同 P0.5 同源理由）——P1 识别完本次工作涉及模块后，把对应 module spec 文件无条件 echo 到 transcript。一个模块可能含多个功能型规格文档，echo **模块上下文目录里的 `spec.md` 主文件**即可；必要时再按 `docs/modules/INDEX.md` 追加读取相关功能型规格文档：

   ```bash
   # 步骤 1 识别出的涉及模块（LLM 填）
   MODULES=(
     # 例：
     # "部门+用户+角色设计"
     # "日志"
   )

   # 每模块 echo 主 spec 文件（按 INDEX.md 当前路径）
   MODULE_SPECS=(
     # 例：
     # "$REPO_ROOT/docs/modules/日志/spec.md"
     # "$REPO_ROOT/docs/modules/部门用户角色/spec.md"
   )

   for f in "${MODULE_SPECS[@]}"; do
     if [ -f "$f" ]; then
       echo "════════════════════════════════════════════════════════════════"
       echo "FORCE READ: $f"
       echo "════════════════════════════════════════════════════════════════"
       cat "$f"
       echo "════════════════════════════════════════════════════════════════"
       echo "END $f"
       echo "════════════════════════════════════════════════════════════════"
     fi
   done
   ```

   边界：
   - 涉及模块为空（如 IA 重整类工作改的是框架配置不绑某模块）→ 跳过本步骤
   - 单模块 spec > 1500 行 → 仍 echo 全文（PRD 写作要全局视野，截读会漏）
   - 跨模块功能型规格文档 / 既有规格补差目标跳过（同 P0.5 理由）

P2. **选择规格模块和功能需求写法**——功能型规格文档先选规格模块，再选功能需求写法。不要默认把所有内容都塞进 PRD §六 4 列表格。
   - **规格模块菜单**：版本信息、变更日志、名词解释、背景 / 需求分析、用户场景、范围 / 非目标、关键规则、功能需求、字段口径、状态 / 分类、流程、权限矩阵、验收标准、非功能要求、附件。按文档目标选择，不为凑完整而强加章节。
   - **功能需求写法选择器**：
     - 规则收口 / 口径统一：短定义 + 分组规则 + 验收清单。
     - 状态 / 分类 / 卡片：分类定义 + 触发条件表 + 展开字段表 + 按钮 / 消失规则。
     - 多步流程：按先后、条件、异常分支分段叙述；表格只放并列字段或状态。
     - 字段很多：字段口径表；字段含义、来源、是否必填、默认值、校验规则各列写清。
     - 权限 / 角色差异：权限矩阵或可见范围表；必要时追加边界说明。
     - CRUD / 管理后台动作清单：可使用 4 列功能表。
     - PRD 体例 §六：默认使用 4 列功能表 + 二级 / 三级拆分 + PRD lint。
   - **选择原则**：读者更快懂优先。表格是并列信息工具，不是所有功能需求的默认容器；内容本质是流程、状态、规则时，首选叙述或专用表。

P2-PRD. **PRD 体例的功能分解 + 原型覆盖范围表**——只有功能型规格文档采用 PRD / 评审稿体例时，才进入本步骤。显式选择 4 列功能表 preset 但未选择 PRD 体例时，只走 P2.5 的二级 / 三级拆分确认和 P3.5 lint，**不要求**原型覆盖范围表、§六原型节或完整 PRD 附件。PRD 体例中，§六功能需求的层级**从模块 `spec.md` + 最终原型的实际结构派生**：把规格里列出的功能 / 页面 / 字段，对照原型里**真实建出来的**结构，按用户动作重组为 §六的一级 / 二级 / 三级层级。动词锚定规则不变（见 P2.5），重组对象是「模块规格功能项 + 原型真实结构」。
   - **模块规格（`spec.md`）**：规格是功能项的权威来源；§六层级从它派生。
   - **最终原型（`prototype/`）**：实际页面 / 弹窗 / 字段 / 按钮按它落 §六行 + 原型节。**只取结构，不从 mock 实现反推业务规则** —— 权限 / 审批 / 校验等口径从模块 `spec.md` + `decisions.md` 锁定（真系统口径铁律）。
   - **原型覆盖范围表**——反向 PRD 必含一张「原型覆盖范围表」，落到 §九 附件：列出范围清单里每个功能 / 页面，对照原型标注覆盖状态（已完整覆盖 / mock 占位 / 未覆盖）。让评审一眼看出本次工作把哪些做实了、哪些还是壳。表结构与示例见下方「PRD 体例 preset」§九 附件。
   - **原型节怎么写**——§六的「原型」节沉淀阶段**优先放真实原型截图**（原型已建完）；暂无截图时由 AI 按原型实际结构现画 ASCII，不写"待补充"。规则：
     - **数量**：模块下有几个页面 / 弹窗 / 抽屉就放几张，**一一对应不省略**。例：「角色管理」模块含「角色列表页 + 创建角色弹窗 + 角色详情抽屉」 → 放 3 张。识别清单参考最终原型实际结构 + 范围清单功能项 + §六二级功能动作组（创建 / 编辑 / 详情类动作通常对应一个弹窗或抽屉）。
     - **详细度**：中等。ASCII 兜底时每张 30-60 行，含：顶部标题 / 主要分区框 / 表头列名 / 列表行示例（2-3 行真实数据样例）/ 主要按钮文案 / 表单字段名。**不画**：像素 / 颜色 hex / 组件库名（Badge / Tag / Drawer 等）/ 字体字号 —— 这些是 DESIGN.md 范畴。
     - **每张原型上方 1 句兜底说明**：「这是 X 页面 / X 弹窗 / X 抽屉」+ 用户主路径一句话；ASCII 块如被替换成真实截图，这句话仍保留作锚。
     - **格式**：截图用标准 markdown 图片；ASCII 兜底用 markdown fenced code block 包裹（` ``` ` 标记），保证等宽对齐不被渲染破坏。
     - 示例见 spec-writing skill few-shots「§六 原型节 ASCII 示例」段。

P2.5. **§六功能拆分预处理（只绑定 PRD 体例 / 4 列功能表 preset）**——写 §六表格之前做一次结构预处理；目的是把「按 UI 容器组织」重组为「按业务本质对应的一致维度组织」。本步骤**不适用于模块 `spec.md`、规则收口、状态分类、流程叙述、字段口径或既有文档补差**，除非 P2 已明确选择 4 列功能表。PRD 体例的重组对象是 **模块 `spec.md` 功能项 + 最终原型的真实结构**；维度选取规则见 a。

   **a. 选定组织维度**——先认定本次模块工作业务本质对应的**一致维度**作为二级 / 三级层级的组织轴；选定后所有二级 / 三级命名围绕同一维度展开。常见维度（不限于这些，AI 看 spec / decisions 业务本质临场判断）：

   | 业务类型 | 维度 | 二级 / 三级命名风格 |
   |---|---|---|
   | CRUD 管理后台 | 用户**动作 / 操作** | 动词或动词派生名词（"分配额度到部门" / "调整分配" / "查看许可证详情"） |
   | 信息架构 / 导航重整 | **分组分类** | 名词分组词（"工作台" / "数据中心" / "系统设置"） |
   | 配置 / 设置类 | **设置项归类** | 设置项名称 |
   | 流程 / 状态机类 | **步骤 / 节点** | 步骤名 |

   维度判定优先级：**模块规格 / 决策记录明示** > **业务本质推断** > **e 步骤请 PM 拍板**。`spec.md` 或 `decisions.md` 已言明（如决策记录写「按菜单分组重组」）直接采用；不清晰时在 e 步骤一并请 PM 拍板，不替 PM 决定维度。

   以 prose 形式列出本次工作各一级模块下属于该维度的所有功能项；每模块 3-15 项。CRUD 业务可参考下方「层级划分原则」§二级功能动作组常用词汇表（仅动作维度适用）。

   **b. 聚类成二级 / 三级**——按选定维度聚类：同维度下的归类作为二级功能、细分作为三级功能。命名风格随维度变（见 a 表格）；同一维度内保持一致。同一二级下三级 ≤ 2 个时可不分级（避免强行分级）。

   **c. UI 词汇黑名单扫描**——生成的二级 / 三级名命中下列词汇时**强制重写**（跨业务通用约束，与 a 维度无关）：
      - **必抓黑名单**：弹窗 / Dialog / 面板 / 视图 / 视角 / 入口 / 字段 / 段 / 区块 / 菜单 / 顶部 / 底部 / 行级 / 池行 / Tab / Drawer / 紧凑形态
      - **启发式次抓**：「X 弹窗」「X 视图」「X 入口」「X 字段」「X 段」「X 面板」「顶部 X」「行级 X」「操作菜单」等组合
      - 命中即 fail，必须重写为符合 a 选定维度的命名。例：
        - 动作维度：「分配额度弹窗」→「分配额度到部门」
        - 分组维度：「Tab 1 工作台」→「工作台」（去掉 UI 容器名）
        - 设置项维度：「角色权限设置面板」→「角色权限」
        - 「池行紧凑形态」→ 删除（下沉到 d 步骤）
      - 例外：若 `菜单` 是本次工作业务本质核心词（IA 重整类工作），允许保留但不作为二级 / 三级命名本身 ——「菜单结构」属业务领域词，「工作台菜单」作为二级则仍命中（应改「工作台」）。

   **d. 下沉规则**——以下内容**禁外溢成独立二级或三级，必须写进对应三级的需求描述列编号项**（跨业务通用，与 a 维度无关）：
      - 角色视角差异（不同角色看到的范围 / 入口可见性差异）
      - UI 视图切换（如部门视角 / 许可证视角 / Tab 切换）
      - UI 形态规则（如紧凑形态 / 失效证简化 / 字段排序 / 折叠规则）
      - 弹窗 / 面板的触发方式、内部字段、校验规则

   **e. 产物 + PM 确认门（强制）**——把 a/b/c/d 的产物整理成 PM 视图语言输出给 PM 看，**采用 PRD 体例的功能型规格文档都必须等 PM 拍板**才进 P3。

   **PM 看的展示模板**（标题用「功能模块拆分」；不出现「§六」「P2.5」「拆分预处理」「reorg pass」「黑名单扫描」「下沉」「动作组」等工程章节号 / 内部规则名 / 模型术语；**「一级 / 二级 / 三级功能」保留** —— PRD §六层级标准术语，PM 看 PRD 时本就是这套，chat 用同名反而一致。详见 `_shared/pm-view/writing-rules.md` §3.12「禁工程黑话」）：

   ```
   功能模块拆分

   [AI 一句话说明组织维度 + 理由，用 PM 大白话 —— 不照搬 a 表格的"维度"二字，用本次工作业务本质对应的具体词。
    示例（AI 临场填，不照抄）：
      · "这次按用户操作组织二级 / 三级（CRUD 后台业务，每个二级是一类动作）"
      · "这次按一级菜单分组组织二级，三级是该分组下的具体菜单项（导航结构重整）"
      · "这次按设置项归类组织（按生效范围分组）"
    ]

   一级功能：[模块名]
     ├ 二级功能 [A]：三级功能 [a1] / [a2] / [a3]
     ├ 二级功能 [B]：三级功能 [b1]
     └ 二级功能 [C]：三级功能 [c1] / [c2]

   一级功能：[另一模块名]
     ├ ...

   下面这些细节会写进对应三级功能的需求描述里，不单独列：
   - [视角切换 / 紧凑形态 / 弹窗细节…] → 归到「[三级功能名]」下

   哪些要改 / 加 / 删 / 调整归类（含维度选取本身）？回 OK 就按这个写 PRD 表格。
   ```

   **门规则**：
   - PM 回「OK」/「就这样」/「可以」→ 进 P3 写表格。
   - PM 给修改意见 → 回 a-d 重做拆分，再次输出展示模板请 PM 确认（迭代直到 PM 拍板）。
   - **禁止 AI 自判「无歧义」跳过本门**。理由：本门确认的是 §六层级的**命名底稿**（PM 决定怎么分组 / 怎么叫），与 `/pmai-build-close` 的成品收尾确认职责不同（一个看结构、一个看成品），不存在叠加 —— PM 在这一门是结构裁判，跳了 PM 就失去了对菜单 / 模块归类的拍板机会。
   - 黑名单命中（c 步骤）由 AI 自己重写后再展示给 PM 看最终版，**不要把违规原命名贴给 PM 看**（PM 看了反而困惑）。
   - 发现规则空白（c 步骤黑名单漏抓 / 词汇表缺词），同步补到「层级划分原则」段。

   跳过条件：本次文档不是 PRD 体例，也未选择 4 列功能表 preset；或本次工作不含 §六功能需求章节内容。

P3. **生成功能型规格文档**——如果 PM 要 PRD / 评审稿，按下方「PRD 体例 preset」生成完整 PRD 体例文档到**产物路径 `$PRD_PATH`**（骨架见 `$PMAI_HOME/skills/spec-writing/templates/prd.md.tmpl`）；如果 PM 要功能需求 / 功能描述 / 功能规格，则按 P2 选择的规格模块和功能需求写法生成，保留必要的范围、规则、功能需求、字段 / 状态 / 流程、验收和附件，精简非必要 PRD 元信息。语言风格对齐「写作规则」与「few-shots」。**`$PRD_PATH` 按文档目标解析**：功能型规格文档默认 `docs/modules/<按内容命名>.md`；补差 = 现有文档同路径覆盖；PM 明确指定路径则用 PM 指定路径。选择 PRD 体例或 4 列功能表 preset 时，**§六功能需求表格的二级 / 三级命名严格按 P2.5 的版本写入；不允许在写表格时再发明新的二级 / 三级名。** PRD 体例的 §六「原型」节按 P2-PRD 现画 ASCII（每模块下每个页面 / 弹窗 / 抽屉一张 + 1 句文字兜底）。

P3.5. **PRD / 4 列功能表 lint（自动兜底，条件必跑）**——写完 PRD 体例功能型规格文档，或显式选择 4 列功能表 preset 后，跑 `python3 $REPO_ROOT/scripts/check-prd-hierarchy.py "$PRD_PATH"`（`$PRD_PATH` = P3 按文档目标解析的产物路径；既有规格补差目标时只有原文是 PRD 体例或含 4 列功能表才跑）。模块 `spec.md`、规则收口、状态分类、流程叙述、字段口径文档**不跑本 lint**。脚本做三类机械检查：

   **类 1 — §六层级**：扫描 §六表格的二级 / 三级 cell 是否含 UI 词违规（弹窗 / 面板 / 视图 / 视角 / 入口 / 字段 / 段 / 区块 / 菜单 / 顶部 / 行级 / 池行 / Tab / Drawer / 紧凑形态 + 启发式形态如「X弹窗」「X字段」「顶部X」「行级X」等）。

   **类 2 — 描述风格违规**（全篇扫描，对应 writing-rules.md「描述风格规则」6 类）：
   - 视觉细节：颜色 hex（`#[0-9A-F]{6}`）、Badge / 视觉弱化 / 警示图标 / destructive / warning / 主色填充 / ghost 按钮 / 明文按钮 / 紧凑形态 / 加粗加红
   - URL 路由：`?view=` / `?tab=` / `<licenseId>` / `<productId>` / `&license=` / 图标字符 ▾▸↔
   - 排版分隔符：中文方角引号 `「」`（应该全部用 `"..."`）/ 中点 `·`（用顿号 `、`）
   - 否定式描述：`无 ⋮` / `不再有` / `不再展示` / `不再拆` / `不再渲染` / `不是 destructive`
   - 工程黑话：`触发(弹窗|开通|分配|对应|二次)` / `锚定` / `池行末` / `顶部右侧` / `顶部右上` / `focus trap` / ` loading ` / ` disabled ` / ` remove ` / `池树` / `账本` / `跟随失效` / `同口径` / `漂移`

   **退出码语义**：
   - **0** = 无违规，进入 P3.6
   - **1** = 有违规，把脚本输出原样贴到 chat 给 PM 看；类 1 违规回到 P2.5 重新预处理 §六，类 2 违规直接修订对应位置；发现新规则时补到**权威单一真相源** `_shared/pm-view/writing-rules.md` + `scripts/check-prd-hierarchy.py` 黑名单（`references/writing-rules.md` 只补样例，不补规则 —— §3.12 权威已搬 `_shared`）
   - **2** = 文件读取错误，报错退出

   lint 是 PRD 体例 / 4 列功能表的 mechanical check，不依赖 AI 内化规则，也不代表所有规格文档都应该使用 4 列表格。

P3.6. **PRD §三 名词解释 = 本次工作临时词典**——本次工作范围内引入的新业务术语 / 角色由 AI 写 §三时落地（见 §三章节写作要求 + `references/few-shots.md` 三、名词解释示例）。

P3.7. **关键产品决策候选清单**——PRD 成文后，检查 §四里的关键产品决策是否已经存在于模块 `decisions.md` 或项目级 `PRODUCT-RULES.md`。

   - 已存在：PRD 只引用结果，不重复写一套备选和理由。
   - 不存在：列成「建议回写」候选交给调用方；绑定当前工作的功能型规格文档由 `/pmai-build-close` 统一处理基线回写，跨模块功能型规格文档 / 既有规格补差目标只在文档内保留决策结果。
   - 本 skill 不在写 PRD 时直接改 `decisions.md` / `PRODUCT-RULES.md`，避免和 `/pmai-build-close` 的基线回写职责重叠。

P3.8. **候选跨功能产品规则清单**——写 PRD 过程中，若规划期讨论里浮出**全项目跨功能产品行为规则**（不是某次实现反馈、而是「产品在 X 情况下应 / 不应 Y」、适用范围超出本次工作单个模块的规则），列成候选交给 `/pmai-build-close` 或 PM 手动确认：

   - AI 预判候选 + 拟写条目（标题 / 规则 / scope 全局或域限定 / 来源工作）逐条列出
   - 绑定当前工作的功能型规格文档 → 交回 `/pmai-build-close`，由 close 的决策 / 规则回写门统一问 PM 并落盘
   - 跨模块功能型规格文档 / 补差 → 只在文档内保留，不自动改项目基线；PM 明确要求记录时另走 `/pmai-build-close` 或 `/pmai-record`
   - `PRODUCT-RULES.md` 不存在 / 无候选 → silent skip
   - **边界**：用词术语 → PRODUCT.md；模块级规则 → modulespec；视觉规范 → DESIGN.md。本步只捞全项目跨功能产品行为规则。

   > 补「规划期发现的规则无沉淀路径」缺口：spec-writing 捞范围确认 / 沉淀讨论里的跨功能规则候选。

## PRD 体例 preset

PRD 体例是功能型规格文档的完整 preset。只有 PM 明确要 PRD / 研发评审稿，或当前工作需要完整评审结构、权限矩阵、原型覆盖范围表时使用。不要把本 preset 套到模块 `spec.md`、规则收口、状态分类、流程说明或轻量功能规格上。

**章节固定 9 节**：摘要 / §一 文档版本信息 / §二 变更日志 / §三 名词解释 / §四 需求分析 / §五 用户与场景 / §六 功能需求 / §七 验收标准 / §八 非功能性需求 / §九 附件（可选）。摘要 / §五 5.2 用户故事 / §五 5.3 非目标 / §七 验收标准 / §八 非功能性需求 **不可省**；§九 附件 按需输出。

### 摘要

写一段不超过 80 字的概述：本 PRD 的范围、覆盖的功能模块、计划交付迭代或时间。让评审人在 5 秒内得到 scope。开头用「本 PRD 旨在明确...」或「本 PRD 描述了...」。

| 字段 | 值 |
| --- | --- |
| 文档名称 | 万智平台 - [模块名称] - 产品需求文档 |
| 版本号 | V1.0 |
| 撰写人 | xxx |
| 评审人 | xxx |
| 撰写时间 | YYYY-MM-DD |
| 当前状态 | 草稿 / 评审中 / 已发布 |

### 二、变更日志

| 日期 | 版本 | 变更说明 | 修改人 |
| --- | --- | --- | --- |
| YYYY-MM-DD | V1.0 | 初版 | xxx |

变更说明必须简要：每条一句，通常 20 字内、最多不超过 30 字；只写"改了什么"，不写原因、过程、背景。复杂理由放 §四或对应模块 `decisions.md`，不要塞进变更日志。

### 三、名词解释

定义专有名词、缩写词、关键概念，避免读者反复猜测。涵盖系统名、业务术语、内部缩写、跨平台/跨角色概念差异（写法见 [`references/few-shots.md`](./references/few-shots.md)「三、名词解释示例」）。

### 四、需求分析

#### 4.1 业务诉求

来自业务、用户的真实需求，从用户视角而非"PM 讲不清需求"等团队内部诱因出发。每条要素以「**加粗短句。**」开头并配段落说明，**不是单纯 bullet 列表**（写作规则见 `references/writing-rules.md` §L1；示例见 `references/few-shots.md` §4.1）。

诉求项数无上限，单条不需要拆得很细；同一类诉求合并为一个加粗短句即可。诉求与设计原则间有"诉求 → 原则"的对应关系，写诉求时心里要清楚每条诉求会演化成哪条设计原则。

#### 4.2 设计原则

由业务诉求推导出的产品设计取向。**表格化呈现**，列结构为「编号 / 原则 / 内容」，可选追加「对应业务诉求」列（让评审一眼看出诉求 → 原则的映射，多平台/多模块场景推荐保留；单平台简单场景可省）。

| 编号 | 原则 | 内容 |
| --- | --- | --- |
| 1 | [原则名 — 4-8 字短句] | [原则的具体描述：是什么/不是什么、目的/边界] |

正文写「§4.1 的业务诉求推导出本模块的 N 条设计原则」，N 与表格行数严格一致。**不允许**把"本 PRD 是规格交付层"等元描述塞进 4.2。

设计原则块里若含**关键产品决策**（在多个方案中选定某一个），决策的**结果**写进 §4.2 / §4.1 对应位置；决策的备选 + 理由由 P3.7 列入候选清单，交给 `/pmai-build-close` 或 PM 手动确认，不在 PRD 正文堆备选清单。

#### 4.3 方案价值（Impact）

按 5 个维度组织：用户价值、业务价值、商业价值、风险消解、量化指标（如有）。**业务价值**：用户能完成什么、业务能解决什么；**风险消解**：消除高价值内容外流 / 提供合规审计能力等。**禁止写**"降低规格交付成本""文档治理收益"等文档治理价值——4.3 是产品价值，不是 PM 协作价值（写作规则见 `references/writing-rules.md` §L1）。

**指标对象边界（含可选量化指标段）**：所有验证指标的对象必须是**产品能力达成度**（如"无 download 权限的普通成员所有指定入口下载按钮均置灰且无法触发"），**不能是 PRD 文档覆盖度**（禁写"用户能从本 PRD 找到答案""PM 能直接引用本 PRD §6.X 给出标准回答""部门管理员能从本 PRD §6.4 自助查到完整边界"等指向 PRD 文档自身作为答案库的指标）。

### 五、用户与场景

#### 5.1 用户角色

列出本模块所有相关角色，按平台/层级分组。**单平台 3 列扁平表**（角色名 / 描述 / 与本功能的关系）；**多平台/多层场景 4 列分组表**（角色归属 / 角色 / 描述 / 与本模块的关系）。**一律用 GFM 管道表格（`| ... |`），禁用 HTML `<table>`** —— 飞书发布工具只认管道表格，HTML `<table>` 会被压成纯文本、表结构全丢。4 列分组表要「角色归属」跨行合并：同一归属下第一行写归属名、其余行该格留空，发布到飞书时自动合并成跨行单元格（合并交给 publish-to-lark）。示例见 `references/few-shots.md` §5.1。

#### 5.2 用户故事

按"作为 [角色]，我希望 [行为]，以便 [价值]"格式组织。每个核心 Story 编号（Story 1 / Story 2…），便于 §七 验收标准对应引用（"Story 1：无权限时下载按钮行为"）。覆盖主要使用场景与边界场景。

#### 5.3 非目标

明确列出**不在本期范围内**的功能点，避免范围蔓延。例如"本期不建设审计日志查询 UI""不对资源创建者设置豁免权"等。本次工作范围外的功能显式写进 §5.3，让评审一眼看出范围边界。

### 六、功能需求

按业务模块组织，每个 §6.X 章节对应一个**一级业务模块**（如「产品访问管理」「许可证管理」）；该章节内的 4 列表格以二级 / 三级动作组织（二级 = 动作组、三级 = 动作子项，详见下方「层级划分原则」+ P2.5）。结构：先一段产品定义（用 §L3 等式短定义，可省略），再「原型」节（真实原型截图 / ASCII 兜底），再表格化展开功能。

**模块引语风格**：模块章节开头的 blockquote 引语（`> **模块名 = ...**`）必须**短句直陈 + 可选加粗核心动作**：1-2 句话说清这个模块**给谁用、能做什么**。

- **禁堆抽象原则名词**——如果读者必须回头查 §4.2 设计原则才能理解引语，就是失败的引语。
- **禁迭代版本语言**——见 `references/writing-rules.md` §禁用版本 / 迭代过程语言
- **章节标题已自明可省略引语**——如二级章节标题已是"产品列表" / "导入许可证"，直接进表格即可，不强行写引语凑结构

**「原型」节（真实原型截图优先 · ASCII 兜底）**：每个 §6.X 模块在功能表格前写「原型」节 —— 沉淀阶段原型已建完，**优先放真实原型截图**；暂无截图时由 AI 按原型实际结构现画 ASCII。

- **数量**：模块下涉及几个页面 / 弹窗 / 抽屉就放几张，一一对应。例：「角色管理」模块含角色列表页 + 创建角色弹窗 + 角色详情抽屉 → 放 3 张。
- **详细度**：中等。ASCII 兜底时每张 30-60 行，含顶部标题 / 主要分区 / 表头列名 / 列表行示例（2-3 行）/ 表单字段名 / 主要按钮文案。
- **每张图上方 1 句文字兜底**：「这是 X 页面 / 弹窗 / 抽屉」+ 用户主路径一句话；ASCII 被真实截图替换时这句话保留。
- **禁画**：像素 / 颜色 hex / 组件库名（Badge / Tag / Drawer）/ 字体字号（DESIGN.md 范畴）。
- **格式**：截图用标准 markdown 图片；ASCII 兜底用 markdown fenced code block（` ``` ` 标记）包裹，保证等宽对齐。

ASCII 原型示例见 `references/few-shots.md`「§六 原型节 ASCII 示例」段。

表格结构 / 写法详见下方「功能需求写法选择器」里的「PRD / CRUD 的 4 列功能表 preset」。

### 七、验收标准（Acceptance Criteria）

按 5.2 用户故事编号组织。每条 Story 列出可独立验证的验收点。**用普通项目符号，不要嵌引用块、不要用 `- [ ]` 复选框** —— 飞书发布工具会吞掉「引用块里嵌复选框列表」结构，只剩 Story 标题：

**Story 1：[Story 标题]**

- 验收点 1（具体可测）
- 验收点 2

**Story 2：[Story 标题]**

- ...

验收点必须可测量、可执行；避免"系统应稳定运行""用户体验良好"等无法测的描述。验收标准是 `/pmai-build` 行为审与 `/pmai-build-close` 验收的依据 —— 写得越可测，下游越好用。

### 八、非功能性需求

涵盖：**性能**（响应时间 / 吞吐 / 并发）、**安全性**（鉴权 / 越权 / 注入 / IDOR）、**可用性**（SLA / 容错 / 降级）、**可观测性**（埋点 / 日志 / 审计）、**向后兼容**（升级影响 / 数据迁移）、**可扩展性**（容量预估 / 横向扩展点）。

每条用一句明确的指标 / 行为描述，避免"系统应高性能"。

**禁文档级元约束**：本节只写**产品级约束**（如"本模块依赖租户许可证授权""产品访问额度由许可证决定"），**禁写文档级元约束**（"本 PRD 是产品规格交付层""本 PRD 不修改既有规则""本文档面向研发评审"）。同一约束如本属"依赖与约束"性质，也走产品级措辞落本节，不开独立章节复读。

### 九、附件

存放：**原型覆盖范围表**（反向 PRD 必含，见下）、**权限矩阵**（默认权限策略表）、**字段字典**（审计日志必须字段、状态机字段定义）、**枚举值表**（资源类型、操作类型、错误码）、**占位字典**（§六「原型」节里用到的占位词 → 实际值映射，如有）。提取规则：当某功能的默认值/枚举值/字段清单行数较多，且多处功能行会引用同一份数据时，提取到附件，表格中注明"具体见附件 X"（示例见 `references/few-shots.md` §九）。

**原型覆盖范围表（反向 PRD 必含）**：列出范围清单里每个功能 / 页面，对照最终原型标注覆盖状态，让评审一眼看出本次工作把哪些做实了、哪些仍是壳。每行一个功能 / 页面：

| 功能 / 页面 | 覆盖状态 | 说明 |
| --- | --- | --- |
| 角色列表页 | 已覆盖 | 列表 / 搜索 / 筛选均可交互 |
| 创建角色弹窗 | mock 占位 | 表单可填，提交走 mock 数据、未接真后端 |
| 批量导入角色 | 未覆盖 | 本次工作未建，列入后续 |

覆盖状态三档：**已覆盖**（功能在原型里建实、可交互）/ **mock 占位**（界面在、数据 / 逻辑是 mock 壳）/ **未覆盖**（原型未建）。状态来自步骤 2 对范围清单逐项对照原型的标注。

## 身份 / 权限类 PRD 专属可选章节

适用范围：当本次工作涉及身份认证 / RBAC / 角色权限 / 账号体系 / 组织架构等场景时，在 §六 功能需求之后插入两个专属章节（§七、§八），原有 §七 验收标准 顺延为 §九，§八 非功能性需求 顺延为 §十，§九 附件 顺延为 §十一。最终结构变为 11 节。

### 数据权限范围

> **数据权限范围 = 各角色在产品界面上能看到的数据范围。**

按平台分子节展开，每个平台一个表格列出"角色 / 列 1 / 列 2 / ..."的可见范围矩阵（列名根据平台业务确定）。表末追加"通用边界说明"段，包含两条硬规则：

- **可见 ≠ 可修改。** 能否对可见对象执行操作类动作，由 §角色权限清单 与"自提权防护、最高管理员保留规则"等业务约束共同决定。
- **管辖范围与可见性的对齐口径。** 部门管理员、含查看类权限点的自定义角色持有者，其可见范围与角色分配的管辖范围保持一致。

示例见 `references/few-shots.md`「身份/权限类专属·数据权限范围示例」。

### 角色权限清单

完整列出**每个一级功能 × 每个二级功能 × 每个三级功能**对**每个角色**的权限点。**用 GFM 管道表格写，表前加一行 `<!-- lark:no-merge -->` 标记。**

权限矩阵是**数据表** —— 每个单元格（`✅` 或空）都是独立数据，空格表示「无权限」而不是「上一行的延续」，**整张表不做任何跨行合并**。因此：

- 「一级功能」列**每行都重复写全名**（如连续三行都写「用户管理」），不留空、不依赖 rowspan。
- 表前的 `<!-- lark:no-merge -->` 让 publish-to-lark 跳过对这张表的启发式合并，原样发布到飞书。
- **禁用 HTML `<table>`** —— lark-cli 不识别，会把整张矩阵压成纯文本。

✅ 单元格内容统一用 `✅`（有权限）/ 空单元格（无权限），避免 `Y/N` / `是/否` / `允许/不允许` 等多写法混用。

示例见 `references/few-shots.md`「身份/权限类专属·角色权限清单示例」。

## 功能需求写法选择器

功能需求没有唯一格式。先判断内容形态，再选择最清楚的写法；只有 PRD 体例、CRUD 管理后台动作清单、PM 明确要求功能表时，才默认使用 4 列功能表。

| 内容形态 | 首选写法 | 不要这样写 |
|---|---|---|
| 规则收口 / 口径统一 | 短定义 + 分组规则 + 验收清单 | 为了套表强拆成二级 / 三级功能 |
| 状态 / 分类 / 卡片 | 分类定义 + 触发条件表 + 展开字段表 + 按钮 / 消失规则 | 把每个状态写成 CRUD 动作 |
| 多步流程 | 分段叙述：先后顺序、条件分支、异常分支 | 把长流程塞进单个表格 cell |
| 字段很多 | 字段口径表：字段 / 含义 / 来源 / 是否必填 / 默认值 / 校验 | 全塞进一段需求描述 |
| 权限 / 角色差异 | 权限矩阵 / 可见范围表 + 边界说明 | 用散文重复每个角色 |
| CRUD / 管理后台动作清单 | 4 列功能表 | 用页面 / 弹窗 / Tab 名当二级功能 |
| PRD 体例 §六 | 4 列功能表 + P2.5 拆分确认 + PRD lint | 绕过拆分确认临场发明二级 / 三级 |

### PRD / CRUD 的 4 列功能表 preset

**适用**：PRD 体例 §六、CRUD 管理后台动作清单、PM 明确要求功能清单表格。**不适用**：模块 `spec.md` 的规则收口、状态分类、流程说明、字段口径，除非该段内容本身就是动作清单。

**表格结构（4 列，与 `_shared/PM-VIEW-RULES.md` §五的表格 preset 一致）：**

| 二级功能 | 三级功能 | 使用角色 | 需求描述 |
| --- | --- | --- | --- |

PRD §六 按一级业务模块组织成 §6.X，**一级功能写在 §6.X 章节标题里**（如 `#### 6.2.1 角色管理`），表内不复读 → 默认就是上面这 4 列。这是 `PM-VIEW-RULES.md §五` 表格 preset（二级功能 / 三级功能 / 使用角色 / 需求描述）的标准形态。

**列结构调整：**

- 极少数不按 §6.X 分模块、需在表内并列多个一级功能时，可加回"一级功能"列；常规按模块分章不需要。
- 新需求场景（非纯回溯）可选追加"优先级"列；回溯型 PRD 通常省略。
- **原型素材**：沉淀阶段原型已建完 —— §六每个 §6.X 模块的「原型」节优先放真实原型截图（标准 markdown 图片，飞书正常渲染，作为**独立图片**放进对应 §6.X 模块的「原型」节）；暂无截图时 AI 按原型实际结构现画 ASCII 兜底（fenced code block 包裹，每个页面 / 弹窗 / 抽屉一张 + 1 句文字兜底）。**不另开「原型」表格列、不用 HTML `<table>`** —— 截图塞进表格单元格再 `rowspan` 合并，飞书发布会塌成纯文本、截图也被压扁。
- **范围外行的处理（不删行，划线保留）**：当某一行明确不在本 PRD 范围、但读者会基于功能模块期望它存在（如身份权限 PRD 中的"产品额度"、"产品访问"），用 `<del>` 标签划线整行内容（包括三级功能名和需求描述），**保留行**而不是删除。同时在 §摘要 / §5.3 非目标 中明确"X 不在本 PRD 范围内，由对应模块单独定义"。这样研发评审时一眼可见"产品里有这个、但本 PRD 不覆盖"，不会以为遗漏。

**分级规则：**

- 一级功能：顶层业务模块（如"超级员工管理""产品访问管理""许可证管理""角色管理"）
- 二级功能：该模块下用户可发起的**动作组**（如"列表""搜索""筛选""操作""导入""创建""详情"）
- 三级功能：该动作组下的**具体动作子项**，命名以**动词**锚定（如筛选下的"是否发布 / 发布渠道 / 发布时间"；操作下的"查看 / 体验 / 发布 / 下架 / 删除"）；无三级时填 `/`

**层级划分原则（4 条硬规则）：**

- **二级功能 = 用户动作组，不是 UI 组件。** 二级命名以"该模块下用户能发起的一类操作"为锚点（列表 / 搜索 / 筛选 / 操作 / 导入 / 创建），不以"页面 / Tab / 弹窗 / Drawer / 视图"等 UI 组件为锚点。反例：「产品列表页」「Tab 1 额度分配视图」「分配额度弹窗」「许可证 Drawer」并列成 4 个二级——读起来像 UI 实现说明，不是用户动作清单；评审看完不知道租户管理员到底能做什么。
- **三级功能 = 动作子项，不是 UI 形态描述。** 三级命名以动词锚定（分配 / 调整 / 撤销 / 启用 / 吊销 / 导入 / 查看），不以 UI 形态命名（"池行紧凑形态" / "视图入口" / "顶部右侧操作按钮" / "多维度展示规则"）。反例：把"分配额度"动作拆成"弹窗触发 / 弹窗内字段 / 多维度数字输入"三个三级——这些是同一动作的实现细节，应作为该三级功能下需求描述列的 1./2./3. 编号项。
- **角色视角差异 / UI 视图切换 / UI 形态规则 → 需求描述列编号项，不外溢成独立三级。** 同一个动作下：不同角色看到的范围差异、UI 视图切换（部门视角 / 许可证视角）、紧凑形态规则、失效证简化规则、显示字段清单等，**全部用 1./2./3. 编号写在需求描述列里**。反例：把"部门视角池树组织""许可证视角池树组织""部门视角'租户直接开通'段"作为并列三级——这些是"查看额度分配"这一个动作下的视角切换 + 角色差异规则，应合并为单个三级"查看额度分配" + 需求描述里依次写"1. 租户管理员看全部部门……2. 部门管理员只看其管辖部门……3. 池树支持部门视角 / 许可证视角二选一切换……"。
- **判别简则**：
  - 写完二级问："用户在产品里能直接对应到这个动作吗？"——能（"分配""撤销""筛选"）→ 留下；不能（"分配额度弹窗""Tab 1 额度分配视图"）→ 改名或拆开。
  - 写完三级问："换一套 UI 这个三级名还成立吗？"——成立（"分配额度到部门"）→ 留下；不成立（"池行紧凑形态"）→ 它是 UI 描述，下沉到需求描述列编号项。

**二级功能动作组常用词汇表**（首选锚点；业务上不在表内时另命名，但要保持"动作组"语义）：

| 类别 | 二级功能名（动作组） |
|---|---|
| 数据浏览 | 列表 / 搜索 / 筛选 / 详情 |
| 增改删 | 创建 / 编辑 / 删除 / 复制 |
| 状态 / 流转 | 操作 / 状态变更 / 启用停用 / 发布下架 |
| 关系 / 授权 | 分配 / 取消分配 / 授权 / 移除 |
| 数据流 | 导入 / 导出 / 上传 / 下载 |
| 配置 / 设置 | 配置 / 设置 / 偏好 |

写作前先把本模块的二级功能名拉一遍这张表，从中挑选；不要发明新词或用页面名顶替。

**其它边界规则：**

- 二级 / 三级层级**来自该功能模块的真实业务逻辑**——参考**模块 `spec.md` 功能项 + 最终原型的真实结构**（功能清单自然形成"列表 / 创建 / 编辑 / 详情……"的二级层级）。
- **不得在 PRD 阶段拍脑袋分组**——例如把"列表 / 详情"硬归到"查看"组下、把"创建 / 编辑 / 启用停用 / 删除"硬归到"定义"组下，这种强行分级会让二级功能逻辑做作。
- 同一二级功能下若三级功能 ≤ 2 个，可考虑不分级（避免强行分级）。
- 详情类功能本身常常是一个完整的二级功能（下面再分基础信息 / 操作按钮 / 权限配置 / 授权对象等三级），不要把"详情"和"列表"硬塞到同一二级里。

**与范围清单 + 原型对齐：**

- 表格行内的功能、结构以 **模块 `spec.md` + 最终原型的真实结构**为依据；业务规则 / 权限语义 / 校验口径以 **模块 `decisions.md` + PRODUCT-RULES**为依据（真系统口径，不从 mock 实现反推）。
- 模块规格描述模糊 / 决策页未覆盖某口径时，按 P1 在写 PRD 前编号提问 PM 确认，不在表格里自行拍板。
- 反向 PRD 本身已是基于最终原型反向合成 —— 不再做二次反向对齐。

**需求描述写法：**

- 写动作与结果，不写"支持/优化/提升体验"等泛词。
- 有规则/限制/默认值的，必须明确写出（使用"默认……""不允许……""如果……则……"等句式）。
- **多条规则采用续行 rowspan + 需求描述列内联编号格式**——选择 4 列功能表 preset 时，与 `_shared/PM-VIEW-RULES.md` §五 一致：第一行 4 列填齐 + 需求描述写「1. ……」；第二行起前 3 列（二级功能 / 三级功能 / 使用角色）留空，需求描述列依次写「2. ……」「3. ……」……每条规则各占一个表格行。**禁止用中文分号 `；` 串接成一段**，**禁止用 `<br>` 或 `<ol><li>` 在同一 cell 内塞多条**。能一句话说清的不要分条；单条规则的 cell 不写编号前缀。
- 续行 rowspan 配合 `/pmai-publish-to-lark` 步骤 4 的合并逻辑：前 3 列的空 cell 合并到上方非空 anchor（rowspan 效果），需求描述列的同一 row group 多条编号通过把非锚点 cell 的 children blocks 拷贝到锚点 cell + 清空原 cell + `merge_table_cells` 三步落成单 cell 内多行编号列表（详见 `skills/publish-to-lark/SKILL.md` 步骤 4）。
- 表格行中含结构化参考数据（权限矩阵、字段清单、枚举值映射等）时，提取到九、附件，需求描述中注明"具体见附件 X"，不在单元格内展开。判断标准：同一格内需要超过 3 个字段/枚举值列举，且其他行可能引用同一份数据。

**相同内容单元格视觉规范：**

- 同一列下连续多行出现**相同内容**时，按"合并单元格"的视觉效果呈现——只在第一行展示该值，后续相同的行该列留空（在飞书 docx 中即合并单元格的效果）。
- 最典型场景：同一二级功能下有多个三级功能（如"角色列表"作为二级在相邻 5 行重复），第一行展示"角色列表"，第 2-5 行该列留空。
- 此规则对二级功能列、使用角色列同样适用——同一二级功能下多个三级功能的使用角色相同时，使用角色列也合并展示。
- 标准 markdown 不支持合并单元格语法；本规则首要约束的是**视觉效果**。
- **发布到飞书时由 `/pmai-publish-to-lark` 步骤 4 自动合并** — 前 N-1 列：非空 anchor 吸收下方相同内容 cell + 下方空 cell（续行 rowspan 语义）；末列（需求描述）：识别续行 row group 后把非锚点 cell 的 children blocks 拷贝到锚点 cell（保留富文本）+ 清空原 cell + `merge_table_cells`。markdown 写法保持"留空 cell"+ 内联编号 1./2./3.（4 列功能表 preset）即可，AI 在发布时机械补齐合并；无需 PM 手工。
- **同步到飞书时先走 `/pmai-lark-sync`**：由它判断首次发布、精细同步、覆盖发布、飞书回拉或只 diff；只有明确进入整篇覆盖发布时，才调用 `/pmai-publish-to-lark`。
- 不发布到飞书 / 用其它工具链时，PM 在工具侧选中相邻相同 cell 手工合并即可。

## 写作规则（全篇遵守）

详见 [`references/writing-rules.md`](./references/writing-rules.md)：
- **总则**：先结论后规则 / 短句动作先行 / 同信息单点主写 / 术语统一 / 规格正文自包含（PRD 体例必须完整自包含）
- **一套语体：简要易懂**（spec 和 PRD 都用，不分两套）：按"谁 · 看到什么 · 做什么 · 点了怎样"组织 / 加粗克制 / 公式纯文本（单个 `×÷` 可留，`Σ≥⊆` 堆砌和 `→✘✅⚠️` 装饰不用）/ 不留迭代痕迹 / 不引路径不中英混杂 / 规则验收用能读出声的自然句。金标准实例见 `few-shots.md` 顶部。
- **通用卫生（任何文档都守）**：8 类禁用清单（代码路径 · UI 实现术语 · 书面冷僻词 · 中英混杂 · 技术 jargon · 数学/装饰符 · 元描述自指 · 兜底/主观词 · 版本迭代语）+ 术语锁定（名词表全文一个叫法）+ 引号统一（`"..."` / `[...]`，禁 `「」`）。
- **可选讲清楚工具（原 L1–L5，按需用不强加）**：加粗短句开题 / 边界并列（是 X 不是 Y）/ 等式定义（X = …）/ 对偶（A ≠ B）/ cell 加粗——能让读者更快懂时才用，别拿它们把文档写重（L1 的"反例+后果"过头正是写成白皮书腔的元凶）。
- **UI 元素指代规则 + 引号风格统一**（按钮名 `[...]` / 状态名+字段名+卡片名+提示文案 `"..."` / 禁 `「」`）
- **cross-reference 处理**（PRD 内禁用 §6.X 跳转，仅可引用外部 DESIGN.md 等）
- **抽象动词使用规则**（更新 / 保存 / 立即更新 / 执行 X 必须搭配具体效果）

**§3.12 描述风格规则**（已搬到 `_shared/pm-view/writing-rules.md` 作为权威单一真相源，PM 视图必读段已要求加载）:
