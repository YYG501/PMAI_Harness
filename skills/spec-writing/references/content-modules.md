## 使用方式

1. 先根据已确认决定选择内容模块，不为凑齐目录强加章节。
2. 再叠加适用 Profile 的覆盖要求。Profile 只补领域问题，不复制通用模块。
3. PM 明确要完整 PRD 时，最后套用唯一的完整 PRD Preset；否则按阅读顺序自由组合。
4. 同一事实只写一次。动作里引用对象名，验收里验证动作结果，不复制整段规则。

复杂功能默认使用这条主干：

```text
信息模型 -> 核心动作 -> 异常与空状态 -> 验收标准
```

它不是企业平台专属结构。只要功能包含多个对象、状态、权限或跨页面动作，就优先使用这条主干。

## M1 背景、目标与范围

回答：为什么做、谁受影响、本次改变什么、不改变什么。

至少包含：

- 当前问题和可观察后果；
- 本次目标与成功信号；
- 范围、非目标和外部依赖；
- 已确认但不在本文展开的上游决定。

若定位、目标用户、价值链、AI 必要性、平台/应用边界或 MVP 假设仍未确定，停止成文并返回 `/pmai-proposal`。不要在本模块里临时补产品前提。

## M2 用户、角色与场景

只保留会改变任务、权限、责任或体验的角色。每个核心场景写清：

- 谁在什么情况下进入；
- 要完成什么任务；
- 由谁确认或审批；
- 完成后得到什么结果。

角色只是称谓不同但行为相同，合并描述；不要为了“完整”制造无产品差异的角色。

## M3 信息模型

先定义用户需要理解的对象，再写功能动作。至少覆盖：

| 内容 | 要回答的问题 |
| --- | --- |
| 对象 | 系统中有哪些稳定业务对象？哪些只是视图、输入或过程记录？ |
| 身份 | 每个对象如何唯一识别？允许重名吗？ |
| 关系 | 对象之间是一对一、一对多还是多对多？谁拥有谁？ |
| 生命周期 | 对象如何创建、启用、停用、归档、移出或删除？ |
| 状态 | 每个状态只表达哪个维度？由什么事件改变？ |
| 权威来源 | 哪个对象或系统保存最终事实？同步冲突时以谁为准？ |
| 历史保留 | 状态变化或删除后，业务数据、审计和关联关系如何处理？ |

字段较多时使用字段表；字段只在某个动作中出现时，放到该动作的输入/结果里，不在信息模型重复。

## M4 核心动作

按用户目标和业务动作组织，不按页面、弹窗、Tab 或接口组织。每个动作至少讲清：

| 内容 | 要回答的问题 |
| --- | --- |
| 目标与角色 | 谁为什么执行这个动作？ |
| 触发与入口 | 什么情况可发起，从哪个业务上下文进入？ |
| 前置条件 | 权限、对象状态和依赖必须满足什么？ |
| 输入 | 用户需要提供或确认什么？字段如何校验？ |
| 处理规则 | 系统如何判断、阻止、确认或联动？ |
| 结果 | 成功后创建或改变什么？用户看到什么反馈？ |
| 状态与关联变化 | 哪些正式对象发生变化？哪些历史必须保留？ |
| 失败与恢复 | 失败时哪些内容保持不变，用户如何继续？ |

多步动作按“先做什么、再做什么、最后得到什么”叙述。字段表、权限矩阵和状态表是动作详情的辅助，不替代动作本身。

## M5 状态、权限与规则

内容简单时写进信息模型或动作，不强制独立成章；跨多个动作复用时再集中说明。

- 状态：进入条件、允许动作、退出条件和联动结果；
- 操作权限：谁可以发起、查看结果、确认、审批或撤销；
- 数据范围：同一角色能看到哪些对象；
- 通用规则：默认值、唯一性、数量限制、冲突优先级和不可逆边界。

“可见”和“可操作”必须分别定义。权限不足、状态变化和并发冲突要在动作与异常模块中有可验证结果。

## M6 异常与空状态

不要只写理想路径。至少检查：

- 首次使用无数据；
- 搜索或筛选无结果；
- 表单校验失败；
- 提交时对象状态或权限已变化；
- 外部服务超时、拒绝或部分成功；
- 重复提交、并发修改或关系冲突；
- 数据缺失、过期、冲突或无法判断；
- 操作中断后的重试、恢复与原数据保持规则。

每种异常写“用户看到什么、系统保留什么、能否重试、由谁处理”。

## M7 验收标准

验收从动作、状态和异常推导，不从页面数量或文档章节推导。

每条验收点至少包含：

- 明确前置条件；
- 执行动作或发生事件；
- 可观察结果；
- 必要时补充不应发生的结果。

按用户故事或核心动作分组。正常路径、权限边界、状态变化、异常与恢复都必须有对应验收点。

## M8 非功能要求

只写本次产品真实需要的约束，不为完整而虚构指标。按需覆盖：

- 性能与容量；
- 安全、隐私和越权防护；
- 可用性、降级和恢复；
- 审计、日志和可观测性；
- 兼容、迁移和数据保留；
- 国际化、无障碍或合规。

没有可靠阈值时，写验证方法和确认责任，不编造数字。

## M9 附件与参考数据

权限矩阵、字段字典、枚举、错误码、设计资产和外部协议只有在多处复用或影响评审时才放附件。附件是正文的补充，不承担正文里缺失的核心规则。

## 覆盖检查

成文前后都检查：

1. 每个核心对象是否有身份、关系、状态和权威来源？
2. 每个核心动作是否能追到角色、前置条件、输入、结果和失败路径？
3. 每个状态与权限差异是否有对应产品行为？
4. 每个高风险异常是否有恢复或保持不变的规则？
5. 每项关键规则是否有可执行验收点？
