# /pmai-lark-sync intent routing

## 目标

先判断真相源和同步方向，再选择动作。这个判断比执行更重要：最危险的错误不是不会改飞书，而是把飞书协作稿误当成发布面，用本地旧稿整篇覆盖掉。

## 四种模式

| 模式 | 用户说法 | 真相源 | 动作 |
|---|---|---|---|
| A 精细同步到飞书 | "更新飞书"、"同步到飞书"、"不要覆盖"、"别丢图"、"只改几段" | 本地 markdown | 按差异最小修改飞书 |
| B 整篇覆盖发布 | "覆盖发布"、"重新发布"、"整篇更新"、"本地为准全部替换" | 本地 markdown | 调 `/pmai-publish-to-lark` |
| C 飞书回拉本地 | "飞书是最终版"、"以飞书为准"、"把飞书拉回来" | 飞书 | 用飞书正文覆盖本地正文 |
| D 只 diff | "看哪里不一致"、"比一下"、"先别改" | 双方 | 只读比较，输出差异 |

## 判定顺序

1. 用户是否说已经在飞书 review、修改或批注，并要求反向更新规格 / 决定 / 原型？是则转 `/pmai-lark-review`，不进入 A-D。
2. 用户是否明确指定"以飞书为准"？是则模式 C。
3. 用户是否明确要求"只比较 / 先别改"？是则模式 D。
4. 用户是否明确说"覆盖 / 重新发布 / 整篇更新"？是则模式 B。
5. 用户是否提到"同步飞书 / 更新飞书 / 不覆盖 / 别丢图 / 只改某几段"？是则模式 A。
6. 如果只说"更新一下"，看最近上下文是否有明确方向；没有就问 PM。

## 不能默认的事

- 不能把"更新飞书"默认理解成 overwrite。
- 不能把本地 markdown 永远当 source of truth。
- 不能把飞书在线内容永远当发布缓存；飞书可能是 PM 的最终协作面。
- 不能因为本地 frontmatter 有 `lark_doc_id` 就直接整篇覆盖。
