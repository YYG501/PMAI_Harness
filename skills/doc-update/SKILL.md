# Doc Update — 文档偏差修复

## When To Use

- task 状态为「已完成」，PM 已通过验收
- task 文件的「文档偏差」section 有内容（不是"无偏差"）
- 准备运行 `close-task.sh` 合并代码之前

## Required Inputs

1. task 文件路径（从中读取「文档偏差」section）
2. 偏差涉及的原始文档（docs/solution.md、docs/DESIGN.md 等）

## Workflow

### 步骤 1：读取偏差

从 task 文件的「文档偏差」section 提取所有偏差条目。

### 步骤 1.5：判断是否涉及模块规格功能清单

检查偏差条目中是否有指向 `docs/modules/<module>.md` 功能清单表格的偏差：

- **有模块规格偏差**：进入步骤 1.6
- **无模块规格偏差**：跳到步骤 2

### 步骤 1.6：模块规格对账

A. 读取偏差涉及的模块规格全文（`docs/modules/<module>.md`）
B. 读取最终实现的代码（task worktree 的关键文件）
C. 对照功能清单表格，逐行核对实际实现是否匹配
D. 生成修改方案（行级别精确操作）：
   - 功能清单表格的行级更新（修改需求描述以匹配最终实现）
   - 实现指引 section 的更新（组件选择、状态处理变化）
   - 新增行（PM 迭代中追加的功能点）
   - 删除行（PM 确认不做的功能点）
E. 向 PM 展示对账结果，逐条确认后执行

对账仍遵循最小修改原则：只改偏差涉及的行和 section，不重写整个模块规格。

### 步骤 2：读取原文

对每条偏差，读取对应文档的原文上下文（前后各 5 行），理解：
- 原文的语言风格（中文/英文、正式/口语、用词习惯）
- 原文的格式（markdown 表格、列表、段落）
- 原文的信息密度（简洁还是详细）

### 步骤 3：生成修改方案

对每条偏差生成精确的 Edit 操作，向 PM 展示：

```
📝 文档修改方案（共 N 处）

修改 1/N:
  文件: docs/solution.md
  行号: 592
  原文: "用户列表显示 10 个字段（姓名、邮箱、角色...）"
  改为: "用户列表显示 8 个字段（姓名、邮箱、角色...，移除了 X 和 Y）"
  原因: [来自文档偏差记录]

修改 2/N:
  ...

PM 请逐条确认：全部通过 / 逐条批注 / 全部驳回
```

### 步骤 4：等 PM 确认

- PM 说"全部通过" → 执行所有修改
- PM 对某条有意见 → 按 PM 意见调整后重新展示
- PM 说"不改" → 跳过，直接进入 close-task.sh

### 步骤 5：执行修改

用 Edit 工具逐条修改（不用 Write），确保：
- 只改偏差涉及的具体行
- 不重写整段、不调整排版
- 不修改偏差以外的内容

### 步骤 6：完成

修改完成后提示 orchestrator 运行 `close-task.sh`。

## Rules

**最小修改原则（强制）：**
- 只改偏差记录中列出的内容，不改任何其他部分
- 用 Edit 工具的 old_string → new_string，精确替换
- old_string 必须从文档中实际读取，不能凭记忆
- 如果偏差说"10 个字段改成 8 个"，只改数字和字段列表，不重写整段描述

**风格一致原则（强制）：**
- 读取原文前后 5 行，匹配语言风格
- 原文用中文 → 修改用中文；原文用英文 → 修改用英文
- 原文是表格 → 修改在表格内；原文是段落 → 修改在段落内
- 不引入原文没有的格式（如原文没有 emoji 就不加 emoji）

**禁止：**
- 不重写整个 section
- 不"顺手"优化文档其他部分
- 不改排版、不加注释
- 不修改 docs/ 以外的文件
