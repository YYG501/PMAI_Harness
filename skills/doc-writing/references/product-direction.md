# 产品方向文档写作参考

> 本文件吸收社区写作 / 内容策略 / 市场研究类 skill 的做法，并结合产品管理公开模板整理成 `/pmai-doc-writing` 的产品方向文档方法。它不是新流程入口；入口仍是 `/pmai-doc-writing`。

## 一、吸收了什么

**社区 skills 的共同点**

- `content-strategy`：每份内容先定目标、受众、渠道和指标；不要随机写。
- `copywriting`：文字要推动读者做决定；先抓注意力，再给理由、证据、异议回应和行动。
- `market-research`：先把问题问具体；市场、竞品、客户验证都要区分信号强弱。
- `blog-writer`：有明确观点，开头先给 thesis；用短段落和真实经验，不写泛泛资料汇编。
- `seo-content-writer`：读者意图要对齐；开头直接回答核心问题；关键 claim 要有证据。

**产品管理公开模板的共同点**

- 产品策略文档要回答：服务谁、给他们什么收益、产品目标是什么。
- 产品需求 / 方向材料要写 objective、success metrics、assumptions、options、supporting docs、open questions、out of scope。
- 价值主张要从 customer jobs、pains、gains 出发，再写产品如何 relieve pain / create gain。

本轮外部参考：
- ProductPlan 的产品策略定义：产品策略要回答用户是谁、给他们什么收益、产品生命周期里的业务目标是什么；并把 vision、goals、initiatives 串起来。
- Atlassian 的 PRD 模板：好的产品材料要写 objective、success metrics、assumptions、options、supporting docs、open questions，防止方向材料只剩热情和口号。
- Strategyzer 的 Value Proposition Canvas：先定义 customer jobs、pains、gains，再写产品如何缓解痛点、创造收益，并基于 customer evidence 调整。

落到 PMAI 里，产品方向文档要先讲判断，再讲材料；先讲谁的什么问题，再讲我们怎么解决；先讲为什么现在做，再讲下一步怎么验证。

## 二、产品方向六问

写方向、定位、介绍、汇报前，先在脑子里回答这六问。答不出来就不要硬写成结论。

| 问题 | 要产出的内容 | 写不出来时 |
|---|---|---|
| 谁遇到什么问题 | 目标用户 / 角色 / 场景 / 当前卡点 | 回读 `PRODUCT.md`、相关模块 spec 或问 PM |
| 为什么现在要处理 | 时机、触发、风险、机会、阶段位置 | 写成假设或待验证，不编外部趋势 |
| 产品回答是什么 | 一句话定位 + 核心能力组合 | 不按页面列功能，按用户任务组织 |
| 为什么这条路更值得走 | 取舍、替代方案、差异化 | 至少写一个被放弃选项 |
| 怎么知道有效 | 成功指标、验证信号、风险观察 | 没数据时写验证方式 |
| 下一步要谁做什么决定 | CTA / 决策项 / 后续动作 | 不用泛泛的"持续优化"结尾 |

## 三、证据地图

写作时给每个关键判断标一类证据。文档里不一定逐条显式引用，但 AI 自己必须对得上。

| 证据类型 | 强度 | 用法 |
|---|---|---|
| 已落地产品现状 | 强 | 来自 `PRODUCT-STATE.md`、原型、已完成模块 |
| 模块规格 / 决策记录 | 强 | 来自 `docs/modules/<模块>/spec.md` / `decisions.md` |
| PM 明确判断 | 强 | PM 在会话中拍板过的方向、取舍、非目标 |
| 用户/客户材料 | 强 | 访谈、会议纪要、客户问题、销售反馈 |
| 竞品 / 市场资料 | 中 | 只能支持"环境判断"，不能替 PM 拍产品方向 |
| AI 推断 | 弱 | 必须标"推断 / 假设 / 待验证" |

红线：
- 不把 mock 演示写成已落地。
- 不把"计划中"写成当前能力。
- 不把竞品存在某功能写成"我们必须做"。
- 不把 AI 推断写成用户事实。

## 四、常用结构模板

### 1. 产品方向 memo

适合回答"接下来产品往哪里走 / 为什么这样走"。

1. **结论**：一句话说当前方向。
2. **当前位置**：产品现在做到哪，哪些是真能力，哪些仍是演示。
3. **目标用户与场景**：谁在什么场景里遇到什么问题。
4. **为什么现在**：触发因素、窗口、风险或机会。
5. **产品回答**：产品将如何解决，按能力组合讲，不按页面讲。
6. **关键取舍**：做什么、不做什么；为什么不走替代方案。
7. **成功指标**：怎么知道方向对了。
8. **风险与待验证假设**：哪些还没证据。
9. **下一步决定**：需要 PM / 老板 / 客户拍什么。

### 2. 产品定位说明

适合回答"这个产品到底是什么"。

1. 一句话定位：`面向 <用户>，在 <场景> 下，帮助他们 <完成什么结果> 的 <产品类型>`。
2. 用户和场景：不要泛化成"企业用户"，写具体角色和任务。
3. 当前替代方案：用户现在靠什么解决，哪里不够好。
4. 产品差异：我们和替代方案不同在哪里。
5. 核心能力：3-5 个能力柱，每个写"能力 + 具体效果"。
6. 边界：不是谁、不解决什么、不承诺什么。
7. 可证明材料：产品现状、原型范围、客户材料、指标。

### 3. 产品叙事 / 介绍稿

适合给客户、老板、业务方快速理解。

1. 开头直接讲问题，不铺行业大词。
2. 说明旧方式为什么不够。
3. 给出产品回答。
4. 展开 3-5 个核心能力，每个能力都绑定一个用户任务。
5. 用当前状态说明可信度：已落地 / 原型演示 / 计划中。
6. 结尾给下一步动作：看演示、评审方向、确认范围、继续调研。

可用内部表达框架：
- PAS：问题 → 为什么严重 → 产品回答。
- FAB：功能 → 为什么比旧方式好 → 用户得到什么。
- AIDA：先抓核心问题 → 让读者认同 → 给产品答案 → 指向下一步。

最终不要显式写 AIDA / PAS / FAB 字样。

### 4. 产品功能清单

适合把产品能力讲给非研发读者。

1. 先按能力域分组，不按页面、路由或原型目录分组。
2. 每项能力写三列：能力 / 解决什么 / 当前状态。
3. 状态只用三档：已落地、原型演示、计划中。
4. 不写验收标准、不写字段级规则、不写实现路径。
5. 功能太多时先写"能力地图"，再附详细清单。

### 5. 高管一页纸

适合快速要决策。

1. **要拍的决定**：今天要同意什么。
2. **一句判断**：推荐方向是什么。
3. **为什么现在**：机会、风险、阶段、窗口。
4. **为什么这条路**：和其它选项比，优势是什么。
5. **投入与收益**：可量化则量化，不能量化就写验证指标。
6. **风险和兜底**：最可能错在哪里，怎么尽早发现。
7. **下一步**：谁负责，何时看什么结果。

### 6. 决策材料

适合对比多个方向或争取资源。

1. 背景和约束。
2. 决策问题。
3. 选项 A / B / C。
4. 对比维度：用户价值、业务价值、实现代价、风险、验证难度。
5. 推荐方案和理由。
6. 反对意见与回应。
7. 不采纳方案的后果。
8. 下一步和验证点。

## 五、异议处理清单

方向文档必须主动处理读者会问的问题。根据读者挑 2-5 个回答：

- 为什么现在做，不是以后做？
- 为什么是这个用户 / 场景，不是更大的市场？
- 为什么是这个产品形态，不是服务 / 咨询 / 流程改造？
- 为什么不是竞品那条路？
- 已有产品能力够不够支撑这个方向？
- 哪些是已验证，哪些只是 PM 判断？
- 如果方向错了，最早会在哪个信号上暴露？
- 下一步投入多大，什么时候复盘？

## 六、语气和表达

- 产品方向文档要有主张，但不要装成确定性过强的战略报告。
- 写"我认为 / 当前判断是 / 建议先"，比写"必须 / 必然 / 全面"更稳。
- 不写大词：生态、闭环、抓手、赋能、全链路、顶层设计。
- 不写空优势：更高效、更智能、更灵活。必须说谁少做了什么、少等了多久、少承担什么风险。
- 不用引号堆概念，不造四字抽象短语。
- 对外材料保留专业，但不暴露内部协作词：worktree、spec、close、沉淀、冻结档、mock。需要区分时写"已落地 / 原型演示 / 计划中"。

## 七、最终质检

- 主张：第一屏有没有一句明确判断？
- 读者：这份文档是给谁看的？他读完要做什么？
- 用户：文档里的用户是否具体到角色和场景？
- 价值：每个能力是否说明了用户得到什么，而不只是功能存在？
- 证据：关键判断是否能找到来源？没有来源是否标假设？
- 取舍：有没有写不做什么、为什么？
- 指标：有没有说明怎么知道方向对了？
- 异议：有没有回答主要反对意见？
- 状态：已落地 / 原型演示 / 计划中是否清楚？
- 文风：是否还有 AI 腔、口号、黑话、泛词？
