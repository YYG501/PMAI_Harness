# /pmai-doc-writing

> **这是什么**：写产品方向 / 产品叙事 / 介绍型材料的入口。它面向"把产品判断讲清楚"，不是"把功能规格定下来"。
>
> **边界**：PM 要 PRD、功能需求、功能描述、功能规格、功能评审稿时，直接转 `/pmai-prd-writing`。这些是功能型文档，落 `docs/modules/<按内容命名>.md`，不放 `docs/deliverables/`。

## 产物

| 文档类型 | 默认落点 | 说明 |
|---|---|---|
| 产品方向 memo | `docs/deliverables/<按内容命名>.md` | 讲判断、取舍、阶段重点和为什么 |
| 产品定位说明 | `docs/deliverables/<按内容命名>.md` | 讲服务谁、解决什么、与什么不同 |
| 产品介绍 | `docs/deliverables/<按内容命名>.md` | 给客户、老板、业务方快速理解产品 |
| 产品功能清单 | `docs/deliverables/<按内容命名>.md` | 介绍性清单，不作为 build 契约 |
| 产品优势说明 | `docs/deliverables/<按内容命名>.md` | 价值、差异化、卖点表达 |
| 产品一页纸 | `docs/deliverables/<按内容命名>.md` | 适合转 PDF / 发外部 |
| 汇报 / 决策材料 | `docs/deliverables/<按内容命名>.md` | 用于解释方向、争取资源、对齐判断；不是功能规格评审稿 |

默认格式是 Markdown。

- PM 要 doc / docx：先写 Markdown 初稿，再调用文档类 skill 转 docx。
- PM 要 PDF：先写 Markdown 初稿，再调用 gstack 的 Markdown 转 PDF skill。
- PM 要飞书：写完 Markdown 后可走 `/pmai-publish-to-lark`。

## 高质量标准

产品方向文档不是把材料拼起来。写出来必须有判断。完整方法见 `references/product-direction.md`，主流程只保留必守标准：

- **一句主张**：读者 10 秒内知道这份文档要说服他接受什么判断。
- **具体对象**：明确服务谁、解决哪个场景、当前卡点是什么。先写受众任务，再写产品回答。
- **取舍清楚**：写清楚现在做什么、不做什么、为什么不做另一条路。
- **证据落地**：每个关键判断都能回到产品现状、模块规格、用户/客户材料、真实原型或 PM 明确判断；没有依据就标"假设 / 待验证"。
- **功能升维**：功能清单按业务能力 / 用户任务 / 价值链组织，不按原型页面机械罗列。
- **异议处理**：主动回答读者会反问的 2-5 个问题，例如"为什么现在做""为什么不是另一条路""投入产出怎么判断"。
- **成功指标**：方向文档必须说明怎么知道方向对了；介绍材料至少说明读者下一步该做什么。
- **少口号**：不写"提升效率 / 赋能 / 闭环 / 全链路"这类空话，必须落到具体效果。
- **能被转述**：老板、客户或业务方读完后能用两三句话复述产品方向。

## Required Inputs

写作前按材料用途读取，不整仓乱读：

- `docs/INDEX.md`：先确认文档入口和相关材料位置。
- `PRODUCT-STATE.md`：当前产品现状，只取"现在做到哪、哪些是真系统哪些是 mock"。
- `PRODUCT.md`：定位、用户画像、业务术语表。
- `PRODUCT-RULES.md`：跨模块产品规则，避免介绍材料和已定规则冲突。
- `docs/modules/INDEX.md`：需要讲具体能力时，从这里挑相关模块 / 功能型文档。
- 相关 `docs/modules/<模块>/spec.md` / `decisions.md`：只读和本材料相关的模块。
- `docs/decisions/`：只有写产品方向、定位、重大取舍时才按索引/文件名点读相关冻结档；默认不扫全目录全文。
- `TODO.md`：只有写路线、下一步、阶段重点时读取。
- PM 提供的外部材料：访谈、竞品、会议纪要、汇报要求；没有提供就不编市场事实。

禁止把全部模块历史全文塞进上下文；需要补某模块细节时再按索引点读。

## Workflow

### 步骤 0：先判是不是本 skill

如果 PM 的目标是以下任一类，继续：

- 产品方向 / 产品定位 / 产品策略说明
- 产品介绍
- 产品功能清单（介绍用途）
- 产品优势说明
- 产品一页纸
- 对外说明 / 老板汇报 / 客户沟通材料
- 查看某份介绍型材料并整体优化结构、内容、文风

如果 PM 的目标是以下任一类，停止本 skill，转 `/pmai-prd-writing`：

- PRD
- 功能需求
- 功能描述
- 功能规格
- 功能评审稿
- 作为 `/pmai-build` 锚点的功能方案

### 步骤 1：确认写作目标

PM 没说清时，只问必要问题：

1. 读者是谁：老板 / 客户 / 业务方 / 内部团队 / 评审人。
2. 文档用途：判断方向 / 介绍产品 / 汇报 / 对外发送 / 转 PDF / 发飞书。
3. 输出文件名：默认按内容取名，落 `docs/deliverables/<文件名>.md`。

已有足够信息时不要机械三连问，直接进入读材料。

### 步骤 2：读材料并先做产品判断

按 Required Inputs 读取。然后先写一份短判断，不急着落盘：

```text
我准备这样写：

主张：<这份文档要让读者接受的判断>
读者：<谁会读>
证据：<会引用哪些产品现状 / 模块规格 / PM 材料>
取舍：<会明确写哪些做 / 不做>
结构：
1. <章节>
2. <章节>
3. <章节>

落点：docs/deliverables/<文件名>.md
```

如果 PM 没明确说"直接写"，等 PM 确认提纲后再落盘。

写产品方向、定位、决策材料时，先按 `references/product-direction.md` 的"产品方向六问"做内部判断：

1. 谁遇到什么问题。
2. 为什么现在要处理。
3. 我们的产品回答是什么。
4. 为什么这条路比其它路更值得走。
5. 怎么知道它有效。
6. 下一步要谁做什么决定。

### 步骤 3：按文档类型选结构

不要所有材料都套一份模板。按目标选结构：

**产品方向 memo**

1. 结论先行：当前方向是什么。
2. 当前产品位置：已经有什么、缺什么、为什么现在要判断。
3. 目标用户与核心场景：服务谁，解决哪件高频/高价值问题。
4. 产品定位：一句话定义产品，不堆愿景词。
5. 关键取舍：做什么、不做什么、为什么。
6. 方案对比：至少写清一个被放弃的替代方案及原因。
7. 阶段路线：近一步 / 后一步，每步要验证什么。
8. 风险与验证：哪些是假设，怎么知道方向对了。

**产品定位 / 产品介绍**

1. 一句话定位。
2. 目标用户与痛点。
3. 产品如何解决。
4. 核心能力，按业务能力组织。
5. 差异化价值。
6. 当前状态与可演示范围。
7. 下一步或行动建议。

**产品功能清单**

1. 先按业务能力 / 用户任务分组。
2. 每项写"能做什么 + 给谁用 + 当前状态"。
3. 区分已落地、mock 演示、计划中。
4. 不写成验收表，不作为 build 契约。

**优势说明 / 一页纸**

1. 读者关心的问题。
2. 产品的明确回答。
3. 3-5 个优势，每个优势必须带具体能力或场景。
4. 可证明的现状、案例或原型范围。
5. 行动建议。

**汇报 / 决策材料**

1. 这次要 PM / 老板 / 客户拍什么。
2. 背景和约束。
3. 选项对比。
4. 推荐方案。
5. 反对意见与回应。
6. 风险、代价和下一步。

更多结构模板见 `references/product-direction.md`：
- 产品方向 memo
- 产品定位说明
- 产品叙事 / 介绍稿
- 产品功能清单
- 高管一页纸
- 决策材料

### 步骤 4：写 Markdown

写作规则：

- 讲当前产品，不编未来能力；未来规划必须明确写成"计划 / 后续 / 假设"。
- 产品方向材料必须有判断，不写成资料汇编。
- 每个关键判断都要能对应一个证据来源；缺证据就写成假设，不能写成结论。
- 产品功能清单是介绍材料，不作为功能规格；不要写成可执行验收表。
- 对外材料少用内部过程词：不写 worktree、mock、spec、close、沉淀、冻结档等内部协作词；如果必须区分真实系统和演示壳，用"已落地 / 原型演示 / 计划中"。
- 术语使用 `PRODUCT.md` 的业务术语表；不要临时发明同义词。
- 涉及未落地能力时，明确标注"未落地 / 计划中 / 仅原型演示"。
- 写作可吸收 AIDA / PAS / FAB 等表达框架，但只作内部组织工具；最终文档要像产品判断，不像营销话术。
- 写一句话定位、标题、页首主张时，按 `references/product-direction.md` 的成文规则先定读者、判断、证据和旧方式；可吸收 `/pmai-meta` 的重定位结论，但最终由本 skill 成文。
- 最后一遍按 `/pmai-humanize` 的表达层规则打磨文字：去 AI 味、去黑话、删空话、保留产品判断。
- PM 明确想在发出前“多角度看看 / 找盲区 / 让几个 agent 分别看”时，可建议跑 `/pmai-meta <文档路径>` 的压测模式做多视角冷读；它只给诊断和改法方向，不替代本 skill 成文。

### 步骤 5：优化已有介绍型 / 产品方向文档

PM 说"帮我看某个文件，整体优化结构、内容、文风"时，按这条走：

1. 先判断文档类型。功能型文档转 `/pmai-prd-writing`；介绍型 / 产品方向材料留在本 skill。
2. 读原文和最小真相源。
3. 先给三类诊断：
   - 结构：主张是否前置、章节是否重复、读者路径是否顺。
   - 内容：事实是否缺依据、是否混入未落地能力、是否缺取舍和边界。
   - 文风：是否空泛、AI 腔、像营销稿或咨询报告。
4. PM 明确"直接改"时可就地覆盖；否则先给改稿提纲等 PM 确认。
5. 改完最后按 `/pmai-humanize` 的表达层规则收口，但不要让 humanize 改产品判断。

### 步骤 6：质量自检

交付前逐条扫：

- [ ] 开头 10 秒能读出主张。
- [ ] 每个核心判断都有来源、证据或明确假设。
- [ ] 目标读者、读者要做的决定、下一步动作都明确。
- [ ] 已落地 / 原型演示 / 计划中没有混写。
- [ ] 没有把介绍材料写成功能规格。
- [ ] 没有空泛口号：提升、赋能、闭环、拉通、全链路等词出现就换成具体效果。
- [ ] 一句话定位 / 标题（如有）能独立说清对象、判断或效果，不靠黑话撑场。
- [ ] 功能清单按业务能力 / 用户任务组织，不按页面目录机械罗列。
- [ ] 至少处理了主要异议：为什么现在做、为什么做这条路、为什么可信。
- [ ] 有成功指标或验证方式；没有数据时写"待验证"，不假装已有结论。
- [ ] 对外材料不出现内部流程词。
- [ ] PM 若要求多视角把关，已用 `/pmai-meta` 的压测模式做旁路冷读；PM 没要求时不强制。

### 步骤 7：更新 deliverables 索引

写完 `docs/deliverables/<文件名>.md` 后，同步更新 `docs/deliverables/INDEX.md`：

| 文档 | 类型 | 读者 | 用途 | 状态 |
|---|---|---|---|---|

没有 `docs/deliverables/INDEX.md` 时，按 `$PMAI_HOME/templates/deliverables-INDEX.md.tmpl` 新建。

### 步骤 8：回执

只给 PM 需要的信息：

```text
已写好：docs/deliverables/<文件名>.md
已更新：docs/deliverables/INDEX.md
```

如果 PM 要 docx / PDF / 飞书，再按对应 skill 继续。

## Rules

- 本 skill 不写 `docs/modules/<模块>/discussion.md` / `decisions.md` / `spec.md`。
- 本 skill 不写 `docs/modules/<按内容命名>.md` 的功能型文档；那些走 `/pmai-prd-writing`。
- 本 skill 默认产出 Markdown；docx / PDF 是后续转换动作，不在这里手写二进制文件。
- `docs/deliverables/` 是对外交付物 / 汇报材料 / 独立评审文档的容器，但"独立评审文档"只有在它是介绍型/表达型材料时才放这里；功能范围评审稿仍归 `/pmai-prd-writing`。
