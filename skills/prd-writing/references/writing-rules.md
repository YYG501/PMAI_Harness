# 写作规则全篇遵守（详细版）

> 本文件是 `skills/prd-writing/SKILL.md` 「写作规则」段的物理拆分。**核心模型**：整份文档（spec 和 PRD）只有**一套语体——简要易懂**；spec 与 PRD 的区别只在**勾了哪些章节块**（见 SKILL.md 章节菜单）和**"功能需求"那一节怎么组织**（见 SKILL.md 功能需求按类）。本文件含：语体（简要易懂 6 条）+ 通用卫生（8 类禁用 + 术语锁定 + 引号）+ 可选讲清楚工具（原 L1–L5，降为按需）+ UI 元素指代 + cross-reference + 抽象动词。

## 写作规则（全篇遵守）

### 总则

- 先结论，后规则；短句，动作先行。
- 同一信息只在一处主写；其他处引用功能名称，不重复展开。
- 术语统一使用三、名词解释中定义的名词，不另行解释。
- **PRD 自包含**：所有规则、约束、文案在当前位置直接展开。读者是研发评审，不让他们追跳转、查字典、读源码。

### 语体：简要易懂（全文唯一一套，spec 和 PRD 都用）

整份文档只有一套语言风格：**简要易懂**。**不分"spec 大白话 / PRD 重型"两套**——spec 和 PRD 语言风格完全一样，区别只在勾了哪些章节块、以及"功能需求"那一节怎么组织。金标准 = 待办 spec 那种"产品同事读一遍就懂"的讲法（实例见 `few-shots.md` 顶部「大白话模块 spec 金标准」）。

写完每节逐条核，命中就改：

1. **按"谁 · 看到什么 · 做什么 · 点了之后发生什么"组织**，不按"方法论 / 架构 / 计算步骤"组织。读者是产品同事，不是论文评审。
2. **加粗克制**：一段最多一两处，只给真正的关键词（一个限定词、一个默认行为、一处唯一约束）。满屏加粗 = 等于没有重点。
3. **公式 / 口径用一句纯文本讲清**。单个能读出来的算式符号（`×` `÷`）可留；`Σ ≥ ≤ ⊆ ⊊` 这种符号堆砌、`→ ✘ ✅ ⚠️` 流程装饰一律不用。
4. **不留迭代痕迹**：正文不写"V0.3 在 V0.2 基础上 / 重做 / 老版新版 / 沉淀回规格"；改了什么只在变更日志一行带过。
5. **不引文件路径、不中英混杂、不写工程词**（详见下方 8 类禁用）。
6. **规则 / 验收用能读出声的自然句**，一句一条，像当面跟人解释。

**通用卫生（任何文档、任何节都守，没有例外）**：① 8 类禁用清单（下方展开）；② **术语锁定**——名词解释表里定义的词全文一个叫法到底，写完 grep 一遍近义词全换回（原 L6，升为通用卫生、不可选）；③ 引号统一——状态/字段/文案 `"..."`、按钮 `[...]`、禁 `「」`。

**收词标准（名词解释表收哪些词）**：只收"全文反复出现、或两个概念容易混"的词；一次性出现的 UI 名（某个抽屉、某个标识）留在正文，不进表。

### 可选的"讲清楚"工具（需要时才用，不强加；判据永远是简要易懂）

下面 L1–L5 原是真系统 PRD 的重型风格指纹，现**降为可选工具**：能让读者更快懂时**才**用，用不上别用——别拿它们把文档写重（L1 那种"反例 + 后果"展开过头，正是把 spec 写成白皮书腔的元凶）。术语一致（原 L6）已升入上面的通用卫生、不在此列。

#### L1 · 加粗短句开题 + 段落展开 + 反例 + 后果

bullet 形式的"原则 / 诉求 / 价值"段（§4.1 业务诉求 / §4.3 方案价值 / §6.x 关键产品定义）必须用「**X。** 段落说明」结构，**不能用单纯短语 bullet**。段落内除了正面说什么外，**给出反例 + 反例后果**——让读者明白"为什么不那样设计"，不是只看到"这样设计"。

| ❌ 错误（短语 bullet） | ✅ 正确（加粗短句 + 段落 + 反例 + 后果） |
| --- | --- |
| - 跨部门集中管理：支持非本部门成员管理某部门 | - **跨部门集中管理。** 真实组织内大量存在"由非本部门成员管理某部门"的合法岗位：人力业务伙伴同时管理多个事业部、合规审计员横跨全租户查看审计日志。这类岗位**不应通过**"调入目标部门"或"为每个部门单独建一个管理员角色"**来表达**——前者破坏组织结构，后者造成角色数量爆炸。 |

#### L2 · 正面定义 + 边界并列（分号串接「是 X；不是 Y」）

§三 名词解释、§4.2 设计原则、§6.x 产品定义类条目，必须**正面定义和边界并列写出**，用分号串接对仗结构：「X 是 Y；不是 Z」 / 「只描述 A，不描述 B；C 在 D 时指定」。**不要只写正面定义**——边界与正面定义同等重要。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 部门：组织归属结构 | 部门：组织归属与数据范围锚点；**不直接承载权限** |
| 角色：权限点集合 | 角色：权限点集合，定义"能做什么"；**不携带任何管辖范围**，**管辖范围在角色分配时指定** |
| 角色与管辖范围分离：分配时指定管辖范围 | 角色**只描述**"能执行哪些动作"，管辖范围**只描述**"对哪些部门的数据生效"；分配角色时再指定管辖范围 |

#### L3 · 等式短定义：`**X：** Y = Z`

关键产品概念第一次正式定义时，使用「**X：** Y = Z」段首加粗小标题 + 等式定义；或整段就一行加粗等式。让读者一眼锁定核心定义，不必从段落里捞。

| 场景 | 写法 |
| --- | --- |
| 子节首段下定义 | **产品定义：** 部门管理员的可见范围 = 其角色分配的管辖范围里勾选了的所有部门。 |
| 整节首段下大定义 | **数据权限范围 = 各角色在产品界面上能看到的数据范围。** |

#### L4 · 对偶式表达：`X ≠ Y`、对仗短语

需要把"两件容易混淆的事"区分开时，用 `X ≠ Y` 或对仗短语，**比展开一段解释更有力**。一处足以确立的概念，不要用多段绕。

| ❌ 错误（绕）| ✅ 正确（对偶） |
| --- | --- |
| 用户能否看到对象不等于能否对该对象执行操作动作；权限校验和视图过滤分别由不同字段控制 | **可见 ≠ 可修改。** 能否对可见对象执行操作动作，由角色权限清单与"自提权防护"等约束共同决定。 |
| 运营管理员管的是租户对象层面的产品配置，租户管理员管的是租户内部的人事权限 | 运营管理员**管的是**"租户作为对象的产品开通和许可证"，租户管理员**管的是**"租户内部的人和权限"。 |

#### L5 · 表格 cell 内加粗关键约束

功能需求表 / 数据权限范围表 / 名词解释表的 cell 内，**关键定义、默认行为、唯一约束、非直观规则**用 `**...**` 或 `<b>...</b>` 加粗，让评审一眼锁定，不用通读整段才发现重点。

加粗对象（必加）：

- 「**仅**」「**只**」「**不允许**」「**必须**」等限定语紧跟的子句
- 默认值与默认行为（"**默认启用**"、"**默认 P0**"）
- 跨平台 / 跨角色的关键差异点（"**租户管理平台**，能够为部门分配产品额度…**主运营平台、下级运营平台没有这个功能**"）
- 系统硬约束**首次出现的子句**（如自提权防护、最高管理员保留规则——首次出现整句加粗，后续在其他 cell 引用时只写术语名不加粗）

不加粗对象：所有非关键描述、已在 §三 名词解释中定义且本表反复出现的术语名（避免过度加粗导致重点稀释）。

#### L6 · 术语一致性硬约束（名词表锁定）

§三 名词解释表中定义的术语，**全篇必须使用同一称呼**，禁止任何换称。常见违规：

| ❌ 错误（换称） | ✅ 正确（一致） |
| --- | --- |
| §三 写"租户管理员"，§五写"租户超级管理员" | 全篇统一"租户管理员" |
| §三 写"管辖范围"，§六 写"管辖区域" / "数据范围" / "授权范围" | 全篇统一"管辖范围" |
| §三 写"角色分配"，§六 写"授权" / "授予角色" / "权限分配" | 全篇统一"角色分配" |
| §三 写"自提权防护"，§六 写"提权检查" / "权限自防护" | 全篇统一"自提权防护" |

写作时检查路径：先把 §三 名词解释表里所有术语列出来 → 全文搜索这些术语的近义词 → 全部替换为 §三 定义的称呼。

### 禁用清单（必须遵守）

#### 禁用代码 / 实现层引用

PRD 是产品规格层文档，不出现任何代码 / 路径 / 字段名 / 文档章节号。

| 类型 | ❌ 错误 | ✅ 正确 |
| --- | --- | --- |
| 代码常量名 | `TENANT_ADMIN`、`DEPARTMENT_ADMIN` | "租户管理员"、"部门管理员" |
| 文件名 / 路径 | `TenantRolesPage`、`prototype/src/...` | 用产品功能名称指代页面 |
| 文档章节号 | `task-022 §1`、`V4.1 §十二.2` | PRD 自包含，不依赖外部章节号 |
| 数据库 / 字段名 | `enabled`、`createdBy`、`includeDescendants`、`permissions[]` | "角色启用状态"、"创建人字段"、"是否含子部门" |

#### 禁用 UI 实现术语

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 扁平区、摘要卡、Badge | 详情页顶部、摘要信息行、标识 / 标签 |
| 按钮置灰、按钮级隐藏、按钮不展示 | 按钮处于禁用状态、按钮在界面上不展示 |
| 统一渲染、悬浮、扁平化 | 按以下规则展示、鼠标悬停时 |

#### 禁用书面冷僻词

明示 / 暗中 / 链路 / 范畴 / 颗粒度 / 失控点 / 覆盖关系 / 隐式约定 / 落库——替换为日常的、研发评审场景下不需要查字典的中文词。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 明示"该角色为默认角色" | 提示"该角色为默认角色" |
| 字段映射 | 字段对应关系 |

#### 禁用中英混杂

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| review / 逐节 review | 核对 / 评审 / 逐节核对 |
| CRUD | 创建 / 编辑 / 删除 / 启用停用（列全） |
| scope | 管辖范围（首次定义后统一作为产品术语） |

#### 禁用技术 jargon

死锁 / 互锁 / 悬挂引用 / 鉴权 / 三件套——改成业务语言。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 悬挂引用 | 管辖范围里仍引用了不存在的部门 |
| 互锁保护陷入死锁 | 双方互相阻止对方操作的循环 |
| 不参与鉴权 | 不参与权限判断 |

#### 禁用数学化表达

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 严格小于 / 严格更大 / ⊊ / ⊆ | 完全包含在 X 之内（且至少少一个部门） |

#### 禁用元描述 / 自指

PRD 内不出现任何对自身的描述。这条已在 §4.1-§4.4 和 §8 各处明示，写作时全程注意以下措辞一律不写：

- "本 PRD 是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚……"
- "本 PRD 不修改既有规则"

#### 禁用兜底词

"等"、"之类的"、"相关的"——必须列全所有项。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| "编辑 / 启用停用 / 删除"等操作 | "编辑"、"启用 / 停用"、"删除"三个操作 |

#### 禁用主观词

"清晰区分"、"清晰展示"、"明显标识"——改为具体展示方式。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 默认角色清晰区分 | 默认角色行带"默认"标识 |

#### 禁用版本 / 迭代过程语言

PRD 是最终需求规格，读者不应感知中间迭代过程。所有"v1 / v2 / 重做 / 重构 / 第二代 / 下一版 / 老版 / 新版 / 主战场 / 整个 v2 范围内"一律不写。

| 类别 | ❌ 错误 | ✅ 正确 |
| --- | --- | --- |
| 标题用版本号 | `# 权限管理 — 整体设计重审 v2 PRD` | `# 权限管理 PRD`（直接说最终产物） |
| 摘要 / 描述用过程语言 | "本 PRD 描述了 XX 的整体重做方案" / "重构后的体验" / "v1 老版" / "下一版" | "本 PRD 描述了 XX 的功能需求" / "支持..." / "覆盖..." |
| 章节范围限定用版本 | "整个 v2 范围内不出现..." / "全 v2 范围内 UI 文案..." | "本 PRD 范围内..." / "本模块范围内..." |
| 模块定位用迭代版本 | "产品详情页 = v2 主战场" / "第二代体验" | 删除或改为"主操作页" / "主功能" |

例外：
- §一 文档版本信息 / §二 变更日志（PRD 文档版本号本身，不是产品迭代过程）
- §三 名词解释里产品名版本（如"万智平台 2.1"）作为产品名一部分时可保留

### UI 元素指代规则

涉及按钮 / 弹窗 / 提示行为的描述，必须明确：

- **按钮名**：用方括号 `[...]` 包按钮上的具体文字（如 `[添加用户]` 按钮、`[编辑基本信息]` 按钮）。
- **弹窗场景**：弹窗在哪个页面 / 哪个动作触发（如"移出归属确认弹窗"、"删除自定义角色二次确认弹窗"）。
- **具体文案**：用 ASCII 双引号 `"..."` 包实际显示的文字（如鼠标悬停时提示"该角色已停用，不能新增分配"）。
- **状态名 / 字段名 / 卡片名 / 区块名**：同样用 `"..."` 包（如`"已开通用户数"`列、`"产品授权项 & 使用情况"`区块）。

引号风格统一用 `"..."`（半角双引号）和 `[...]`（按钮）。**禁用** `「」`（中文方角引号）。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 按钮处于禁用状态，提示原因 | `[添加用户]` 按钮处于禁用状态，鼠标悬停时提示"该角色已停用，不能新增分配" |
| 弹窗中提示用户将失去权限 | 停用前需二次确认，确认弹窗中提示"已分配该角色的用户将立即失去该角色带来的权限" |
| 「按部门查看」段头 | "按部门查看"段头 |
| 「分配额度到部门」按钮 | `[分配额度到部门]` 按钮 |

### cross-reference 处理规则

- 禁止用"详见 §6.X" / "见 §X.Y" 让读者跳转。
- 关键规则的简要说明应直接写在当前位置；如果同一规则在多处出现，可在多处都简要描述（约 1-2 句）。
- "详见 §X" **仅在引用本 PRD 之外的文档**（如设计规范 DESIGN.md）时使用。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 添加 / 移除受自提权防护与管理员保护规则约束（详见 §6.4） | 添加用户时受自提权防护约束：操作者只能分配权限点不超过自身的角色，且目标管辖范围不能超出自身管辖范围 |

### 抽象动词使用规则

以下动词使用时必须搭配**具体效果**，不能孤立出现：

- **"更新 X 定义"** → 必须写"更新后，X 对持有它的对象立即按新规则生效"
- **"保存后生效"** → 必须写生效后什么变化、对谁生效
- **"立即更新"** → 必须写更新的具体内容
- **"执行 X 操作"** → 必须写操作的具体步骤或结果

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 保存后立即更新角色定义 | 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权 |

### 定稿磨文纪律（模块规格操作正本）

框架瘦身后写规格只剩一个 skill，磨文是 `/pmai-prd-writing` 的收口步。`_shared/pm-view/writing-rules.md` §3.13 保留跨 PM 视图的对账说明和细则；本节是模块 `spec.md` 定稿时的操作清单。

写完规格后逐条扫：

1. 正文只写最终事实，不写"本次新增 / 调整为 / 暂时 / 后续"这类迭代过程。
2. 一个概念只用一个名字；同义词、简称、英文混写全部收敛。
3. 规格不解释"为什么这么设计"；原因放 `decisions.md` 或项目级决策档。
4. 规格不描述"原型长什么样"；视觉和布局引用确认过的 mock / prototype，不把 ASCII 骨架嵌进正文。
5. 多步流程用自然叙述讲触发、动作、结果，不堆命令式步骤。
6. 字段、状态、动作必须写清楚进入条件、可做什么、不可做什么、下游影响。
7. 派生 / 计算 / AI 判定类内容必须写清来源、生成规则、变更后如何重算、人工锁定时是否覆盖。
8. 术语按 `PRODUCT.md` 业务术语表 grep 一遍；发现新词先判断是否该收词。
9. 最后跑一遍禁用清单和工程黑话扫描；发现是结构问题就回设计，不用文字润色硬补。

### 规格 4 问自检

每次生成或修改模块 `spec.md`，交付前问四件事：

1. **原型和规格有没有分清？** 规格是权威定义；原型只是表现和验证材料。规格不嵌原型 ASCII，不用"页面上看起来"代替产品规则。
2. **术语是否统一？** 同一个对象、状态、动作只用一个名字；新词要么进入术语表，要么改回既有词。
3. **是否把解释写进了规格？** 为什么这么定放 `decisions.md`；原型长什么样放 mock / prototype；规格只写产品事实和行为。
4. **有没有因为原型缺失悄悄删规格？** 如果老规格在新原型里找不到对应，必须让 PM 拍"确认删"还是"漏实现"，不能自动删除。
