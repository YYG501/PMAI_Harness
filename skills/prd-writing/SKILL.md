# PRD Writing（req 级）

## When To Use

- 当前 req 的所有 task 已关闭，原型行为已稳定，准备输出本 req 范围的 `prd.md`。
- 由 `/close-req` 在 stage 6 调用；产出落在当前 req 目录（`$ACTIVE_REQ_DIR/prd.md`）。
- 这一步是 req 级交付规格化：本 req 范围内"做了什么、为谁做、怎么验收"的一次性产物，定稿后不再修订。
- **不替代项目主 PRD**：`docs/prd.md` 是累积视图，由 `/project-prd-update` 在 close-req 时增量同步。
- **不替代实现前的工作规格**：task 级实施方案在 task 文件里，模块级 spec（如有）在 `docs/modules/`。

## PM 视图规则（必读）

本 skill 产出 `prd.md`（最终交付的产品规格），须遵守 `skills/_shared/PM-VIEW-RULES.md`。
特别注意：
- §三 PM 视图写作规则（明确指代 / 正向描述 / 禁工程词 / 禁像素颜色 / 禁反向约束）
- §五 功能清单格式（标题 + 角色限定一句话 + 业务规则编号 + 字段口径独立表；业务规则只说 what，禁 how/why/字段口径混入）
- §四 文档级严格度对照表（prd.md 行）
- §九 输入流约束（**所有项目级文档全部必读**：brief / analysis / solution（PM 视图）/ tasks（PM 视图）/ docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/；不接受任何 .engineering.md 输入）

`prd.md` 不拆文件（PM-VIEW-RULES §二），是 PM 视图链路的最终交付层。

prd-writing 历史上自带的写作规则（§186 禁用清单 / §266 UI 元素指代规则 / §289 抽象动词使用规则）现已统一搬到 `PM-VIEW-RULES.md` §三作为单一真相源；本 skill 内的同名章节保留作为本文位置参照，但权威以共享规则为准。

## Required Inputs

按 `PM-VIEW-RULES.md §9.1` 表格，所有项目级文档**仓库存在则必读**（不再标"如存在"）：

1. `$ACTIVE_REQ_DIR/brief.md`（必读，stage 1 产出）
2. `$ACTIVE_REQ_DIR/analysis.md`（必读，stage 2 产出）
3. `$ACTIVE_REQ_DIR/solution.md`（PM 视图，必读 — 读取关键产品决策 / 交付物清单 / 验收标准等）
4. `$ACTIVE_REQ_DIR/tasks/*.md`（**仅 PM 视图主文件**；不读 .engineering.md — 已关闭 task 的实际交付字段、交互、规则）
5. `$REPO_ROOT/docs/CONTEXT.md`（必读，项目背景）
6. `$REPO_ROOT/docs/DESIGN.md`（必读，视觉规范）
7. `$REPO_ROOT/docs/prd.md`（必读，已发布的项目主 PRD 作为基线）
8. `$REPO_ROOT/docs/modules/*.md`（必读，已沉淀的模块规格作为权威基线）
9. `$REPO_ROOT/prototypes/`（必读，反向校验所有上游描述 — PM-VIEW-RULES §9.3；原型已定稿时，读取相关页面文件，提取最终字段布局、交互细节、组件用法，作为 §6.2 功能需求表格的权威来源）

## Workflow

1. 读取 `$ACTIVE_REQ_DIR/brief.md`、`analysis.md`、`solution.md`（如有）和 `tasks/*.md`，拆出"已确认决策"和"待确认决策"；有待确认项则先编号提问，确认后再写 PRD。
2. 如果 `prototypes/` 存在已定稿的原型代码，读取相关页面文件，提取最终确认的字段、交互方式、组件选择等细节，作为功能需求表格的**权威依据**。读取后必须用原型实际行为**反向校验** task / module-spec 文档的描述：若文档与原型不一致，**以原型为准**写入 PRD，并在对应章节末尾备注"task 文档此处与原型不一致，以原型为准"，让研发评审时同步修正 task 文档；不允许仅复制 task 文档原话而不验证原型行为。
3. 按下方"PRD 结构"生成完整 `$ACTIVE_REQ_DIR/prd.md`（骨架见 `templates/req-prd.md.tmpl`），语言风格对齐下方"写作规则"与"few-shots"。
4. 在对话中请求 PM 确认 PRD；确认后写入文件。控制权交回 `/close-req`，由其判断是否调 `/project-prd-update` 同步项目主 PRD。

## PRD 结构（必须完整输出）

**章节固定 9 节**：摘要 / §一 文档版本信息 / §二 变更日志 / §三 名词解释 / §四 需求分析 / §五 用户与场景 / §六 功能需求 / §七 验收标准 / §八 非功能性需求 / §九 附件（可选）。摘要 / §五 5.2 用户故事 / §五 5.3 非目标 / §七 验收标准 / §八 非功能性需求 **不可省**；§九 附件 按需输出。

**身份 / 权限 / RBAC / 账号体系类 PRD** 可在 §六 功能需求 之后插入两个专属章节（详见本节末「身份 / 权限类 PRD 专属可选章节」）：「数据权限范围」与「角色权限清单」。插入后原 §七 / §八 / §九 顺延为 §九 / §十 / §十一，编号在文末"专属可选章节"段给出对照。

### 摘要

1-3 句话概述本 PRD 旨在说明的功能范围与所属迭代，放在文档最顶部，不编号。

### 一、文档版本信息

| 字段 | 值 |
| --- | --- |
| 文档版本号 | V |
| 创建日期 | |
| 编写人 | |
| 产品版本号 | V |
| 对应原型版本号 | V（如无则留空） |

### 二、变更日志

表格：时间 / 版本号 / 对应原型版本 / 变更人 / 主要变更内容

### 三、名词解释

表格（术语 / 缩略词 | 说明）；无则写"无"。

### 四、需求分析

#### 4.1 业务诉求

自然语言段落，每条以「**加粗短句。**」（一句话定义该诉求）开头，紧跟一段话说明该诉求的具体场景与影响。诉求条数无硬上限（典型 3-6 条），覆盖能支撑 §4.2 设计原则推导的核心业务面即可。开头给一段引子（1-2 句）说明本模块在业务上面临一组什么样的真实诉求，再列具体诉求。

**视角要求：必须从用户在使用产品时遇到的具体问题出发**（如"租户管理员误把员工调入部门来授予管理权"、"部门管理员遇到按钮禁用不知所措"、"业务方误以为主运营是租户超级管理员"）。`analysis.md` 通常是 PM / 团队从内部诱因写的（"我们讲不清"、"规格交付卡住"），引用时必须**翻译为用户视角**，不能直接搬。

禁止以"PM 讲不清"、"团队内部规格交付卡住"、"我们要补一个 PRD"等团队内部诱因切入。研发评审 PRD 不接受元叙事——读者不关心 PM 的内部困扰，只关心产品要解决什么用户问题。

#### 4.2 设计原则

§4.1 的业务诉求推导出本模块的 N 条设计原则。第六章的功能定义直接承接这些原则。

**表格输出**，列结构：`| 编号 | 原则 | 内容 | 对应业务诉求 |`。

- 「对应业务诉求」列在原则与诉求 1:1 简单映射时**可省略**；多对多或希望明示溯源时保留。
- 原则名 4-8 字短句（如"角色与管辖范围分离"、"归属与权限相互独立"、"跨层身份隔离"）。
- 内容写产品规则一句话，句式典型为 "X 只描述 A，不描述 B；C 在 D 时指定" / "调整 X 不会自动 Y" / "三层 X 互相隔离"。
- 原则数量典型 5-8 条。表格上方一句话引子承接 §4.1，结尾不写"详见 §六"。

**写产品规则，不写文档自指**：原则内容写产品能怎么做、不能怎么做。禁止任何对 PRD 自身的描述（"输出本 PRD 作为产品规格交付层文档"、"本 PRD 是规格交付层"、"本文档面向研发评审"）。

#### 4.3 方案价值（Impact）

3-5 条 bullet，格式：`**动词短语。** 具体结果`（加粗短句开头 + 一句话说明，与 §4.1 业务诉求段落风格一致）。说明此方案对业务/运营/商业化的价值，回答"为什么值得做"。

**写业务价值，不写文档治理价值**：写产品对业务 / 用户 / 运营的实际价值（如"消除高价值内容外流风险"、"承载真实组织复杂度"、"保障租户自治"）。禁止写文档治理类价值（"降低规格交付沟通成本"、"沉淀业务沟通的稳态版本"、"建立产品规格的稳态版本"等指向 PRD 文档自身或 PM / 团队内部协作的价值）。

### 五、用户与场景

#### 5.1 用户角色

**默认 3 列扁平表**：`| 角色名 | 描述 | 与本功能的关系 |`。来源：`analysis.md` 的用户与场景。

**多平台 / 多层场景**（如租户 / 主运营 / 下级运营三层、平台侧 + 租户侧两层、按角色归属分类时）：扩展为 **4 列分组表**：`| 角色归属 | 角色 | 描述 | 与本模块的关系 |`，第一列用 HTML `<table>` + `rowspan` 合并同一归属下的多个角色（如"运营平台"行合并主运营管理员、下级运营管理员、运营部门管理员；"租户"行合并租户管理员、部门管理员；"都有"行合并自定义角色持有者）。markdown 不支持 `rowspan`，多平台场景必须用 `<table>` 写法（飞书 docx 渲染识别）。

#### 5.2 用户故事

格式：`**Story N：** 作为 <角色>，我希望能 <动作>，以便 <价值>。`

每条 Story 必须加 `**Story N：**` 编号前缀（N 从 1 开始），编号须与七、验收标准中的 AC 分组编号严格对应。全程使用中文，不混用英文关键词。Story 数量 3-5 条，覆盖核心场景和关键边界。

#### 5.3 非目标

bullet list，每条一句。来源：`input.md` 的 Out of Scope 与 `analysis.md` 的非目标。无则写"暂无"。

### 六、功能需求

- **6.1 原型**：填写原型链接或版本号；如无则写"待补充"。
- **6.2 功能需求**：见下方"功能需求表格写法"。

### 七、验收标准（Acceptance Criteria）

为五、用户故事的每条 Story 提供一组验收条件，使用 checklist 格式。AC 组数以用户故事数为准，不以六、功能需求的表格行数为准：

```markdown
**Story [编号]：[故事名称简述]**
- [ ] [可验证的结果状态]
```

只写结果状态（"按钮置灰""返回 403"），不写操作步骤；每条 Story 须覆盖正常路径 + 关键边界/异常场景。

### 八、非功能性需求

如无则写"暂无"；有则按维度逐条写明要求。

**仅写产品级约束**（如"本模块依赖租户许可证授权"、"产品访问额度由许可证决定"、"权限校验不使用缓存，每次操作实时查询"）。禁止写文档级元约束（"本 PRD 是产品规格交付层"、"本 PRD 不修改既有规则"等指向 PRD 文档自身的描述）。

### 九、附件（可选）

直接输出内容（分类表 / 字段字典 / 枚举值等）；无此章节则不写。

## 身份 / 权限类 PRD 专属可选章节

当 PRD 范围是身份、权限、RBAC、账号体系、组织架构等类型时，把"数据可见性"和"权限矩阵"从功能行内单独抽出独立成节，可以让研发评审更容易对齐落地口径。在 §六 功能需求 之后插入下面两节：

### 数据权限范围

按平台分层给出"各角色在产品界面上能看到的数据范围"。建议结构：

- **N.1 通用前提**：一句话定义"数据权限范围 = 各角色在产品界面上能看到的数据范围"，说明跨层隔离前提（账号、部门、角色完全隔离，跨层互不可见）。
- **N.2 / N.3 / N.4 ...**：每个平台一个表格。列结构：`| 角色 | 用户列表 | 部门列表 | 角色列表 | (其他列表) |`。每个角色一行，单元格写该角色在对应列表能看到的数据范围（如"本租户全部用户"、"角色分配的管辖范围内部门下的全部用户"、"权限点 ⊆ 自身权限点的角色"）。
- **N.末 通用边界说明**：bullet 形式补跨平台规则——典型的两条：
  - **可见 ≠ 可修改**：能否对可见对象执行操作类动作，由"角色权限清单"与"自提权防护、最高管理员保留规则"等业务约束共同决定。
  - **管辖范围与可见性的对齐口径**：含查看类权限点的角色持有者，其用户 / 部门列表的可见范围与其角色分配的管辖范围保持一致。

### 角色权限清单

权限矩阵大表，列结构：`| 一级功能 | 二级功能 | 三级功能 | 角色1 | 角色2 | ... |`。

- 单元格用 ✅（可执行）/ 空（不可执行）/ ❌（显式禁止，仅用于"该角色对该动作有明确不可执行的产品定义"）三档表达。
- 一级 / 二级 / 三级功能与 §六 功能需求表的层级保持一致；不重新分组。
- 同一二级功能下多行三级动作连续时，"一级功能"、"二级功能"列用 `rowspan` 合并到首行（必须用 HTML `<table>`）。
- 角色列覆盖 §5.1 用户角色表的全部角色；按"租户 → 主运营 → 下级运营 → 运营部门"等业务层级排列。

## 功能需求表格写法（6.2 必须遵守）

**默认表格结构（6 列）：**

| 一级功能 | 二级功能 | 三级功能 | 优先级 | 使用角色 | 需求描述 |
| --- | --- | --- | --- | --- | --- |

**列结构调整：**

- 当章节标题已经写明一级功能（如 `#### 6.2.1 角色管理`），表格内**省略"一级功能"列**，避免每行复读章节标题。实际表头变为 4 列：`| 二级功能 | 三级功能 | 使用角色 | 需求描述 |`。
- 新需求场景保留"优先级"列；已发布功能的回溯型 PRD（close-req 阶段最常见）通常不需要优先级列。
- **原型已定稿且关键页面有可贴素材图时，加「原型」列**（最右一列），单元格用 `<img name="image.png" mime="image/png" scale="1.000000" src="<token>"/>` 嵌入飞书素材；同一二级功能下多行用 `rowspan` 合并到首行。素材 token 由 `/publish-to-lark` 在发布到飞书后回填，本地写作时可先用占位符 `<img placeholder="原型截图：[页面名]"/>`，发布时替换。加了原型列后整张表必须用 HTML `<table>` 写法以支持 `rowspan`。
- **范围外行的处理（不删行，划线保留）**：当某一行明确不在本 PRD 范围、但读者会基于功能模块期望它存在（如身份权限 PRD 中的"产品额度"、"产品访问"），用 `<del>` 标签划线整行内容（包括三级功能名和需求描述），**保留行**而不是删除。同时在 §摘要 中明确"X 不在本 PRD 范围内，由对应模块单独定义"。这样研发评审时一眼可见"产品里有这个、但本 PRD 不覆盖"，不会以为遗漏。

**分级规则：**

- 一级功能：顶层业务模块（如"探索""发布""角色管理"）
- 二级功能：具体页面 / 子模块（如"Agent广场""发布超级员工""角色详情"）
- 三级功能：具体功能点（如"分类筛选""版本号及版本说明""基础信息""操作按钮"）；无三级时填 `/`

**层级划分原则：**

- 二级 / 三级层级**来自该功能模块的真实业务逻辑**，参考已有 task 文档 / module-spec 的章节结构（如 task 文档的 §1~§N 自然形成"角色列表 / 创建自定义角色 / 编辑自定义角色 / 角色详情……"的二级层级）。
- **不得在 PRD 阶段拍脑袋分组**——例如把"列表 / 详情"硬归到"查看"组下、把"创建 / 编辑 / 启用停用 / 删除"硬归到"定义"组下，这种强行分级会让二级功能逻辑做作。
- 同一二级功能下若三级功能 ≤ 2 个，可考虑不分级（避免强行分级）。
- 详情类功能本身常常是一个完整的二级功能（下面再分基础信息 / 操作按钮 / 权限配置 / 授权对象等三级），不要把"详情"和"列表"硬塞到同一二级里。

**与原型 / task 文档对齐：**

- 表格行内的字段、状态、按钮、提示文案必须以**原型实际行为**为准；task 文档原话与原型不一致时按原型写，并在该行末尾备注"以原型为准"。
- ❌ 错误示例：task 文档写"停用 Badge（若已停用）"——直接搬到 PRD 写"停用标识（若已停用）"。
- ✅ 正确示例：先打开原型确认实际行为是"启用 / 停用都展示状态标识"，PRD 写"角色状态标识（启用 / 停用）"。

**需求描述写法：**

- 写动作与结果，不写"支持/优化/提升体验"等泛词。
- 有规则/限制/默认值的，必须明确写出（使用"默认……""不允许……""如果……则……"等句式）。
- 同一格内多条规则用 `<br>` 换行分隔，不强制编号；能一句话说清的不要分条。飞书 docx 表格 cell 渲染 `<br>` 为真实换行（终端 markdown 渲染器看不出，以飞书渲染效果为准）。
- 表格行中含结构化参考数据（权限矩阵、字段清单、枚举值映射等）时，提取到九、附件，需求描述中注明"具体见附件 X"，不在单元格内展开。判断标准：同一格内需要超过 3 个字段/枚举值列举，且其他行可能引用同一份数据。

**相同内容单元格视觉规范：**

- 同一列下连续多行出现**相同内容**时，按"合并单元格"的视觉效果呈现——只在第一行展示该值，后续相同的行该列留空（在飞书 docx 中即合并单元格的效果）。
- 最典型场景：同一二级功能下有多个三级功能（如"角色列表"作为二级在相邻 5 行重复），第一行展示"角色列表"，第 2-5 行该列留空。
- 此规则对二级功能列、使用角色列同样适用——同一二级功能下多个三级功能的使用角色相同时，使用角色列也合并展示。
- 标准 markdown 不支持合并单元格语法；本规则首要约束的是**视觉效果**，PM 在飞书侧选中相邻相同 cell 手工合并即可，具体实现路径由项目工具链决定。

## 写作规则（全篇遵守）

### 总则

- 先结论，后规则；短句，动作先行。
- 同一信息只在一处主写；其他处引用功能名称，不重复展开。
- 术语统一使用三、名词解释中定义的名词，不另行解释。
- **PRD 自包含**：所有规则、约束、文案在当前位置直接展开。读者是研发评审，不让他们追跳转、查字典、读源码。

### 语言风格（必须遵守）

PRD 行文层面的 6 条语言指纹，§4.1 / §4.2 / §三 / §6.x / §七 / §八 全篇适用。

#### L1 · 加粗短句开题 + 段落展开 + 反例 + 后果

bullet 形式的"原则 / 诉求 / 价值"段（§4.1 业务诉求 / §4.3 方案价值 / §6.x 关键产品定义）必须用「**X。** 段落说明」结构，**不能用单纯短语 bullet**。段落内除了正面说什么外，**给出反例 + 反例后果**——让读者明白"为什么不那样设计"，不是只看到"这样设计"。

| ❌ 错误（短语 bullet） | ✅ 正确（加粗短句 + 段落 + 反例 + 后果） |
| --- | --- |
| - 跨部门集中管理：支持非本部门成员管理某部门 | - **跨部门集中管理。** 真实组织内大量存在"由非本部门成员管理某部门"的合法岗位：人力业务伙伴同时管理多个事业部、合规审计员横跨全租户查看审计日志。这类岗位**不应通过**"调入目标部门"或"为每个部门单独建一个管理员角色"**来表达**——前者破坏组织结构，后者造成角色数量爆炸。 |

#### L2 · 正面定义 + 边界并列（分号串接「是 X；不是 Y」）

§三 名词解释、§4.2 设计原则、§6.x 产品定义类条目，必须**正面定义和边界并列写出**，用分号串接对仗结构：「X 是 Y；不是 Z」 / 「只描述 A，不描述 B；C 在 D 时指定」。**不要只写正面定义**——边界与正面定义同等重要。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 部门：组织归属结构 | 部门：组织归属与数据范围锚点；**不直接承载权限** |
| 角色：权限点集合 | 角色：权限点集合，定义"能做什么"；**不携带任何管辖范围**，**管辖范围在角色分配时指定** |
| 角色与管辖范围分离：分配时指定管辖范围 | 角色**只描述**"能执行哪些动作"，管辖范围**只描述**"对哪些部门的数据生效"；分配角色时再指定管辖范围 |

#### L3 · 等式短定义：`**X：** Y = Z`

关键产品概念第一次正式定义时，使用「**X：** Y = Z」段首加粗小标题 + 等式定义；或整段就一行加粗等式。让读者一眼锁定核心定义，不必从段落里捞。

| 场景 | 写法 |
| --- | --- |
| 子节首段下定义 | **产品定义：** 部门管理员的可见范围 = 其角色分配的管辖范围里勾选了的所有部门。 |
| 整节首段下大定义 | **数据权限范围 = 各角色在产品界面上能看到的数据范围。** |

#### L4 · 对偶式表达：`X ≠ Y`、对仗短语

需要把"两件容易混淆的事"区分开时，用 `X ≠ Y` 或对仗短语，**比展开一段解释更有力**。一处足以确立的概念，不要用多段绕。

| ❌ 错误（绕）| ✅ 正确（对偶） |
| --- | --- |
| 用户能否看到对象不等于能否对该对象执行操作动作；权限校验和视图过滤分别由不同字段控制 | **可见 ≠ 可修改。** 能否对可见对象执行操作动作，由角色权限清单与"自提权防护"等约束共同决定。 |
| 运营管理员管的是租户对象层面的产品配置，租户管理员管的是租户内部的人事权限 | 运营管理员**管的是**"租户作为对象的产品开通和许可证"，租户管理员**管的是**"租户内部的人和权限"。 |

#### L5 · 表格 cell 内加粗关键约束

功能需求表 / 数据权限范围表 / 名词解释表的 cell 内，**关键定义、默认行为、唯一约束、非直观规则**用 `**...**` 或 `<b>...</b>` 加粗，让评审一眼锁定，不用通读整段才发现重点。

加粗对象（必加）：

- 「**仅**」「**只**」「**不允许**」「**必须**」等限定语紧跟的子句
- 默认值与默认行为（"**默认启用**"、"**默认 P0**"）
- 跨平台 / 跨角色的关键差异点（"**租户管理平台**，能够为部门分配产品额度…**主运营平台、下级运营平台没有这个功能**"）
- 系统硬约束**首次出现的子句**（如自提权防护、最高管理员保留规则——首次出现整句加粗，后续在其他 cell 引用时只写术语名不加粗）

不加粗对象：所有非关键描述、已在 §三 名词解释中定义且本表反复出现的术语名（避免过度加粗导致重点稀释）。

#### L6 · 术语一致性硬约束（名词表锁定）

§三 名词解释表中定义的术语，**全篇必须使用同一称呼**，禁止任何换称。常见违规：

| ❌ 错误（换称） | ✅ 正确（一致） |
| --- | --- |
| §三 写"租户管理员"，§五写"租户超级管理员" | 全篇统一"租户管理员" |
| §三 写"管辖范围"，§六 写"管辖区域" / "数据范围" / "授权范围" | 全篇统一"管辖范围" |
| §三 写"角色分配"，§六 写"授权" / "授予角色" / "权限分配" | 全篇统一"角色分配" |
| §三 写"自提权防护"，§六 写"提权检查" / "权限自防护" | 全篇统一"自提权防护" |

写作时检查路径：先把 §三 名词解释表里所有术语列出来 → 全文搜索这些术语的近义词 → 全部替换为 §三 定义的称呼。

## Few-shots（来自真实 PRD 案例）

> 以下示例来自万智平台项目，仅用于说明格式与写作风格。跨项目使用本 skill 时，可替换为当前项目的真实案例。

**摘要示例（权限控制场景）：**

> 本 PRD 旨在明确万智平台「导出/下载/分享」权限控制收口的功能需求，覆盖历史记录、会话文件、Agent 产物、知识库/问答库、高代码五类入口及统一下载网关与审计日志建设，计划在 V2.3 迭代交付 P0 部分。

**摘要示例（探索与发布场景）：**

> 本 PRD 旨在明确万智平台「探索」功能的需求，包括 Agent 广场与 Agent 商店的聚合展示、体验与复制能力，以及超级员工和工作流发布到探索的完整流程，计划在 V2.3 迭代交付。

**三、名词解释示例（正面定义 + 边界并列，对仗结构）：**

> 每条术语写"产品定义；边界（不是什么）"，分号串接，让读者一眼看到正面与边界两面。
>
> | 术语 | 说明 |
> | --- | --- |
> | 部门 | 组织归属与数据范围锚点；**不直接承载权限** |
> | 角色 | 权限点集合，定义"能做什么"；**不携带任何管辖范围** |
> | 用户 | 身份主体，是**唯一**可被分配角色的对象 |
> | 角色分配 | 把某角色在某管辖范围下授予某用户的一条授权记录 |
> | 管辖范围 | 角色分配时指定的"管哪些部门的数据"；包含两种顶层形态 |
> | 全租户范围 | 命中本租户的全部部门，**且自动包含未来新增的部门** |
> | 指定部门范围 | 由若干部门节点组成的集合；**不包含未来新增的部门** |
> | 默认角色 | 系统预置不可删除的角色：租户管理员、部门管理员；运营平台上有同名同构的默认角色 |
> | 自定义角色 | 由租户管理员或运营管理员按业务需要新建的角色，权限点按需勾选组装 |
> | 自提权防护 | 一条系统硬规则：任何用户能分配的角色权限点必须是其自身权限点的子集；目标管辖范围必须不超过其自身管辖范围 |

**4.1 业务诉求示例（身份权限场景，加粗短句 + 段落）：**

> 多租户多应用后台系统在身份与权限管理上面临一组真实业务诉求。这些诉求共同决定了本模块的功能边界与设计取向。
>
> - **跨部门集中管理。** 真实组织内大量存在"由非本部门成员管理某部门"的合法岗位：人力业务伙伴同时管理多个事业部、区域销售总监管理多个区域销售部、合规审计员横跨全租户查看审计日志。这类岗位不应通过"调入目标部门"或"为每个部门单独建一个管理员角色"来表达——前者破坏组织结构，后者造成角色数量爆炸。
> - **治理边界与数据可见性的分离。** 管理员"能操作哪些数据"与"能看到哪些数据"是两件不同的事：前者属于权限管控，后者属于产品视图。如果用同一个字段表达，跨部门协作中"能看见但不能修改"的边界会变模糊，产品视图层的列表过滤也无法单独调整。
> - **多平台并存下的租户自治。** 主运营平台对租户的运营层管理动作应通过给运营管理员授予对应权限点来调用，而非依赖在租户内部建立账号；租户内部的人事、组织、自定义角色由租户管理员自决。三层平台（主运营 / 租户 / 下级运营）的账号、组织、角色完全隔离。
> - **审计追溯的完整性。** 任何一条权限变更，事后都能独立回答"谁授予的、什么时候授予的、对哪些部门生效"；任何一次组织变更也能独立追溯。两条记录链各自独立，不会互相覆盖。

**4.1 业务诉求示例（权限控制场景，加粗短句 + 段落）：**

> 当前平台在多处功能区都存在文件下载、内容导出或分享链接入口，但各入口的权限校验逻辑差异较大，给业务带来一组真实诉求。
>
> - **入口权限统一收口。** 历史记录、Agent 产物、知识库 / 问答库、高代码等多处入口的权限校验各自为政，普通成员可不受限制下载全平台内容，高价值内容（如 AI 生成的 PPT / Excel、知识库文件、高代码工程包）存在外流风险。
> - **后端强制兜底。** 部分下载入口使用前端直链或对象存储直链，权限控制完全依赖前端按钮状态。只要获取到 URL，任何人均可绕过前端按钮的状态控制完成下载，后端必须提供强制兜底。
> - **审计可追溯。** 每次下载 / 导出 / 分享操作（含被拒绝）都需要写入审计日志，事后可按用户、资源、时间窗等维度独立检索，覆盖企业合规要求。

**4.3 方案价值示例（身份权限场景）：**

> - **适配真实组织复杂度。** 人力业务伙伴、合规审计员、区域管理员、跨部门协调员等岗位的授权诉求，可在保留原组织结构的前提下完成授权，不必为了授权而调动归属。
> - **降低权限治理风险。** "默认窄边界 + 自定义角色扩展"机制避免默认角色随业务诉求一路膨胀，把权限管理的复杂度限制在新增的自定义角色里。
> - **保障租户自治。** 三层平台身份隔离让运营平台与租户的责任边界清晰可对外解释——运营管理员管的是"租户作为对象的产品开通和许可证"，租户管理员管的是"租户内部的人和权限"。
> - **支持完整审计追溯。** 组织变更与权限变更各自独立留下操作记录，事后能独立查询每条权限的授予人和授予时间。

**4.3 方案价值示例（权限控制场景）：**

> - **消除高价值内容外流风险。** 普通成员默认无法下载 / 分享任何内容，高价值产物（AI PPT、知识库文件、高代码工程包）不再有外流漏洞。
> - **建立企业级审计能力。** 所有下载 / 导出 / 分享操作（含被拒绝）均可追溯，覆盖企业合规要求。
> - **为商业化分层提供能力基础。** download / share 权限可按角色 / 套餐灵活配置，Max 版本差异化下载能力由此可落地。

## 阶段 6 边界：交付规格化

- 允许产出：`$ACTIVE_REQ_DIR/prd.md`
- 允许动作：基于定稿原型 + brief / analysis / solution / 已关闭 task 生成 req 级字段级 PRD
- 禁止顺手推进：不要在写 PRD 的同时反向改范围边界；不要顺手改项目主 PRD（`docs/prd.md`）——那是 `/project-prd-update` 的职责
- 退出条件：PRD 经过 PM 质检并定稿；控制权交回 `/close-req`

## 阶段 6 结束模板

```md
## 阶段 6 完成 — [req 标题]

**产出：** `$ACTIVE_REQ_DIR/prd.md`（req 级，本 req 范围一次性产出）
**未做：** 未扩大范围、未改 analysis.md / solution.md / task spec、未动 docs/prd.md（项目主 PRD 由 close-req 后调 /project-prd-update 同步）

**当前状态：** req 级 PRD 初稿完成，可选做质检或直接定稿。

**建议：** 选 A，质检成本低，能在定稿前发现遗漏的边界情况。定稿后如需把 PRD 同步到飞书评审，再选 D。

A) 做 PRD 质检——用质检 prompt 过一遍，发现边界和矛盾

D) 发布到飞书——调用 /publish-to-lark $ACTIVE_REQ_DIR/prd.md --type prd（首次发布会回填飞书 URL 到 frontmatter，后续发布自动覆盖原文档；会自动合并表格相同内容 cell）
```
