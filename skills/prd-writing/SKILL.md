# PRD Writing（req 级）

## When To Use

- 当前 req 的所有 task 已关闭，原型行为已稳定，准备输出本 req 范围的 `prd.md`。
- 由 `/close-req` 在 stage 6 调用；产出落在当前 req 目录（`$ACTIVE_REQ_DIR/prd.md`）。
- 这一步是 req 级交付规格化：本 req 范围内"做了什么、为谁做、怎么验收"的一次性产物，定稿后不再修订。
- **不替代项目主 PRD**：`docs/prd.md` 是累积视图，由 `/project-prd-update` 在 close-req 时增量同步。
- **不替代实现前的工作规格**：task 级实施方案在 task 文件里，模块级 spec（如有）在 `docs/modules/`。

## PM 视图规则（必读）

本 skill 产出 `prd.md`（最终交付的产品规格），须遵守 `skills/_shared/PM-VIEW-RULES.md`（主索引）。具体读以下子文件：
- `_shared/pm-view/writing-rules.md`（§三 写作规则：明确指代 / 正向描述 / 禁工程词 / 禁像素颜色 / 禁反向约束）
- `_shared/PM-VIEW-RULES.md` §五（功能清单格式：4 列表格 + 续行 rowspan + 需求描述列内联编号；业务规则只说 what，禁 how/why/字段口径混入）
- `_shared/pm-view/doc-strictness.md`（§四 严格度对照表 — prd.md 行）
- `_shared/pm-view/input-flow.md`（§九 输入流；**所有项目级文档全部必读**：brief / analysis / solution（PM 视图）/ tasks（PM 视图）/ docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/；不接受任何 .engineering.md 输入）

`prd.md` 不拆文件（主文件 §二），是 PM 视图链路的最终交付层。

prd-writing 历史上自带的写作规则（§186 禁用清单 / §266 UI 元素指代规则 / §289 抽象动词使用规则）现已统一搬到 `_shared/pm-view/writing-rules.md` §三作为单一真相源；本 skill 内的同名章节保留作为本文位置参照，但权威以共享规则为准。

## Required Inputs

按 `_shared/pm-view/input-flow.md` 中 **Stage 7.4 prd-writing** 段执行。

特别遵守：
- `input-flow.md` §9.1.1 章节匹配强约束——`tasks/task-*.md` 遍历时只读 §📋 / §🎯 / §✅ 三段（任务卡 / 历史档案 / PM 反馈对 PRD 价值低，禁整文件 Read）

## Workflow

1. 读取 `$ACTIVE_REQ_DIR/brief.md`、`analysis.md`、`solution.md`（如有）和 `tasks/*.md`，拆出"已确认决策"和"待执行决策"；有待执行项则先编号提问，确认后再写 PRD。
2. 如果 `prototypes/` 存在已定稿的原型代码，读取相关页面文件，提取最终确认的字段、交互方式、组件选择等细节，作为功能需求表格的**权威依据**。读取后必须用原型实际行为**反向校验** task / module-spec 文档的描述：若文档与原型不一致，**以原型为准**写入 PRD，并在对应章节末尾备注"task 文档此处与原型不一致，以原型为准"，让研发评审时同步修正 task 文档；不允许仅复制 task 文档原话而不验证原型行为。
3. 按下方"PRD 结构"生成完整 `$ACTIVE_REQ_DIR/prd.md`（骨架见 `$REPO_ROOT/templates/req-prd.md.tmpl`），语言风格对齐下方"写作规则"与"few-shots"。
4. 在对话中请求 PM 确认 PRD；确认后写入文件。控制权交回 `/close-req`，由其判断是否调 `/project-prd-update` 同步项目主 PRD。

## PRD 结构（必须完整输出）

**章节固定 9 节**：摘要 / §一 文档版本信息 / §二 变更日志 / §三 名词解释 / §四 需求分析 / §五 用户与场景 / §六 功能需求 / §七 验收标准 / §八 非功能性需求 / §九 附件（可选）。摘要 / §五 5.2 用户故事 / §五 5.3 非目标 / §七 验收标准 / §八 非功能性需求 **不可省**；§九 附件 按需输出。

### 摘要

写一段不超过 80 字的概述：本 PRD 的范围、覆盖的功能模块、计划交付迭代或时间。让评审人在 5 秒内得到 scope。开头用「本 PRD 旨在明确...」或「本 PRD 描述了...」。

### 一、文档版本信息

| 字段 | 值 |
| --- | --- |
| 文档名称 | 万智平台 - [模块名称] - 产品需求文档 |
| 版本号 | V1.0 |
| 撰写人 | xxx |
| 评审人 | xxx |
| 撰写时间 | YYYY-MM-DD |
| 当前状态 | 草稿 / 评审中 / 已发布 |

### 二、变更日志

| 日期 | 版本 | 变更说明 | 修改人 |
| --- | --- | --- | --- |
| YYYY-MM-DD | V1.0 | 初版 | xxx |

### 三、名词解释

定义专有名词、缩写词、关键概念，避免读者反复猜测。涵盖系统名、业务术语、内部缩写、跨平台/跨角色概念差异（写法见 [`references/few-shots.md`](./references/few-shots.md)「三、名词解释示例」）。

### 四、需求分析

#### 4.1 业务诉求

来自业务、用户的真实需求，从用户视角而非"PM 讲不清需求"等团队内部诱因出发。每条要素以「**加粗短句。**」开头并配段落说明，**不是单纯 bullet 列表**（写作规则见 `references/writing-rules.md` §L1；示例见 `references/few-shots.md` §4.1）。

诉求项数无上限，单条不需要拆得很细；同一类诉求合并为一个加粗短句即可。诉求与设计原则间有"诉求 → 原则"的对应关系，写诉求时心里要清楚每条诉求会演化成哪条设计原则。

#### 4.2 设计原则

由业务诉求推导出的产品设计取向。**表格化呈现**，列结构为「编号 / 原则 / 内容」，可选追加「对应业务诉求」列（让评审一眼看出诉求 → 原则的映射，多平台/多模块场景推荐保留；单平台简单场景可省）。

| 编号 | 原则 | 内容 |
| --- | --- | --- |
| 1 | [原则名 — 4-8 字短句] | [原则的具体描述：是什么/不是什么、目的/边界] |

正文写「§4.1 的业务诉求推导出本模块的 N 条设计原则」，N 与表格行数严格一致。**不允许**把"本 PRD 是规格交付层"等元描述塞进 4.2。

#### 4.3 方案价值（Impact）

按 5 个维度组织：用户价值、业务价值、商业价值、风险消解、量化指标（如有）。**业务价值**：用户能完成什么、业务能解决什么；**风险消解**：消除高价值内容外流 / 提供合规审计能力等。**禁止写**"降低规格交付成本""文档治理收益"等文档治理价值——4.3 是产品价值，不是 PM 协作价值（写作规则见 `references/writing-rules.md` §L1）。

**指标对象边界（含可选量化指标段）**：所有验证指标的对象必须是**产品能力达成度**（如"无 download 权限的普通成员所有指定入口下载按钮均置灰且无法触发"），**不能是 PRD 文档覆盖度**（禁写"用户能从本 PRD 找到答案""PM 能直接引用本 PRD §6.X 给出标准回答""部门管理员能从本 PRD §6.4 自助查到完整边界"等指向 PRD 文档自身作为答案库的指标）。

### 五、用户与场景

#### 5.1 用户角色

列出本模块所有相关角色，按平台/层级分组。**单平台 3 列扁平表**（角色名 / 描述 / 与本功能的关系）；**多平台/多层场景 4 列分组表**（角色归属 / 角色 / 描述 / 与本模块的关系，第一列 `rowspan` 合并；多平台必须用 HTML `<table>` 写法以支持 rowspan）。示例见 `references/few-shots.md` §5.1。

#### 5.2 用户故事

按"作为 [角色]，我希望 [行为]，以便 [价值]"格式组织。每个核心 Story 编号（Story 1 / Story 2…），便于 §七 验收标准对应引用（"Story 1：无权限时下载按钮行为"）。覆盖主要使用场景与边界场景。

#### 5.3 非目标

明确列出**不在本期范围内**的功能点，避免范围蔓延。例如"本期不建设审计日志查询 UI""不对资源创建者设置豁免权"等。

### 六、功能需求

按业务模块组织，每个一级章节（§6.1 / §6.2 / …）对应一个二级业务模块。结构：先一段产品定义（用 §L3 等式短定义），再表格化展开功能。

表格结构 / 写法详见下方「功能需求表格写法」。

### 七、验收标准（Acceptance Criteria）

按 5.2 用户故事编号组织。每条 Story 列出可独立验证的验收点（checkbox 形式）：

> **Story 1：[Story 标题]**
> - [ ] 验收点 1（具体可测）
> - [ ] 验收点 2
>
> **Story 2：[Story 标题]**
> - [ ] ...

验收点必须可测量、可执行；避免"系统应稳定运行""用户体验良好"等无法测的描述。

### 八、非功能性需求

涵盖：**性能**（响应时间 / 吞吐 / 并发）、**安全性**（鉴权 / 越权 / 注入 / IDOR）、**可用性**（SLA / 容错 / 降级）、**可观测性**（埋点 / 日志 / 审计）、**向后兼容**（升级影响 / 数据迁移）、**可扩展性**（容量预估 / 横向扩展点）。

每条用一句明确的指标 / 行为描述，避免"系统应高性能"。

**禁文档级元约束**：本节只写**产品级约束**（如"本模块依赖租户许可证授权""产品访问额度由许可证决定"），**禁写文档级元约束**（"本 PRD 是产品规格交付层""本 PRD 不修改既有规则""本文档面向研发评审"）。同一约束如本属"依赖与约束"性质，也走产品级措辞落本节，不开独立章节复读。

### 九、附件（可选）

存放：**权限矩阵**（默认权限策略表）、**字段字典**（审计日志必须字段、状态机字段定义）、**枚举值表**（资源类型、操作类型、错误码）。提取规则：当某功能的默认值/枚举值/字段清单行数较多，且多处功能行会引用同一份数据时，提取到附件，表格中注明"具体见附件 X"（示例见 `references/few-shots.md` §九）。

## 身份 / 权限类 PRD 专属可选章节

适用范围：当本 req 涉及身份认证 / RBAC / 角色权限 / 账号体系 / 组织架构等场景时，在 §六 功能需求之后插入两个专属章节（§七、§八），原有 §七 验收标准 顺延为 §九，§八 非功能性需求 顺延为 §十，§九 附件 顺延为 §十一。最终结构变为 11 节。

### 数据权限范围

> **数据权限范围 = 各角色在产品界面上能看到的数据范围。**

按平台分子节展开，每个平台一个表格列出"角色 / 列 1 / 列 2 / ..."的可见范围矩阵（列名根据平台业务确定）。表末追加"通用边界说明"段，包含两条硬规则：

- **可见 ≠ 可修改。** 能否对可见对象执行操作类动作，由 §角色权限清单 与"自提权防护、最高管理员保留规则"等业务约束共同决定。
- **管辖范围与可见性的对齐口径。** 部门管理员、含查看类权限点的自定义角色持有者，其可见范围与角色分配的管辖范围保持一致。

示例见 `references/few-shots.md`「身份/权限类专属·数据权限范围示例」。

### 角色权限清单

完整列出**每个一级功能 × 每个二级功能 × 每个三级功能**对**每个角色**的权限点。**必须用 HTML `<table>` 写法**以支持 `rowspan`（一级功能跨多个三级功能行时合并）。markdown 表格不支持 rowspan，会让评审者无法一眼看清功能层级；飞书 docx 渲染时识别 HTML `<table>` 并转换为合并单元格效果。

✅ 单元格内容统一用 `✅`（有权限）/ 空单元格（无权限），避免 `Y/N` / `是/否` / `允许/不允许` 等多写法混用。

示例见 `references/few-shots.md`「身份/权限类专属·角色权限清单示例」。

## 功能需求表格写法（6.2 必须遵守）

**默认表格结构（6 列）：**

| 一级功能 | 二级功能 | 三级功能 | 优先级 | 使用角色 | 需求描述 |
| --- | --- | --- | --- | --- | --- |

**列结构调整：**

- 当章节标题已经写明一级功能（如 `#### 6.2.1 角色管理`），表格内**省略"一级功能"列**，避免每行复读章节标题。实际表头变为 4 列：`| 二级功能 | 三级功能 | 使用角色 | 需求描述 |`。
- 新需求场景保留"优先级"列；已发布功能的回溯型 PRD（close-req 阶段最常见）通常不需要优先级列。
- **原型已定稿且关键页面有可贴素材图时，加「原型」列**（最右一列），单元格用 `<img name="image.png" mime="image/png" scale="1.000000" src="<token>"/>` 嵌入飞书素材；同一二级功能下多行用 `rowspan` 合并到首行。素材 token 由 `/publish-to-lark` 在发布到飞书后回填，本地写作时可先用占位符 `<img placeholder="原型截图：[页面名]"/>`，发布时替换。加了原型列后整张表必须用 HTML `<table>` 写法以支持 `rowspan`。
- **范围外行的处理（不删行，划线保留）**：当某一行明确不在本 PRD 范围、但读者会基于功能模块期望它存在（如身份权限 PRD 中的"产品额度"、"产品访问"），用 `<del>` 标签划线整行内容（包括三级功能名和需求描述），**保留行**而不是删除。同时在 §摘要 中明确"X 不在本 PRD 范围内，由对应模块单独定义"。这样研发评审时一眼可见"产品里有这个、但本 PRD 不覆盖"，不会以为遗漏。

**分级规则：**

- 一级功能：顶层业务模块（如"探索""发布""角色管理"）
- 二级功能：具体页面 / 子模块（如"Agent广场""发布超级员工""角色详情"）
- 三级功能：具体功能点（如"分类筛选""版本号及版本说明""基础信息""操作按钮"）；无三级时填 `/`

**层级划分原则：**

- 二级 / 三级层级**来自该功能模块的真实业务逻辑**，参考已有 task 文档 / module-spec 的章节结构（如 task 文档的 §1~§N 自然形成"角色列表 / 创建自定义角色 / 编辑自定义角色 / 角色详情……"的二级层级）。
- **不得在 PRD 阶段拍脑袋分组**——例如把"列表 / 详情"硬归到"查看"组下、把"创建 / 编辑 / 启用停用 / 删除"硬归到"定义"组下，这种强行分级会让二级功能逻辑做作。
- 同一二级功能下若三级功能 ≤ 2 个，可考虑不分级（避免强行分级）。
- 详情类功能本身常常是一个完整的二级功能（下面再分基础信息 / 操作按钮 / 权限配置 / 授权对象等三级），不要把"详情"和"列表"硬塞到同一二级里。

**与原型 / task 文档对齐：**

- 表格行内的字段、状态、按钮、提示文案必须以**原型实际行为**为准；task 文档原话与原型不一致时按原型写，并在该行末尾备注"以原型为准"。
- ❌ 错误示例：task 文档写"停用 Badge（若已停用）"——直接搬到 PRD 写"停用标识（若已停用）"。
- ✅ 正确示例：先打开原型确认实际行为是"启用 / 停用都展示状态标识"，PRD 写"角色状态标识（启用 / 停用）"。

**需求描述写法：**

- 写动作与结果，不写"支持/优化/提升体验"等泛词。
- 有规则/限制/默认值的，必须明确写出（使用"默认……""不允许……""如果……则……"等句式）。
- 同一格内多条规则用 `<br>` 换行分隔，不强制编号；能一句话说清的不要分条。飞书 docx 表格 cell 渲染 `<br>` 为真实换行（终端 markdown 渲染器看不出，以飞书渲染效果为准）。
- 表格行中含结构化参考数据（权限矩阵、字段清单、枚举值映射等）时，提取到九、附件，需求描述中注明"具体见附件 X"，不在单元格内展开。判断标准：同一格内需要超过 3 个字段/枚举值列举，且其他行可能引用同一份数据。

**相同内容单元格视觉规范：**

- 同一列下连续多行出现**相同内容**时，按"合并单元格"的视觉效果呈现——只在第一行展示该值，后续相同的行该列留空（在飞书 docx 中即合并单元格的效果）。
- 最典型场景：同一二级功能下有多个三级功能（如"角色列表"作为二级在相邻 5 行重复），第一行展示"角色列表"，第 2-5 行该列留空。
- 此规则对二级功能列、使用角色列同样适用——同一二级功能下多个三级功能的使用角色相同时，使用角色列也合并展示。
- 标准 markdown 不支持合并单元格语法；本规则首要约束的是**视觉效果**。
- **发布到飞书时由 `/publish-to-lark` 步骤 4 自动合并** — 调用飞书 docx OpenAPI `PATCH /blocks/:block_id` + `merge_table_cells` 子请求，扫描 markdown 表格连续相同内容的列做合并。markdown 写法保持"留空 cell"即可（相邻多行同二级功能时只在第一行展示），AI 在发布时机械补齐合并；无需 PM 手工。
- 不发布到飞书 / 用其它工具链时，PM 在工具侧选中相邻相同 cell 手工合并即可。

## 写作规则（全篇遵守）

详见 [`references/writing-rules.md`](./references/writing-rules.md)：
- **总则**：先结论后规则 / 短句动作先行 / 同信息单点主写 / 术语统一 / PRD 自包含
- **L1-L6 语言风格指纹**：L1 加粗短句开题 + 段落 + 反例 + 后果 / L2 正面定义 + 边界并列 / L3 等式短定义 / L4 对偶式表达 / L5 表格 cell 加粗关键约束 / L6 术语一致性（名词表锁定）
- **禁用清单 8 类**：代码 / 实现层引用 · UI 实现术语 · 书面冷僻词 · 中英混杂 · 技术 jargon · 数学化表达 · 元描述 / 自指 · 兜底词 · 主观词
- **UI 元素指代规则**（按钮名 / 弹窗场景 / 提示文案必须明示）
- **cross-reference 处理**（PRD 内禁用 §6.X 跳转，仅可引用外部 DESIGN.md 等）
- **抽象动词使用规则**（更新 / 保存 / 立即更新 / 执行 X 必须搭配具体效果）

`writing-rules.md` 按上述大纲展开，含每条的反例/正例对照表与触发场景说明。

## 阶段 6 边界：交付规格化

- 允许产出：`$ACTIVE_REQ_DIR/prd.md`
- 允许动作：基于定稿原型 + brief / analysis / solution / 已关闭 task 生成 req 级字段级 PRD
- 禁止顺手推进：不要在写 PRD 的同时反向改范围边界；不要顺手改项目主 PRD（`docs/prd.md`）——那是 `/project-prd-update` 的职责
- 退出条件：PRD 经过 PM 质检并定稿；控制权交回 `/close-req`

## PRD 质检 prompt（可选）

prd-writing 产出初稿后，定稿前可运行以下 prompt 做一轮质检：

```
你现在是一个资深产品总监，正在用挑剔的眼光审查一份 req 级 PRD 草稿。
读取 $ACTIVE_REQ_DIR/prd.md 和 $ACTIVE_REQ_DIR/analysis.md，然后找出：

1. 逻辑矛盾或自相冲突的地方
2. 遗漏的边界情况（error state、empty state、权限边界、异常流）
3. 验收标准模糊、无法测量的条目
4. 功能需求描述里有"支持/优化/提升体验"等无法执行的泛词
5. prd.md 与 analysis.md 的"In Scope"不一致的地方
6. 是否包含代码常量名（如 TENANT_ADMIN）/ 文件路径（如 prototypes/src/...）/ 文档章节引用（如 task-022 §1）/ 数据库字段名（如 enabled、createdBy）/ UI 实现术语（如扁平区、Badge、按钮置灰）
7. §4.1 业务诉求是否从用户视角（而非"PM 讲不清"等团队内部诱因），是否每条以"**加粗短句。**"开头并配段落说明（不是单纯 bullet 列表）

9. §4.3 方案价值是否业务价值（而非"降低规格交付成本"等文档治理价值），是否 `**加粗短句。** 段落说明` 风格
10. 是否含 cross-reference（"详见 §X"）让读者跳转，是否含元描述 / 自指（"本 PRD 是..." / "本文档面向..."）
11. 是否含书面冷僻词（明示 / 暗中 / 链路 / 范畴 / 颗粒度）/ 中英混杂（review / CRUD）/ 数学化表达（严格小于 / ⊊）/ 兜底词（"等操作" / "之类的"）/ 主观词（"清晰区分" / "明显标识"）
```
