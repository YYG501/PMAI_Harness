# PRD Writing（req 级）

## When To Use

- 当前 req 的所有 task 已关闭，原型行为已稳定，准备输出本 req 范围的 `prd.md`。
- 由 `/close-req` 在 stage 6 调用；产出落在当前 req 目录（`$ACTIVE_REQ_DIR/prd.md`）。
- 这一步是 req 级交付规格化：本 req 范围内"做了什么、为谁做、怎么验收"的一次性产物，定稿后不再修订。
- **不替代项目主 PRD**：`docs/prd.md` 是累积视图，由 `/project-prd-update` 在 close-req 时增量同步。
- **不替代实现前的工作规格**：task 级实施方案在 task 文件里，模块级 spec（如有）在 `docs/modules/`。

## PM 视图规则（必读）

本 skill 产出 `prd.md`（最终交付的产品规格），须遵守 `skills/_shared/PM-VIEW-RULES.md`。
特别注意：
- §三 PM 视图写作规则（明确指代 / 正向描述 / 禁工程词 / 禁像素颜色 / 禁反向约束）
- §五 功能清单格式（强制三列表 + 数字编号列表）
- §四 文档级严格度对照表（prd.md 行）
- §九 输入流约束（**所有项目级文档全部必读**：brief / analysis / solution（PM 视图）/ tasks（PM 视图）/ docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/；不接受任何 .engineering.md 输入）

`prd.md` 不拆文件（PM-VIEW-RULES §二），是 PM 视图链路的最终交付层。

prd-writing 历史上自带的写作规则（§186 禁用清单 / §266 UI 元素指代规则 / §289 抽象动词使用规则）现已统一搬到 `PM-VIEW-RULES.md` §三作为单一真相源；本 skill 内的同名章节保留作为本文位置参照，但权威以共享规则为准。

## Required Inputs

按 `PM-VIEW-RULES.md §9.1` 表格，所有项目级文档**仓库存在则必读**（不再标"如存在"）：

1. `$ACTIVE_REQ_DIR/brief.md`（必读，stage 1 产出）
2. `$ACTIVE_REQ_DIR/analysis.md`（必读，stage 2 产出）
3. `$ACTIVE_REQ_DIR/solution.md`（PM 视图，必读 — 读取关键产品决策 / 交付物清单 / 验收标准等）
4. `$ACTIVE_REQ_DIR/tasks/*.md`（**仅 PM 视图主文件**；不读 .engineering.md — 已关闭 task 的实际交付字段、交互、规则）
5. `$REPO_ROOT/docs/CONTEXT.md`（必读，项目背景）
6. `$REPO_ROOT/docs/DESIGN.md`（必读，视觉规范）
7. `$REPO_ROOT/docs/prd.md`（必读，已发布的项目主 PRD 作为基线）
8. `$REPO_ROOT/docs/modules/*.md`（必读，已沉淀的模块规格作为权威基线）
9. `$REPO_ROOT/prototypes/`（必读，反向校验所有上游描述 — PM-VIEW-RULES §9.3）
6. （可选）`$REPO_ROOT/prototypes/` 原型代码 — 原型已定稿时，读取相关页面文件，提取最终字段布局、交互细节、组件用法，作为功能需求表格的权威来源

## Workflow

1. 读取 `$ACTIVE_REQ_DIR/brief.md`、`analysis.md`、`solution.md`（如有）和 `tasks/*.md`，拆出"已确认决策"和"待确认决策"；有待确认项则先编号提问，确认后再写 PRD。
2. 如果 `prototypes/` 存在已定稿的原型代码，读取相关页面文件，提取最终确认的字段、交互方式、组件选择等细节，作为功能需求表格的**权威依据**。读取后必须用原型实际行为**反向校验** task / module-spec 文档的描述：若文档与原型不一致，**以原型为准**写入 PRD，并在对应章节末尾备注"task 文档此处与原型不一致，以原型为准"，让研发评审时同步修正 task 文档；不允许仅复制 task 文档原话而不验证原型行为。
3. 按下方"PRD 结构"生成完整 `$ACTIVE_REQ_DIR/prd.md`（骨架见 `templates/req-prd.md.tmpl`），语言风格对齐下方"写作规则"与"few-shots"。
4. 在对话中请求 PM 确认 PRD；确认后写入文件。控制权交回 `/close-req`，由其判断是否调 `/project-prd-update` 同步项目主 PRD。

## PRD 结构（必须完整输出）

### 摘要

1-3 句话概述本 PRD 旨在说明的功能范围与所属迭代，放在文档最顶部，不编号。

### 一、文档版本信息

| 字段 | 值 |
| --- | --- |
| 文档版本号 | V |
| 创建日期 | |
| 编写人 | |
| 产品版本号 | V |
| 对应原型版本号 | V（如无则留空） |

### 二、变更日志

表格：时间 / 版本号 / 对应原型版本 / 变更人 / 主要变更内容

### 三、名词解释

表格（术语 / 缩略词 | 说明）；无则写"无"。

### 四、需求分析

#### 4.1 问题陈述（Problem Statement）

自然语言段落，每段写一个现象及其影响。

**视角要求：必须从用户在使用产品时遇到的具体问题出发**（如"租户管理员误把员工调入部门来授予管理权"、"部门管理员遇到按钮禁用不知所措"、"业务方误以为主运营是租户超级管理员"）。`analysis.md` 通常是 PM / 团队从内部诱因写的（"我们讲不清"、"规格交付卡住"），引用时必须**翻译为用户视角**，不能直接搬。

禁止以"PM 讲不清"、"团队内部规格交付卡住"、"我们要补一个 PRD"等团队内部诱因切入。研发评审 PRD 不接受元叙事——读者不关心 PM 的内部困扰，只关心产品要解决什么用户问题。

#### 4.2 解决方案（Proposed Solution）

1-3 句话，说明本次做什么来解决上述问题。来源：`analysis.md` 的已确认决策。

**写产品行为，不写文档自指**：必须写产品做什么（具体行为 / 规则 / 能力组合），承接 §4.1 的业务诉求推导出的设计原则集合。禁止任何对 PRD 自身的描述（"输出本 PRD 作为产品规格交付层文档"、"本 PRD 是规格交付层"、"本文档面向研发评审"）。

#### 4.3 成功指标（Success Criteria）

3-5 条 bullet，每条一句可验证结果。使用"所有……均……""无……时……返回……""……后立即……"等句式；不写"提升体验"等无法验证的描述。

**指标对象是产品能力**：必须是"**产品能力是否达成**"的可验证指标（如"所有指定入口无 download 权限的普通成员，按钮均置灰且无法触发"），不是"**文档质量是否达成**"的覆盖度指标。禁止写"用户能从本 PRD 找到答案"、"PM 能直接引用本 PRD §X 给出回答"等指向 PRD 文档自身的指标。

#### 4.4 方案价值（Impact）

3-5 条 bullet，格式：`动词短语：具体结果`。说明此方案对业务/运营/商业化的价值，回答"为什么值得做"。

**写业务价值，不写文档治理价值**：写产品对业务 / 用户 / 运营的实际价值（如"消除高价值内容外流风险"、"承载真实组织复杂度"、"保障租户自治"）。禁止写文档治理类价值（"降低规格交付沟通成本"、"沉淀业务沟通的稳态版本"、"建立产品规格的稳态版本"等指向 PRD 文档自身或 PM / 团队内部协作的价值）。

### 五、用户与场景

#### 5.1 用户角色

表格（角色名 | 描述 | 与本功能的关系）。来源：`analysis.md` 的用户与场景。

#### 5.2 用户故事

格式：`**Story N：** 作为 <角色>，我希望能 <动作>，以便 <价值>。`

每条 Story 必须加 `**Story N：**` 编号前缀（N 从 1 开始），编号须与七、验收标准中的 AC 分组编号严格对应。全程使用中文，不混用英文关键词。Story 数量 3-5 条，覆盖核心场景和关键边界。

#### 5.3 非目标

bullet list，每条一句。来源：`input.md` 的 Out of Scope 与 `analysis.md` 的非目标。无则写"暂无"。

### 六、功能需求

- **6.1 原型**：填写原型链接或版本号；如无则写"待补充"。
- **6.2 功能需求**：见下方"功能需求表格写法"。

### 七、验收标准（Acceptance Criteria）

为五、用户故事的每条 Story 提供一组验收条件，使用 checklist 格式。AC 组数以用户故事数为准，不以六、功能需求的表格行数为准：

```markdown
**Story [编号]：[故事名称简述]**
- [ ] [可验证的结果状态]
```

只写结果状态（"按钮置灰""返回 403"），不写操作步骤；每条 Story 须覆盖正常路径 + 关键边界/异常场景。

### 八、非功能性需求

如无则写"暂无"；有则按维度逐条写明要求。

**仅写产品级约束**（如"本模块依赖租户许可证授权"、"产品访问额度由许可证决定"、"权限校验不使用缓存，每次操作实时查询"）。禁止写文档级元约束（"本 PRD 是产品规格交付层"、"本 PRD 不修改既有规则"等指向 PRD 文档自身的描述）。

### 九、附件（如有）

直接输出内容（分类表 / 字段字典 / 枚举值等）；无此章节则不写。

## 功能需求表格写法（6.2 必须遵守）

**默认表格结构（6 列）：**

| 一级功能 | 二级功能 | 三级功能 | 优先级 | 使用角色 | 需求描述 |
| --- | --- | --- | --- | --- | --- |

**列结构调整：**

- 当章节标题已经写明一级功能（如 `#### 6.2.1 角色管理`），表格内**省略"一级功能"列**，避免每行复读章节标题。实际表头变为 4 列：`| 二级功能 | 三级功能 | 使用角色 | 需求描述 |`。
- 新需求场景保留"优先级"列；已发布功能的回溯型 PRD（close-req 阶段最常见）通常不需要优先级列。

**分级规则：**

- 一级功能：顶层业务模块（如"探索""发布""角色管理"）
- 二级功能：具体页面 / 子模块（如"Agent广场""发布超级员工""角色详情"）
- 三级功能：具体功能点（如"分类筛选""版本号及版本说明""基础信息""操作按钮"）；无三级时填 `/`

**层级划分原则：**

- 二级 / 三级层级**来自该功能模块的真实业务逻辑**，参考已有 task 文档 / module-spec 的章节结构（如 task 文档的 §1~§N 自然形成"角色列表 / 创建自定义角色 / 编辑自定义角色 / 角色详情……"的二级层级）。
- **不得在 PRD 阶段拍脑袋分组**——例如把"列表 / 详情"硬归到"查看"组下、把"创建 / 编辑 / 启用停用 / 删除"硬归到"定义"组下，这种强行分级会让二级功能逻辑做作。
- 同一二级功能下若三级功能 ≤ 2 个，可考虑不分级（避免强行分级）。
- 详情类功能本身常常是一个完整的二级功能（下面再分基础信息 / 操作按钮 / 权限配置 / 授权对象等三级），不要把"详情"和"列表"硬塞到同一二级里。

**与原型 / task 文档对齐：**

- 表格行内的字段、状态、按钮、提示文案必须以**原型实际行为**为准；task 文档原话与原型不一致时按原型写，并在该行末尾备注"以原型为准"。
- ❌ 错误示例：task 文档写"停用 Badge（若已停用）"——直接搬到 PRD 写"停用标识（若已停用）"。
- ✅ 正确示例：先打开原型确认实际行为是"启用 / 停用都展示状态标识"，PRD 写"角色状态标识（启用 / 停用）"。

**需求描述写法：**

- 写动作与结果，不写"支持/优化/提升体验"等泛词。
- 有规则/限制/默认值的，必须明确写出（使用"默认……""不允许……""如果……则……"等句式）。
- 同一格内多条规则用 `<br>` 换行分隔，不强制编号；能一句话说清的不要分条。飞书 docx 表格 cell 渲染 `<br>` 为真实换行（终端 markdown 渲染器看不出，以飞书渲染效果为准）。
- 表格行中含结构化参考数据（权限矩阵、字段清单、枚举值映射等）时，提取到九、附件，需求描述中注明"具体见附件 X"，不在单元格内展开。判断标准：同一格内需要超过 3 个字段/枚举值列举，且其他行可能引用同一份数据。

**相同内容单元格视觉规范：**

- 同一列下连续多行出现**相同内容**时，按"合并单元格"的视觉效果呈现——只在第一行展示该值，后续相同的行该列留空（在飞书 docx 中即合并单元格的效果）。
- 最典型场景：同一二级功能下有多个三级功能（如"角色列表"作为二级在相邻 5 行重复），第一行展示"角色列表"，第 2-5 行该列留空。
- 此规则对二级功能列、使用角色列同样适用——同一二级功能下多个三级功能的使用角色相同时，使用角色列也合并展示。
- 标准 markdown 不支持合并单元格语法；本规则首要约束的是**视觉效果**，PM 在飞书侧选中相邻相同 cell 手工合并即可，具体实现路径由项目工具链决定。

## 写作规则（全篇遵守）

### 总则

- 先结论，后规则；短句，动作先行。
- 同一信息只在一处主写；其他处引用功能名称，不重复展开。
- 术语统一使用三、名词解释中定义的名词，不另行解释。
- **PRD 自包含**：所有规则、约束、文案在当前位置直接展开。读者是研发评审，不让他们追跳转、查字典、读源码。

### 禁用清单（必须遵守）

#### 禁用代码 / 实现层引用

PRD 是产品规格层文档，不出现任何代码 / 路径 / 字段名 / 文档章节号。

| 类型 | ❌ 错误 | ✅ 正确 |
| --- | --- | --- |
| 代码常量名 | `TENANT_ADMIN`、`DEPARTMENT_ADMIN` | "租户管理员"、"部门管理员" |
| 文件名 / 路径 | `TenantRolesPage`、`prototypes/src/...` | 用产品功能名称指代页面 |
| 文档章节号 | `task-022 §1`、`V4.1 §十二.2` | PRD 自包含，不依赖外部章节号 |
| 数据库 / 字段名 | `enabled`、`createdBy`、`includeDescendants`、`permissions[]` | "角色启用状态"、"创建人字段"、"是否含子部门" |

#### 禁用 UI 实现术语

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 扁平区、摘要卡、Badge | 详情页顶部、摘要信息行、标识 / 标签 |
| 按钮置灰、按钮级隐藏、按钮不展示 | 按钮处于禁用状态、按钮在界面上不展示 |
| 统一渲染、悬浮、扁平化 | 按以下规则展示、鼠标悬停时 |

#### 禁用书面冷僻词

明示 / 暗中 / 链路 / 范畴 / 颗粒度 / 失控点 / 覆盖关系 / 隐式约定 / 落库——替换为日常的、研发评审场景下不需要查字典的中文词。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 明示"该角色为默认角色" | 提示"该角色为默认角色" |
| 字段映射 | 字段对应关系 |

#### 禁用中英混杂

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| review / 逐节 review | 核对 / 评审 / 逐节核对 |
| CRUD | 创建 / 编辑 / 删除 / 启用停用（列全） |
| scope | 管辖范围（首次定义后统一作为产品术语） |

#### 禁用技术 jargon

死锁 / 互锁 / 悬挂引用 / 鉴权 / 三件套——改成业务语言。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 悬挂引用 | 管辖范围里仍引用了不存在的部门 |
| 互锁保护陷入死锁 | 双方互相阻止对方操作的循环 |
| 不参与鉴权 | 不参与权限判断 |

#### 禁用数学化表达

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 严格小于 / 严格更大 / ⊊ / ⊆ | 完全包含在 X 之内（且至少少一个部门） |

#### 禁用元描述 / 自指

PRD 内不出现任何对自身的描述。这条已在 §4.1-§4.4 和 §8 各处明示，写作时全程注意以下措辞一律不写：

- "本 PRD 是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚……"
- "本 PRD 不修改既有规则"

#### 禁用兜底词

"等"、"之类的"、"相关的"——必须列全所有项。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| "编辑 / 启用停用 / 删除"等操作 | "编辑"、"启用 / 停用"、"删除"三个操作 |

#### 禁用主观词

"清晰区分"、"清晰展示"、"明显标识"——改为具体展示方式。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 默认角色清晰区分 | 默认角色行带"默认"标识 |

### UI 元素指代规则

涉及按钮 / 弹窗 / 提示行为的描述，必须明确：

- **按钮名**：用引号引出按钮上的具体文字（如"添加用户"按钮、"编辑基本信息"按钮）。
- **弹窗场景**：弹窗在哪个页面 / 哪个动作触发（如"移出归属确认弹窗"、"删除自定义角色二次确认弹窗"）。
- **具体提示文案**：用引号给出实际显示的文字（如鼠标悬停时提示"该角色已停用，不能新增分配"）。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 按钮处于禁用状态，提示原因 | "添加用户"按钮处于禁用状态，鼠标悬停时提示"该角色已停用，不能新增分配" |
| 弹窗中提示用户将失去权限 | 停用前需二次确认，确认弹窗中提示"已分配该角色的用户将立即失去该角色带来的权限" |

### cross-reference 处理规则

- 禁止用"详见 §6.X" / "见 §X.Y" 让读者跳转。
- 关键规则的简要说明应直接写在当前位置；如果同一规则在多处出现，可在多处都简要描述（约 1-2 句）。
- "详见 §X" **仅在引用本 PRD 之外的文档**（如设计规范 DESIGN.md）时使用。

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 添加 / 移除受自提权防护与管理员保护规则约束（详见 §6.4） | 添加用户时受自提权防护约束：操作者只能分配权限点不超过自身的角色，且目标管辖范围不能超出自身管辖范围 |

### 抽象动词使用规则

以下动词使用时必须搭配**具体效果**，不能孤立出现：

- **"更新 X 定义"** → 必须写"更新后，X 对持有它的对象立即按新规则生效"
- **"保存后生效"** → 必须写生效后什么变化、对谁生效
- **"立即更新"** → 必须写更新的具体内容
- **"执行 X 操作"** → 必须写操作的具体步骤或结果

| ❌ 错误 | ✅ 正确 |
| --- | --- |
| 保存后立即更新角色定义 | 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权 |

## Few-shots（来自真实 PRD 案例）

> 以下示例来自万智平台项目，仅用于说明格式与写作风格。跨项目使用本 skill 时，可替换为当前项目的真实案例。

**摘要示例（权限控制场景）：**

> 本 PRD 旨在明确万智平台「导出/下载/分享」权限控制收口的功能需求，覆盖历史记录、会话文件、Agent 产物、知识库/问答库、高代码五类入口及统一下载网关与审计日志建设，计划在 V2.3 迭代交付 P0 部分。

**摘要示例（探索与发布场景）：**

> 本 PRD 旨在明确万智平台「探索」功能的需求，包括 Agent 广场与 Agent 商店的聚合展示、体验与复制能力，以及超级员工和工作流发布到探索的完整流程，计划在 V2.3 迭代交付。

**4.1 问题陈述示例（权限控制场景）：**

> 当前平台在历史记录、Agent 产物、知识库/问答库、高代码等多处功能区均存在文件下载、内容导出或分享链接入口，但各入口的权限校验逻辑各自为政，无统一标准。普通成员可不受限制地下载全平台内容，高价值内容（如 AI 生成的 PPT/Excel、知识库文件、高代码工程包）存在大规模外流风险。
>
> 部分下载入口（尤其是高代码文件）使用前端直链或对象存储直链下载，权限控制完全依赖前端判断，后端无强制兜底。只要获取到 URL，任何人均可绕过前端按钮的状态控制完成下载。

**4.1 问题陈述示例（探索与发布场景）：**

> 当前平台的超级员工广场与工作流广场相互独立，用户需要在两个入口分别查找应用，无法一站式搜索全量内容；对于平台管理者来说，分散的入口也增加了维护与管理成本。
>
> 超级员工缺乏公开的发布渠道，用户自行配置的超级员工无法分享给组织内其他成员使用，导致优质应用停留在个人工作区，无法产生组织层面的复用价值。

**4.2 解决方案示例（权限控制场景）：**

> 新建统一下载网关作为唯一文件下载链路，所有入口接入 RBAC 动作权限校验（download/share），并全量写入审计日志。普通成员默认禁止下载与分享，管理员可在配置页调整角色权限。

**4.2 解决方案示例（探索与发布场景）：**

> 新增独立「探索」页面，聚合展示所有已发布的超级员工和工作流；在发布流程中增加「发布到探索」选项并支持按二级分类标签归档；在超级员工和工作流页面加入已发布/未发布状态标识。

**4.3 成功指标示例：**

> - 所有指定入口无 `download`/`share` 权限的普通成员，相关按钮均置灰且无法触发下载/分享。
> - 高代码版本包通过直接 URL 访问返回 HTTP 403（后端强制拦截，不依赖前端）。
> - 每次下载/导出/分享操作（含被拒绝的）均产生完整审计日志，必须字段无缺失。
> - 管理员变更"普通成员"角色权限后，用户下次操作立即生效，无需重新登录。

**4.4 方案价值示例：**

> - 消除高价值内容外流风险：普通成员默认无法下载/分享任何内容，高价值产物（AI PPT、知识库文件、高代码工程包）不再有外流漏洞。
> - 建立企业级审计能力：所有下载/导出/分享操作（含被拒绝）均可追溯，覆盖企业合规要求。
> - 为商业化分层提供能力基础：download/share 权限可按角色/套餐灵活配置，Max 版本差异化下载能力由此可落地。

**5.1 用户角色示例：**

| 角色名 | 描述 | 与本功能的关系 |
| --- | --- | --- |
| 普通成员 | 组织内一般成员，无特殊权限 | 默认无 download/share 权限，操作受控 |
| 组织管理员 | 负责管理组织成员与权限配置 | 可为"普通成员"角色开关 download/share 权限 |
| 租户管理员 | 平台最高权限管理员 | 拥有全量权限，可审计所有操作日志 |

**5.3 非目标示例：**

**七、验收标准示例：**

## 阶段 6 边界：交付规格化

- 允许产出：`$ACTIVE_REQ_DIR/prd.md`
- 允许动作：基于定稿原型 + brief / analysis / solution / 已关闭 task 生成 req 级字段级 PRD
- 禁止顺手推进：不要在写 PRD 的同时反向改范围边界；不要顺手改项目主 PRD（`docs/prd.md`）——那是 `/project-prd-update` 的职责
- 退出条件：PRD 经过 PM 质检并定稿；控制权交回 `/close-req`
