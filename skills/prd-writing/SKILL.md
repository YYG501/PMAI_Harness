# PRD Writing

## When To Use

- 所有模块都已完成并验收，最终原型已经基本稳定，准备输出最终 `prd.md`。
- 需要把 `analysis.md`、`solution.md`（如有）、`docs/modules/*.md`、已确认原型收敛成一份可交付、可复核的 `prd.md`。
- 这一步是阶段 6：交付规格化，不替代实现前的模块工作规格。

## Required Inputs

1. `docs/input.md`
2. `docs/analysis.md`
3. （可选）`docs/solution.md` — 如有，读取对应模块的 `7.2 各模块功能说明` 章节，吸收原型中最终确认的字段取舍和功能边界
4. `docs/modules/*.md`（至少读取当前项目已交付模块对应的规格）
5. （可选）`docs/prd_input.md`（补充说明，如有）
6. （可选）`docs/glossary.md`（名词表，如有）
7. （可选）`prototypes/<项目名>/` 原型代码 — 原型已定稿时，读取页面代码获取最终的字段布局、交互细节、组件用法，作为功能需求表格的权威来源

## Workflow

1. 读取 `docs/analysis.md`、`docs/modules/*.md`，以及 `docs/solution.md` 对应模块章节（如有），拆出"已确认决策"和"待确认决策"；有待确认项则先编号提问，确认后再写 PRD。
2. 如果 `prototypes/<项目名>/` 存在已定稿的原型代码，读取相关页面文件，提取最终确认的字段、交互方式、组件选择等细节，作为功能需求表格的依据。
3. 按下方"PRD 结构"生成完整 `docs/prd.md`，语言风格对齐下方"写作规则"与"few-shots"。
4. 在对话中请求用户确认 PRD；确认后写入文件，并提醒执行 `prd:` 提交。

## PRD 结构（必须完整输出）

### 摘要

1-3 句话概述本 PRD 旨在说明的功能范围与所属迭代，放在文档最顶部，不编号。

### 一、文档版本信息

| 字段 | 值 |
| --- | --- |
| 文档版本号 | V |
| 创建日期 | |
| 编写人 | |
| 产品版本号 | V |
| 对应原型版本号 | V（如无则留空） |

### 二、变更日志

表格：时间 / 版本号 / 对应原型版本 / 变更人 / 主要变更内容

### 三、名词解释

表格（术语 / 缩略词 | 说明）；无则写"无"。

### 四、需求分析

#### 4.1 问题陈述（Problem Statement）

自然语言段落，每段写一个现象及其影响；直接来源于 `analysis.md`，保留关键原话。

#### 4.2 解决方案（Proposed Solution）

1-3 句话，说明本次做什么来解决上述问题。来源：`analysis.md` 的已确认决策。

#### 4.3 成功指标（Success Criteria）

3-5 条 bullet，每条一句可验证结果。使用"所有……均……""无……时……返回……""……后立即……"等句式；不写"提升体验"等无法验证的描述。

#### 4.4 方案价值（Impact）

3-5 条 bullet，格式：`动词短语：具体结果`。说明此方案对业务/运营/商业化的价值，回答"为什么值得做"。

### 五、用户与场景

#### 5.1 用户角色

表格（角色名 | 描述 | 与本功能的关系）。来源：`analysis.md` 的用户与场景。

#### 5.2 用户故事

格式：`**Story N：** 作为 <角色>，我希望能 <动作>，以便 <价值>。`

每条 Story 必须加 `**Story N：**` 编号前缀（N 从 1 开始），编号须与七、验收标准中的 AC 分组编号严格对应。全程使用中文，不混用英文关键词。Story 数量 3-5 条，覆盖核心场景和关键边界。

#### 5.3 非目标

bullet list，每条一句。来源：`input.md` 的 Out of Scope 与 `analysis.md` 的非目标。无则写"暂无"。

### 六、功能需求

- **6.1 原型**：填写原型链接或版本号；如无则写"待补充"。
- **6.2 功能需求**：见下方"功能需求表格写法"。

### 七、验收标准（Acceptance Criteria）

为五、用户故事的每条 Story 提供一组验收条件，使用 checklist 格式。AC 组数以用户故事数为准，不以六、功能需求的表格行数为准：

```markdown
**Story [编号]：[故事名称简述]**
- [ ] [可验证的结果状态]
```

只写结果状态（"按钮置灰""返回 403"），不写操作步骤；每条 Story 须覆盖正常路径 + 关键边界/异常场景。

### 八、非功能性需求

如无则写"暂无"；有则按维度逐条写明要求。

### 九、附件（如有）

直接输出内容（分类表 / 字段字典 / 枚举值等）；无此章节则不写。

## 功能需求表格写法（6.2 必须遵守）

**表格结构：**

| 一级功能 | 二级功能 | 三级功能 | 优先级 | 使用角色 | 需求描述 |
| --- | --- | --- | --- | --- | --- |

**分级规则：**

- 一级功能：顶层业务模块（如"探索""发布""角色管理"）
- 二级功能：具体页面 / 子模块（如"Agent广场""发布超级员工"）
- 三级功能：具体功能点（如"分类筛选""版本号及版本说明"）；无三级时填 `/`

**需求描述写法：**

- 写动作与结果，不写"支持/优化/提升体验"等泛词
- 有规则/限制/默认值的，必须明确写出（使用"默认……""不允许……""如果……则……"等句式）
- 同一格内多条规则用 `<br>` 换行分隔，不强制编号；能一句话说清的不要分条
- 表格行中含结构化参考数据（权限矩阵、字段清单、枚举值映射等）时，提取到九、附件，需求描述中注明"具体见附件 X"，不在单元格内展开。判断标准：同一格内需要超过 3 个字段/枚举值列举，且其他行可能引用同一份数据

---

## 写作规则（全篇遵守）

- 先结论，后规则；短句，动作先行。
- 禁止写"支持/优化/提升体验"，必须写明"怎么做 + 规则/限制"。
- 同一信息只在一处主写；其他处引用功能名称，不重复展开。
- 术语统一使用三、名词解释中定义的名词，不另行解释。

## Few-shots（来自真实 PRD 案例）

> 以下示例来自万智平台项目，仅用于说明格式与写作风格。跨项目使用本 skill 时，可替换为当前项目的真实案例。

**摘要示例（权限控制场景）：**

> 本 PRD 旨在明确万智平台「导出/下载/分享」权限控制收口的功能需求，覆盖历史记录、会话文件、Agent 产物、知识库/问答库、高代码五类入口及统一下载网关与审计日志建设，计划在 V2.3 迭代交付 P0 部分。

**摘要示例（探索与发布场景）：**

> 本 PRD 旨在明确万智平台「探索」功能的需求，包括 Agent 广场与 Agent 商店的聚合展示、体验与复制能力，以及超级员工和工作流发布到探索的完整流程，计划在 V2.3 迭代交付。

**4.1 问题陈述示例（权限控制场景）：**

> 当前平台在历史记录、Agent 产物、知识库/问答库、高代码等多处功能区均存在文件下载、内容导出或分享链接入口，但各入口的权限校验逻辑各自为政，无统一标准。普通成员可不受限制地下载全平台内容，高价值内容（如 AI 生成的 PPT/Excel、知识库文件、高代码工程包）存在大规模外流风险。
>
> 部分下载入口（尤其是高代码文件）使用前端直链或对象存储直链下载，权限控制完全依赖前端判断，后端无强制兜底。只要获取到 URL，任何人均可绕过前端按钮的状态控制完成下载。

**4.1 问题陈述示例（探索与发布场景）：**

> 当前平台的超级员工广场与工作流广场相互独立，用户需要在两个入口分别查找应用，无法一站式搜索全量内容；对于平台管理者来说，分散的入口也增加了维护与管理成本。
>
> 超级员工缺乏公开的发布渠道，用户自行配置的超级员工无法分享给组织内其他成员使用，导致优质应用停留在个人工作区，无法产生组织层面的复用价值。

**4.2 解决方案示例（权限控制场景）：**

> 新建统一下载网关作为唯一文件下载链路，所有入口接入 RBAC 动作权限校验（download/share），并全量写入审计日志。普通成员默认禁止下载与分享，管理员可在配置页调整角色权限。

**4.2 解决方案示例（探索与发布场景）：**

> 新增独立「探索」页面，聚合展示所有已发布的超级员工和工作流；在发布流程中增加「发布到探索」选项并支持按二级分类标签归档；在超级员工和工作流页面加入已发布/未发布状态标识。

**4.3 成功指标示例：**

> - 所有指定入口无 `download`/`share` 权限的普通成员，相关按钮均置灰且无法触发下载/分享。
> - 高代码版本包通过直接 URL 访问返回 HTTP 403（后端强制拦截，不依赖前端）。
> - 每次下载/导出/分享操作（含被拒绝的）均产生完整审计日志，必须字段无缺失。
> - 管理员变更"普通成员"角色权限后，用户下次操作立即生效，无需重新登录。

**4.4 方案价值示例：**

> - 消除高价值内容外流风险：普通成员默认无法下载/分享任何内容，高价值产物（AI PPT、知识库文件、高代码工程包）不再有外流漏洞。
> - 建立企业级审计能力：所有下载/导出/分享操作（含被拒绝）均可追溯，覆盖企业合规要求。
> - 为商业化分层提供能力基础：download/share 权限可按角色/套餐灵活配置，Max 版本差异化下载能力由此可落地。

**5.1 用户角色示例：**

| 角色名 | 描述 | 与本功能的关系 |
| --- | --- | --- |
| 普通成员 | 组织内一般成员，无特殊权限 | 默认无 download/share 权限，操作受控 |
| 组织管理员 | 负责管理组织成员与权限配置 | 可为"普通成员"角色开关 download/share 权限 |
| 租户管理员 | 平台最高权限管理员 | 拥有全量权限，可审计所有操作日志 |

**5.2 用户故事示例：**

> **Story 1：** 作为普通成员，我希望能在无下载权限时看到清晰的按钮禁用状态和提示文案，以便我知道应联系管理员而不是面对一个无响应的按钮。
>
> **Story 2：** 作为组织管理员，我希望能在一个集中的配置页为"普通成员"角色开关下载和分享权限，以便我能在不修改个人用户的情况下统一管控内容外带策略。

**5.3 非目标示例：**

> - 本期不建设审计日志查询 UI，仅保存数据，查询界面后续单独建设。
> - 预览操作不纳入权限控制范围，所有用户均可预览。
> - 不对资源创建者设置豁免权，创建者与普通成员执行相同权限策略。
> - 不改造现有文件生成机制，改造范围仅限于下载/导出/分享入口。

**七、验收标准示例：**

> **Story 1：无权限时下载按钮行为**
>
> - [ ] 无 `download` 权限的普通成员，所有指定入口下载/导出按钮置灰
> - [ ] 点击置灰按钮后弹出提示"无下载权限，请联系管理员"
> - [ ] 预览按钮不受影响，所有用户均可正常使用
>
> **Story 2：管理员权限配置**
>
> - [ ] 角色权限配置页展示 download 和 share 两个独立开关
> - [ ] 关闭权限后，普通成员下次操作（无需重新登录）即生效
> - [ ] 资源创建者不享有豁免权，策略与普通成员一致

**八、非功能性需求示例：**

> - **权限实时性**：权限校验不使用缓存，每次操作实时查询 RBAC；变更后立即生效。
> - **可用性**：统一下载网关可用性 ≥ 99.9%（与现有文件服务 SLA 对齐）。
> - **安全性**：跨租户资源访问返回 403（防 IDOR）；高代码直链访问返回 403；签名 URL 有效期不超过 15 分钟。
> - **向后兼容**：改造不影响现有文件生成机制，不影响运行中任务逻辑。
> - **可观测性**：前端统一埋点（曝光/点击/阻断事件，含 reason_code 与来源页面）；审计日志可通过 request_id 追溯单次操作。

## 阶段 6 边界：交付规格化

- 允许产出：`docs/prd.md`
- 允许动作：基于定稿原型与分析文档生成字段级 PRD
- 禁止顺手推进：不要在写 PRD 的同时反向改范围边界
- 退出条件：PRD 经过 PM 质检并定稿

## 阶段 6 结束模板

```md
## 阶段 6 完成 — [项目标题]

**产出：** `docs/prd.md`
**未做：** 未继续扩大范围，未修改已定稿的 analysis.md / solution.md / module-spec

**当前状态：** PRD 初稿完成，可选做质检或直接定稿。

**建议：** 选 A，质检成本低，能在定稿前发现遗漏的边界情况。

A) 做 PRD 质检——用质检 prompt 过一遍，发现边界和矛盾
B) 直接定稿——PRD 已符合预期，不需要质检
C) 打回修订——有需要修改的地方，先改再定稿
```

```
读取 docs/prd.md 和 docs/analysis.md，然后找出：

以编号 list 格式输出问题，每条附上建议修改方向。

```
