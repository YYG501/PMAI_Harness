# /mock

> **这是什么**：把讨论里定下来的"这张卡/这一页放什么、谁看、信息怎么分块"画成**几版能看的草图**，摊在 PM 面前并排挑——挑定哪版方向，再回去把规格写定。**用看得见的草图代替规格里那段 ASCII 线框**，省掉"PM 看规格里的方框想象不出来→建出来才说不对→返工"。
> **和 /design 的关系**：`/design` 把信息设计讨论清楚后，到"该让 PM 看看长什么样"那一步**调本 skill**；PM 挑定方向，`/design` 接着把规格写定（规格里只留文字定义 + 指一句"长什么样见 mock 看版"，不再画线框）。
> **和 /build 的关系**：两码事。`/mock` 出的是**便宜的静态草图**（HTML 比稿、不接数据、不进主原型），只为挑方向；`/build` 才是在 `prototype/` 主原型里**真建**那一份能跑的实现。挑定方向走 `/build`（大需求）或直接在主原型里改（小改）。
> **不动主原型**：`mocks/` 是摊在桌上比来比去的草图集，和 `prototype/`（跑着的那一份主原型）是分开的两个家。本 skill 只写 `mocks/`，不碰 `prototype/`。

## When To Use

- 信息设计讨论已经把"这张卡/这一页放什么、谁看、信息怎么分块"理清了，**该让 PM 用眼睛挑一版方向**——视觉/布局上有岔路（左导航还是顶 tab、信息上卡面还是进抽屉、几栏排版），文字描述掰不清，PM 想看着挑。
- `/design` 流程走到第 3 步（信息设计结论已出、规格还没定稿）时由它调本 skill。
- PM 手动 `/mock "<想看哪块的草图>"`：随时想给某块界面出几版草图比一比。
- **不适用**：
  - 信息还没理清就想看图 → 先回 `/design` 把"放什么、谁看、怎么分块"讨论清楚，再来出草图（没想清楚出的草图是瞎画）。
  - 要真建那一份能跑的实现 → `/build`（大需求）或直接在 `prototype/` 改（小改）。
  - 纯文字微调、没有视觉岔路 → 不用出草图，直接定稿规格。

## Preamble

```bash
source "$HOME/.pmai/scripts/skill-preamble.sh"
echo "SKILL: mock"
```

本 skill 从**主仓 main** 触发（动的是探索草图，不进任何 req worktree）。`mocks/` 在 main 上随时可写（属探索草稿、`check-branch.sh` 已豁免），所以**不开分支、不开 worktree、不拉 PM 进工作区**。

## 借 gstack /design-shotgun

一次出多个变体并排让 PM 挑，是 gstack `/design-shotgun` 趟熟的做法。本 skill **借它的做法、不抄它的实现**：

- **能调就调**：gstack 装了、`/design-shotgun` 可用时，**直接用 Skill 工具调它**生成多版视觉草图（接受它写的 HTML / 看版、跟随它升级，不解析不重写）。调它时把讨论结论喂成 design brief（见步骤 2）。
- **调不动就降级**：gstack 没装 / 调用失败 → AI 自己用 `frontend-design` 技能（或直接写静态 HTML）出几版草图，照样并排给 PM 挑。多变体并排是目的，design-shotgun 只是其中一条好路子。
- **挑定后统一收口**：不管哪条路出的草图，**都落进框架的 `mocks/` + 清单 + 看版**（步骤 3），别留在 gstack 自己的 `~/.gstack/...` 里——那会"探过的 mock 找不回"。

## Workflow

> **PM 视图纪律**：跟 PM 说话**禁出现** `manifest` / `featured` / `variant` / `design brief` / `信息模型` / `三身份` / `派生 4 环` 等内部词。用大白话：「几版草图」「挑定方向」「留在看版里翻得到」。AskUserQuestion 按 `_shared/pm-view/askuser-rules.md` 走。

### 步骤 1：拿讨论结论 + 锁定要画哪块

- **/design 调进来**：讨论结论已在手（这张卡/这一页谁看、放什么、信息怎么分块、有哪些视觉岔路）——直接用，跳到步骤 2。
- **PM 手动调**：用**一句话**问要给哪块界面出草图、有哪些拿不准的方向；拿到回答再继续。讨论结论散在模块 `discussion.md` / `decisions.md` 里的，顺手读进来对齐。

**没想清楚就别画**：如果"放什么、谁看、怎么分块"还没定，停下来，告诉 PM 一句「这块还没想清楚，先把放什么、谁看理一下再出草图」，回 `/design`。瞎画草图比不画更费事。

### 步骤 2：把讨论结论变成几版方向

从讨论结论里挑出**真正的视觉/布局岔路**，定**几个变体方向**（默认 2-3 版；重要界面到 4-5 版）。每版围绕一条想试的方向，比如：

- 信息怎么排：左导航 vs 顶 tab vs 单栏长滚动；
- 信息密度：全上卡面 vs 主信息上卡面、细节进抽屉；
- 一行是什么单元：按对象一行 vs 按动作一行；
- 状态/空态怎么呈现。

把这些方向连同"谁看、放什么字段、哪些信息一组"整理成一段交代清楚的说明，喂给生成器（design-shotgun 的 brief 或 AI 自己画的依据）。**变体之间要真不一样**（不同方向，不是同一版换个颜色），PM 才挑得出取舍。

> **边界靠判断、不机械**：出几版、围绕哪些岔路，是 AI 临场看讨论结论判，不是"每次必出 N 版"。没几条真岔路的简单界面，出 1-2 版意思一下就够。

### 步骤 3：生成草图 + 落进看版

1. **生成几版草图**（走上面"借 gstack"那条：能调 `/design-shotgun` 就调，调不动就 AI 自己画静态 HTML）。

2. **落进 `mocks/`**：每版草图存成 `mocks/` 下一个文件/目录（如 `<界面>-a/index.html`、`<界面>-b/index.html`）。**所有生成的都留下、都进版本库——包括待会儿被否掉的那几版**（否掉不等于删掉，留着下次还能翻回来看）。

3. **登记进清单**：往 `mocks/manifest.json` 的 `variants` 数组**每版追加一条对象**。**key 必须英文**（`gen-mock-board.py` 只认英文 key，中文 key 会被静默渲染成"—"），值可中文：

   ```json
   { "path": "<界面>-a/index.html", "explores": "左导航排版",
     "good_parts": "导航始终可见、层级清楚", "status": "活跃",
     "round": "<本轮/模块标识>", "featured": false, "retired_note": "" }
   ```

   字段含义见 `templates/mocks-manifest.json.tmpl` 的 `_fields`；`status` 枚举 `活跃` / `待合并` / `已退役`（这一步新出的都填 `活跃`）。

4. **刷新看版**：
   ```bash
   python3 "$PMAI_HOME/scripts/gen-mock-board.py" "$REPO_ROOT"
   ```
   读 `mocks/manifest.json`、重生成 `mocks/index.html`（看版导航页，**纯生成物、别手改**）。

5. **打开给 PM 看**：把看版 `mocks/index.html`（或各草图）打开给 PM——几版并排，点开能看每一版。

### 步骤 4：PM 挑定方向

PM 挑哪版/哪些块好。用 AskUserQuestion 让 PM 选（每版一个选项 + 一句话说清这版试的方向和取舍）。允许的结果：

- **挑定一版**：那版标 `featured: true`（看版里会突出）。
- **挑某几版的某几块拼**：记下"取 A 的导航 + B 的抽屉"这类结论，作为回 `/design` 写规格的依据。
- **都不行 / 想再试**：按 PM 反馈调方向，回步骤 2 再出一轮（新一轮的 `round` 标清楚，老的留着不删）。

挑定后把 `featured` / 必要的 `status` 改进 `manifest.json`，重跑 `gen-mock-board.py` 刷新看版。

> **挑定 ≠ 定稿规格**：本 skill 只负责"PM 用眼睛挑定了方向"。规格怎么写、为什么这么定，是回 `/design` 做的事——规格里写文字定义 + 指一句"长什么样见 mock 看版第 N 版"，不再画 ASCII 线框。

### 步骤 5：交回 /design（或给手动 PM 一个去向）

- **/design 调进来的**：把"挑定了哪版方向 / 哪几块怎么拼"作为结论交回 `/design`，它接着把规格写定。
- **PM 手动调的**：告诉 PM 草图都留在看版里翻得到、挑定的那版已标出，给一个 Next Up：方向定了就 `/design` 把这块写进规格（小改）或 `/build` 去真建（大需求）。

> **草图怎么收尾不归本 skill**："探了哪几版、为何选这版"的最终收口在沉淀那一步（`/close` 或 `/deposit` 的探索变体归位）——挑定的标 `featured`、并进主原型的标 `已退役` 留存。本 skill 这一步只登记不删、不做最终收口。

## Rules

- **只动 `mocks/`、不碰 `prototype/`**：草图是静态比稿的家，主原型是另一回事。本 skill 不往主原型写任何东西。
- **不开 worktree、不开分支、不拉 PM 进工作区**：在 main 上直接出草图（`mocks/` 探索草稿豁免）。这是它"轻"的根本，别给它套 build 的隔离仪式。
- **草图是便宜的静态比稿**：HTML 线框/页面即可，不接真数据、不搭真组件树、不追求能跑——只为让 PM 用眼睛挑方向。要真能跑的实现是 `/build` 的事。
- **多变体要真不一样**：变体之间是不同方向（导航/密度/分块），不是同一版改色。同质的几版让 PM 无从取舍。
- **生成的都留下、否掉≠删掉**：所有草图都进版本库、进清单；没挑中的留在看版折叠区、翻得到。治"上次那版找不回"。
- **`manifest.json` 是唯一真相源，`index.html` 是纯生成物**：永远改清单、重生成看版，别手改看版页。
- **清单 key 必须英文**：`path` / `explores` / `good_parts` / `status` / `round` / `featured` / `retired_note`（中文 key 会被 `gen-mock-board.py` 静默丢成"—"）。
- **借 design-shotgun 不抄**：能调就调它的 skill、接受它的产物；调不动就降级 AI 自己画。无论哪条路，草图统一收进框架 `mocks/`，不留在 gstack 自己的目录里。
- **没想清楚不画**：信息设计（放什么、谁看、怎么分块）没定就回 `/design`，别瞎画草图凑数。

### PM-facing 输出禁词

跟 PM 对话 / AskUser 文案 / Next Up 块里**禁出现**：`manifest` / `featured` / `variant` / `design brief` / `信息模型` / `派生 4 环` / `三身份` / `worktree` / `brief`。用 PM 视角的话替：

| 禁词 | PM 视角替代 |
|---|---|
| `manifest` / `index.html` 看版 | 「草图清单」/「看版」（翻得到的那个页） |
| `featured` | 「挑定的那版」/「标出来了」 |
| `variant` / 多变体 | 「几版草图」/「不同方向」 |
| `design brief` / `brief` | 「交代清楚要画什么」 |
| `信息模型` / `派生 4 环` / `三身份` | 「放什么、谁看、信息怎么来」 |
| `worktree` / 开分支 | 砍掉（本 skill 本就不开） |
