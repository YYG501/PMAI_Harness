## 📌 方案摘要 示例

> PM 在向研发讲 V4.1 身份与权限模块规格时讲不清楚——根因是缺少业务意图层文档（现有 11 份 docs 全是工程视角）。本方案新增一份「业务意图映射导览」作为与总设计并列的入口文档，并对现有 12 份 docs 增加 cross-link 指向导览。本 req 不动 V4.1 模型本身、不改原型代码（后续视使用反馈再决定是否做 UI 嵌入）。

## 🎯 关键产品决策 示例

| # | 决策项 | 当前选择 | 备选方案 |
|---|---|---|---|
| 1 | 在「身份权限模块」中如何弥合 PM 与现有 docs 之间的叙事层缺口 | 新增一份「业务意图映射导览」与 V4.1 总设计并列；同时对现有 12 份 docs 增 cross-link 指向导览 | 重写 V4.1 总设计为 v4.2（成本高、风险大）；只改文档不加导览（讲不通的根因仍在）|
| 2 | 「业务意图映射导览」的反直觉点解释深度 | 带案例版（每个反直觉点配虚构人名 + 真实职能 + 真实业务场景）| 仅一句话定义版（PM 讲业务时仍需现编案例）|
| 3 | 现有 docs 的 cross-link 增补范围 | 一次修 12 份全部（2 总设计 + 9 task 文档 + 1 INDEX）| 只修核心 3 份（漏修部分会让 admin 进文档时找不到导览入口）|

> 决策的共同理由：PM 反馈表明业务意图层完全缺失，根因不是现有 docs 写得不对，而是没有这一层；新增导览 + cross-link 是最小侵入解决方案，避免重写既有规格带来的迁移成本。

## 🧩 模块职责与边界 示例

### 模块 · 部门 + 用户 + 角色设计

本模块负责身份与权限的总体规格。本 req 在该模块下新增一个文档（intent-mapping-guide），承担"业务讲述者视角"的入口职责，与 V4.1 总设计形成两层入口：

- 总设计：模型定义层（数据结构 / 规则 / 工程落地），主读者是研发实现者
- 导览：业务意图层（从"某人想做某事"出发，映射到模型），主读者是 PM、产品经理、需求分析师

模块边界保持不变：本 req 不改 V4.1 模型核心命题、不改任何 task 文档的功能清单、不改 INDEX 之外的目录组织。

## 写作要点

写 solution.md 时，按上面这个简短风格走：

- **决策项必须明确"在「具体页面 / 区域」对什么对象做什么决策"**，不要只写一个泛泛标题
- **交付物用产品视角的业务名**（"业务意图映射导览"，不要写"intent-mapping-guide.md 文档实现"）
- **数据模型用业务语言**（"许可证状态 5 种" / "部门额度账本闭环"），不写 TS 类型 / Record / discriminated union
- **风险用正向句式**（"X 场景下可能 Y"），反向约束（"禁止 X" / "不允许 Y"）一律移到 `solution.engineering.md` §6
- **验收标准是 PM 走查清单**（不是 grep 校验、单测断言、覆盖率阈值——这些进 `solution.engineering.md` §10 工程层验收清单）
