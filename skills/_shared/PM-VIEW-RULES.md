# PM 视图通用规则（PM-VIEW-RULES）

> 适用范围：所有 PM 视角的 stage 文档 — `brief.md` / `analysis.md` / `solution.md` / `task-plan.md` / `tasks/task-NNN-*.md` / `prd.md`。
>
> 本文件是 **单一真相源**。下列 skill 都引用本文件，不在 skill 内部独立维护：
> `new-req` · `req-analysis` · `req-solution` · `task-plan` · `task-spec` · `prd-writing`
>
> AI 在生成、修改任何上述文档前，先读完本文件。

---

## 一、三层信息分层（核心结构原则）

每份文档都按三层组织内容。**不允许**把工程实现细节放到 PM 视图层。

### 1. PM 视图（首屏可见）
PM 创建 / 审核 / 验收时直接看的内容。回答 PM 关心的问题：
- 这个东西在做什么？
- 关键产品决策是什么？
- 用户能做什么 / 看到什么？
- 哪些会被改 / 哪些不动？
- 怎么验收？

### 2. 工程合同（PM 默认折叠 / 拆文件）
给执行 agent 的实现规范。回答工程问题：
- 启动前必读哪些文件？
- 实现时用哪些函数 / 组件 / 字段？
- 反向禁止哪些做法？
- review skill（plan-eng-review / plan-design-review）沉淀的细化决策？

### 3. 历史档案（验收时按需查）
版本演进留痕。验收时只看最新一轮：
- 执行日志
- 文档偏差
- 自审记录
- PM 反馈

---

## 二、拆文件约定

`solution.md` / `task-plan.md` / `task-NNN-*.md` 三类文档拆成两个文件：

| 文件 | 内容 | 命名 |
|---|---|---|
| 主文件（PM 视图）| 一、PM 视图层 + 三、历史档案 | 原名不变（`solution.md` / `task-001-xxx.md`） |
| 工程合同 | 二、工程合同层 | `<原名>.engineering.md`（同目录、同 slug）|

**约定**：
- 主文件路径不变，所有现有引用（git / req-stage-gate / lark publish）不需要改
- 主文件底部加一行：`> 工程实现细节见 <slug>.engineering.md`
- 两文件成对出现 — `task-transition.py` / `req-transition.py` 校验，缺工程合同 = error
- agent 启动时由 `task-execute` 显式 inject 工程合同内容到 prompt，不依赖 PM 主动打开

`brief.md` / `analysis.md` / `prd.md` **不拆文件**（这三类本身没有工程合同层，PM 视图即全部）。

## 三、PM 视图写作规则（硬约束）

### 3.1 每个名词必须明确指代

PM 视图里出现的每个名词，必须能让读者一眼知道**指代哪个对象 / 哪个页面 / 哪个区域 / 谁的属性**，不允许模糊指代。

| 模糊（❌）| 明确（✅）|
|---|---|
| 树最上面那一层 | 「产品详情页 - Tab 1 额度分配视图」的树形列表，最顶层节点 |
| 状态 Badge | 许可证状态 Badge |
| 状态列 | 许可证状态列 |
| 弹窗 | 「分配额度弹窗」 |
| 列表 | 「产品访问管理 - 产品列表页」的产品列表 |
| 失效证 | 状态为已失效（含已过期 / 已停用 / 已吊销 / 未生效）的许可证 |
| admin | 租户管理员 / 部门管理员（仅在其权限范围内的部门）|
| Tab 2 不动 | 「产品详情页 - Tab 2 用户开通（task-004 实现）」保持现状不动 |

**自检**：单字"状态"、"列表"、"树"、"弹窗"、"操作"、"按钮"、"用户"出现时，前面必须有完整指代前缀。

### 3.2 只描述功能行为

PM 视图回答：
- 系统应该提供什么
- 用户能做什么
- 业务规则是什么
- 数据字段之间的关系是什么
- 角色权限是什么
- 异常路径如何呈现

PM 视图**不**回答：

| 类别 | 不出现 | 替换为 |
|---|---|---|
| 像素值 | 24px / 420px / w-14 / py-5 | 移到工程合同 |
| 颜色码 | #C9CDD4 / #FFA39E | 移到工程合同 |
| 文字色名 | "红色文字" / "黄色警告" | "视觉高亮" / "视觉弱化" / "警告信息"（语义保留）|
| Emoji 视觉 | 🟡🔴⚫ | 移到工程合同；状态文案保留（未生效 / 已过期）|
| 反向约束 | "禁止 X" / "不允许 Y" | 移到工程合同；正向改写"系统不保留 Y"|
| 设计意图解释 | "（避免双重计数）" / "（防止角色爆炸）" | 移到「关键产品决策」的"共同理由"行 |
| 组件实现名 | reducer / dispatch / props / hook / useReducer / useState | 移到工程合同 |

### 3.3 保留产品视角行业词（含指代前缀）

所有 PM 视图文档都可以使用产品视角的 UI 行业词，但**必须**加完整指代前缀，让读者一眼知道指代哪个对象：

| 行业词（保留） | 必须加的指代前缀（举例）|
|---|---|
| Badge | 许可证状态 Badge / 部门额度状态 Badge |
| Drawer | 「额度明细 Drawer」 / 「用户详情 Drawer」 |
| Tab | 「产品详情页 - Tab 1 额度分配视图」 |
| Tooltip | 鼠标悬停时给出的说明性提示 |
| Toast | 系统给出成功反馈（Toast 形式）|
| Dialog / 弹窗 | 「分配额度弹窗」 / 「调整额度弹窗」 |
| 折叠区 | 「已失效」折叠区 |

### 3.4 正向描述系统行为

PM 视图用正向句式：

| 反向（❌）| 正向（✅）|
|---|---|
| 系统不允许保留中间态 | 系统将所有改动整体回滚到操作前的状态 |
| 禁止在该行额外添加文字标签 | 该行以视觉高亮方式区分 |
| 禁用「含子」概念 | UI 文案统一使用"勾选部门"的实操描述 |

反向约束（"禁止 X / 不允许 Y"）一律移到工程合同。

### 3.5 抽象动词必须搭配具体效果

以下动词出现时必须紧跟具体效果或对象：

| 动词 | 必须补全 |
|---|---|
| "更新 X 定义" | 更新后，对持有 X 的对象立即按新规则生效 |
| "保存后生效" | 生效后什么变化、对谁生效 |
| "立即更新" | 更新的具体内容 |
| "执行 X 操作" | 操作的具体步骤或结果 |

| 模糊（❌）| 完整（✅）|
|---|---|
| 保存后立即更新角色定义 | 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权 |

### 3.6 文档自包含

- 关键规则的简要说明应直接写在当前位置；同一规则在多处出现，每处都简要描述（约 1-2 句）。
- 禁止用「详见 §6.X」让读者跳转。
- "详见 §X" 仅用于引用本文件之外的文档（如 `docs/DESIGN.md`）。

### 3.7 禁用兜底词 / 主观词

| ❌ 错误 | ✅ 正确 |
|---|---|
| "编辑 / 启用停用 / 删除"等操作 | "编辑"、"启用 / 停用"、"删除"三个操作 |
| 默认角色清晰区分 | 默认角色行带"默认"标识 |

兜底词（"等"、"之类的"、"相关的"）必须列全所有项。

### 3.8 禁用书面冷僻词 / 中英混杂 / 技术 jargon / 数学化表达

| 类别 | ❌ 错误 | ✅ 正确 |
|---|---|---|
| 冷僻词 | 明示 / 暗中 / 链路 / 范畴 / 颗粒度 | 替换为日常中文（提示 / 隐含 / 流程 / 范围 / 粒度）|
| 中英混杂 | review / CRUD / scope | 评审 / 创建-编辑-删除-启用停用 / 管辖范围 |
| 技术 jargon | 悬挂引用 / 互锁陷入死锁 / 不参与鉴权 | 仍引用了不存在的对象 / 双方互相阻止对方操作 / 不参与权限判断 |
| 数学化表达 | 严格小于 / ⊊ / ⊆ | 完全包含在 X 之内（且至少少一个）|

### 3.9 禁用元描述 / 自指

文档内不出现对自身的描述：
- "本文档是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚……"

## 五、功能清单格式（强制）

`task spec` / `prd` / `solution` 涉及功能描述时必须使用统一格式：

### N · [功能名 — 必须含指代前缀]

| 二级功能 | 三级功能 | 使用角色 |
|---------|---------|---------|
| [二级功能名] | [三级功能名] | [角色名 — 角色限定条件] |

1. [需求条目，正向描述功能行为]
2. ...

**填写要求**：
- 标题用产品视角的功能名，含完整指代（如「产品详情页 - Tab 1 额度分配视图」树形列表）
- 三列表必须填全（二级功能 / 三级功能 / 使用角色）
- 数字编号列表里每条 = 一个功能行为或业务规则
- 不得在功能清单内嵌入反向约束、设计意图解释、像素 / 颜色 / 工程词

## 六、关键产品决策格式（solution / task spec 必填）

每份 `solution.md` 和涉及关键产品选择的 `task spec` 必须有「关键产品决策」节：

```markdown
## 🎯 关键产品决策

| # | 决策项 | 当前选择 | 备选方案 |
|---|---|---|---|
| 1 | [在「具体页面 - 区域」对什么对象做什么决策] | [当前选择，含完整业务描述] | [1-2 种备选，标明取舍] |

> 决策的共同理由：[一段话集中说明，不在每行重复]
```

**填写要求**：
- "决策项"列必须明确"在哪个页面 / 哪个 Tab / 哪个区域，对什么对象，做什么决策"
- "当前选择"用一句完整业务描述，不写实现细节
- "备选方案"列 1-2 种合理替代，注明为什么没选
- "共同理由"放表格下方，集中表达决策依据；不在每行的"备选方案"里重复

如果某 task 是纯执行型（无 PM 决策点）：本节填一行 `本 task 无关键产品决策（执行 solution.md §X.Y 已确定方案）`。

## 八、自检清单（生成 / 修改 PM 视图后）

- [ ] 文档章节顺序符合第七节约束

## 九、输入流约束（信息来源 / 反向校验 / 反馈分类）

本节约束各 skill 写文档前**读哪些上游产物**，以及**怎么读**——避免工程化内容沿 stage 链路渗透到 PM 视图。

### 9.1 PM 视图链路只读 PM 视图层

PM 视图文档之间互相喂入时**只读对方的 PM 视图层**（即主文件），**不读** `*.engineering.md`。

**统一原则**：仓库中存在的项目级权威产物（`docs/CONTEXT.md` / `docs/DESIGN.md` / `docs/prd.md` / `docs/modules/*.md` / `prototypes/`）一律**必读**——AI 不得以"觉得不必要"为由跳过。

下表分两列展示：左列是上游 **stage 文档**（brief → analysis → solution → task-plan → tasks 的链路），右列是 **项目级文档**（已沉淀的权威基线）。

| Skill → 产物 | 上游 stage 文档（必读）| 项目级文档（必读，仓库存在则读）| 不读 |
|---|---|---|---|
| `req-analysis` → `analysis.md` | brief.md | docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/ | 任何 .engineering.md |
| `req-solution` → `solution.md`（PM 视图）| brief.md / analysis.md | docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/ | 任何 .engineering.md |
| `req-solution` → `solution.engineering.md` | analysis.md / 上游 .engineering.md（如有）| docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/ | — |
| `task-plan` → `task-plan.md`（PM 视图）| brief.md / analysis.md / solution.md（PM 视图）| docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/ | solution.engineering.md |
| `task-spec` → `task-NNN.md`（PM 视图）| brief.md / analysis.md / task-plan.md / solution.md（PM 视图）/ 同模块已完成 task 的 PM 视图 | docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/<module>.md / prototypes/ | solution.engineering.md / 任何 .engineering.md |
| `task-spec` → `task-NNN.engineering.md` | analysis.md / solution.engineering.md（按章节匹配）/ 同模块已完成 task 的 .engineering.md（如有）| docs/DESIGN.md / docs/prd.md / docs/modules/<module>.md / prototypes/ | — |
| `prd-writing` → `prd.md` | brief.md / analysis.md / solution.md（PM 视图）/ tasks/\*.md（PM 视图）| docs/CONTEXT.md / docs/DESIGN.md / docs/prd.md / docs/modules/\*.md / prototypes/（反向校验） | 任何 .engineering.md |

**理由 1**：PM 视图文档若读了 .engineering.md，工程内容会被沿链路复制下去——当前 task spec 把 solution §五派生状态规则（代码层）等内容搬到自身实现指引就是因为不分层读。

**理由 2**：项目级文档列为"应读"时 AI 容易跳过，导致 skill 闭门造车。所有产出 PM 视图的 skill 都应该把已沉淀的项目级产物作为基线，避免重复设计或与已有规格冲突。

### 9.2 工程合同的喂入时机

工程合同层只在以下时机被读：
- `task-execute` 启动 agent 时显式 inject 到 prompt（agent 读完才动手）
- `task-confirm` 校验两文件成对存在
- `task-spec` 生成 task 工程合同时按章节匹配 `solution.engineering.md`

PM 视图链路（§9.1 表格中的"必读"和"应读"）一律不读 .engineering.md。

### 9.3 原型代码作为反向校验源（task-plan / task-spec / prd-writing 必读）

`task-plan` / `task-spec` / `prd-writing` 三个 skill 必须读 `prototypes/` 现有原型代码：

**目的**：用原型实际行为反向校验上游文档描述。

**读法**：
- 按"所属模块 + 文件路径"匹配，不全量读
- 重点关注：现有页面的字段 / 交互方式 / 已落地组件 / UI 文案

**发现不一致时的处理**：
| 情况 | 处理 |
|---|---|
| 原型已删除 / 砍掉某个工程概念，但上游文档（solution / analysis）还在写 | PM 视图以**原型为准**；上游文档的工程化措辞放进**工程合同的反向约束**（如"UI 文案禁用「含子」概念—原型已无对应控件"）|
| 原型与文档命名不一致（字段名 / 按钮名 / 状态名）| PM 视图以**原型为准**；产物末尾备注"原型与文档不一致，已采用原型现状"|
| 原型实现细节（reducer / props / 组件路径）出现在上游 solution 中 | 这些细节**只放工程合同**；PM 视图描述功能行为 |

**避坑**：原型里有但上游文档没写的"工程概念"（如 V4.1 里的 `includeDescendants`、"含子"复选框），属于工程层细节——
- 不要把它们引入 PM 视图当作功能要求
- 如果原型已砍掉、PM 决策不再支持，必须在工程合同的反向约束里显式标注

### 9.4 PM 反馈的三类分流（task-spec 强制）

`task-spec` 读"同模块已完成 task 的 `## PM 反馈` section"时**必须分三类**分别写入：

| PM 反馈类型 | 识别特征 | 写入位置 |
|---|---|---|
| **正向规则**（统一文案 / 统一行为）| "统一用 X" / "全文用 Y" / "应该按 Z 处理" | 当前 task 的「跨功能产品规则」节 |
| **反向约束**（禁止做某事 / 不要再这样写）| "禁用 X" / "不要 Y" / "不允许 Z" | 当前 task 的工程合同「易错点 / 禁止项」节 |
| **决策记录**（PM 反馈推动了某个产品选择改变）| "改为 X" / "二审决定 Y" / "重做为 Z" | 当前 task 的「关键产品决策」节（备选方案列标注"已被 PM 反馈推翻"）|

**禁止**：把 PM 反馈整段搬到「实现指引-易错点」（这是当前的反模式，导致 PM 视图被反向约束污染）。

**举例**（来自 task-002 PM 反馈）：
- "统一用「可开通」，不混用「还能开通」「可开 N 人」" → 正向规则 → 跨功能产品规则
- "禁用「含子」/ `includeDescendants` 概念，原型已砍掉" → 反向约束 → 工程合同
- "二审改：聚合行展开看证 breakdown，不是平铺" → 决策记录 → 关键产品决策
