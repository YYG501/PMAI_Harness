## 一、三层信息分层（核心结构原则）

每份文档都按三层组织内容。**不允许**把工程实现细节放到 PM 视图层。

### 1. PM 视图（首屏可见）
PM 创建 / 审核 / 验收时直接看的内容。回答 PM 关心的问题：
- 这个东西在做什么？
- 关键产品决策是什么？
- 用户能做什么 / 看到什么？
- 哪些会被改 / 哪些不动？
- 怎么验收？

### 2. 实现深水区（不放 PM 首屏）
给执行 agent 的实现约束，可以来自 `DESIGN.md`、模块规格里的执行提示或 build 阶段上下文；不要求新建固定的工程孪生文件。回答工程问题：
- 启动前必读哪些文件？
- 实现时用哪些函数 / 组件 / 字段？
- 反向禁止哪些做法？
- review skill（plan-eng-review / plan-design-review）沉淀的细化决策？

### 3. 历史档案（验收时按需查）
版本演进留痕。验收时只看最新一轮：
- 执行日志
- 文档偏差
- 自审记录
- PM 反馈

## 二、模块三件套

当前活跃 PM 视图以功能模块为组织单位：

| 文件 | 职责 |
|---|---|
| `discussion.md` | 范围讨论、开放问题、PM 输入上下文 |
| `decisions.md` | 已拍板决策、共同理由、否过的方案 |
| `spec.md` | 可建规格：信息模型、功能清单、业务规则、验收路径 |

旧 `task-plan.md` / `tasks/task-NNN-*.md` / `.engineering.md` 只作历史证据，不作为新流程产物。

## 五、功能需求写法选择与表格 preset

适用：模块 `spec.md`、功能型规格文档和 PRD 体例中描述具体产品能力时。

本节只定义**写法选择原则**和**4 列功能表 preset**。4 列功能表不是所有规格的默认格式；只有选择 PRD 体例、CRUD 管理后台动作清单、权限评审清单，或 PM 明确要求“功能清单表格”时才强制使用。

### 5.1 先选写法，再写功能需求

| 内容形态 | 首选写法 | 说明 |
|---|---|---|
| 规则收口 / 口径统一 | 短定义 + 分组规则 + 验收清单 | 适合模块 `spec.md` 中说明产品事实，不强拆二级 / 三级 |
| 状态 / 分类 / 卡片 | 分类定义 + 触发条件表 + 展开字段表 + 按钮 / 消失规则 | 适合待办卡、通知、状态机等内容 |
| 多步流程 | 分段叙述：先后顺序、条件分支、异常分支 | 表格只放并列字段或状态，不把长流程塞进单格 |
| 字段很多 | 字段口径表 | 字段 / 含义 / 来源 / 是否必填 / 默认值 / 校验分列写 |
| 权限 / 角色差异 | 权限矩阵 / 可见范围表 + 边界说明 | 每个角色差异是数据，不要散落在长段落里 |
| CRUD / 管理后台动作清单 | 4 列功能表 preset | 用二级 / 三级动作组织，不用页面 / 弹窗 / Tab 名 |
| PRD 体例 §六 | 4 列功能表 preset + PRD lint | 由 `/pmai-spec-writing` 的 PRD 体例 preset 负责 |

判断标准：**这段信息是并列项、流程、规则、状态、字段，还是动作清单？** 并列项可上表；流程用叙述；规则用分组规则；动作清单才用二级 / 三级功能表。

### 5.2 4 列功能表 preset

适用：PRD 体例 §六、CRUD 管理后台动作清单、PM 明确要求功能表的功能型规格文档。模块 `spec.md` 只有当该段确实是动作清单时才使用。

```
### N · [功能名 — 必须含完整指代前缀]

> **使用角色**：[当本节整体角色统一时写在此 blockquote；逐行不同则只填表内列，本行删除]

| 二级功能 | 三级功能 | 使用角色 | 需求描述 |
|---------|---------|---------|---------|
| [二级功能名] | [三级功能名] | [角色名 — 角色限定条件] | 1. [业务命题或规则] |
| | | | 2. ... |
| [二级功能名] | [另一三级功能名] | [角色名] | 1. ... |
| | | | 2. ... |

> **注**：[可选，写明本节额外约束 / 边界；不需要时整行删除]
```

**关键约定**：
- **4 列表格**：二级功能 / 三级功能 / 使用角色 / 需求描述。
- **续行 rowspan 模式**：同一三级功能的多条需求，第 2 条起的前 3 列留空。
- **需求描述列内联编号**：每条 1. / 2. / 3. ...
- **二级功能 = 用户动作组，不是 UI 组件**：列表 / 搜索 / 筛选 / 操作 / 创建 / 导入 / 详情等。
- **三级功能 = 动作子项，不是 UI 形态描述**：分配 / 调整 / 撤销 / 启用 / 吊销 / 查看等。
- **角色视角差异 / UI 视图切换 / UI 形态规则**写进需求描述列编号项，不外溢成独立三级。
- 表前后的 blockquote 按需写，没东西写就整行删。

### 5.3 表格 preset 的需求描述列约束

4 列功能表里，需求描述列的每条编号项只回答“产品在业务层提供什么”：业务命题、业务规则、角色权限、可见范围、字段定义。**不描述 UI 长什么样**。

字段定义、计算口径可以写进需求描述列编号项；当字段较多、会被多处复用、或读者需要对照时，抽成字段口径表或附件。不要因为使用了 4 列功能表，就禁止所有字段表。

**判别简则**：写完一条后问自己：“这条规则换一套 UI 还成立吗？”
- 成立 → 它是业务规则，留下。
- 不成立 → 它是 UI 描述，移到产物预览、设计规范或实现上下文。

### 5.4 自检清单（按所选写法检查）

- [ ] 已先判断内容形态：规则 / 状态 / 流程 / 字段 / 权限 / 动作清单。
- [ ] 选了表格 preset 时，4 列表格存在，二级 / 三级命名是动作，不是页面 / 弹窗 / Tab / 区块。
- [ ] 选了表格 preset 时，同一三级功能的多条需求采用续行 rowspan 模式。
- [ ] 选了自由规格写法时，没有为了套表把规则、状态、流程强拆成二级 / 三级功能。
- [ ] 需求描述通过“换 UI 还成立”测试。
- [ ] 无 UI 排版词、控件类型词、样式参照词、实现路径、工程字段、反引号代码引用。

## 六、关键产品决策的文档边界

模块 `spec.md` 和功能型规格正文只写当前有效的产品事实、规则和行为。备选方案、被否方向、共同理由与 supersede 关系只写模块 `decisions.md`；跨模块现行规则写 `PRODUCT-RULES.md`；项目级冻结理路写 `docs/decisions/`。

禁止在规格正文里保留“关键产品决策”历史表、旧版本正文、删除线方案或迭代流水账。若读者需要理解为什么，链接到相应决定记录；若决定尚未确认，返回 design，不得在 spec-writing 阶段补成规范。
