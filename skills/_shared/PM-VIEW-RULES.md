# PM 视图通用规则（PM-VIEW-RULES）

> 适用范围：所有 PM 视角的 stage 文档 — `brief.md` / `analysis.md` / `solution.md` / `task-plan.md` / `tasks/task-NNN-*.md` / `prd.md`。
>
> 本文件是 **单一真相源**。下列 skill 都引用本文件，不在 skill 内部独立维护：
> `new-req` · `req-analysis` · `req-solution` · `task-plan` · `task-spec` · `prd-writing`
>
> AI 在生成、修改任何上述文档前，先读完本文件。

---

## 一、三层信息分层（核心结构原则）

每份文档都按三层组织内容。**不允许**把工程实现细节放到 PM 视图层。

### 1. PM 视图（首屏可见）
PM 创建 / 审核 / 验收时直接看的内容。回答 PM 关心的问题：
- 这个东西在做什么？
- 关键产品决策是什么？
- 用户能做什么 / 看到什么？
- 哪些会被改 / 哪些不动？
- 怎么验收？

### 2. 工程合同（PM 默认折叠 / 拆文件）
给执行 agent 的实现规范。回答工程问题：
- 启动前必读哪些文件？
- 实现时用哪些函数 / 组件 / 字段？
- 反向禁止哪些做法？
- review skill（plan-eng-review / plan-design-review）沉淀的细化决策？

### 3. 历史档案（验收时按需查）
版本演进留痕。验收时只看最新一轮：
- 执行日志
- 文档偏差
- 自审记录
- PM 反馈

## 二、拆文件约定

`solution.md` / `task-NNN-*.md` 两类文档拆成两个文件：

| 文件 | 内容 | 命名 |
|---|---|---|
| 主文件（PM 视图）| 一、PM 视图层 + 三、历史档案 | 原名不变（`solution.md` / `task-001-xxx.md`） |
| 工程合同 | 二、工程合同层 | `<原名>.engineering.md`（同目录、同 slug）|

**约定**：
- 主文件路径不变，所有现有引用（git / req-stage-gate / lark publish）不需要改
- 主文件底部加一行：`> 工程实现细节见 <slug>.engineering.md`
- 两文件成对出现 — `task-transition.py` / `req-transition.py` 校验，缺工程合同 = error
- agent 启动时由 `task-execute` 显式 inject 工程合同内容到 prompt，不依赖 PM 主动打开

`brief.md` / `analysis.md` / `task-plan.md` / `prd.md` **不拆文件**：
- `brief.md` / `analysis.md` / `prd.md`：本身没有工程合同层，PM 视图即全部
- `task-plan.md`：自检结论 / 验收 GAP 索引 / 模块规格状态压成末尾轻量"自检与状态摘要"节附在 PM 视图末，没有独立工程合同需要长期存档

## 三、PM 视图写作规则（硬约束）

### 3.1 每个名词必须明确指代

PM 视图里出现的每个名词，必须能让读者一眼知道**指代哪个对象 / 哪个页面 / 哪个区域 / 谁的属性**，不允许模糊指代。

| 模糊（❌）| 明确（✅）|
|---|---|
| 树最上面那一层 | 「产品详情页 - Tab 1 额度分配视图」的树形列表，最顶层节点 |
| 状态 Badge | 许可证状态 Badge |
| 状态列 | 许可证状态列 |
| 弹窗 | 「分配额度弹窗」 |
| 列表 | 「产品访问管理 - 产品列表页」的产品列表 |
| 失效证 | 状态为已失效（含已过期 / 已停用 / 已吊销 / 未生效）的许可证 |
| admin | 租户管理员 / 部门管理员（仅在其权限范围内的部门）|
| Tab 2 不动 | 「产品详情页 - Tab 2 用户开通（task-004 实现）」保持现状不动 |

**自检**：单字"状态"、"列表"、"树"、"弹窗"、"操作"、"按钮"、"用户"出现时，前面必须有完整指代前缀。

### 3.2 只描述功能行为

PM 视图回答：
- 系统应该提供什么
- 用户能做什么
- 业务规则是什么
- 数据字段之间的关系是什么
- 角色权限是什么
- 异常路径如何呈现

PM 视图**不**回答：

| 类别 | 不出现 | 替换为 |
|---|---|---|
| 像素值 | 24px / 420px / w-14 / py-5 | 移到工程合同 |
| 颜色码 | #C9CDD4 / #FFA39E | 移到工程合同 |
| 文字色名 | "红色文字" / "黄色警告" | "视觉高亮" / "视觉弱化" / "警告信息"（语义保留）|
| Emoji 视觉 | 🟡🔴⚫ | 移到工程合同；状态文案保留（未生效 / 已过期）|
| 反向约束 | "禁止 X" / "不允许 Y" | 移到工程合同；正向改写"系统不保留 Y"|
| 设计意图解释 | "（避免双重计数）" / "（防止角色爆炸）" | 移到「关键产品决策」的"共同理由"行 |
| 组件实现名 | reducer / dispatch / props / hook / useReducer / useState | 移到工程合同 |

### 3.3 保留产品视角行业词（含指代前缀）

所有 PM 视图文档都可以使用产品视角的 UI 行业词，但**必须**加完整指代前缀，让读者一眼知道指代哪个对象：

| 行业词（保留） | 必须加的指代前缀（举例）|
|---|---|
| Badge | 许可证状态 Badge / 部门额度状态 Badge |
| Drawer | 「额度明细 Drawer」 / 「用户详情 Drawer」 |
| Tab | 「产品详情页 - Tab 1 额度分配视图」 |
| Tooltip | 鼠标悬停时给出的说明性提示 |
| Toast | 系统给出成功反馈（Toast 形式）|
| Dialog / 弹窗 | 「分配额度弹窗」 / 「调整额度弹窗」 |
| 折叠区 | 「已失效」折叠区 |

### 3.4 正向描述系统行为

PM 视图用正向句式。**隐式反向（"无 X / 没有 X / 不出现 X / 不通过 Y"）等同于显式反向（"禁止 / 不允许"）**——同样要改写正向。

| 反向（❌）| 正向（✅）|
|---|---|
| 系统不允许保留中间态 | 系统将所有改动整体回滚到操作前的状态 |
| 禁止在该行额外添加文字标签 | 该行以视觉高亮方式区分 |
| 禁用「含子」概念 | UI 文案统一使用"勾选部门"的实操描述 |
| 行末**没有**跳转或操作入口 | 失效证仅供查看，管理员通过「租户配置 - 许可证管理」主入口处理 |
| **不出现**任何跳转入口 | 同上——描述系统提供什么 / 通过哪个入口处理 |
| **不通过**抽共享组件保证 | 由 PM 走查对照保证 |
| **不展示**「已用 / 剩余」两列 | 每维度展示总额单值 |

反向约束（"禁止 / 不允许 / 不准 / 禁用 / 不得 / 不出现 / 不展示 / 不通过 / 没有...入口"）一律移到工程合同。

**例外（lint 自动豁免）**：
- §📦 范围 描述本 task 移除/不再保留 X：天然反向，是 scope-change 描述（如"行展开内子行不再保留 [查看 ↗] 入口"）
- §✅ 验收清单 列出 PM 走查项时用"verify X 不出现"句式：天然反向，验证视角友好（如"不出现英文字段名"）
- §📋 编号项陈述当前数据未触发某规则的事实（如"当前数据下不出现「+N 个其他维度」提示"）：事实陈述而非反向约束

### 3.5 抽象动词必须搭配具体效果

以下动词出现时必须紧跟具体效果或对象：

| 动词 | 必须补全 |
|---|---|
| "更新 X 定义" | 更新后，对持有 X 的对象立即按新规则生效 |
| "保存后生效" | 生效后什么变化、对谁生效 |
| "立即更新" | 更新的具体内容 |
| "执行 X 操作" | 操作的具体步骤或结果 |

| 模糊（❌）| 完整（✅）|
|---|---|
| 保存后立即更新角色定义 | 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权 |

### 3.6 文档自包含

- 关键规则的简要说明应直接写在当前位置；同一规则在多处出现，每处都简要描述（约 1-2 句）。
- 禁止用「详见 §6.X」让读者跳转。
- "详见 §X" 仅用于引用本文件之外的文档（如 `docs/DESIGN.md`）。

### 3.7 禁用兜底词 / 主观词

| ❌ 错误 | ✅ 正确 |
|---|---|
| "编辑 / 启用停用 / 删除"等操作 | "编辑"、"启用 / 停用"、"删除"三个操作 |
| 默认角色清晰区分 | 默认角色行带"默认"标识 |

兜底词（"等"、"之类的"、"相关的"）必须列全所有项。

### 3.8 禁用书面冷僻词 / 中英混杂 / 技术 jargon / 数学化表达

| 类别 | ❌ 错误 | ✅ 正确 |
|---|---|---|
| 冷僻词 | 明示 / 暗中 / 链路 / 范畴 / 颗粒度 | 替换为日常中文（提示 / 隐含 / 流程 / 范围 / 粒度）|
| 中英混杂（业务词）| review / CRUD / scope / admin / breakdown / mock / self-contained / workflow / pipeline | 评审 / 创建-编辑-删除-启用停用 / 管辖范围 / 管理员（角色名首次出现可用"租户管理员 / 部门管理员"）/ 明细 / 模拟 / 各自独立 / 流程 / 流水线 |
| 中英混杂（状态字面量）| active / pending / null / undefined | 已激活 / 待生效 / 无值 / 未设置 |
| 中英混杂（数学/集合/函数）| sum / count / map / filter / reduce | 累加 / 统计 / 按 X 归并 / 按 X 筛选 / 合并 |
| 中英混杂（数据结构 / 实现词）| schema / record / props / hook / reducer / dispatch / topContent / kebab / segmented control | 这些是工程词，全部驱逐到 `*.engineering.md`（见 §3.2）|
| 反引号代码引用 | `\`quotaPoolId=null\`` / `\`useState\`` | 反引号包裹的代码 / 字段 / API 名 一律不出现在 PM 视图 |
| URL 参数字面量 | "URL 带 tab=pools&view=dept 查询参数" | "详情页直接定位到 Tab 1 额度分配视图、部门视角"——描述跳转结果而不是 query string |
| 技术 jargon | 悬挂引用 / 互锁陷入死锁 / 不参与鉴权 | 仍引用了不存在的对象 / 双方互相阻止对方操作 / 不参与权限判断 |
| 数学化表达 | 严格小于 / ⊊ / ⊆ | 完全包含在 X 之内（且至少少一个）|

**例外**：UI 行业词（Badge / Drawer / Tab / Tooltip / Toast / Dialog 等）允许保留，参见 §3.3。

### 3.9 禁用元描述 / 自指

文档内不出现对自身的描述：
- "本文档是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚……"

### 3.10 UI 骨架代码块内只写"屏幕上的字"

`§🖼 页面 UI 骨架` 章节里的 ASCII 框图代码块（` ``` ` 围起来的那段），**只允许出现 admin / 用户在屏幕上实际能看见的文案**。任何对字段、区块、状态的解释、注释、设计意图、口径说明 → 全部剥离到骨架代码块**下方**的「关键交互说明」段。

**反例对比**（一个浓缩示例覆盖所有变体）：

❌ 骨架内混入非屏幕字：

```
┌─ 许可证使用情况（新增·简化版） ─────────┐
│ 席位（独占）：1（独占，固定）            │
│ Agent 实例：3 个 · 独占 · 已使用 1 / 剩 2│
│ 配额（按该产品维度集动态显示）          │
├─ 旧版授权 V1（已吊销，弱化） ───────────┤
│ [▸ 高级配置]   ← 默认值藏在这里        │
└─────────────────────────────────────────┘

[选择来源许可证（多证场景下出现）]
```

✅ 骨架内只写屏幕字 + 解释下沉：

```
┌─ 许可证使用情况 ─────────────────────────┐
│ 席位：1                                  │
│ Agent 实例：3 个 · 已使用 1 / 剩 2        │
│ 配额：32 万 token                        │
├─ 旧版授权 V1（已吊销） ──────────────────┤
│ 共享部门：研发部 / 产品部                │
│ 范围：仅本部门  [改为共享部门额度]       │
└──────────────────────────────────────────┘

[选择来源许可证]
```

**关键交互说明**（骨架下方文字段，承载所有被剥离的注释）：
- 「许可证使用情况」区块在 task-XXX 新增；展示形态延续 task-YYY 的多维度透明展示模式
- 「席位」字段对所有产品恒为独占占用（系统保证）；UI 不重复标注
- 「配额」字段按产品配置的多种计量维度动态展示（token / 调用次数 / 存储 GB 等）
- 「旧版授权 V1」区块视觉弱化（具体视觉规范见 `docs/DESIGN.md`）
- 「改为共享部门额度」按钮：席位默认为独占，仅当 admin 显式切换为共享时进入共享部门选择流程
- 「选择来源许可证」入口仅在多证场景出现（admin 名下持有该产品 ≥2 个许可证时）

**5 类失败模式都是这条规则的应用**：

| 失败模式 | 错在哪 | 怎么改 |
|---|---|---|
| 默认值标注（"席位（独占）"） | 系统恒定属性，屏幕字本身没有这个标 | 直接写值，元数据进 §交互说明 |
| 文档元注释（"（新增·简化版）"） | 给文档读者看的，admin 看不见 | 完全删除（变更范围说明在 §📋 / §🔄 已有） |
| 设计意图（"（已吊销，弱化）"） | 给设计师/工程师的实现指令 | 文案保留状态名「已吊销」；视觉弱化进 §交互说明，引 `docs/DESIGN.md` |
| 字段口径（"（多证场景下出现）"） | 给读者解释字段定义 | 屏幕字保留入口名；触发条件进 §交互说明 |
| 折叠藏默认值（"[▸ 高级配置]"） | 默认值伪装成扩展项 | 默认值直接渲染；override 走单独按钮（如「改为共享部门额度」） |

**自动 lint 边界**：`check-doc-pm-view.py` 仅对骨架代码块内出现的 `（...）` 报 warning（不区分类型）。warning 不阻塞，由 PM/AI 自判是合法标识型（CSV / 1080p / 2 个）还是非法释义型（基于 X / 按 Y / 多 Z 场景）。其余 4 类失败模式 lint 抓不全，靠步骤 5 自检 + reviewer。

#### 3.10.1 骨架宽度硬约束

ASCII 框图模式下，骨架代码块每行 ≤ 80 字符（约 78 列内容 + 2 列 border）。

**为什么**：标准 viewport（VS Code preview / 飞书 / Notion / GitHub）能在不水平滚动的前提下完整显示；超过 80 字符时部分渲染器会强制折行，box 字符与中文全宽字符混合 wrap，列对齐崩塌（v3.5 实证）。

**超出 80 字符的常见原因 + 修法**：

| 原因 | 修法 |
|---|---|
| 紧凑行用了完整业务名（"Agent 实例数 / API 调用次数 / 图片生成插件"） | 改用维度简称（席位 / Agent / API / 图片 / 美元）——简称是 80 字符硬约束派生的命名约定，与"产品详情页 Tab 1 池行" convention 对齐 |
| 单行塞太多字段 | 拆成多行（header 行 + 数据行）；每行只放一个语义单元 |
| 列宽设置过大 | 列名长度不超过对应数据最大长度 + 2 字符 |

**渲染兜底**：即便 ≤ 80 字符也可能在某些 markdown 渲染器（不识别代码块 monospace）下挂掉。如果你的渲染器对 ASCII 框图不友好，换用 VS Code preview / Obsidian / Typora 等支持 monospace 的 viewer 看。框架不再为非 monospace 渲染器降级——保留 ASCII 框图的 PM 直觉价值。

## 五、功能清单格式（强制）

适用：`task spec` / `prd` / `solution` 中描述具体功能时。

参照模板：`docs/modules/部门+用户+角色设计/department-group-role-design-v4.1.md` §五数据模型 / §十一鉴权规则 的节奏 — 先角色定位、再列业务规则、再独立给字段口径。

### 5.1 单功能节结构

每个功能节固定三块：标题 + 可选 section 级使用角色 blockquote + 4 列功能表格。

```
### N · [功能名 — 必须含完整指代前缀]

> **使用角色**：[当本节整体角色统一时写在此 blockquote；逐行不同则只填表内列，本行删除]

| 二级功能 | 三级功能 | 使用角色 | 需求描述 |
|---------|---------|---------|---------|
| [二级功能名] | [三级功能名] | [角色名 — 角色限定条件] | 1. [业务命题或规则] |
| | | | 2. ... |
| [二级功能名] | [另一三级功能名] | [角色名] | 1. ... |
| | | | 2. ... |

> **注**：[可选，写明本节额外约束 / 边界；不需要时整行删除]
```

**关键约定**：
- **4 列表格**：二级功能 / 三级功能 / 使用角色 / 需求描述
- **续行 rowspan 模式**：同一三级功能的多条需求 → 第 2 条起的前 3 列**留空**（视觉等同 rowspan，纯 markdown 也能渲染）
- **需求描述列内联编号**：每条 1. / 2. / 3. ...
- **二级功能跨多个三级功能**：同一二级功能字符串可在多行重复出现（不强制收敛 rowspan 在二级功能列）
- **字段定义、计算口径、边界规则等**：直接写进需求描述列的某条编号项；**不另起字段口径独立表**
- 表前后的 blockquote（`> **使用角色**：` / `> **注**：`）按需写，没东西写就整行删

**已弃格式**（详见 §5.5 反例）：
- 3 列表（二级功能 / 三级功能 / 使用角色）+ 需求列表脱表（1./2./3. 写在表格外）
  - 弃因 1：3 列容易把同一件事拆两层凑数（"产品详情-基本信息 / 信息块展示"）
  - 弃因 2：需求脱表后，每条需求与"使用角色"对应关系丢失（同一节多角色时尤其混乱）
- 4 块结构（标题 + `> 使用角色` + `**业务规则**` 编号 + `**字段口径**` 独立表）
  - 弃因：内容拆两个 markdown 块，PM 阅读时反复跳；4 列表把"二级 / 三级"分层 + 角色 + 需求集中在一张表里更直观，也方便后续 PRD 做权限矩阵聚合

如有跨子功能聚类需要，标题用 "功能 A · 功能 B · 功能 C" 列举即可。

### 5.2 需求描述列编号项写作约束（硬规则）

**核心原则**：4 列表格里需求描述列的每条编号项只回答"产品在业务层提供什么"——业务命题、业务规则、角色权限、可见范围、字段定义。**不描述 UI 长什么样**——UI 形态是「📐 产物预览」章节的职责。

✅ 允许（业务层语言）：

| 类别 | 范例句式 |
|---|---|
| 业务命题 / 用户场景 | "用户进入产品详情页时，需要在第一时间得到本产品的额度状态画像" |
| 业务规则 | "总席位 / 已用席位 / 剩余席位三者构成数学闭环：总席位 = 已用席位 + 剩余席位 + 已分配给各部门未用的额度" |
| 角色权限 / 可见范围 | "部门管理员只看到其管辖范围内的产品；超出范围的额度不计入字段值" |
| 可执行的业务动作 | "用户可以从本页发起'分配额度到部门'的动作" |
| 数据筛选 / 排序业务规则 | "默认只展示已激活许可证下的额度记录；用户可主动切换到全部状态" |

❌ 禁止（这些都是 how，分别归位）：

| 类别 | 反例 | 怎么处理 |
|---|---|---|
| **UI 排版 / 视觉容器** | "顶部固定展示一块灰底信息块" / "按 2 列 grid 排版" / "信息块上方保留页面标题区" | 进「📐 产物预览」章节（线框图）+ `*.engineering.md` §8 视觉规范 |
| **元素位置 / 顺序 / 区块结构** | "字段顺序：第 1 行 X / Y / Z；第 2 行 A / B / C" / "右侧依次是 [+ 分配额度] 主按钮、[返回产品列表] 二级按钮" | 进「📐 产物预览」+ `*.engineering.md` §8 |
| **UI 控件类型** | "用 segmented control 切换" / "操作列折叠为 kebab 下拉" / "树形 connector 字符（├ └）" | 进「📐 产物预览」+ `*.engineering.md` §8 |
| **样式参照 / 视觉对齐** | "与 X 详情页的 topContent 样式对齐" / "灰底圆角容器" | 进 `*.engineering.md` §8 |
| how — 实现步骤 / 组件路径 / 代码引用 | "复用 SegmentedControl 组件" / "使用 `topContent` 同款" | 进 `*.engineering.md` §3 / §4 |
| why — 设计意图解释 | "便于不同详情页之间视觉一致" / "避免视觉认知负担过重" | 进「🎯 关键产品决策」的"决策的共同理由" |
| 字段值口径用工程英文 | "总席位 = 跨所有 active 证的产品级总席位 sum" | 改为业务语言写在需求描述列编号项里："总席位 = 累加所有已激活许可证的产品级总席位"（业务动词 + 中文状态词）|
| 反向约束 | "禁止 X" / "不允许 Y" | 进 `*.engineering.md` §6 |
| 工程参数 | 像素值 / 颜色码 / 字号 / 反引号代码 | 进 `*.engineering.md` §8 |

**判别简则**：写完一条后问自己——"这条规则换一套 UI（不同页面布局、不同控件）还成立吗？"
- **成立** → 它是业务规则，留下
- **不成立**（描述了具体怎么排、怎么呈现）→ 它是 UI 描述，移到「📐 产物预览」或工程合同

### 5.3 字段值口径写作（在需求描述列内）

字段定义、计算口径直接写在需求描述列的编号项里，不另起表。计算口径必须用业务语言：

- 数学 / 集合 / 函数：`sum` / `count` / `reduce` / `map` / `filter` → 用「累加」/「统计」/「按 X 归并」
- 状态 / 字面量：`active` / `null` / `undefined` → 用「已激活」/「无值」/「未设置」
- 数据结构：`schema` / `record` / `Array<T>` → 用「数据结构」/「记录」（避免直接说结构）
- UI 实现词：`segmented control` / `kebab` / `topContent` / `props` / `hook` → 全部驱逐到工程合同

**写法示例**（在需求描述列编号项里）：
> 3. 字段：产品 ID（直接取产品记录的标识值）、来源许可证数（统计本产品下所有许可证数量含已失效）、总席位（累加所有已激活许可证的产品级总席位）、剩余席位（总席位 减 已用席位 减 已分配给各部门但未用的额度）。

### 5.5 示例

**反例**（task-003 当前 §1 形态，禁用）：

```markdown
### 1 · 「产品详情页」顶部产品基本信息块（与「部门管理 - 部门详情页」对齐）

| 二级功能 | 三级功能 | 使用角色 |
|---------|---------|---------|
| 产品详情-基本信息 | 信息块展示 | 租户管理员、部门管理员（在其管辖范围内） |

1. 「产品详情页」顶部使用与「部门管理 - 部门详情页」`topContent` 相同样式的灰底信息块（圆角容器 + 2 列 grid）；admin 在不同详情页之间切换时视觉语言一致

### 1 · 「产品详情页 - 产品概览」

| | | | 2. 产品概览是产品级聚合视图，不区分许可证；许可证维度的细分是 Tab 1 内部视图切换的职责，不在本节范围。 |
| | | | 3. 字段：产品 ID（直接取产品记录的标识值）、来源许可证数（统计本产品下所有许可证数量含已失效）、总席位（累加所有已激活许可证的产品级总席位）、已用席位（累加所有挂在已激活许可证下的开通记录，含直接开通的用户和各部门内开通的用户）、剩余席位（总席位 减 已用席位 减 已分配给各部门但未用的额度）、部门覆盖数（统计在本产品下持有任意非零额度的部门数，含子部门）、产品描述（直接取产品记录的描述字段）。 |

| | | | 2. 产品概览的字段值与 Tab 1「部门视图」根节点行的字段值口径完全一致——同一个数字只允许有一个真实来源。 |

> **注**：本节字段是产品聚合层；许可证维度细分由 Tab 1 内部视图承接。

正例与反例的差别：
- 标题改为业务名（"产品概览"），去掉"顶部信息块"这种 UI 元素称呼
- 4 列表格 + 续行 rowspan + 需求描述列内联编号；同一节多个三级功能用多个表行 + 续行 rowspan 区分；不再用 3 列表 + 表外列表
- 字段定义内联在需求描述编号项里，含计算口径业务动词（"累加 / 统计 / 取 / 减"），**不另起字段口径独立表**
- 需求描述只说**业务命题**：用户在该场景下需要什么、产品提供什么、不同角色看到的范围有什么差别、与其他位置的口径一致性
- **完全不提**：灰底信息块 / 2 列 grid / 字段排几行 / 按钮在哪边 / 与哪个页面的样式对齐——这些 UI 形态去看「📐 产物预览」章节
- 全节无中英混杂工程词、无反引号代码引用

**判别"是不是 UI 描述"的简单 test**：把这条规则套到一个完全不同的 UI 实现上（如换成纯文字列表、或者换成两栏布局）——业务上还成立吗？
- 反例编号 1：换成"两栏布局"就不成立了 → 是 UI 描述
- 正例需求描述列编号 1："用户需要看到宏观状态画像"——任何 UI 都成立 → 是业务规则

**另一类已弃格式（4 块结构）**：标题 + `> 使用角色` blockquote + `**业务规则**` 数字编号 + `**字段口径**` 独立表（曾在 d4024eb 提交后短暂作为 §5.1 标准）。问题是 PM 阅读时反复跳两个 markdown 块，且无法承接 PRD 权限矩阵聚合 — 已被 4 列表格替代。

#### 9.1.1 "按章节匹配" 操作语义（强约束）

§9.1 表中标 🟡 "章节 grep" 的文件 → **禁止** 整文件 Read。读法：

1. `grep -nE "^### .*(<关键词1>|<关键词2>)" <文件>` 命中相关章节标题
2. 按命中行号 + 下一个同级或更高级 header 之间的区间 offset/limit Read
3. 关键词从当前 task 标题 / 所属模块 / 功能名提取

适用：`solution.engineering.md` / 同模块 `task-*.md`（`## PM 反馈` 段）/ `docs/DESIGN.md`（task-spec PM 视图）/ `tasks/task-*.md`（prd-writing 三章节遍历）。

**solution.md（PM 视图）特殊**——逃生口：
- **first-gen 模式**：整文件读（顶端核心产物，需要全局视野）
- **revise 模式**：按 §🎯 / §📦 / §✅ 章节 grep 局部读

#### 9.1.2 grep 不命中的 fallback 读法（防"0 行读"丢失）

按 §9.1.1 grep 章节标题时，若 0 命中（关键词与文件章节命名不匹配），不要直接放弃读。按文件类型走 fallback：

| 文件 | 命中 0 时 fallback |
|---|---|
| `docs/DESIGN.md`（task-spec PM 视图）| 读「页面模板」+「动效规范」+「间距系统」三个通用章节（约 100-150 行），不读颜色 / 字体细节 |
| `solution.engineering.md` | 读 §1 数据结构 + §2 派生状态 + §6 易错点 三个稳态章节（约 200 行），不读全文 |
| `tasks/task-*.md`（prd-writing 三章节遍历）| 0 命中说明该 task 没有 §📋 / §🎯 / §✅——按需追问 PM「该 task 是否真无可写入 PRD 的功能 / 决策 / 验收」|
| 同模块 `task-*.md`（`## PM 反馈` 段）| 0 命中即说明无反馈，跳过即可（不 fallback）|

**为什么不机械追问 PM**：fallback 读的章节是预先盘点过的"业务关键词稀疏但确实需要的通用规则"。每次都追问 PM 增加心智负担；预设 fallback 把判断收敛到设计期。

**理由 1**：PM 视图文档若读了 .engineering.md，工程内容会被沿链路复制下去——当前 task spec 把 solution §五派生状态规则（代码层）等内容搬到自身实现指引就是因为不分层读。

**理由 2**：项目级文档列为"应读"时 AI 容易跳过，导致 skill 闭门造车。本表用 🟢/🟡/⚪/❌ 等级明确化，避免 AI 按"觉得不必要"自由裁量。

### 9.3 原型代码作为反向校验源（task-plan / task-spec / prd-writing 必读）

`task-plan` / `task-spec` / `prd-writing` 三个 skill 必须读 `prototypes/` 现有原型代码：

**目的**：用原型实际行为反向校验上游文档描述。

**读法**：
- 按"所属模块 + 文件路径"匹配，不全量读
- 重点关注：现有页面的字段 / 交互方式 / 已落地组件 / UI 文案

**发现不一致时的处理**：
| 情况 | 处理 |
|---|---|
| 原型已删除 / 砍掉某个工程概念，但上游文档（solution / analysis）还在写 | PM 视图以**原型为准**；上游文档的工程化措辞放进**工程合同的反向约束**（如"UI 文案禁用「含子」概念—原型已无对应控件"）|
| 原型与文档命名不一致（字段名 / 按钮名 / 状态名）| PM 视图以**原型为准**；产物末尾备注"原型与文档不一致，已采用原型现状"|
| 原型实现细节（reducer / props / 组件路径）出现在上游 solution 中 | 这些细节**只放工程合同**；PM 视图描述功能行为 |

**避坑**：原型里有但上游文档没写的"工程概念"（如 V4.1 里的 `includeDescendants`、"含子"复选框），属于工程层细节——
- 不要把它们引入 PM 视图当作功能要求
- 如果原型已砍掉、PM 决策不再支持，必须在工程合同的反向约束里显式标注

#### 9.3.1 prototype 读取强约束（>500 行禁止整文件 Read）

prototype 文件 > 500 行 → **禁止** 整文件 Read。读法：

1. 先列**上游工程概念清单**（从 brief / analysis / solution / task-plan 中提取字段名 / 控件名 / 状态名 / 操作名）
2. 对每个概念在 prototype 范围内 grep：`grep -nE "<概念>" prototypes/<相关文件>`
3. **grep 命中**：Read offset = 命中行 -10, limit = 30
4. **grep 不命中**：列出已搜关键词清单 + 追问 PM「这个概念是否真不存在于原型里」。**禁止** AI 自行判定为"已砍掉"——可能是 false negative（关键词中英文不一致："额度" vs "quota" vs "allocation"；控件用 className 而非语义命名；概念名拆词等）。判断留给 PM。

例外：< 500 行的小 prototype 文件可全文 Read。

**理由**：原型 page.tsx 经常 2000+ 行，整文件 Read 浪费 90% 上下文。grep 命中段直接局部读；grep 不命中**不能**机械判为"原型已砍掉"——这种判断是 prose-as-judgment，需要 PM 拍板。

**例外 — task-execute**：task-execute 步骤 2.1 的 prototype 读法是「参考已有组件结构与布局模式」（写新页面"长一样"），属于**实现参考**而非反向校验，需要全局结构感 → 保留整文件读，**不应用本节约束**。

### 9.4 PM 反馈的四类分流（task-spec 读前三类 + close-task 读第四类）

PM 反馈在 task PM 视图的 `## PM 反馈` section 内必须分**四类**之一标注。两个 skill 分工读：

- **task-spec** 读"同模块已完成 task 的 PM 反馈"（前三类）→ 写入下一个 task 的相应 section
- **close-task 步骤 1.5** 读"本 task 的 PM 反馈"（第四类）→ 反推到 `docs/DESIGN.md`

| PM 反馈类型 | 识别特征 | 写入位置 | 消费者 |
|---|---|---|---|
| **正向规则**（统一文案 / 统一行为）| "统一用 X" / "全文用 Y" / "应该按 Z 处理" | 下一个 task 的「跨功能产品规则」节 | task-spec |
| **反向约束**（禁止做某事 / 不要再这样写）| "禁用 X" / "不要 Y" / "不允许 Z" | 下一个 task 的工程合同「易错点 / 禁止项」节 | task-spec |
| **决策记录**（PM 反馈推动了某个产品选择改变）| "改为 X" / "二审决定 Y" / "重做为 Z" | 下一个 task 的「关键产品决策」节（备选方案列标注"已被 PM 反馈推翻"）| task-spec |
| **视觉规范**（控件 / 间距 / 图标 / 配色 / 弹窗模式 / 输入控件类视觉决策）| "spinner 改 +/-" / "ⓘ 用 lucide" / "chip 灰胶囊改 box" / "footer baseline 对齐" | `docs/DESIGN.md` 对应章节（PM 在 close-task 步骤 1.5 逐条选 Y-rule / Y-task-note / N）| close-task |

**禁止**：
1. 把 PM 反馈整段搬到「实现指引-易错点」（PM 视图被反向约束污染的旧反模式）
2. **把视觉规范类反馈塞到工程合同 §6 易错点**（task-001 R6 修了 9 项但没沉淀进 DESIGN.md 的真实反模式——下一个 task 起新 dialog 时 LLM 没参考、重新踩同样坑）

**举例**：
- "统一用「可开通」，不混用「还能开通」「可开 N 人」" → 正向规则 → 跨功能产品规则
- "禁用「含子」/ `includeDescendants` 概念，原型已砍掉" → 反向约束 → 工程合同
- "二审改：聚合行展开看证 breakdown，不是平铺" → 决策记录 → 关键产品决策
- "数字 input 禁用 native spinner 用 +/- 按钮" → **视觉规范** → docs/DESIGN.md §九 9.2
- "弹窗影响范围多维度数字用 box grid 不要 chip 灰胶囊" → **视觉规范** → docs/DESIGN.md §九 9.11

### 9.6 双文件 lazy sync（reconcile 契约）

适用文档：`solution.md` ↔ `solution.engineering.md` / `tasks/task-NNN-*.md` ↔ `tasks/task-NNN-*.engineering.md`。

#### 9.6.1 总原则

PM 在 stage 内反复改 PM 视图时，工程合同**不立即同步**。工程合同允许暂时落后于 PM 视图（"已知 stale"），由 gate 通过时的 **reconcile 步骤**统一对齐。

| 时机 | 行为 |
|---|---|
| 首次生成（skill 第一次产 PM 视图）| 同时写 PM 视图 + 工程合同；工程合同顶部写入当时 PM 视图的 hash |
| 中途 PM 改 PM 视图 | 只改 PM 视图主文件；**不动**工程合同；hash 自然变 stale |
| 中途 PM 提交独立工程层信息（review 沉淀 / autoplan 输出 / 视觉规范补充）| 立即写入工程合同对应章节（§7 / §8 / §9 等"独立来源"章节）；**不更新** hash（PM 视图未动）|
| gate 通过的瞬间 | 触发 reconcile：比对 hash → stale 则重派生工程合同里"PM 视图驱动"的章节 → 更新 hash → 才允许 `req-transition.py` / 推 `/task-confirm` |
| read-side（task-execute / task-confirm / 中段 review）| 容忍读到 stale 工程合同；不阻塞、不 warn |

#### 9.6.2 hash 标记格式

工程合同顶部元信息块下方插入 HTML 注释：

```markdown
<!-- synced_pm_view_hash: <12 字符> -->
```

计算方式（PM 视图主文件全文）：

```bash
shasum -a 256 <pm-view-file> | cut -c1-12
```

首次生成时填入计算结果。reconcile 完成后用最新 PM 视图重算并覆盖旧 hash。**不允许**手动改 hash；不允许 PM 改 PM 视图时顺手刷 hash。

#### 9.6.3 章节分类（哪些归 reconcile，哪些不归）

工程合同的章节分两类：

**PM 视图驱动章节**（reconcile 时按需重派生）：
- `solution.engineering.md`：§1 数据结构 / §2 派生状态 / §3 组件路径 / §4 mock / §5 算法 / §6 易错点（PM 视图反向条目派生部分）/ §10 工程层验收清单
- `task.engineering.md`：§3 启动前必读 / §4 功能清单工程版 / §5 实现指引 / §6 易错点（PM 反馈反向部分）/ §8 视觉规范（PM 视图像素/颜色派生部分）/ §9 工程层验收清单

**独立来源章节**（reconcile 不动，由各自来源直接写入）：
- `solution.engineering.md`：§7 plan-review 沉淀 / §8 autoplan 输出 / §9 a11y/视口/视觉（DESIGN.md 派生部分）
- `task.engineering.md`：§7 plan-review 沉淀 / §10 文档偏差（execution agent 写）/ §11 自审记录（PM 跑 review 后 append）

#### 9.6.4 reconcile 步骤（标准动作）

skill 在 reconcile 模式下执行：

1. 计算 PM 视图当前 hash：`shasum -a 256 <pm-view-file> | cut -c1-12`
2. 读工程合同顶部 `synced_pm_view_hash`
3. **一致** → no-op，结束
4. **不一致** → 进入更新流程：
   a. 用 PM 视图最新内容 + 上游产物（`analysis.md` / 上游 `.engineering.md` / `docs/modules/*.md` / `prototypes/`）重派生**PM 视图驱动章节**的内容
   b. 不动**独立来源章节**（§7 / §8 等）；如发现独立来源章节的引用与新 PM 视图脱节（章节编号变了 / 功能名变了），同步修引用，但不重派生主体
   c. 把工程合同顶部 `synced_pm_view_hash` 改为最新 hash
   d. PM 视图主文件「📁 历史档案」/ 工程合同末尾追加一行：`<YYYY-MM-DD HH:MM> reconcile：<旧 hash> → <新 hash>`，并简述变更范围
5. 输出"reconcile 完成"信号，把控制权交回调用方（stage-gate / task-spec 步骤 12.5）

#### 9.6.5 read-side 容忍 stale

- `task-execute` 启动 agent 时读到的工程合同**可能是 stale 版本**（PM 视图已改但还没到 gate）。这是允许的——因为 PM 视图未到 gate 意味着 task 还没 confirm，agent 还没启动。task-execute 走到时必然已经过 reconcile。
- 中段 PM 跑 `/plan-eng-review`（stage 3 阶段）/ `/qa`（stage 6 阶段）看到的工程合同也允许是 stale。PM 在 chat 报告 review 发现后，AI 按 9.6.1 表格行为：纯 PM 视图层修订写 PM 视图、纯工程层沉淀写工程合同 §7。
- **禁止**：read-side 在读取前自动跑 reconcile（会破坏"gate 才同步"语义）。

#### 9.6.6 自检（生成 / reconcile 后）

工程合同写完或 reconcile 完成后自检：
- [ ] 顶部 `<!-- synced_pm_view_hash: ... -->` 注释存在且 12 字符
- [ ] hash 与 PM 视图主文件 `shasum -a 256 | cut -c1-12` 一致
- [ ] PM 视图驱动章节没有出现"已被 PM 视图删除"的旧概念
- [ ] 独立来源章节（§7 / §8）未被 reconcile 误改

### 9.7 跨 skill 共享原则

1. **`.engineering.md` 仅工程合同链路读**：PM 视图 skill（req-analysis / req-solution PM / task-plan / task-spec PM / prd-writing）一律 ❌ 不读任何 `.engineering.md`（§9.1 / §9.2）

2. **`docs/DESIGN.md` 在 PM 视图链路保留必读但分级**（按 §9.1 各 skill 行）：
   - `req-solution` PM 视图 / 工程合同：🟢 全文必读（方案设计需视觉规范基线）
   - `task-spec` PM 视图（first-gen + revise）：🟡 章节 grep（按 task 涉及功能 grep 相关章节，§9.1.1）
   - `task-spec` 工程合同：🟢 全文必读
   - `task-plan`：⚪ 按需（视觉决策不影响 task 拆分粒度）
   - `task-execute`：🟢 强制 cat 全文（视觉一致性护身符）
   - `close-task`：🟢 全文必读（PM 反馈第四类反推沉淀目标）
   - `prd-writing`：🟢 全文必读
   - **不可整体砍**：DESIGN 是 PM 反馈第四类（视觉规范）沉淀地（§9.4），不同 skill 按不同强度引用

3. **`prototypes/` 反向校验场景按 §9.3.1 grep 强约束**：仅 task-execute 例外（实现参考全文读）

4. **章节匹配场景按 §9.1.1 grep 强约束**：solution.md 在 first-gen 整文件读 / revise grep

5. **`PM-VIEW-RULES.md` 步骤 0 读 1 次/会话，后续步骤不重读**

6. **PM 反馈四类分流的读取分工**（§9.4）：
   - `task-spec` 读"同模块已完成 task 的 PM 反馈"前三类（正向规则 / 反向约束 / 决策记录）→ 落到当前 task 对应章节
   - `close-task` 步骤 1.5 读"本 task 的 PM 反馈"第四类（视觉规范）→ 反推沉淀到 `docs/DESIGN.md`
   - `prd-writing` **不读** `## PM 反馈` 段；prd-writing 读 task PM 视图的 `^## (📋 功能清单|🎯 关键产品决策|✅ 验收清单)` 三段是另一个目的（抽功能需求），与 §9.4 PM 反馈分流读法**不同读法 / 不同来源段**，不冲突

7. **closed/ 旧 task 读取边界**：扫描 `requirements/closed/**/tasks/*.md` 时，**只读 `## PM 反馈` 段**抽反馈条目；**不读**顶部 frontmatter / 元信息段落 / 任务卡表格的字段布局（v1 历史格式，新 task 按 v2 模板生成；混读会触发 task-spec 步骤 10.6 字段校验拦截重写）
