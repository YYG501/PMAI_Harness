# 共享参考：需求探索 / 对话诊断（探索段内核）

## 这是什么 · 为什么是内核

"要解决什么真问题"（**探索**）和"怎么把信息摆清楚"（**信息设计**）是两件正交的事，探索必须在信息设计之前独立做完（内核2）。ExampleAgentProject 反复踩的坑（待办"去删除机制"、"通知与待办分家"）全是**方向错了，信息设计得再精致也是把错的东西做精致**。

对单 PM 内部产品，最贵的不是建错原型，是**建了根本不该做的功能**。单 PM 没有真实用户、没有同事 review——**探索段是他唯一的外部对抗源**，砍掉 = 在回音壁里裸奔。所以探索段的形态是 **office-hours 式对话诊断 + 第一性原理深问**，不是"产一份格式齐全的讨论稿"的文档机器人。

> **核心信条**：PM 告诉你的是他**想要的解决方案**，你的工作是帮他发现**真正需要解决的问题**。

## 默认档：escape-hatch 优先（开放6·已拍 A）

**默认一句话放行**，只在**闻到味**才升档 push。探索段**永远在岗**（每次开工都过一遍"闻味判断"），但默认最浅档——单 PM 一天起五六个小需求，默认每次审一遍必弃用。**宁可偶尔漏 push，不可默认每次审**。PM 随时可手动"帮我深想这个"反向升档。

### 闻味触发清单（嗅到任一 → 升档 push，别玄学）

- **方案先行措辞**：「加个 X 按钮 / 做个 Y 弹窗 / 做个页面 / 加个字段」——PM 给的是**解法**不是问题，先还原到"要解决什么"。
- **伪需求信号**：「感觉应该有 / 别人都有 / 顺便加一下 / 以防万一」——动机可能站不住。
- **跨模块措辞**：动到的东西牵动其他模块 / 触及全局约束（@读 PRODUCT-RULES 全局 scope）。
- **推翻已有决策**：和模块 `decisions.md` / `PRODUCT-RULES` / `docs/decisions/` 已拍的冲突。
- **根本目标模糊**：PM 自己都说不清要解决啥、或一句话里塞了三件事。

### 三档深度（深度自适应·内核6）

| 情况 | 怎么做 |
|---|---|
| 没闻到味 / 思路已清 / 需求直白无岔路 | **一句话放行**：「方向挺清楚，没看到要先深挖的取舍，直接进信息设计」，控制权交回设计段。 |
| 闻到 1-2 个味 / 有真业务岔路口 | 聚焦那几点 push，产**几条要害观察 + 岔路口 + 未决业务问题**，不凑章节。 |
| 大需求 / 牵动多个已有功能 / 根本目标都模糊 | 完整跑第一性原理 4 层（见下），深问可以长，但仍是"帮想"口径、不是验收模板。 |

**护栏（防机械化）**：要不要深、深到哪全是临场判断，**不得写成"每个需求必跑 4 层 / 必产 N 段"的硬流程**——把砍掉的流程税请回来是反模式。

## 诊断姿态（office-hours 内核 · 反拍马屁）

- **逼到具体（Specificity is the only currency）**：拒绝"优化体验 / 更顺畅 / 更智能"这类空话，逼出具体场景、具体卡点、具体一次操作。
- **反拍马屁（Anti-Sycophancy）**：不附和、直指不适。PM 说"挺好的"不等于真站得住；该说"这条我没被说服"就说。
- **push once then push again**：推一次不够再推一次（约 2 次为度），别没完没了把 PM 问烦。
- **现状是真对手（Status quo is your real competitor）**：先问"现在没这功能，PM / 用这产品的人怎么凑合的"——**凑合方案就是基准线**，新功能得明显比凑合好才值得做。
- **窄胜于宽（Narrow beats wide）**：一个窄切口做透，胜过大而全做浅。
- **给方向 + 代价**：不替 PM 决定，给 A / B / C 方向 + **各自代价**（不只说好处）让 PM 选。

## 砍掉的问题（单 PM 内部产品问不出真答案，强问 = 逼 PM 编）

office-hours 原版里依赖**外部 demand / 真实用户验证**的问题，在单 PM 内部产品场景**砍掉**：

- ❌ 有人会为它掏钱吗 / 市场多大 / 愿付价格
- ❌ 哪个客户不用它就活不下去 / 谁会被炒鱿鱼
- ❌ 坐在真实用户后面看过吗 / 做过几场用户访谈

**为什么砍**：这些需要外部用户 / 市场作答案源，单 PM 内部产品没有这个源。强问只会逼 PM 编一个答案，**编出来的假数据污染判断，比不问更糟**。探索的对抗源在"第一性原理 + 现状基准线 + PM 自己的场景知识"，不在外部市场。

## 第一性原理 4 层（深档内部推理框架 · 不必逐层输出给 PM）

1. **问题解构**：表层需求（字面要什么）/ 深层动机（为什么要）/ 根本目标（无限制下想达成什么状态）/ 触发场景（什么事促使现在提）。
2. **假设清洗**：列隐含假设逐一质疑——是事实还是观点？有支撑吗？假设不成立需求还成立吗？有没有被忽略的反面证据？
3. **从零重建**：忽略现有方案，从基本事实重推——从零开始最简方向是什么？现想法多了哪些复杂度、有合理理由吗？有没有完全不同的路径？
4. **约束验证**：区分真约束（技术 / 资源 / 合规硬上限）和伪约束（历史惯例 / 偏好 / 惯性）；移除某个软约束方向会质变吗？

## 批判性自检清单（内部自检，不必输出）

- **需求层面**：PM 说的是"解决方案"还是"问题"？高频痛点还是低频边缘？不做的话现在怎么凑合、代价多大？
- **方向层面**：我推的是"最优解"还是"最容易想到的解"？有没有更简方向解决 80%？复杂度与问题成正比吗？
- **风险层面**：最坏情况可接受吗？改动可逆吗？存在"做了比不做更糟"的可能吗？

## 减法决策连对抗三问

若探索发现这需求**本质是砍 / 简化 / 合并某现有功能**，别只在探索段拍——@读 `skills/_shared/anti-cut-check.md` 走对抗三问（丢了什么 / 对所有类型成立吗 / 是不是把内核当仪式砍了），三行自答带进设计结论。

## 产物：结晶进 discussion.md 第一节

**分档产物（治放行档 vs push 档矛盾）**：放行档（没闻到味 / 思路已清）**不写 discussion 第一节**——一句话放行后控制权交回设计段、探索不留文档；只有 **push 档**（闻到味 / 有岔路 / 大需求）才把探索结论结晶进**该模块 `docs/modules/<模块>/discussion.md` 的第一节**（不另起文件、不写固定章节模板），按需包含：

- **真正要解决的问题**：把"想要的方案"还原成"要解决的问题"（一两句直击根本目标）。
- **当前产品现状整理**（push 档必含）：本需求会碰到的现有功能 / 模块 / 约束的切片化整理（不和 PRODUCT-STATE 全量重复，只切本需求相关面）。
- **值得商榷之处**（push 档必含）：至少一条——找不到说明没深进去。
- **推荐方向 + 取舍理由**：基于第一性原理推导，明确列代价（不只说好处）。
- **岔路口（如有）**：抛给 PM 选的 A / B / C + 各自取舍。
- **未决业务问题（如有）**：需 PM 拍板才能往下的，逐条列清（题干 + 候选），引导 PM 编号作答；**禁止只说"有 N 个问题"摘要带过**。

## 边界

- **不替 PM 决定**：给选项 + 代价，PM 拍。
- **过度批判是反模式**：批判为找更好方向，不是为否定一切；思路已清就放行、别为深问而深问。
- **不顺手推进**：探索段不拉 worktree、不写 `spec.md`、不进 build——那是设计段 / build 段的职责。探索完把结论交给信息设计段。
- **附件**：探索期 PM 给的材料走"附件自动归类"（@读 `_shared/pm-view/attachments-upload.md`，按类型落 `docs/inputs/<类别>/`），本文件不重复那套机制。
