# 项目设计系统合同

本合同只负责把消费仓已经选择的设计系统接入 PMAI 的 UI 工作流。它不实现、复制或版本化任何具体设计系统，也不替代项目自己的产品设计基线。

## 1. 三层真相源

涉及界面的 design、mockup、build、quick-fix、mirror-site 和视觉验收，始终按下面三层读取：

1. 根目录 `DESIGN.md`：定义当前产品的体验目标、视觉基调、交互习惯、采用范围和共享组件 inventory；无论是否接入外部设计系统都必须先读。
2. `DESIGN.md` 声明的项目级设计系统 Skill：定义该设计系统的组件 API、token、Pattern、安装方法、版本边界、可访问性和其它内部规则。
3. `.pm-workflow/project.yml` 与当前实现：定义真实技术栈、实现根、入口、已安装依赖和现有组件；外部 Skill 不得绕过项目定义另起一套应用框架。

模块 `spec.md` / `decisions.md` 继续定义本次功能做什么。外部设计系统 Skill 只约束如何用其设计能力实现，不能替代产品决定、规格或 PMAI 的 build 生命周期。

## 2. 识别项目声明

先读取 `DESIGN.md` 的“项目设计系统”段：

- 旧消费仓没有该段，或 `状态` 为 `未接入`：视为没有外部设计系统 Skill。继续按 `DESIGN.md`、共享组件 inventory、现有页面和现有组件工作；这不是忽略 `DESIGN.md`。
- `状态` 为 `已接入`：必须取得 `设计系统`、`使用范围`、`项目级 Skill` 和 `Skill 文件`。这些字段缺失时停止当前 UI 工作，先修复消费仓声明。
- `Skill 文件` 必须是仓内相对路径，不能是绝对路径或包含 `..`，必须解析为仓内普通文件，并且已经被 Git 跟踪。缺失、不可读、越出仓库或未跟踪时停止；不能只凭记忆、网页摘要或相似 Skill 假装已经遵循。

`使用范围` 是产品采用边界。即使当前页面不在采用范围内，也要执行已声明 Skill 以确认边界，但不得把它的组件或视觉语言扩散到范围外。改变状态、范围或设计系统属于产品/技术方案决定，由 design 让 PM 拍板并更新 `DESIGN.md`，其它流程不得静默改写。

## 3. 执行项目级 Skill

当状态为 `已接入` 时：

1. 当前宿主能按 `项目级 Skill` 原生解析时，直接调用该 Skill。
2. 当前宿主不能原生发现项目 Skill 时，完整读取 `Skill 文件`，并按其中要求继续完整读取 required references、清单和安装说明，再执行同一流程。
3. 不把项目 Skill 复制到 `.codex/skills`、`.claude/skills`、`.opencode/skills` 或其它宿主目录来制造多份真相源。跨宿主始终引用 `DESIGN.md` 声明的同一个仓内文件。
4. Skill 要求联网、安装依赖、修改配置或访问公司资源时，仍遵守当前宿主权限和 PM 确认规则；未完成的步骤必须如实标为未完成。

首次进入 UI 工作、每轮反馈修改、中断恢复、主控切换，以及最终视觉验收前，都重新读取 `DESIGN.md` 和已声明 Skill。不能依赖前一轮 prompt 中的旧快照。

## 4. 冲突与证据

- `DESIGN.md` 与模块规格决定产品体验和采用范围；项目 Skill 决定设计系统内部的正确用法；`project.yml` 决定实现框架和代码边界。三者无法同时满足时，停止并向 PM 说明具体冲突，不自动覆盖任一真相源。
- 外部 Skill 若要求改变 framework、implementation root、产品范围或 prototype/product 实现深度，返回 `/pmai-design` 处理；不能在 build 或 quick-fix 中顺手改造。
- 设计系统仍处于 Alpha、试点或其它受限阶段时，沿用其真实成熟度和采用限制；未经相应评审，不得描述为 production-ready。
- HTML、图片或静态 mockup 只应用了设计规则时，只能说“按该设计系统规则探索”。只有真实实现已经安装并实际导入对应 Core / 组件，且通过该 Skill 要求的检查后，才能声称“使用了该设计系统组件”。

PMAI 的验收继续对照 `DESIGN.md`、模块规格、当前实现和本合同；项目 Skill 的专属检查作为附加证据接入，不取代 production build、浏览器验收或 prototype boundary。
