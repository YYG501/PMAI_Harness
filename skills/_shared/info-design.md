# 共享方法论：信息设计

设计任何一张卡 / 一个页面 / 一套后端规则 / 一个流程之前，先把"信息长什么样"想清楚，再决定怎么写规格。这份文档是 `/pmai-design` 段②设计 + `/pmai-prd-writing` 模块规格模式的方法底座，分四块：

1. **理结构** —— 真通用内核（3 条，任何需求都过）+ 按需求类型选方法（七类，开放分类）。
2. **写规格** —— 通用灵活骨架（章节是菜单不是死模板）。
3. **磨文字** —— 收口纪律（去 AI 腔、术语统一、说人话）。
4. **规格 4 问的治法** —— 这是规格写得好不好的验收标准。

> **一条贯穿原则 · 根因优先**：PM 说"不对 / 不合理 / 没明白" → 立刻停，回信息模型本身重新想，**不在表面加提示文字打补丁**（加文字 → 加更醒目的文字 → 在错误消息里塞更多字）。概念打架先理正交（如"产品状态"和"计价方式"是两件事、别混成一个维度）；讲不清就上一条真实数据的具体例子，别堆抽象名词。
>
> **一步一停**：理结构的几问、写规格的几节，**一步一停、和 PM 确认了再进下一步**，不要一口气把全部分析做完丢给 PM。一次跑偏代价大，来回返工反而更慢。

## 一、理结构 · 真通用内核（3 条，任何需求都过）

> **2026-06-21 改（开放3 + 总纲内核2）**：删掉原"主干 5 问对任何需求都成立"——grep 实证三份非 UI 规格（商机专家AgentV2 / ROI / 成本）里"三身份"出现 0 次，5 问里至少 3 问（谁看 / 三身份 / 卡面抽屉）对无界面需求空转。改成 **很小的真通用内核（3 条）+ 按需求类型选方法（七类，见第二块）**。三身份等已下沉到对应类型的特化里。

下面 3 条 grep 实证所有类型都成立，**任何需求都过**；其余按需求类型选特化问题集（第二块）。

### 内核 1 · 真问题 · 谁因此能做什么决策 · 下游倒逼

- 真问题在 ①探索段已还原（@读 `module-questioning.md`）；这里确认："谁在什么情境看 / 用 → 从粗到细想知道什么 → 看完能拍什么板 / 做什么决策"。
- **下游倒逼结构**（最易漏）：这块信息若要喂给下游另一个对象（报价按"产品"列价、上一张卡按"客户"分组），本处就得用同一维度对齐，否则下游接不住。
- 一块信息若不支撑任何决策、也不喂下游，就问它为什么在这。
- **划清承诺边界**：哪些是对内判断、哪些会变成对外承诺，别让内部估算被当成对客户的保证。

### 内核 2 · 派生信息 4 环（框架最缺、ExampleAgentProject 最值钱的一步）

对**每一类 AI 派生 / 计算的信息**过完整 4 环——只标一句"这是算出来的"不给逻辑 = 没说清：

- **① 来源**：逐条分**录入 / 引用 / 计算**（录入 → 谁录、维护在哪；引用 → 哪个源；计算 → 指向第②环或单独逻辑文档）。先广泛收真相源（文档 + 上传材料 `docs/inputs/` + 现有原型代码，但**代码只是原型、不是真相源**）；本该有源的信息绝不手写编造。
- **② 生成**：复合计算 / AI 判定要把**计算流程写清 + 完整提示词整段写出**。判据 = 能不能稳定落成一个 prompt 跑出一致结果；写不出 prompt = 逻辑没定清。
- **③ 变更**：依据变了 Agent 怎么重算；人发现不对怎么定位根因（需求变了 / 引用源该改 / 规则有缺陷 / 还是这单是个案要锁定不动）。
- **④ 重算影响**：人工拍过的决策，AI 重算**不许静默覆盖**；新算结果和人定的冲突要提请人确认，不能默默盖掉。
- **自检**：4 环都答得出吗？第②环写不出 prompt = 没定清；第④环没想清 = 人改完会被默默盖回。

### 内核 3 · 状态（别只画正常态）

枚举这个东西会处于的所有状态，**别只画"一切正常"那一种**。常漏：空（还没数据）/ 计算中 / 正常 / 基于旧数据 · 待重算 / 有冲突 · 待人澄清 / 人工已锁定（人定死、不许 AI 动）。每个状态画出来：怎么进入、界面长什么样、能做什么不能做什么。

> **文案风格**贯穿所有类型，纪律统一收在「四、磨文字」：第一步先判需求类型走对应风格——讲"一个东西怎么运转"（Agent / 流程 / 状态机）= **机制叙事型**大白话；讲"一堆字段 / 状态 / 权限是什么"（卡片 / 管理页）= **规范定义型**。一份规格里可混用（讲机制的章节叙事、字段表仍按定义型）。界面文案能少则少，不出"重算 / 漂移 / 派生"这类系统内部词。

## 二、理结构 · 按需求类型选方法（两面：逻辑面 + 呈现面）

①探索段收尾，AI 必须说一句 **"这是 X 类需求，所以打算用 Y 套设计问题"**、PM 拍——**定类型是理结构的前提，必须在动手前完成**。

**关键：'类型'不是从一张清单里挑一个就完——很多功能同时有两面，只做一面就会漏掉另一面。** 反面教训：把一个'后端引擎'判定（如 ROI）**只当逻辑面、声明'非界面卡'**，就把它在卡上怎么显示、人怎么交互（看依据 / 否决 / 过目）整个漏了，事后才发现"输出根本没想过怎么呈现给人"。两面拆开判：

- **逻辑面**（它在后端怎么算）：后端规则 / 纯算法 / Agent·引擎 / 业务流程·状态机。
- **呈现面**（它给人看的那张脸怎么设计）：信息密集 UI 卡 / 多对象管理页 / 数据产物。

**先判逻辑面是哪类，再判有没有呈现面**——**只要结果要展示给人，就必须同时按对应的呈现类型把那张脸设计出来**：落点（显示在哪张卡 / 哪个位置）、卡面放什么、抽屉看什么、人怎么操作（看依据 / 否决 / 过目）、待办落哪——**并和 PM 确认、视觉 / 布局拿不准调 /mockup**。**纯后端、没有界面的，才只有逻辑面。** 引擎类那句'输出落哪几张卡'不是一笔带过，是要按呈现类型真设计的一面。

除 3 条通用内核外，按两面各自所属类型加特化问题集 + 专属硬自检：

| 面 | 需求类型 | 特化问题集（除 3 条通用内核外） | 专属硬自检 |
|---|---|---|---|
| 逻辑 | **后端规则** | 触发前置 + 判定（可落 prompt）+ 默认值 + 冲突兜底 + 对谁可见 | 判定写得出 prompt 吗 |
| 逻辑 | **纯算法** | 输入域与边界 + 判定逻辑（完整 prompt）+ 输出精度（档位 vs 数值、不给假精确）+ 回归怎么验 | 换批数据漂不漂、精度档位定了吗 |
| 逻辑 | **Agent / 引擎** | 触发时序（攒批 / 防抖 / 上限）+ 重算依赖传播 + 人机权威 + 静默还是提醒 + 输出落哪几张卡 | 人改完会被静默盖吗、触发会风暴吗 |
| 逻辑/流程 | **业务流程 / 状态机** | 全状态枚举 + 分支 + 异常路径 + 在场 / 不在场两套 + 回退 | 异常路径和回退画了吗 |
| 呈现 | **信息密集 UI 卡** | 一行原子粒度 + 卡面 vs 抽屉 + **三身份界面可区分**（AI 建议 / 已确认 / 待确认——三身份归这里、非 UI 呈现不出现） | 卡面是否只答漏斗前 1-2 层 |
| 呈现 | **多对象管理页** | CRUD 全列 + 列表 / 详情 / 批量 + 权限边界 + 空态 | 动作列写全没（别"等操作"） |
| 呈现 | **数据产物**（如报价 BOM Excel） | 字段 schema / 列定义 + 命名规则 + 版本与覆盖策略 + 可信度继承 + 预览即文件不前端重建 | 多版本会互相覆盖吗、字段有真相源吗 |

**类型是常见型、不写死（开放3·已拍 B）**：判出某面"不属于任何已列类型" → AI **逐类说明为何不适用 + 明说理由 → PM 拍 → 临时定一套方法 → 事后把新类型特化集沉淀回本表**。新类型 = 昂贵的例外，不是逃逸的默认（防用"这是新类型"绕既有方法纪律）。

**深度自适应**：默认轻过，拖深附理由 + PM 拍——别机械化成"每类必跑全部特化问题"。

**选方法层 = 写规格 §八 = 同一套类型**：这里定的需求类型，直接决定写规格 §八核心动作怎么排（见第三块 §八）。理结构问什么、写规格怎么排，用同一分类，不另起一套。

### 信息密集 UI 卡 · 特化说明（一行原子粒度 + 卡面 vs 抽屉）

- **一行 / 一条原子粒度**：多对多关系挑**跟下游对齐的那一侧**当主线、另一侧退明细。**同一对象别在一张卡里重复出现**（反例：能力匹配按"细分能力"为一行 → 同一产品冒 5 次；正确按"产品 / 定制项"为一行、细分能力退抽屉）。定不下"一行代表什么"，卡就建错。
- **卡面 vs 抽屉**：卡面只答漏斗前 1–2 层（扫一眼能拍板的）；深读 / 取证 / 看明细进抽屉，**一个对象的深读合进一个抽屉**，别散成"查看产品 / 查看需求 / 详情"三个入口。信息不上卡面就进抽屉，别堆一脸。

## 三、写规格 · 通用灵活骨架（章节是菜单，不是死模板）

理清结构后写规格。**这是写规格动作**（段③）——写骨架、磨文字、自检都在这一步里。核心要求：**骨架是可选菜单 + 自适应形式，不是逐章必填的死模板。**

### 顶部声明（建议写，成熟规格可省）

规格第一屏建议钉一句，治"分不清原型还是规格"：

> 本规格是这个功能的**权威定义**。与原型不一致时，以规格为准；规格没说清的，先和 PM 确认再实现，不要照着原型臆测。

**何时可省**：成熟 / 已对外发布、读者本就清楚"这是规格不是原型描述"的，可不写（金标准待办 spec 就没写）。新规格、原型与规格易混的场景仍建议写。

### 格式骨架（统一，别灵活）

"内容呈现灵活"指的是**功能清单 / 核心动作怎么排**（表格 / 文字 / 编号句按内容选）；**文档骨架格式要统一、不灵活**，照金标准（待办 spec）来——别把"灵活"理解成连标题序号、术语表格都随意：

- **标题带序号 + 用标准节名**：大标题用中文数字（`## 一、概述`……）+ 子标题用 `N.M` 阿拉伯数字（`### 4.1`、`### 4.2`，N = 所属大节号），不用无序号标题。**标题用规范节名（名词化：概述 / 名词解释 / 用户与场景 / 信息模型 / 业务规则 / 核心动作 / 状态机 / 验收标准…，见下「章节菜单」），不用口语句子当标题**——"各种状态，别只画正常的"这种是**写作提醒、放正文**，标题就叫"状态机"；"一个干系人这一行放什么"→标题用"信息模型"，"人能做什么"→"核心动作"。内容大白话，但标题标准化。
- **名词解释 / 版本信息 / 变更日志 用表格**：名词解释固定 `| 术语 | 含义 |` 两列、不用 bullet 列表；版本信息、变更日志也用表格。
- **并列项用表格、讲机制流程用叙述**：字段 / 状态 / 对照这类并列信息用表格；有先后 / 条件的流程用大白话分段（① ② ③）。

### 章节菜单（有就写、没有就省）

下面 10 节是**菜单**。先判这个功能需要哪几节、每节用什么形式，再动笔。唯一判据 = **把需求讲清楚**，不硬凑全 10 节、不硬塞表格。**注意"哪几节灵活、每节什么形式灵活"，但上面「格式骨架」（标题序号、术语 / 版本 / 变更日志用表格）不灵活。**

| 节 | 装什么 | 什么时候要 / 形式 |
|---|---|---|
| 摘要 | 一段话说清这功能是什么、给谁、范围 | 都要，≤ 80 字 |
| 一 · 版本信息 | 文档名 / 版本号 / 撰写人 / 评审人 / 时间 / 状态 | 都要，格式对齐姊妹规格 |
| 二 · 变更日志 | 日期 / 版本 / 改了什么 | 都要 |
| 三 · 名词解释 | 本功能的术语 / 角色 / 关键概念 | 有术语才写，无则从简 |
| 四 · 概述 | 业务诉求 → 设计取向；为什么做、解决什么 | 复杂功能写，小改省 |
| 五 · 用户与场景 | 角色 + 用户故事 + 非目标 | 都要（非目标尤其别省，划清边界） |
| **六 · 信息模型** | **派生信息 4 环 + 字段口径 + 状态机**（框架最缺的一节） | **信息密集才写**（卡 / 多对象页）；简单功能省 |
| 七 · 业务规则 | 判定规则、约束、默认值 | 有规则才写；复合 / AI 判定要可落 prompt |
| 八 · 核心动作 / 功能需求 | 用户能做什么、怎么做 | **形式按需求类型自适应**，见下 |
| 九 · 验收标准 | 可独立验证的验收点，按用户故事编号 | 都要，写得可测 |
| 十 · 附件 | 枚举值 / 字段字典 / 原型覆盖范围 / 实施技术 | 按需 |

### §六信息模型：按需出现

信息密集的功能（卡、多对象页）才写这一节，把「理结构」内核 2、3 的产出落进来：

- **字段口径集中在这一节一处用表格**（字段 / 含义 / 来源 / 格式 / 必填 / 限制），不散在多处。需求描述提到某字段时把含义就地带出。
- 名词 / 枚举写明判定条件（"什么情况算 X"）。
- 派生字段写清 4 环；状态机画全（别只画正常态）。

简单功能（一条后端规则、一个小流程）没有复杂信息模型，**省掉这一节**。

### §八核心动作：按需求类型自适应（和第二块选方法层同一套七类）

这是明确"按需求类型灵活"的一节——**用第二块定的类型决定怎么排**，不对号入座硬塞表格：

- **信息密集 UI 卡**（能力匹配 / 上下文头）→ 按**信息块**拆（卡面 / 详情 / 纠正…）；卡片多是"看 + 少量交互"，表格难懂就直接写散文 / 小标题，更好读。
- **多对象管理页**（产品库这类）→ 按**创建 / 编辑 / 删除 / 启用停用**拆，用功能表格（动作列全，别写"等操作"）。
- **后端规则** → 按**触发 → 判定（可落 prompt）→ 默认值 → 冲突兜底**拆。
- **纯算法** → 别塞功能表，单独用**流程图 + 完整 prompt + 输入域 / 输出精度 + 回归怎么验**。
- **业务流程 / 状态机** → **全状态枚举 + 分支 + 异常路径 + 回退**，多步用分段叙述。
- **Agent / 引擎 / 机制** → 按**处理环节**拆（触发时序 / 输入 / 计算逻辑[可落 prompt] / 重算传播 / 人机权威 / 输出落哪几张卡）。
- **数据产物**（报价 BOM Excel）→ **字段 schema / 命名规则 / 版本覆盖策略 / 可信度继承**；预览即文件、不前端重建。

先和 PM 确认核心动作的分级骨架，再写内容。

### 其余节同理

有就写、没有省掉：无术语则 §三从简，无非功能需求写"暂无"。**保留的是写作纪律**（见第三块磨文字），**放开的是章节与形式**。

### 写产品行为，不写原型布局（按产品写、不以原型为主）

规格写的是**产品需求**（这东西是什么、谁用、什么时候出现 / 消失、能做什么决策、点了怎样），不是**描述原型长什么样**。把握一条线：**UI 只写到"按钮 / 页面 / 区块"级**（`[确认]` 按钮、项目详情页、待办列表），**布局细节交给 mock**——段头折叠展开、卡片排几列、弹窗里控件怎么摆、按钮置灰还是隐藏这类，规格不写。

- **判据**：每写一条问自己——这是**定义产品要做什么**（规格留），还是**描述原型现在长什么样**（删 / 交给 mock）？
- **金标准参照**：模块 spec 学待办 spec 那种"讲产品行为、UI 到按钮级"的写法。真系统研发 PRD（`prd-writing` 的 PRD 模式产出、UI 即交付契约）才穷举 UI 细节——那是另一类产物，别把它的写法搬进模块 spec（见第四块「两类产物、两套风格」）。

### 设计确认靠 mock，不靠规格里画 ASCII

**规格里不嵌原型 ASCII**（它既是"分不清原型 / 规格"的混淆源、又是多余的原型解释）。设计长什么样，提前用 `/mockup` 生成的页面给 PM 确认；规格只留 normative 文字 + 一句引用那个 mock（"页面布局见已确认的 mock：<路径>"）。这条同时治规格 4 问的问题 1 和问题 3。

### spec 正文 = 纯最终事实（不留迭代痕迹）

spec 正文只写"现在是什么"，**不留删除线 / "（6-14 改）" / "老版新版"这类迭代语**（变更日志一行说改了什么即可）；"为什么从 A 改成 B"的完整留痕只在 `decisions.md`。这条消除"就地升版要留痕"和磨文字"只写最终事实"的指令冲突——留痕归 decisions、正文保持干净。

### 重做模块 = 就地升版，不另开文件夹

重做一个已有模块时，**在同一个 `docs/modules/<模块>/` 文件夹里就地演进**：

- `spec.md` 顶部版本号 +1、变更日志加一行说改了什么。
- 被推翻的旧结论在 `decisions.md` 里标 supersede（删除线或注明"已被 X 取代"），**不是删掉假装没发生过**，留得下"为什么从 A 改成 B"。
- **不 per-版本另开新文件夹**。只有"模块身份本身变了"（不再是同一个东西）才另起 + 归档旧的——这是例外，边界模糊时让 PM 拍。

### 合并 / 迁移旧内容时 reconcile

把旧文档合进新真相源时，不是照搬——要**先 reconcile**：被推翻的旧结论标 supersede 或删、清掉残留，矛盾内容绝不照搬进新真相源。

## 四、磨文字 · 收口纪律（写完照着扫一遍）

信息和结构齐了之后，把文字层磨成简洁、易懂、无 AI 腔的定稿。**只动表达和格式，不动信息结构**——发现要改的其实是结构（某字段该不该在、两个状态该不该合），停下来，那是回第一块「理结构」的事（甚至回②选方法 / ①探索），别在磨文字时顺手改了。

下面是收口纪律，分两层：**底线**（写的时候就守）和 **9 条磨文**（定稿时逐条扫）。

### 写作底线（边写边守）

- **先结论后规则、短句、动作先行。**
- **自包含**：规则 / 约束 / 文案在当前位置直接写清，不让读者追"详见 §X"跳转、查字典、读源码。（"详见 §X"只在引用本规格之外的文档时用。）
- **一套语体、章节菜单、功能需求按类（重要）**：spec 和 PRD **语言风格完全一样——都走"简要易懂"**（待办 spec 那种产品同事读一遍就懂的讲法，金标准实例见 `few-shots.md` 顶部）。**不分"spec 大白话 / PRD 重型"两套**；两者区别只在：① **勾了哪些章节块**（PRD 比 spec 多 §业务诉求 / 设计原则 / 方案价值 / 数据权限范围等，见 SKILL.md 章节菜单"必写/可选"），② **"功能需求"那一节怎么组织**（按功能模块类别选表格 / 叙述 / 流程+提示词…，见第二块七类 + SKILL.md §八）。**通用卫生任何文档都守**：8 类禁用 + 术语锁定（原 L6）+ 引号统一。`writing-rules.md` 原 L1–L5 重型指纹（加粗短句+反例后果 / 边界并列 / 等式 / 对偶 / cell 加粗）**降为"可选讲清楚工具"——需要时才用、不强加**；别拿它们把任何文档写重。
- **禁黑话清单（单一真相源：`skills/prd-writing/references/writing-rules.md` 的 8 类禁用）**——本文不另立一份禁用清单，只摘要、详则以那份为准：
  - 不出代码 / 字段名 / 路径 / 文档章节号。
  - 不中英混杂（prompt → 判定提示词、review → 核对、CRUD → 列全创建 / 编辑 / 删除、scope → 管辖范围）。
  - 不用技术 jargon（鉴权 → 权限判断、悬挂引用 → 引用了不存在的部门）。
  - 不用书面冷僻词（链路 / 颗粒度 / 派生 / 漂移 / 承接 / 落库）。
  - 不用版本迭代语（v1 / v2 / 重做 / 第 N 轮 / 老版新版）——读者看的是最终需求，不是迭代过程。
  - 不用兜底词（等 / 之类）、主观词（清晰展示 / 明显标识）——列全、给具体展示方式。
  - 引号用半角 `"..."`，按钮用 `[...]`，**不用 `「」`**。

### 9 条磨文（定稿时逐条扫，发现一处改一处）

每条都带"为什么"——理解了为什么，遇到没列到的情况也能照着判断。

1. **只写最终事实。** 正文不写"（6-14 定）""（原型注意）""见决策 X"这类改动标注和元信息。规格是给读者看"现在是什么"，不是看"怎么一步步改过来的"——那些归变更日志和决策记录。
2. **不造词，一个概念一个词。** 同一个东西别整两套说法（"待过目"和"待审核"指同一件事，读者会以为是两个）。优先用产品里已有的词，全文一套词到底。
3. **去 AI 腔。** 不用对仗的小标题（"主动产出，待办露头"这种），不用"亮点 / 露头 / 赋能 / 抓手 / 闭环"这类空词。直接说人话。
4. **去行话动词。** 圈定 / 拉 / 撑起 / 收口 → 界定 / 给 / 据以算 / 统一。读者不用先在脑子里翻译一遍。
5. **多步流程用叙述、别塞表格。** 有先后、有条件的流程（先怎样、再怎样、人在场怎样、不在场怎样），用大白话分段讲（① ② ③）最清楚。表格留给"字段 / 状态 / 对照"这种并列项。
6. **术语精确、角色别搞错。** 同一概念、同一角色全文叫法统一；容易混的角色（A 是不是就是 B）核准了再写。
7. **删含糊修饰。** 引歧义的词（"演示期不数值化"——临时的还是一直这样？）要么删、要么一句讲清。模棱两可比不写更糟。
8. **格式对齐基线。** 版本信息这类固定格式、章节结构跟同体系的姊妹规格保持一致，读者不该每份都重新适应格式。
9. **写完自查。** 通读 + grep 残留——刚去掉的旧词、造的词、AI 腔词，确认真清干净。改一半最伤。

### 派 subagent 冷读自检

自己写的盲点自己看不出。规格写完，**派一个 subagent 拿这份文档当尺子冷读**，扫两类残留：

1. **机制 / 落点没说清**：状态 / 动作只给了名字，没说怎么发生、落在哪（界面标记 vs 进待办）、记什么、界面长什么样。
2. **内部简称 / 浓缩词读者要猜**：如"四面"得就近说清是功能 / 指标 / 部署 / 服务。

拿回清单逐条改。这是 silent 自检，不升格成强制 review 门。

## 五、规格 4 问的治法（写规格的验收标准）

PM 列过 4 个老问题。这 4 条是"规格写得好不好"的验收标准——写完对照自查。

| PM 提的问题 | 根因 | 治法 |
|---|---|---|
| **1 · 分不清原型 / 规格，忘了规格要指导实现** | 把规格写成"描述原型现状" | 规格里**不嵌原型 ASCII**；设计长什么样提前用 `/mockup` 确认、规格只留 normative 文字 + 引用那个 mock；顶部钉"本规格是权威定义、与原型不一致以规格为准、没说清先确认"。每写一条自检：这是**定义需求**（规格留），还是**描述原型**（删）？ |
| **2 · 术语不统一** | 没有强制收口 | §三名词解释先列全 → grep 全文近义词 → 全部替换成 §三 定的称呼（L6 名词锁定）；开场加载项目级业务术语表（用既有词）；收口再 grep 一遍残留。 |
| **3 · 多余的原型 / 设计解释** | 把"为什么"和"原型样子"塞进规格 | 靠三件套分工甩出去：**"为什么"→ `decisions.md`**、**"原型样子"→ DESIGN / mock**、**规格只留 normative**。叠禁用清单（禁 UI 实现术语 / 禁元描述）+ 第 9 条磨文（只写最终事实）。 |
| **4 · review 原型时规格信息被悄悄删（drift）** | 规格 ↔ 原型 漂移、同步时丢内容 | **一致性扫描**（做法见 `_shared/consistency-scan.md`）：改了原型或规格就 grep 相关文档对账，每条对不上的都 flag"确认删 / 还是漏实现"让 PM 拍，不静默吞、不盲目重写。 |

> 这 4 条治法分散落在前面各块（不嵌原型在第三块、术语收口在第四块、一致性扫描单独成文）；这张表是把它们当"验收清单"汇总，写完规格逐条核。
