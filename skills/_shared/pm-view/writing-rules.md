# §三 PM 视图写作规则（硬约束）

> 本文件是 [`PM-VIEW-RULES.md`](../PM-VIEW-RULES.md) §三 的物理拆分。配套阅读：[`doc-strictness.md`](./doc-strictness.md)（§四 文档级严格度对照表）。

适用：所有 PM 视图层文档 — `brief.md` / `analysis.md` / `solution.md` / `task-plan.md` / `tasks/task-NNN-*.md` / `prd.md`。

---

## 3.1 每个名词必须明确指代

PM 视图里出现的每个名词，必须能让读者一眼知道**指代哪个对象 / 哪个页面 / 哪个区域 / 谁的属性**，不允许模糊指代。

| 模糊（❌）| 明确（✅）|
|---|---|
| 树最上面那一层 | 「产品详情页 - Tab 1 额度分配视图」的树形列表，最顶层节点 |
| 状态 Badge | 许可证状态 Badge |
| 状态列 | 许可证状态列 |
| 弹窗 | 「分配额度弹窗」 |
| 列表 | 「产品访问管理 - 产品列表页」的产品列表 |
| 失效证 | 状态为已失效（含已过期 / 已停用 / 已吊销 / 未生效）的许可证 |
| admin | 租户管理员 / 部门管理员（仅在其权限范围内的部门）|
| Tab 2 不动 | 「产品详情页 - Tab 2 用户开通（task-004 实现）」保持现状不动 |

**自检**：单字"状态"、"列表"、"树"、"弹窗"、"操作"、"按钮"、"用户"出现时，前面必须有完整指代前缀。

## 3.2 只描述功能行为

PM 视图回答：
- 系统应该提供什么
- 用户能做什么
- 业务规则是什么
- 数据字段之间的关系是什么
- 角色权限是什么
- 异常路径如何呈现

PM 视图**不**回答：

| 类别 | 不出现 | 替换为 |
|---|---|---|
| 像素值 | 24px / 420px / w-14 / py-5 | 移到工程合同 |
| 颜色码 | #C9CDD4 / #FFA39E | 移到工程合同 |
| 文字色名 | "红色文字" / "黄色警告" | "视觉高亮" / "视觉弱化" / "警告信息"（语义保留）|
| Emoji 视觉 | 🟡🔴⚫ | 移到工程合同；状态文案保留（未生效 / 已过期）|
| 反向约束 | "禁止 X" / "不允许 Y" | 移到工程合同；正向改写"系统不保留 Y"|
| 设计意图解释 | "（避免双重计数）" / "（防止角色爆炸）" | 移到「关键产品决策」的"共同理由"行 |
| 组件实现名 | reducer / dispatch / props / hook / useReducer / useState | 移到工程合同 |

## 3.3 保留产品视角行业词（含指代前缀）

所有 PM 视图文档都可以使用产品视角的 UI 行业词，但**必须**加完整指代前缀，让读者一眼知道指代哪个对象：

| 行业词（保留） | 必须加的指代前缀（举例）|
|---|---|
| Badge | 许可证状态 Badge / 部门额度状态 Badge |
| Drawer | 「额度明细 Drawer」 / 「用户详情 Drawer」 |
| Tab | 「产品详情页 - Tab 1 额度分配视图」 |
| Tooltip | 鼠标悬停时给出的说明性提示 |
| Toast | 系统给出成功反馈（Toast 形式）|
| Dialog / 弹窗 | 「分配额度弹窗」 / 「调整额度弹窗」 |
| 折叠区 | 「已失效」折叠区 |

## 3.4 正向描述系统行为

PM 视图用正向句式。**隐式反向（"无 X / 没有 X / 不出现 X / 不通过 Y"）等同于显式反向（"禁止 / 不允许"）**——同样要改写正向。

| 反向（❌）| 正向（✅）|
|---|---|
| 系统不允许保留中间态 | 系统将所有改动整体回滚到操作前的状态 |
| 禁止在该行额外添加文字标签 | 该行以视觉高亮方式区分 |
| 禁用「含子」概念 | UI 文案统一使用"勾选部门"的实操描述 |
| 行末**没有**跳转或操作入口 | 失效证仅供查看，管理员通过「租户配置 - 许可证管理」主入口处理 |
| **不出现**任何跳转入口 | 同上——描述系统提供什么 / 通过哪个入口处理 |
| **不通过**抽共享组件保证 | 由 PM 走查对照保证 |
| **不展示**「已用 / 剩余」两列 | 每维度展示总额单值 |

反向约束（"禁止 / 不允许 / 不准 / 禁用 / 不得 / 不出现 / 不展示 / 不通过 / 没有...入口"）一律移到工程合同。

**例外（lint 自动豁免）**：
- §📦 范围 描述本 task 移除/不再保留 X：天然反向，是 scope-change 描述（如"行展开内子行不再保留 [查看 ↗] 入口"）
- §✅ 验收清单 列出 PM 走查项时用"verify X 不出现"句式：天然反向，验证视角友好（如"不出现英文字段名"）
- §📋 编号项陈述当前数据未触发某规则的事实（如"当前数据下不出现「+N 个其他维度」提示"）：事实陈述而非反向约束

## 3.5 抽象动词必须搭配具体效果

以下动词出现时必须紧跟具体效果或对象：

| 动词 | 必须补全 |
|---|---|
| "更新 X 定义" | 更新后，对持有 X 的对象立即按新规则生效 |
| "保存后生效" | 生效后什么变化、对谁生效 |
| "立即更新" | 更新的具体内容 |
| "执行 X 操作" | 操作的具体步骤或结果 |

| 模糊（❌）| 完整（✅）|
|---|---|
| 保存后立即更新角色定义 | 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权 |

## 3.6 文档自包含

- 关键规则的简要说明应直接写在当前位置；同一规则在多处出现，每处都简要描述（约 1-2 句）。
- 禁止用「详见 §6.X」让读者跳转。
- "详见 §X" 仅用于引用本文件之外的文档（如 `docs/DESIGN.md`）。

## 3.7 禁用兜底词 / 主观词

| ❌ 错误 | ✅ 正确 |
|---|---|
| "编辑 / 启用停用 / 删除"等操作 | "编辑"、"启用 / 停用"、"删除"三个操作 |
| 默认角色清晰区分 | 默认角色行带"默认"标识 |

兜底词（"等"、"之类的"、"相关的"）必须列全所有项。

## 3.8 禁用书面冷僻词 / 中英混杂 / 技术 jargon / 数学化表达

| 类别 | ❌ 错误 | ✅ 正确 |
|---|---|---|
| 冷僻词 | 明示 / 暗中 / 链路 / 范畴 / 颗粒度 | 替换为日常中文（提示 / 隐含 / 流程 / 范围 / 粒度）|
| 中英混杂（业务词）| review / CRUD / scope / admin / breakdown / mock / self-contained / workflow / pipeline | 评审 / 创建-编辑-删除-启用停用 / 管辖范围 / 管理员（角色名首次出现可用"租户管理员 / 部门管理员"）/ 明细 / 模拟 / 各自独立 / 流程 / 流水线 |
| 中英混杂（状态字面量）| active / pending / null / undefined | 已激活 / 待生效 / 无值 / 未设置 |
| 中英混杂（数学/集合/函数）| sum / count / map / filter / reduce | 累加 / 统计 / 按 X 归并 / 按 X 筛选 / 合并 |
| 中英混杂（数据结构 / 实现词）| schema / record / props / hook / reducer / dispatch / topContent / kebab / segmented control | 这些是工程词，全部驱逐到 `*.engineering.md`（见 §3.2）|
| 反引号代码引用 | `\`quotaPoolId=null\`` / `\`useState\`` | 反引号包裹的代码 / 字段 / API 名 一律不出现在 PM 视图 |
| URL 参数字面量 | "URL 带 tab=pools&view=dept 查询参数" | "详情页直接定位到 Tab 1 额度分配视图、部门视角"——描述跳转结果而不是 query string |
| 技术 jargon | 悬挂引用 / 互锁陷入死锁 / 不参与鉴权 | 仍引用了不存在的对象 / 双方互相阻止对方操作 / 不参与权限判断 |
| 数学化表达 | 严格小于 / ⊊ / ⊆ | 完全包含在 X 之内（且至少少一个）|

**例外**：UI 行业词（Badge / Drawer / Tab / Tooltip / Toast / Dialog 等）允许保留，参见 §3.3。

## 3.9 禁用元描述 / 自指

文档内不出现对自身的描述：
- "本文档是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚……"

## 3.10 UI 骨架代码块内只写"屏幕上的字"

`§🖼 页面 UI 骨架` 章节里的 ASCII 框图代码块（` ``` ` 围起来的那段），**只允许出现 admin / 用户在屏幕上实际能看见的文案**。任何对字段、区块、状态的解释、注释、设计意图、口径说明 → 全部剥离到骨架代码块**下方**的「关键交互说明」段。

**反例对比**（一个浓缩示例覆盖所有变体）：

❌ 骨架内混入非屏幕字：

```
┌─ 许可证使用情况（新增·简化版） ─────────┐
│ 席位（独占）：1（独占，固定）            │
│ Agent 实例：3 个 · 独占 · 已使用 1 / 剩 2│
│ 配额（按该产品维度集动态显示）          │
├─ 旧版授权 V1（已吊销，弱化） ───────────┤
│ [▸ 高级配置]   ← 默认值藏在这里        │
└─────────────────────────────────────────┘

[选择来源许可证（多证场景下出现）]
```

✅ 骨架内只写屏幕字 + 解释下沉：

```
┌─ 许可证使用情况 ─────────────────────────┐
│ 席位：1                                  │
│ Agent 实例：3 个 · 已使用 1 / 剩 2        │
│ 配额：32 万 token                        │
├─ 旧版授权 V1（已吊销） ──────────────────┤
│ 共享部门：研发部 / 产品部                │
│ 范围：仅本部门  [改为共享部门额度]       │
└──────────────────────────────────────────┘

[选择来源许可证]
```

**关键交互说明**（骨架下方文字段，承载所有被剥离的注释）：
- 「许可证使用情况」区块在 task-XXX 新增；展示形态延续 task-YYY 的多维度透明展示模式
- 「席位」字段对所有产品恒为独占占用（系统保证）；UI 不重复标注
- 「配额」字段按产品配置的多种计量维度动态展示（token / 调用次数 / 存储 GB 等）
- 「旧版授权 V1」区块视觉弱化（具体视觉规范见 `docs/DESIGN.md`）
- 「改为共享部门额度」按钮：席位默认为独占，仅当 admin 显式切换为共享时进入共享部门选择流程
- 「选择来源许可证」入口仅在多证场景出现（admin 名下持有该产品 ≥2 个许可证时）

**5 类失败模式都是这条规则的应用**：

| 失败模式 | 错在哪 | 怎么改 |
|---|---|---|
| 默认值标注（"席位（独占）"） | 系统恒定属性，屏幕字本身没有这个标 | 直接写值，元数据进 §交互说明 |
| 文档元注释（"（新增·简化版）"） | 给文档读者看的，admin 看不见 | 完全删除（变更范围说明在 §📋 / §🔄 已有） |
| 设计意图（"（已吊销，弱化）"） | 给设计师/工程师的实现指令 | 文案保留状态名「已吊销」；视觉弱化进 §交互说明，引 `docs/DESIGN.md` |
| 字段口径（"（多证场景下出现）"） | 给读者解释字段定义 | 屏幕字保留入口名；触发条件进 §交互说明 |
| 折叠藏默认值（"[▸ 高级配置]"） | 默认值伪装成扩展项 | 默认值直接渲染；override 走单独按钮（如「改为共享部门额度」） |

**自动 lint 边界**：`check-doc-pm-view.py` 仅对骨架代码块内出现的 `（...）` 报 warning（不区分类型）。warning 不阻塞，由 PM/AI 自判是合法标识型（CSV / 1080p / 2 个）还是非法释义型（基于 X / 按 Y / 多 Z 场景）。其余 4 类失败模式 lint 抓不全，靠步骤 5 自检 + reviewer。

### 3.10.1 骨架宽度硬约束

ASCII 框图模式下，骨架代码块每行 ≤ 80 字符（约 78 列内容 + 2 列 border）。

**为什么**：标准 viewport（VS Code preview / 飞书 / Notion / GitHub）能在不水平滚动的前提下完整显示；超过 80 字符时部分渲染器会强制折行，box 字符与中文全宽字符混合 wrap，列对齐崩塌（v3.5 实证）。

**超出 80 字符的常见原因 + 修法**：

| 原因 | 修法 |
|---|---|
| 紧凑行用了完整业务名（"Agent 实例数 / API 调用次数 / 图片生成插件"） | 改用维度简称（席位 / Agent / API / 图片 / 美元）——简称是 80 字符硬约束派生的命名约定，与"产品详情页 Tab 1 池行" convention 对齐 |
| 单行塞太多字段 | 拆成多行（header 行 + 数据行）；每行只放一个语义单元 |
| 列宽设置过大 | 列名长度不超过对应数据最大长度 + 2 字符 |

**渲染兜底**：即便 ≤ 80 字符也可能在某些 markdown 渲染器（不识别代码块 monospace）下挂掉。如果你的渲染器对 ASCII 框图不友好，换用 VS Code preview / Obsidian / Typora 等支持 monospace 的 viewer 看。框架不再为非 monospace 渲染器降级——保留 ASCII 框图的 PM 直觉价值。
