# /pmai-design · 设计驾驶舱（三段式）

## 入口护栏

执行本 skill 前先运行：

```bash
source "${PMAI_HOME:-$HOME/.pmai}/scripts/skill-preamble.sh"
```

如果输出 `PMAI_PROJECT_INITIALIZED: 0`，停止本 skill，只引导 PM 先发 `/pmai-init-project`。初始化或已有代码接入完成前，不要创建模块三件套。

> 本 skill 是设计的"驾驶舱"。三段式：**①探索 → ②设计 → ③交给 spec-writing 成文**——先懂问题再设计（探索和信息设计是两个正交阶段）。方法论全文不内嵌在这——开工前 `@读`：
> - `skills/design/references/design-method.md`（**①探索 + ②设计**：真问题、Meta 触发、信息底线、按需求两面选方法、design-card 边界、PM 输出模板）
> - `skills/_shared/consistency-scan.md`（收口：改原型 / 规格 → 对账 → flag）
>
> 给 PM 的话里**不出现** 通用内核 / 4 环 / 三身份 / drift 这类内部术语，全程大白话。

## When To Use

- 起一个**新功能模块**（PM 一句话需求："做一张能力匹配卡" / "加一个产品库管理页"）。
- **重做 / 改一个已有模块**的信息结构（一行的单元变了、字段增删、卡面 / 抽屉重分层、状态机变化、判定规则改）。
- PM 说某个东西"不对 / 不合理 / 没明白"——回信息模型重新想（必要时回探索重想要解决什么），不打补丁。

**不适用**：纯样式微调、文案错字、不动信息结构的实现 bug —— 走 `/pmai-quick-fix` 或直接小改；如需要沉淀长期基线再用 `/pmai-record`，别走这套。

## 这个 skill 干什么 · 不干什么

- **干**：判断新开还是重做哪个模块 → 加载跨需求记忆（分档读）→ **业务对象建模硬门** → **①探索还原真问题** → **②按需求类型选方法理清信息**（一步一停，产品判断不清调 `/pmai-meta`，呈现有岔路调 `/pmai-mockup`）→ **③调用 `/pmai-spec-writing` 把已拍板结论写成 `spec.md`** → 一致性扫描收口。
- **不干**：开 worktree（本 skill **全程在 main 上只动文档**）、写代码建原型（那是 `/pmai-build`）、merge 定稿（那是 `/pmai-build-close`）。

> **它是唯一的设计入口，也是设计分流中枢**：探索 + 理结构 + PM 拍板在这一步完成；如果卡点其实是产品判断，交 `/pmai-meta`；如果卡在视觉 / 结构发散，交 `/pmai-mockup`；如果要改主原型，交 `/pmai-build` 或等待 PM 明确确认小改；如果问题是 PMAI skill / workflow 边界，交 `/pmai-skill-improve`。最终成文交给 `/pmai-spec-writing` 的「模块规格目标」，统一控制 `spec.md` 的结构和语言风格。原探索 / 打磨职责已并入本流程，成文规则集中在 spec-writing。

## PM 视图规则（必读）

主产物是模块三件套（`discussion.md` / `decisions.md` / `spec.md`），PM 拍板。须遵守 `skills/_shared/PM-VIEW-RULES.md`（主索引），具体读：
- `_shared/pm-view/writing-rules.md`（写作规则：明确指代 / 正向描述 / 禁工程词 / 禁像素颜色）
- `_shared/pm-view/askuser-rules.md`（PM 答题四条硬规则：空答 STOP / 没拿到答案禁止落盘 / runtime 退化保留 wait / 多决策拆开顺序问）
- `_shared/pm-view/banner-rules.md`（入口 banner + 收尾 ▶ Next Up）
- `_shared/pm-view/attachments-upload.md`（PM 给材料时，按类型归档到 `docs/inputs/<类别>/`，用 `_lib.attachments.copy_attachment` 登记）
- 写规格时由 `/pmai-spec-writing` 执行成文与语言把关；本 skill 只负责把内容讨论清楚、把决策拍定。语言纪律以 `skills/spec-writing/references/writing-rules.md` + `_shared/pm-view/writing-rules.md` 为准——本 skill 不重抄。

## 铁律 · 先懂问题再设计、先讨论清楚再改

- **先懂问题再设计**：①探索（要解决什么真问题）必须在 ②设计（怎么把信息摆清楚）之前做完。单 PM 没有真实用户 / 同事 review，探索段是唯一外部对抗源——跳过 = 在回音壁里裸奔，把根本不该做的功能做精致。
- **先过业务对象建模硬门**：进入 A/B 方案、页面结构、字段摆放、mock 或 spec 前，必须先讲清这轮真实对象链：原始输入是什么、结构化成哪些对象、对象之间什么关系、有哪些状态、最终帮谁做什么判断。讲不清就继续读资料或问 PM，不能靠页面方案掩盖对象没想清。
- **先把信息模型讨论清、拍进决策记录，再动原型**。本 skill 默认产出是**设计结论 + 规格**，不是代码。
- **未确认不改主原型**：`/pmai-design` 只动模块三件套等设计文档；`/pmai-mockup` 只动 `mockups/`。PM 说“改原型看看”时，先停住确认这是小原型改动还是进入 `/pmai-build`，没确认前不碰 `prototype/`。
- **落地意图必须过 prototype 分流门**：PM 说“落地 / 实现 / 做进主原型 / 提交 / 可以做了”时，不自动等于直接改主原型。先判断是否涉及 `prototype/` / `Sources/`；涉及就必须在“小改 prototype-only”和“转 `/pmai-build`”之间明确分流。
- **小改 prototype-only**：小改直接落地只允许单字段、单文案、局部样式、已确认弹窗微调，并且提交范围只能是 `prototype/` 或同等主原型代码。只要同时需要改 `docs/modules/`、吸收 / 更新 `mockups/`、升版规格、重做主卡片结构或改变信息结构，就不是小改，默认转 `/pmai-build`。
- **一步一停**：每步和 PM 确认了再进下一步，不一口气把全部分析做完丢给 PM。
- **根因优先（本 skill 自带，不依赖任何全局 / 外部规则）**：PM 说"不对 / 不合理 / 不易懂" → **第一次就停**，回信息模型（必要时回探索）重新想，不在表面加提示文字、不出"再改一版"。**打补丁自检信号**：当你发现自己在出"修订版 / 又改一版"、或在原方案上加补字段 / 加提示 / 加输出块——这就是在打补丁；停下，明说"我可能在打补丁了"，回信息模型（必要时回探索）重想，而不是继续修。

## Workflow（三段式：探索 → 设计 → 成文）

> 三段正交：**①探索**=要解决什么真问题、**②设计**=怎么把信息摆清楚、**③成文**=调用 `/pmai-spec-writing` 把已拍板内容固化成 `spec.md`。物理对齐三件套自然顺序（discussion → decisions → spec）。

### 准备 A · 判断新开还是重做哪个模块

从 PM 一句话需求判断这次是：

- **新开模块** —— 产品里还没有这个东西 → 段③在 `docs/modules/<新模块>/` 立一套新三件套。
- **重做 / 改已有模块** —— 已经有 `docs/modules/<模块>/`，这次改它 → 段③**就地升版**那套三件套（版本 +1、变更日志、supersede，不另开文件夹）。

判断依据：扫一眼 `docs/modules/` 有没有对得上的模块。拿不准是"改老的"还是"开新的"（模块身份是否还是同一个），用一句话问 PM，别擅自决定。

> 模块文件夹命名英文 kebab；三件套文件名固定英文 `discussion.md` / `decisions.md` / `spec.md`；正文仍中文。

### 准备 A.5 · 后台判断工作类型 + 分流硬门

判断模块身份后，先在后台判这轮到底是哪类工作；它决定后面读什么、问什么、能不能成文，也决定是否应该停在 design 内、调其它 skill、或完全转出 design。**这不是给 PM 的固定汇报模板**，不要把"目标 / 材料 / 边界 / 完成标准"机械输出给 PM。

| 工作类型 | 内部判断 | 处理口径 |
|---|---|---|
| 新建模块 | 产品里没有对应模块 | 先跑探索，再建三件套 |
| 重做已有模块 | 模块身份不变，但信息结构 / 状态 / 规则要改 | 就地升版，同步处理旧结论 supersede |
| 规格冲突对齐 | 多份文档 / 原型口径互相打架 | 先找当前权威口径和冲突点，让 PM 拍哪个算数 |
| 补齐未决口径 | 主方向已定，只缺字段 / 状态 / 操作 / 边界 | 不重开大探索，逐项补齐缺口 |
| 呈现确认 | 内容规则已清楚，剩布局 / 密度 / 分组 / 交互表达 | 必要时调 `/mockup`，不让 mock 替代规格决策 |
| 成文写规格 | 讨论和决策已经收敛 | 交给 `/pmai-spec-writing`，发现结构问题就退回段② |

**分流硬门（不新增外层 router，分流责任就在 design 内）**：

- **产品判断不清**：这需求到底成不成立、服务谁的哪个判断、取舍标准是什么、危险前提是什么 → 停在 design，调 `/pmai-meta` 补产品判断模型；meta 结论降回本 skill 后再继续。
- **视觉 / 结构有岔路**：页面结构、信息密度、用户路径、卡面 / 抽屉、管理页 / 表格、整体第一眼有两个以上方向都说得通 → 调 `/pmai-mockup` 做发散比稿，不用文字硬讲，更不直接改主原型验证。
- **落地意图识别**：PM 说“落地 / 实现 / 做进主原型 / 提交 / 可以做了” → 先停住判断是否涉及主原型。涉及 `prototype/` / `Sources/` 时，必须过 prototype 分流门，不能直接把“落地”解释成小改。
- **要改主原型**：PM 要看真实原型或业务代码变更 → design 停止；大需求转 `/pmai-build`。小的样式 / 文案 / 不动信息结构的改动也必须先让 PM 明确确认“小改 prototype-only”，并确认本次不会同时改 `docs/modules/` 或 `mockups/`，再按轻量入口处理。
- **混合交付转 build**：凡本轮同时涉及主原型、模块文档、mockup 方向吸收 / 退役，或需要规格升版、信息结构变化、主卡片结构重做，都不是小改；默认转 `/pmai-build`，最终由 `/pmai-build-close` 收口。
- **workflow / skill 问题**：卡点是 PMAI 自己的 skill 边界、工具调用、文档同步、gstack/browser 能力或执行流程 → 不回 design，转 `/pmai-skill-improve` 或 workflow 决策。
- **纯文档成文**：讨论和决策已经收敛，只缺写成规格 → 交 `/pmai-spec-writing`；成文中发现对象、状态或呈现没想清，退回段②。

**本轮目标绑定**：每次想顺手改相关模块、同步其它规格、沉淀全局规则、补产品现状或发起 mock 前，先问自己："这件事是否直接服务当前工作类型？" 不直接服务的，只记录为后续项或 flag 给 PM；不得把相关工作扩展成本轮默认范围。PM 明确把它纳入本轮时，才升格处理。

### 准备 B · 加载跨需求记忆（分档读，别全量淹没；进场侧闭环）

抛任何探索 / 设计问题之前，先把历史读进来——AI 知道哪些拍过、用哪些既有词，PM 不重复说。**分档读（开放4·已拍 A）**，别无脑全量（PRODUCT-RULES 越长全量越贵、越淹没重点）：

| 改动范围 | 读什么 |
|---|---|
| **小改 / 单模块** | 本模块 `spec.md`（当前真相源）+ `decisions.md`（拍过 / 否过什么）+ `PRODUCT-RULES.md` 里 **scope=全局** 的规则（全局铁律，始终读）+ `PRODUCT.md` 业务术语表 |
| **跨模块 / 新模块** | 上面全部 + **全量** `PRODUCT-RULES.md` + 相关 `docs/decisions/` 理路冻结档（查"为什么"按需读）+ `PRODUCT-STATE.md` 现状 |
| **拿不准是否触及跨模块约束** | 升档按"跨模块"全量读（两道兜防漏读全局规则：铁律节始终读 + 拿不准升档） |

**进场侧闭环（治"回写做实了进场没接住"）**：开场顺手读 `TODO.md`——本需求若命中某条遗留（上一轮 close 推下来的），浮出来提醒 PM。理路（护城河 / 机制咬合 / 演进故事）在 `docs/decisions/` 冻结档，**查"为什么这么定"时按需读**，不每次全载。

> **落点口径（⑤理路拆家后）**：`PRODUCT-RULES.md` 只装**跨模块规则**（活、scope）；**理路**在 `docs/decisions/` 冻结档（按需读）；单模块决策在模块 `decisions.md`。别再把 PRODUCT-RULES 当"规则 + 理路混装"读。

顺手查索引漂移（advisory、不阻塞）：

```bash
python3 "$PMAI_HOME/scripts/check-state-index-drift.py" "$REPO_ROOT" || true
```

有漏挂的文档一句话提示 PM，点头再补，不强制。基线缺失（新项目还没沉淀）→ 当白纸起步，直接进段①，不报错。

### 准备 C · 业务对象建模硬门 + 强制停顿点

在输出任何 A/B 方案、页面结构、字段分组、mock 请求或规格草稿之前，先用大白话写出这轮的**业务对象链**。这是 design 的第一道硬门，不是可选分析段。

```text
我先把真实对象链对齐一下：
1. 原始输入 / 触发材料：<客户原文、PM 需求、系统事件、上传资料等>
2. 被结构化出来的业务对象：<需求点、客户、产品、交付项、规则、状态等>
3. 对象关系：<谁归属谁、谁匹配谁、谁生成谁、谁覆盖谁>
4. 状态与变化：<空、处理中、待确认、已确认、待重算、人工锁定等>
5. 下游判断 / 动作：<PM 或用户看完要决定什么、推进什么、停止什么>
6. 真相源：<最终以哪份规格、模块文档、系统状态或 PM 拍板为准>
```

**强制停顿点**：以下点没有 PM 明确确认，不进入下一步、不落盘、不改原型：

- 业务对象链确认。
- 这是哪类需求 / 需要哪套设计问题确认。
- 是否调 `/pmai-meta` 确认。
- 是否调 `/pmai-mockup` 确认。
- 是否进入 `/pmai-spec-writing` 成文确认。
- 是否转 `/pmai-build` 或小改主原型确认；若 PM 表达“落地 / 实现 / 提交”，必须先明确它是小改 prototype-only 还是进入 build。

如果 PM 对对象链说“不对 / 不合理 / 感觉不对”，不要出“修订版方案”。先回到根因：是产品判断没想清、对象关系错了、状态缺了、还是 workflow / skill 边界错了；再按准备 A.5 的分流硬门处理。

### 段 ① 探索 · 还原真问题（@读 `design-method.md`）

PM 拿"想要的方案"来，先还原成"要解决的真问题"——这是上一轮 reshape 砍没、现在补回的一整段（探索 ⊥ 信息设计）。

- **escape-hatch 默认放行（开放6·已拍 A）**：每个需求过一遍"闻味判断"，**默认一句话放行**直接进段②；只在闻到味才升档 push。**宁可偶尔漏 push，不可默认每次审**（单 PM 一天起五六个小需求，默认审一遍必弃用）。PM 随时可手动"帮我深想这个"反向升档。
- **闻味触发清单**（嗅到任一 → push）：方案先行措辞（"加个 X 按钮 / 做个 Y 弹窗"）/ 伪需求信号（"感觉应该有"）/ 跨模块措辞 / 推翻已有决策 / 根本目标模糊。详见 `design-method.md`。
- **push 时**按 `design-method.md` 的探索方法做对话诊断：不附和解法、逼到具体、把现状当对手（"现在没这功能你怎么凑合的"）、给方向 + 代价让 PM 选。**砍掉外部 demand 三问**（有人掏钱吗 / 谁被炒鱿鱼 / 坐用户后面看过吗——单 PM 内部产品问不出真答案、强问逼 PM 编）。
- **减法性质需求**（这需求其实是砍 / 简化某现有功能）→ @读 `anti-cut-check.md` 走对抗三问。
- **产品元思考旁路（/pmai-meta）**：push 深想时，如果卡点不只是"怎么摆字段 / 怎么写规格"，而是**这需求到底成不成立、服务哪个目标、按什么标准取舍、帮谁做什么判断、当前方案依赖的前提是否成立、或表达停在功能层**——调 `/pmai-meta`。`/pmai-meta` 负责把表层诉求建成产品判断模型（判断句、地基账本、判断标准、模型轴、分路），不是新阶段、也不是分析段落生成器：它先读资料，再一题一问补模型，给出替代方向并停住让 PM 选，最后把结论降回本 skill 段②理结构。**仍走 escape-hatch**：小需求默认放行不调；一问现状就能还原真问题的，用探索内核轻推即可；闻到"目标不清 / 标准不清 / 旧范式 / 前提存疑 / 表达太功能层"，或 PM 说"帮我深想 / 不合理 / 感觉不对 / 只是复述"才调。
- **根上压测（可选旁路）**：PM 明确说"多角度看看 / 找盲区 / 让几个 agent 分别看 / 对抗分析"，或连续质疑"不合理 / 感觉不对"且单一探索视角仍卡住时，可建议调 `/pmai-meta`。由 meta 先判断已有锚点是否足够：有当前问题 / 方案 / 规格草稿就压测根因和前提；发现缺的是 PM 判断时转回一题一问。它只帮把产品判断模型想清楚，不替代模块结构设计、规格自检或 PM 拍板。**如果问题其实是 PMAI skill / workflow 边界，不回 design，转 `/pmai-skill-improve` 或明确停住。**

**产物 = `discussion.md` 第一节（探索段的第一产物，不是写规格时才补的过程笔记）**，按需含：真正要解决的问题 + **当前产品现状整理（切片化：只装本需求相关现状，明写"全局现状看 PRODUCT-STATE"）** + 值得商榷之处 + 推荐方向 + 代价 + 岔路口 + 未决业务问题（逐条列、引导 PM 编号答，禁"有 N 个问题"摘要带过）。

**收尾必做**：AI 说一句 **"这是 X 类需求，所以打算用 Y 套设计问题"**、PM 拍——**定类型是段②的前提，必须在动手理结构之前完成**。

### 段 ② 设计 · 按需求类型选方法把信息理清（@读 `design-method.md` · 一步一停）

按①定的需求类型选方法理清结构。**不是"一套主干 5 问套所有需求"，而是"很小的真通用内核（3 条）+ 每类一套特化问题集"**（已删原"5 问对任何需求成立"）。

- **真通用内核 3 条**（任何需求都过）：① 真问题 / 谁能做什么决策 + 下游倒逼（①已答、这里确认）② 派生信息 4 环（来源 → 生成[可落 prompt] → 变更 → 重算影响）③ 状态别只画正常态（空 / 计算中 / 待重算 / 冲突待澄清 / 人工已锁定）。
- **页面定位掰不清时**（这页是给人看任务、还是做判断？信息该堆哪些）→ 调 `/pmai-meta`：先定"这页服务谁的哪个判断"，必要时用 meta 的 UI 信息 / 任务 / 判断层工具反推卡面 / 主操作 / 默认筛选 / 不该出现的东西。思路已清可省；一旦 PM 质疑“不合理 / 感觉不对 / 只是复述”，不得继续在原方案上补字段。
- **按类型加特化问题集（两面：逻辑面 + 呈现面，详见 `design-method.md`）**：先判**逻辑面**（后端规则 / 纯算法 / Agent · 引擎 / 流程 · 状态机），再判**有没有呈现面**——**只要结果给人看，就必须同时按呈现类型（信息密集 UI 卡 / 多对象管理页 / 数据产物）把那张脸设计出来**（落点 / 卡面 / 抽屉 / 交互[看依据 · 否决 · 过目] / 待办落点）、和 PM 确认、视觉调 /mockup。**别把'后端引擎'判定只当逻辑面就收工**（ROI 反面教训）。**三身份只在"信息密集 UI 卡"**。判出某面"不属任何已列类型" → 逐类说理由 + PM 拍 + 事后沉淀回 `design-method.md`。
- **深度自适应、AI 提议 PM 拍**：判这次走全套还是轻过，说一句给 PM（"这个信息挺密、我想把字段从哪来、上卡面还是收抽屉都过一遍，行吗？"），PM 同意再走。**不机械化成"每需求必跑全部问题"**——思路清的简单需求轻过，别拖。
- **一步一停**：每问（或每两问）和 PM 对一次。讨论过程续写进 `discussion.md`；拍定的点**上移**进 `decisions.md`（含"这是 X 类需求"判定）/ `spec.md`，底稿不再当真相。
- **呈现面收尾自检（进段③成文前必过）**：这东西有没有用户看得见的输出？有 → 我跟 PM 确认过它**显示在哪、长什么样、怎么交互**了吗？没确认，不许进成文。

成文前跑未决问题检查；如还有未回答项，逐条让 PM 答完再落 `spec.md`：

```bash
python3 "$PMAI_HOME/scripts/check-open-questions.py" "$MODULE_DIR/discussion.md"
```

**调 /mockup 确认设计**：只要页面结构、信息密度、卡面 / 抽屉分层、管理页表格、用户路径或第一眼气质有两个以上方向都说得通，就主动调 `/pmai-mockup` 借 gstack / design-shotgun 或内部发散流程出多变体让 PM 挑。规格里开始画 ASCII、或 AI 想直接改 `prototype/` 来验证视觉，也必须先调 mock。纯后端 / 无界面 / 小改、或文字已讲清且没有呈现岔路的，**不调**。mock 是探索草稿建在 `mockups/`、和 `prototype/` 分开；规格不嵌 ASCII、只引用确认的 mock 路径。PM 选定后记住路径，段③引用。

> **护栏（防机械化）**：什么时候多问、什么时候轻过、什么时候调 mock——AI 临场判断，不得写成"每个需求必跑全部特化问题"的死流程。框架只管两头（记忆进场 + 三件套落盘），中间收敛交给判断。

### 段 ③ 成文 · 调 `/pmai-spec-writing` 演进 spec + 收口 + 分流（@读 `design-method.md` 四 + spec-writing 写作规则）

把①②的结论交给 `/pmai-spec-writing` 的「模块规格目标」落成 `spec.md`，并与前面已写的 `discussion.md` / `decisions.md` 组成模块三件套。三件**维度不同、内容零重叠**：

| 文档 | 装什么 | 铁律 |
|---|---|---|
| `discussion.md` | **第一节 = ①探索结论**（真问题 + 内部现状切片 + 岔路）；其后续写②的讨论过程 | 探索结论是真产物；讨论过程里某点一拍定就**上移**进 decisions / spec，底稿不再当真相 |
| `decisions.md` | 拍定的**本模块**决策（结论 + 为什么 + 否过什么 + 被推翻标 supersede）+ "这是 X 类需求"判定 | 只记决策，**不复制规格口径**、链回 spec |
| `spec.md` | **唯一真相源**：信息模型 + 判定规则 + 字段口径 + 状态机 + 文案 | 评审 / 开发只看这份；别处不许再写一份口径；正文 = 纯最终事实、不留迭代痕迹 |

**spec 怎么写**由 `/pmai-spec-writing` 负责执行：顶部钉权威声明（与原型不一致以规格为准、没说清先确认）；章节是菜单不是死模板（§六信息模型按需出现、§八核心动作按需求类型自适应、其余有就写没有省）；不嵌原型 ASCII（引用确认的 mock 路径）；术语 grep 收口（用准备 B 加载的业务术语表既有词）。

**重做模块 = 就地升版同一文件夹**：`spec.md` 版本 +1 + 变更日志加一行；被推翻的旧结论在 `decisions.md` 标 supersede（不删假装没发生）；只有"模块身份本身变了"才另起 + 归档旧的（例外，PM 拍）；合并旧内容先 **reconcile**（矛盾旧结论标 supersede 或删，不照搬进新真相源）。

**收口三道**（详见 `/pmai-spec-writing` 写作规则 + `consistency-scan.md`）：

1. **成文把关**：由 `/pmai-spec-writing` 对照 9 条逐条扫（只写最终事实 / 不造词 / 去 AI 腔 / 多步流程用叙述 / 术语全文一致……），改完 grep 自查残留。**只动文字、不动结构**——发现要改的是结构，停下回段②（甚至段①）。禁用清单单一真相源 = `skills/spec-writing/references/writing-rules.md`。
2. **派通用 subagent 冷读自检**（白纸读 spec，**不是 `analysis-reviewer`**——那个只评审探索段 discussion 第一节、不审 spec）：拿 spec 当尺子扫两类残留——① 机制 / 落点没说清（状态 / 动作只给名字没说怎么发生、落在哪、记什么）② 内部简称读者要猜。拿回清单逐条改。silent 自检，不升格强制门。
3. **一致性扫描**：这次改动碰的字段 / 规则 / 概念，grep 规格 ↔ 原型 ↔ DESIGN ↔ 术语表对账；对不上的 flag 给 PM 拍（哪个对 / 有意删还是漏实现 / 术语要不要统一），不静默吞、不自动改。

**收尾分流**（本 skill 只完成设计定稿，不开 worktree、不实现）：

| 情况 | 去哪 |
|---|---|
| **要做进主原型 / 真实现** | 转 `/pmai-build`：PM 选工具 + 选要不要隔离环境 → 建 → review loop，完了再 `/pmai-build-close` |
| **只做 PM 明确确认的小改** | 只允许 prototype-only 小改；不得同时改 `docs/modules/` 或 `mockups/`，否则转 `/pmai-build` |
| **先放着** | 不跑命令；下次 `/pmai-status` 会继续提示这个模块可以 build 或继续调整 |
| **先不实现，但这次讨论已形成稳定项目级基线** | 走 `/pmai-record`：只沉淀已稳定的术语 / 跨模块规则 / 当前设计状态，不把它包装成 build-close |

输出一句给 PM 说清在哪、下一步：

```
模块三件套已写好 / 升版（docs/modules/<模块>/）：真问题、信息模型、规格、决策都齐了，成文已按 spec-writing 规则磨过，设计也用 mock 确认过（如涉及界面）。

▶ Next Up：
  · 要做进主原型 / 真实现 → /pmai-build（你选工具、选要不要开隔离环境）
  · 先放着 → 不用操作，下次 /pmai-status 继续
  · 先沉淀项目基线 → /pmai-record（只写已稳定的术语 / 跨模块规则 / 当前设计状态）
```

## Rules

- **三段式：①探索 → ②设计 → ③调用 spec-writing 成文**，先懂问题再设计。探索段是单 PM 唯一外部对抗源，不许跳（但 escape-hatch 默认放行、闻味才 push，不是每次审一遍）。
- **全程在 main 上只动设计文档、不开 worktree、不建主原型**。开 worktree 和改 `prototype/` 是 `/pmai-build` 的事、build 后提交/合并/规格对齐是 `/pmai-build-close` 的事；`/pmai-mockup` 只写 `mockups/`，不算主原型实现。
- **落地意图必须过 prototype 分流门**：PM 说“落地 / 实现 / 做进主原型 / 提交 / 可以做了”时，先判断是否涉及主原型；涉及就明确选“小改 prototype-only”或转 `/pmai-build`，不能自动解释成直接改。
- **小改直接落地必须 prototype-only**：单字段、单文案、局部样式、已确认弹窗微调才算小改；只要同时改 `docs/modules/`、`mockups/`，或涉及信息结构 / 规格升版 / mockup 吸收 / 主卡片结构重做，就不是小改，必须转 `/pmai-build` 并由 `/pmai-build-close` 收口。
- **唯一组织单位 = 功能模块**；一模块一文件夹 `docs/modules/<模块>/`，三件套 `discussion.md` / `decisions.md` / `spec.md`，文件名英文、正文中文。
- **重做模块 = 就地升版同一文件夹**（版本 + 变更日志 + supersede + git 留痕），不 per-版本另开文件夹；身份变了才另起 + 归档旧的（例外，PM 拍）。
- **开场分档加载跨需求记忆（开放4）**：小改读本模块 spec+decisions + PRODUCT-RULES 全局 scope + 术语表；跨模块 / 新模块全量读 PRODUCT-RULES + 相关 docs/decisions 理路 + PRODUCT-STATE；拿不准升档。顺手读 TODO（遗留浮出）。别让 PM 重复说历史决策和术语。
- **落点口径（⑤理路拆家）**：PRODUCT-RULES 只装跨模块规则、理路在 docs/decisions 冻结档（按需读）、单模块决策在模块 decisions.md。
- **按需求类型选方法（开放3）**：真通用内核 3 条任何需求都过；类型分**两面**——逻辑面（后端规则 / 算法 / 引擎 / 流程）+ 呈现面（信息密集 UI 卡 / 管理页 / 数据产物），各配特化问题集。**先判逻辑面、再判有没有呈现面；结果给人看 → 呈现面必做（落点 / 卡面 / 抽屉 / 交互）+ PM 确认 + 视觉调 /mockup，别把引擎判定只当后端就收工**。三身份只在信息密集 UI 卡。判新型逐类说理由 + PM 拍 + 沉淀回 `design-method.md`。**不再"5 问对任何需求成立"**。
- **深度自适应、AI 提议 PM 拍**：信息密集走全套讨论、后端规则 / 流程 / 小改轻过。不机械化成"每需求必跑全部问题"。
- **设计确认靠 mock（有岔路就主动调）**：视觉 / 布局文字掰不清、页面结构有多种可能、信息密度需要眼睛判断、规格里想画 ASCII、或准备改主原型验证视觉时，先调 `/pmai-mockup`；纯后端 / 无界面 / 小改、或文字已讲清且没有呈现岔路可省。规格不嵌 ASCII，只引用确认的 mock。
- **spec 章节是菜单不是死模板**：§六信息模型按需、§八核心动作按需求类型自适应、其余有就写没有省；唯一判据 = 讲清楚。**但格式骨架统一、不灵活**——标题带序号（大标题中文数字、子标题 N.M）、名词解释 / 版本信息 / 变更日志用表格，具体由 `/pmai-spec-writing` 模块规格目标执行；灵活的只是"哪几节、功能清单用什么形式"，不是连标题序号、术语表格都随意。
- **三件套维度零重叠**：spec 唯一真相源、decisions 只记决策（不复制 spec 口径）、discussion 第一节=探索结论 + 后附讨论过程。
- **规格 4 问是验收标准**（由 `/pmai-spec-writing` 执行）：分不清原型规格（不嵌原型 + 顶部声明 + mock 确认）/ 术语不统一（名词锁定 + 术语表加载 + grep 收口）/ 多余原型解释（为什么甩 decisions、原型样子甩 mock）/ review 删规格（一致性扫描 build-close 对账）。
- **收口三道**：磨文字（只动文字不动结构）+ subagent 冷读自检 + 一致性扫描。都是 silent 自检 / 顺手 flag，**不升格成强制 review 门**（守 I-RV1）。
- **`/pmai-meta` 只作产品元思考旁路**：当 PM 想深想、质疑"不合理 / 感觉不对 / 只是复述"、多视角找盲区或反方挑战时建议使用；它用于补齐产品判断模型，不自动插入每次 design，不替代探索段、模块结构设计、规格自检或 PM 拍板。skill / workflow 改造问题不属于 design，按 meta 判断后交 `/pmai-skill-improve`。
- 给 PM 的话翻译掉 通用内核 / 4 环 / 三身份 / drift 等内部术语，用大白话。
