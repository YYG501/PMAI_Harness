# /pmai-design · 设计 + 写规格（唯一写规格 skill）

> 本 skill 是设计的"驾驶舱"。方法论全文不内嵌在这——开工前 `@读`：
> - `skills/_shared/info-design.md`（信息设计全套：理结构 5+2 问、派生信息 4 环、规格通用骨架、磨文字纪律、规格 4 问治法）
> - `skills/_shared/consistency-scan.md`（一致性扫描：改原型 / 规格 → 对账 → flag）
>
> 给 PM 的话里**不出现** 7 步法 / 4 环 / 三身份 / drift 这类内部术语，全程大白话。

## When To Use

- 起一个**新功能模块**（PM 一句话需求："做一张能力匹配卡" / "加一个产品库管理页"）。
- **重做 / 改一个已有模块**的信息结构（一行的单元变了、字段增删、卡面 / 抽屉重分层、状态机变化、判定规则改）。
- PM 说某个东西"不对 / 不合理 / 没明白"——回信息模型重新想，不打补丁。

**不适用**：纯样式微调、文案错字、不动信息结构的实现 bug —— 直接改完 `/close`，别走这套。

## 这个 skill 干什么 · 不干什么

- **干**：判断新开还是重做哪个模块 → 加载跨需求记忆 → 把信息模型理清楚（和 PM 一步一停讨论）→ 调 `/mock` 出页面给 PM 确认设计 → 写 / 演进模块三件套 → 磨文字 + 派 subagent 冷读 + 一致性扫描收口。
- **不干**：开 worktree（本 skill **全程在 main 上只动文档**）、写代码建原型（那是 `/build`）、merge 定稿（那是 `/close`）。

> **它是唯一的写规格 skill**：理结构 + 写骨架 + 磨文字 + 冷读自检全在这一步。原 prd-writing / spec-polish 的活都并进来了（它们已转 dormant）。

## PM 视图规则（必读）

主产物是模块三件套（`discussion.md` / `decisions.md` / `spec.md`），PM 拍板。须遵守 `skills/_shared/PM-VIEW-RULES.md`（主索引），具体读：
- `_shared/pm-view/writing-rules.md`（写作规则：明确指代 / 正向描述 / 禁工程词 / 禁像素颜色）
- `_shared/pm-view/askuser-rules.md`（PM 答题四条硬规则：空答 STOP / 没拿到答案禁止落盘 / runtime 退化保留 wait / 多决策拆开顺序问）
- 写规格时的语言纪律全在 `_shared/info-design.md` 第四块 + `prd-writing/references/writing-rules.md`（L1–L6 + 8 类禁用清单）—— 单一真相源，本 skill 不重抄。

## 铁律 · 先讨论清楚再改

- **先把信息模型讨论清、拍进决策记录，再动原型**。本 skill 默认产出是**设计结论 + 规格**，不是代码。
- **一步一停**：理结构的几问、写规格的几节，一步一停、和 PM 确认了再进下一步，不要一口气把全部分析做完丢给 PM。
- **根因优先**：PM 说"不对" → 立刻停，回信息模型重新想，不在表面加提示文字打补丁。

## Workflow

### 步骤 1 · 判断新开还是重做哪个模块

从 PM 一句话需求判断这次是：

- **新开模块** —— 产品里还没有这个东西 → 步骤 4 在 `docs/modules/<新模块>/` 立一套新三件套。
- **重做 / 改已有模块** —— 已经有 `docs/modules/<模块>/`，这次改它 → 步骤 4 **就地升版**那套三件套（版本 +1、变更日志、supersede，不另开文件夹）。

判断依据：扫一眼 `docs/modules/` 有没有对得上的模块。拿不准是"改老的"还是"开新的"（模块身份是否还是同一个），用一句话问 PM，别擅自决定。

> 模块文件夹命名英文 kebab；三件套文件名固定英文 `discussion.md` / `decisions.md` / `spec.md`；正文仍中文。

### 步骤 2 · 加载跨需求记忆（开场必做，别让 PM 重复说）

抛任何设计问题之前，先把历史决策和既有术语读进来——这样讨论时 AI 知道哪些已经拍过、用哪些既有词，PM 不用重复说。读：

1. **项目基线** `docs/PRODUCT.md`（定位 + **业务术语表** —— 设计讨论用既有词，别造新词）+ `docs/PRODUCT-STATE.md`（当前产品 / 主原型现状）+ `docs/PRODUCT-RULES.md`（跨模块规则 + 关键决策 + 奠基理路；全文读）。
2. **相关模块的三件套**：本次需求触及的模块，读它的 `spec.md`（当前真相源）+ `decisions.md`（拍过什么、否过什么）。重做模块必读自己那套。
3. **顺手查索引漂移**（advisory、不阻塞）：

```bash
python3 "$PMAI_HOME/scripts/check-state-index-drift.py" "$REPO_ROOT" || true
```

有漏挂的文档，一句话提示 PM 要不要顺手补，PM 点头再补，不强制。

> **读什么不读什么**：读项目基线 + 相关模块三件套 + 主原型现状。**不**主动翻无关模块的历史文档（噪声）。基线缺失（新项目还没沉淀）→ 当白纸起步，直接进步骤 3，不报错。

### 步骤 3 · 把信息模型理清（通用设计讨论 · 一步一停）

这是 `/design` 的核心。按 `_shared/info-design.md` 跑——**普适主干 5 问任何需求都过；卡片特化 2 问只在信息密集的 UI 加**。深度自适应：

| 需求类型 | 怎么走 |
|---|---|
| **信息密集**（一张卡 / 多对象管理页 / 字段很多的表） | 走全套：主干 5 问 + 卡片特化 2 问（原子粒度 / 卡面 vs 抽屉） |
| **后端规则 / 流程 / Agent** | 走主干 5 问，特化 2 问省掉；§六信息模型按需 |
| **小改** | 主干轻过一遍即可，不强行拖完整讨论 |

**主干 5 问**（详见 `info-design.md` 一）：① 谁看 · 想知道什么 · 喂给谁（下游倒逼结构）② 决策与动作边界 · 三身份（AI 建议 / 已确认 / 待确认）③ 信息从哪来 · 派生信息 4 环（来源→生成→变更→重算）④ 状态（别只画正常态）⑤ 文案风格。

**卡片特化 2 问**（信息密集才加）：① 一行 / 一条的原子粒度 ② 卡面 vs 抽屉。

**深度由 AI 提议、PM 拍**：AI 判这次该走全套还是轻过，说一句给 PM（"这个信息挺密、我想把字段从哪来、上卡面还是收抽屉都过一遍，行吗？"），PM 同意再走。**不自动走全套、不变成每个需求必跑 N 问的硬流程**——思路清的简单需求轻过，别拖。

**一步一停**：每问（或每两问）和 PM 对一次，确认了再进下一问。讨论过程记进 `discussion.md`（拍定的点上移进 `decisions.md` / `spec.md`，底稿不再当真相）。

> **护栏（防机械化）**：什么时候多问、什么时候轻过、什么时候直接去 mock——AI 临场判断，不得写成"每个需求必跑全 7 问"的死流程。框架只管两头（记忆进场 + 三件套落盘），中间收敛交给判断。

### 步骤 4 · 调 /mock 出页面给 PM 确认设计（取代规格里画 ASCII）

信息模型理清后、写规格之前，**调 `/mock` 据讨论结论生成页面**，给 PM 提前看、提前确认设计长什么样。这是治"分不清原型 / 规格 + 多余原型解释"的关键一步——**确认设计靠 mock，不靠在规格里画 ASCII**。

- `/mock` 借 gstack `/design-shotgun` 一次出**多个变体**让 PM 选；看版留存，没选的不删。
- PM 选定 / 确认了某版 → 记住那个 mock 的路径，步骤 5 写规格时引用它。
- **轻量、不开 worktree**；mock 是探索草稿，建在 `mocks/` 底子上，和 `prototype/` 主原型分开。

> **什么时候可省**：纯后端规则 / 流程、或小改、或这次根本不涉及界面 —— 没有"页面长什么样"要确认，跳过 `/mock` 直接写规格。信息密集的卡 / 页**不要省**——PM 用眼睛挑比看 ASCII 准。

### 步骤 5 · 写 / 演进模块三件套（spec 走通用灵活骨架）

把讨论结论 + 确认的 mock 落成模块三件套。三件**维度不同、内容零重叠**：

| 文档 | 装什么 | 铁律 |
|---|---|---|
| `discussion.md` | 收集的信息 + 讨论过程（外部探索 / 现状 / 待定的概念框架） | 过程前段；某点一拍定就**上移**进 decisions / spec，底稿不再当真相 |
| `decisions.md` | 拍定的**本模块**决策（结论 + 为什么 + 否过什么 + 被推翻的标 supersede） | 只记决策，**不复制规格口径**、链回 spec |
| `spec.md` | **唯一真相源**：信息模型 + 判定规则 + 字段口径 + 状态机 + 文案 | 评审 / 开发只看这份；别处不许再写一份口径 |

**spec 怎么写**（详见 `info-design.md` 三）：

- **顶部钉声明**：本规格是权威定义、与原型不一致以规格为准、没说清先确认。
- **章节是菜单不是死模板**：先判这个功能需要哪几节、每节用什么形式，再动笔。唯一判据 = 把需求讲清楚。
  - §六信息模型 **按需出现**——信息密集才写（派生信息 4 环 + 字段表 + 状态机），简单功能省。
  - §八核心动作 **形式自适应**——卡片按信息块（表格难懂就写散文）、管理页按创建 / 编辑 / 删除、Agent 按处理环节、纯算法用流程图 + 完整 prompt。先和 PM 确认分级骨架再写。
  - 其余节有就写、没有省。
- **不嵌原型 ASCII**：界面长什么样引用步骤 4 确认的 mock（"页面见已确认的 mock：<路径>"），规格只留 normative 文字。
- **术语收口**：§三名词解释列全 → grep 全文近义词 → 替换成统一称呼；用步骤 2 加载的业务术语表里的既有词。

**重做模块 = 就地升版**（不另开文件夹）：

- `spec.md` 版本号 +1、变更日志加一行。
- 被推翻的旧结论在 `decisions.md` 标 supersede（留"为什么从 A 改成 B"），不删掉假装没发生。
- 只有"模块身份本身变了"才另起 + 归档旧的——例外，边界模糊让 PM 拍。
- 合并旧内容时 **reconcile**：矛盾的旧结论标 supersede 或删，不照搬进新真相源。

### 步骤 6 · 收口（磨文字 + 冷读 + 一致性扫描）

三件套写完，三道收口（详见 `info-design.md` 四 + `consistency-scan.md`）：

1. **磨文字**：对照 9 条磨文纪律逐条扫（只写最终事实、不造词、去 AI 腔、多步流程用叙述、术语全文一致……），改完 grep 自查残留。**只动文字、不动结构**——发现要改的是结构，停下回步骤 3。
2. **派 subagent 冷读自检**：拿 spec 当尺子，扫两类残留——① 机制 / 落点没说清（状态 / 动作只给名字没说怎么发生、落在哪、记什么）② 内部简称读者要猜。拿回清单逐条改。silent 自检，不升格强制门。
3. **一致性扫描**：这次改动碰的字段 / 规则 / 概念，grep 规格 ↔ 原型 ↔ DESIGN ↔ 术语表对账；对不上的 flag 给 PM 拍（哪个对 / 有意删还是漏实现 / 术语要不要统一），不静默吞、不自动改。

### 步骤 7 · 收尾分流（小改直接 /close，大需求转 /build）

三件套定稿后，按改动大小分流——**两条都不在本 skill 开 worktree**：

| 情况 | 去哪 |
|---|---|
| **小改 / 纯文档**（信息结构定了、原型改动小或没有） | 直接 `/close`：定稿、决策 / 术语回写基线、文档归位 |
| **大需求**（要建一坨原型 / 真实现） | 转 `/build`：PM 选工具 + 选要不要 worktree → 建 → review loop，完了再 `/close` |

输出一句给 PM 说清在哪、下一步：

```
模块三件套已写好 / 升版（docs/modules/<模块>/）：信息模型 + 规格 + 决策都齐了，设计也用 mock 确认过。

下一步：
  · 改动不大 → 直接 /close 收尾（定稿 + 回写基线 + 归位）
  · 要建原型 / 真实现 → /build（你选工具、选要不要开独立工作区）
```

## Rules

- **全程在 main 上只动文档、不开 worktree、不建原型**。开 worktree 是 `/build` 的事、merge 定稿是 `/close` 的事。
- **唯一组织单位 = 功能模块**；一模块一文件夹 `docs/modules/<模块>/`，三件套 `discussion.md` / `decisions.md` / `spec.md`，文件名英文、正文中文。
- **重做模块 = 就地升版同一文件夹**（版本 + 变更日志 + supersede + git 留痕），不 per-版本另开文件夹；身份变了才另起 + 归档旧的（例外，PM 拍）。
- **开场必加载跨需求记忆**：`PRODUCT.md`（含业务术语表）+ `PRODUCT-STATE` + `PRODUCT-RULES` + 相关模块 `spec.md` / `decisions.md`，别让 PM 重复说历史决策和术语。
- **深度自适应、AI 提议 PM 拍**：信息密集走全套讨论、后端规则 / 流程 / 小改轻过。不机械化成"每需求必跑全 7 问"。
- **设计确认靠 mock，不靠规格里画 ASCII**：信息模型理清后调 `/mock` 出页面给 PM 确认；规格不嵌原型 ASCII，只引用确认的 mock。纯后端 / 无界面 / 小改可省 `/mock`。
- **spec 章节是菜单不是死模板**：§六信息模型按需出现、§八核心动作形式自适应、其余节有就写没有省；保留写作纪律、放开章节与形式；唯一判据 = 讲清楚。
- **三件套维度零重叠**：spec 是唯一真相源、decisions 只记决策（不复制 spec 口径）、discussion 只记过程。
- **规格 4 问是验收标准**（详见 `info-design.md` 五）：分不清原型规格（不嵌原型 + 顶部声明 + mock 确认）/ 术语不统一（名词锁定 + 术语表加载 + grep 收口）/ 多余原型解释（为什么甩 decisions、原型样子甩 mock）/ review 删规格（一致性扫描 close 对账）。
- **收口三道**：磨文字（只动文字不动结构）+ subagent 冷读自检 + 一致性扫描。都是 silent 自检 / 顺手 flag，**不升格成强制 review 门**（守 I-RV1）。
- 给 PM 的话翻译掉 7 步法 / 4 环 / 三身份 / drift 等内部术语，用大白话。
