# /pmai-design 设计方法论

> 这是 `/pmai-design` 的设计专用方法源，不放 `_shared`。`_shared` 只保留多个入口真实复用的规则；本文件承接需求探索、信息设计、design-card 历史经验和 gstack 式决策收敛。

## 一、给 PM 的方法

`/pmai-design` 不是把 PM 说的方案直接写成规格，而是帮 PM 把一个需求收敛成可实现、可继承、可复审的模块结论。

对 PM 的前台表达只保留四步：

1. **先判断真问题。** PM 经常先说解法，例如"加个按钮"、"做个弹窗"、"优化入口"。AI 先还原：用户真正卡在哪里、现在怎么绕、为什么这不是单个 UI 微调。
2. **只讲关键现状。** 现状不是审计报告，只列会影响本次方向的事实，通常 3-5 条足够。
3. **先拍主方向，再拍边界。** 主方向一次只问一个选择；导出、分享、历史兼容、工作台这类边界问题顺序问，不合并成 `1A`。
4. **把拍定结论变成三件套。** `discussion.md` 记录真问题和讨论过程，`decisions.md` 记录拍板与理由，`spec.md` 只写最终产品事实。

给 PM 的话不要出现"通用内核"、"派生 4 环"、"三身份"、"drift"、"信息模型"、"需求类型分类"这类内部词。内部判断要翻译成业务话：

- "这个字段从哪里来、变了谁负责更新"
- "用户看完能做什么决定"
- "这个状态下能做什么、不能做什么"
- "这条规格和原型现在对不上，需要你定哪个算数"

## 二、AI 后台执行内核

### 1. 进场先读上下文

先读本模块 `spec.md` / `decisions.md` / `discussion.md`，再按影响范围读 `PRODUCT-RULES.md`、`PRODUCT-STATE.md`、`PRODUCT.md` 术语表和相关 `docs/decisions/`。读完再问，不让 PM 重复讲已经拍过的东西。

### 2. 探索真问题

每个需求先过"闻味判断"，默认轻放行；闻到下列信号才升档深挖：

- PM 直接给解法：加按钮、做弹窗、加页面、加字段。
- 动机站不住：感觉应该有、别人都有、顺便、以防万一。
- 影响跨模块、全局规则或已有决策。
- PM 自己也说目标不清、标准不清、不合理、感觉不对。

深挖时不要问外部 demand 三问，也不要要求单人 PM 编造真实用户证据。直接问更接近产品现场的问题：

- 现在没有它，PM 或用户怎么凑合？
- 哪一步最费劲，还是哪类判断最容易错？
- 如果只解决一半，先解决哪一半最值？
- 不做这件事，产品会继续丢什么上下文或判断能力？

### 3. Meta 是对焦工具，不是阶段

当卡点不是"字段怎么摆"，而是目标、标准、前提或表达方式不清时，调用 `/pmai-meta`。典型触发：

- PM 说"不合理"、"感觉不对"、"帮我深想"。
- 方案像在旧结构上打补丁。
- 页面到底服务信息查看、任务执行还是判断决策说不清。
- 多个方向的差异不是 UI，而是评价标准不同。

Meta 只产三件东西：重定位结论、取舍标准、降回设计动作。调完必须回到本文件的设计步骤，不能停在高空讨论。

### 4. 理清信息

任何需求都过三条底线：

1. **谁看 / 用它，能做什么决定。** 不支撑判断、不喂下游的信息，要解释为什么存在。
2. **来源、生成、变更、重算影响。** 录入、引用、计算、AI 判定要分清；计算和 AI 判定要能落成稳定规则或 prompt；人工拍过的结论不能被重算静默覆盖。
3. **状态要完整。** 不只画正常态，也要想空态、处理中、失败、待澄清、待重算、人工锁定、权限不足。

然后按需求的两面选择问题集：

| 面 | 类型 | 设计重点 |
|---|---|---|
| 逻辑面 | 后端规则 / 算法 / Agent 引擎 / 流程状态机 | 规则边界、输入输出、状态迁移、异常和人工介入 |
| 呈现面 | 信息密集卡 / 多对象管理页 / 数据产物 | 入口、列表或卡面、详情、主动作、失败反馈、空态、导出或分享 |

只要结果给人看，就必须做呈现面；不要把"后端引擎"当成无界面需求就收工。

### 5. design-card 的边界

design-card 不是通用逻辑，它是信息密集卡沉淀出来的一套特化方法。

适用时机：

- 一张卡要承载多种派生判断。
- 卡面、详情、证据、否决、过目、待办落点之间需要分层。
- 同一个信息要同时服务快速扫读和深入解释。

不适用时机：

- 纯后端规则、算法、流程状态机。
- 多对象管理页的主问题是入口、筛选、批量动作、创建/导入流程。
- 数据产物的主问题是格式、生成、校验、导出和消费方。

因此卡片经验只作为呈现面的一类问题集，不再伪装成所有需求的主干方法。

## 三、前台输出模板

探索段给 PM 的输出应短，按这个顺序：

```text
我先不把它当成"改一个按钮/入口"。
真实问题更像是：<一句话问题>。

当前影响这件事的现状只有几条：
1. <关键现状>
2. <关键现状>
3. <关键现状>

我建议本轮主方向先定为：<推荐方向>。
代价是：<一句话代价>。
好处是：<一句话好处>。

这轮先拍这个主方向：<一个问题>
```

如果还有导出、分享、兼容、是否进工作台等边界，等主方向拍完再问第二题。

## 四、成文和收口

`/pmai-design` 只负责把问题、结构和 PM 决策讨论清楚；`spec.md` 的成文由 `/pmai-prd-writing` 模块规格模式执行。

成文前必须满足：

- 没有未回答的开放问题。
- 用户看得见的输出已经确认入口、形态和交互。
- 拍定点已进入 `decisions.md`，不是只留在讨论过程。
- 规格只写最终事实，不嵌原型 ASCII，不复制为什么。

收口时用 `skills/_shared/consistency-scan.md` 对规格、原型、DESIGN 和术语表做轻量对账。它只 flag 问题让 PM 拍，不自动改、不升格成强制 review 门。
