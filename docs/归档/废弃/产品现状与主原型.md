## §0 原始痛点（已锁定，2026-05-28；后续 review **不可反向修改**）

### §0.1 痛点（核心 1 句）

**范式根错**：当前 PMAI 是"按 stage 生产文档和 task 的流程框架"，但 PMAI 真正要解决的是"让产品项目在长期演进中始终有统一上下文"——范式不对，21 个 skill 做下来 PM 实际工作里上下文还是会失忆。

### §0.2 触发场景

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | **PRD 错位**：当前 stage 3 PRD 是前置重规格门，但很多决策是 PM 看着原型才发现的，过早写 PRD = 浪费 + 反方向 | 当前 stage 模型 brief → analysis → **prd** → … 把 PRD 放在原型之前 |
| 2 | **入口分散**：`PROJECT.md` / `DESIGN.md` / `PRODUCT-RULES.md` 三份分散，AI 容易只读一份漏读其他，PM 心智不统一 | 业务仓初始化产出四份基线（含 ROADMAP），没有单一入口 |
| 3 | **req 之间断片**：没有"主原型"概念，每个 req 是独立工程，AI 每次像从空白开始，上下文只能靠文档复读传递 | 当前 req 流程不假设跨 req 持续演进的产品形态 |
| 4 | **PM 视图被 stage 占满**：PM 看到的是"现在 stage 3，下一步推进 stage 4"，而不是"我产品现在长什么样" | Session 起始播报当前以 stage 进度为主轴（CLAUDE.md M5 规则） |
| 5 | **工程机制溢出 PM 心智**：task / worktree / spec / contract 对 PM 心智负担过大 | PRODUCT.md §对当前框架改造的含义 已识别但未改造完 |

实证总场景：**本次 session（2026-05-28）PM 直接抛出整套新范式判断** —— 证明当前框架方向已偏离 PM 真实工作。

### §0.3 根因

"按 stage 生产文档"范式本身错位。真问题是**产品上下文在长期演进中要统一**，不是每个 req 独立生产文档。当前 stage 模型逼着每个 req 都从 brief 开始生产新一套文档，而不是基于"当前产品现状 + 主原型"做增量。

### §0.4 不解决什么

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 工程隔离能力（worktree / 分支 / merge） | 保留作为 AI 后台机制，本方案不动 |
| 2 | hook / lint / 测试 / 全局安装基础设施 | 已成熟，本方案不动 |
| 3 | 多人协作 SOP | PMAI 是单人 PM 工具，不引入团队语义 |
| 4 | 主原型变体 / fork / 实验分支 | **PM 明确拒绝**（2026-05-28 拍板：绝对单一主原型，不留逃生舱） |
| 5 | "首版原型生成速度"问题 | Claude Design / design-html / Claude Code 等专门工具更强，PMAI 不抢这条 |

→ Review 中任何 finding 指向以上场景的，默认 DEFER（除非 PM 显式接受拉进 §0）

## §1 方案概述

### §1.1 一句话

PMAI 从"按 stage 生产文档和 task 的流程框架"，升级成 **"围绕当前产品和当前主原型持续演进的上下文框架"**。

### §1.2 两个一等概念

**A. 产品现状** — 表达"这个产品现在是什么"

- 业务仓根目录单文件 `PRODUCT-STATE.md`
- 内部 `##` 二级节切分（定位 / 对象 / 规则 / 模块 / 术语 / 主原型映射）
- AI 每次进项目必读
- 是产品已沉淀的当前状态，不是某个 req 的 PRD，也不是 roadmap

**B. 当前主原型** — 表达"这个产品现在如何被体验"

- **单一持续演进的主原型**（绝对单数，不留 fork）
- **真代码项目**（不是静态 HTML），跑 dev server 可看完整交互
- 业务仓内 `prototype/` 固定位置
- 首版来源自由（Claude Design / design-html / Claude Code / 手工 HTML / 截图），AI **一次性"录入"翻译**进 `prototype/` 真代码，之后只在自己代码上演进

### §1.3 PM 主心智（四件事）

1. **当前产品** — 读 `PRODUCT-STATE.md`
2. **当前主原型** — 跑 `prototype/` dev server 看
3. **本次增量** — 这次 req 在主原型上的变化
4. **确认沉淀** — PM 确认后 AI 自动反向沉淀

task / worktree / implementation-design / spec / contract 这些工程机制留在 AI 后台，**不进 PM 主视图**。

### §1.4 req 流程抽象

```
读产品现状 + 跑主原型
  ↓
理解本次需求对当前产品的增量影响
  ↓
方案不清楚就先和 AI 讨论清楚
  ↓
在主原型上做增量原型变化（worktree 内）
  ↓
PM 跑 dev server 看完整交互并反馈
  ↓
PM 确认原型
  ↓
反向沉淀（写 PRD + 更新产品现状 + merge）—— 原子动作
  ↓
进入下一个 req
```

**关键时序**：PRD **后移**到原型确认后，作为正式沉淀物，不再是挡在原型前的重规格门。

### §1.5 产品现状 ↔ 主原型 同步机制

- 两者是**同一个产品的两个视图**，不强耦合
- 平时各自被改：主原型在 req worktree 演进 / 产品现状在 main 上不变
- **同步只在 req 沉淀阶段发生**（原子动作）：
  1. 更新 `PRODUCT-STATE.md`（本次原型变化引入的新对象 / 规则 / 术语 / 模块）
  2. 写本次 req 的 PRD（决策包）
  3. merge 主原型 worktree 回 main

## §2 与现有机制的关系

### §2.1 现状（PMAI 当前长什么样）

1. 21 个 skill，**7-stage 流程**：brief → analysis → **prd** → implementation-design → task-plan → task-spec → execute → verify → close
2. 业务仓初始化产出**四份基线**：`docs/PROJECT.md` / `docs/DESIGN.md` / `docs/PRODUCT-RULES.md` / `docs/ROADMAP.md`
3. PRD 在 stage 3（前置重规格门）
4. task 当前定位 = "PM 可确认 demo 单元 + AI 工程合同"（task-spec 三区结构）
5. close-req 已有 "merge + close-report + 更新 PRD" 语义
6. 已有 hook 体系 / 全局安装 / Session 起始播报机制（基础设施成熟）
7. **没有 `prototype/` 这个一等概念**
8. **没有 `PRODUCT-STATE.md` 这个一等入口**
9. `PRODUCT.md` 写过"产品上下文统一层"方向（抽象口号对，落地机制按当前 stage 模型设计，有结构性冲突）

### §2.2 保留

- worktree 隔离机制（req 改主原型在 worktree 内进行）
- hook 体系 / 全局安装 / 升级 / 测试基础设施
- Session 起始播报机制（**内容反转**：从 stage 进度 → 产品视图，详见 §5.6）
- close-req 的 merge 语义（**扩展**成原子沉淀动作）

## §3 期望需求（PM 想要的体验）

1. AI 每次进项目都知道产品是什么、主原型长什么样、哪些决策已确认、新需求基于哪里继续改
2. 新 req **不从空白开始**，基于产品现状 + 主原型增量
3. PM 主心智只四件事：当前产品 / 当前主原型 / 本次增量 / 确认沉淀
4. 原型确认后 AI **自动反向沉淀** PRD / 决策包 / 产品现状更新
5. task / worktree / implementation-design 留在 AI 后台，不进 PM 主视图
6. **保留当前"实现程度 mode"能力**：同一个框架既能做生产系统也能做原型（不因升级成"主原型上下文框架"就退化成只能做轻量原型）；现有 solution.md 8 字段表 + 项目级 / req 级双层约束的语义要在新模型里有承接位置

**已决议（5 章来源分类，2026-05-28 PM 拍"合理"）**：

PRD 9 章在新模型下来源分三类：

| 来源类型 | 章节 | 关键变化 |
|---|---|---|
| **A. 从主原型代码抽** | §五用户/角色 / §六功能 / §七验收 | AI 读 `prototype/` 直接写；质量门 = "跟代码一致" |
| **B. 从 brief/analysis + 项目级规则抽** | §四需求分析 / §八非功能 | 推理保持原样（原型反映不出"为什么"和非功能约束） |
| **C. 混合** | §五角色业务命名 / §六业务规则 / §七 PM 反馈 | 主原型抽 + 文字补 |

**最大反模式翻转**：§六"**AI 现画 ASCII → close-req 替换截图**"整套机制砍掉。新模型下 PRD 写时 `prototype/` 真代码已存在，直接嵌截图。这是 PRD 后移的最直接收益。

**子节具体变化**：

- **§5.1 用户角色**：AI 读 prototype/ 路由 / 角色守卫 / 页面差异 → 角色列表；角色业务命名（"采购总监"）仍从 PRODUCT-STATE / brief 抽
- **§5.2 用户故事**：AI 读 prototype/ 流转 → 反推 "作为 X 我希望 Y"；"以便 Z"（价值）从 brief 抽
- **§5.3 非目标**：prototype/ mock 占位 / TODO / 占位界面 = 非目标候选；显式不做的仍从 brief 抽
- **§6.X 模块拆分**：原型路由 / 菜单结构 = 拆分依据；**模块命名仍要 PM 拍**（产品命名 ≠ 代码命名）；PM 确认门保留意义变成"模块怎么对外命名"
- **§6.X 功能表格**：AI 读 prototype/ 代码抽路由 / 组件 / 表单字段 / 交互
- **§6.X 业务规则**（"超 X 元二级审批"）：mock 原型反映不出，仍从 brief/analysis 补
- **§七验收点**：真相源 = PM 确认主原型时的反馈 + 主原型实际行为；措辞从抽象转具体（"对照 prototype/ 角色管理页 → 普通成员看不到删除按钮"）；task-verify 角色随之变（见 §5.1.6）
- **§四 §八**：来源不变

**已决议（结构与触发位置，2026-05-28 PM 拍"按推荐"）**：

| Fork | 决议 | 理由 |
|---|---|---|
| 大方向 | **保留 prd-writing 重构为独立 skill** | PRD 是给决策者评审的重磅产物；独立 PRD 跟反向沉淀 PRD 共用结构 + 写作规则 + few-shot，合一 skill 经济 |
| 触发位置 | **close-req 内编排**（不新起 `pmai-req-settle`） | close-req 本来就是 merge 时机；"沉淀"和"关 req"在 PM 视角是同一动作；新起 skill 增加心智负担。close-req 职责从 `merge + close-report + 更新 PRD` 扩展成 `调 prd-writing 写 PRD + 更新 PRODUCT-STATE.md + merge`（同一职责自然扩展，不是新职责） |
| 独立 PRD 命运 | **保留为同一 skill 的 standalone 入口** | 跨模块评审 PRD 跟反向沉淀 PRD 共用 PRD 结构 / 写作规则 / few-shot；合一 skill 维护成本低 |

**入口变化总结**：

| 入口 | 旧 | 新 |
|---|---|---|
| A orchestrated | `req-stage-gate@stage3` 调（前置重规格门） | **`close-req` 调**（PM 确认主原型后反向沉淀） |
| B-1 req 级 standalone | PM 手动 | 不变（手动重写 / 补写已有 req PRD） |
| B-2 独立跨模块评审 | PM 手动 | 不变 |
| B-3 补差 | PM 手动 | 不变 |
