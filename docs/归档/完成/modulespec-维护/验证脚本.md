# D13 验证脚本（adminconsole4 实测）

> **目的**：回答 Codex-H1 的尖锐质疑——D13 的痛点是机制性的（对账模式真处理不了），还是体验性的（PM 觉得 commit 流水重复）？
> **不预设结论**：根据实测数据决定下一步是 D13 / settlement-improvement / 不改
> **执行**：PM 在 adminconsole4 实际操作 + AI 分析数据
> **时长**：半天到一天

## 一、验证目标

回答 3 个具体问题：

| Q | 问题 | 假设 |
|---|---|---|
| **V1** | 后 task 改前 task 工作时，**对账模式**实际表现如何？ | 假设 a：行级 patch 漂亮 → D13 不必要；假设 b：累积出问题 → D13 有依据 |
| **V2** | settlement mode 跑完后 PM 看 modulespec，**主观体验**是"清晰"还是"重复"？ | 体验问题决定是改 settlement summary 还是改 D13 |
| **V3** | quickfix 改原型在 active req 期间，**modulespec 漂移**程度？ | 测当前框架"分层 lazy sync"机制的实际表现 |

## 二、场景设计（4 个真实场景）

### 场景 1：基线 — 单 task settlement 跑通

**前置**：在 adminconsole4 选一个**简单模块**（CRUD 类，2-3 个功能）

**步骤**：
1. 起一个新 req（如 `req-NNN-验证 D13-基线`）
2. 走 stage 1→5 标准流程（brief / analysis / solution / task-plan）
3. 拆 1 个 task A，加一个新功能（如"列表页加筛选条件"）
4. 跑 task A 完整流程：task-spec → task-execute → task-submit → close-task
5. **观察**：close-task 调 doc-update settlement mode 时
   - modulespec 改了哪几行
   - commit message 长什么样
   - PM 看 diff 时主观感受（清晰 / 重复 / 累赘）

**记录**（数据收集）：
- modulespec 修改前后 diff 截图
- doc-update commit 内容
- PM 主观评分：1-5（5 = 漂亮、4 = OK、3 = 一般、2 = 觉得重复、1 = 烦躁）

### 场景 2：核心 — 后 task 改前 task（对账模式触发）

**前置**：场景 1 完成（task A 已 close，modulespec 已有"列表页加筛选条件"）

**步骤**：
1. 在同 req 内起 task B：**改 task A 加的那个筛选条件**（如"加 3 个筛选字段 → 改成 5 个 + 调整默认值"）
2. 跑 task B 完整流程
3. **关键观察**：close-task B 时 doc-update 是走 settlement（新增）还是对账（patch 旧 task A 行）？
   - 看 doc-update §1.5 分流逻辑实际执行哪条
   - 看 modulespec 最终是"两段并存"还是"task B 替换 task A"
4. **再起 task C**：再改一次同一处（如"5 个 → 3 个，但默认值不变"）
5. **关键观察**：连续三次改同一处后 modulespec 最终长什么样

**记录**：
- 三次 close-task 后 modulespec 累积 diff
- 每次 PM 主观评分
- modulespec 最终质量评分（1-5：是否准确反映了最终设计 / 是否有"陈旧痕迹"）
- **关键指标**：对账模式 vs settlement 触发次数

### 场景 3：quickfix 改原型场景

**前置**：场景 2 完成（modulespec 已有筛选功能完整描述）

**步骤**：
1. 在 active req 内跑 `/pmai-quick-fix "改筛选条件 X 字段的默认排序"`（target = prototype）
2. **观察**：quickfix 按 §3.5.2 概念分类是否扫到 docs/modules？
3. 按当前 quick-fix:152 规则，**modulespec 应该不被直接改**
4. 跑 close-req → doc-update 是否把 quickfix 的 prototype 变更同步进 modulespec？

**记录**：
- quickfix 前后 prototype diff
- close-req 后 modulespec 是否反映了 quickfix
- 如果**没反映**，PM 评分"决策丢失"的严重度 1-5（5 = critical，1 = 不重要）

### 场景 4：跨多模块 task

**前置**：场景 2 完成

**步骤**：
1. 起一个 task D 改**两个模块**（modulespec A + modulespec B）
2. 跑 close-task D → doc-update 走 multi-module atomic merge（§1.7.3）
3. **观察**：跑得快不快、PM 是否需要审两次 diff

**记录**：
- close-task D 耗时
- PM 工作量（次数 / 感受）

## 四、结论解读

跑完 4 个场景后按这张表判断走哪条路：

| 场景 2 V1 | 场景 1+2 V2 | 场景 3 V3 | 结论 |
|---|---|---|---|
| 对账行级 patch 漂亮（V1=漂亮）| 不重复（V2≥4）| modulespec 反映（V3 不丢决策）| **D13 不必要**，保持现状 |
| 对账漂亮 | 觉得重复（V2≤3）| 反映 | **改 settlement summary**（PM 体验问题，不改架构）|
| 对账累积失真（V1=累积出问题）| 任意 | 任意 | **D13 有依据**，但要先补 C1/C2/C3 三个 critical 设计 |
| 任意 | 任意 | 决策丢失（V3≥4）| **quickfix metadata 必须做**（不论 D13 是否做）|
