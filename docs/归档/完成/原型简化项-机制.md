## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

> ⚠️ 任何后续 review / autoplan / dual voice 都**不能**给本节加东西、不能重新定义痛点。
> 如果 review 中出现"新发现的痛点"，要么走另一个 D-* 设计文档，
> 要么 PM 主动决策更新 §0 并重置版本号。

### §0.1 痛点（1-3 句）

框架只有一份 req 级需求文档 `prd.md`。它 stage 3 是「评审用的完整真实需求规格」（定稿冻结），close-req 步骤 2a 又把它「反向对齐成 as-built」（逐条改成原型实际做成的样子）。原型故意做得比 PRD 少的地方，在 2a 这步被 as-built 覆盖 —— 真实需求从评审文档消失，只剩 `req-events.jsonl` 的 `before` 字段。框架没有「原型故意简化」这个一等概念，只有「实现期发现偏差 → 把文档改对」。

### §0.2 触发场景（每条要能回答"PM 实际遇到过吗 / 在哪个 req"）

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | 原型简化 PRD 某功能 → close-task 把它当偏差 promote 成 `adjustment` 事件 → close-req 2a 把 PRD 该条从真实需求覆盖成简化行为 | 机制层证据：`close-req/SKILL.md §2a.2`「把内容从 before 改成 after」+ `req-events.py` `adjustment` 无纠错 / 简化区分。痛点根：旧管线 ExampleConsumerApp `req-007-login-entry-rework`（「外部地址拒绝后回哪」5 处复述自相矛盾）。新管线消费仓实证待补 |
| 2 | PM 走查时分不清某行为是"原型简化"还是"真实需求" | 本次对话 2026-05-20 PM 原话："原型的边界没有划分清楚" |
| 3 | PRD 有某功能、task-plan 拆 task 时整块不立 task（kind 2）→ §4.2 验收 GAP 清单只有"待 task 接住"一种处置，无"原型不实现"处置；closed PRD 里该功能完整保留但无任何"原型未实现"标注 | 机制层证据：`task-plan/SKILL.md §4.2`「由 stage 6 task-spec 按编号接住」无第三种处置 |

**没填实证证据的场景标 `[ASSUMED]`，后续过滤时优先 DEFER**。本节 3 条均有实证（#1/#3 机制层 skill 原文 + #1 旧管线痛点根；#2 PM 原话）。

### §0.3 根因（解决什么底层 mechanism）

一份 `prd.md` 同时承载「需求规格」与「as-built 记录」两个生命周期角色，靠 close-req 2a 一次性转换。转换的默认假设是「偏差 = 文档写错了 → 按实际改对」。而「原型故意做少」真实需求没错，是原型选择性少做 —— 框架缺一个区分：**哪些偏差是纠错（PRD→as-built 覆盖），哪些是故意简化（PRD 真实需求保留 + 标注原型差异）**。

### §0.4 不解决什么（显式列衍生场景 / 假设场景，防 review 把这些拉进来）

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 把 `prd.md` 拆成「真实需求 + as-built」两份文件 | 成本大；且 2a as-built 转换是 delta-6 刚定的设计，本方案只在其上加分支、不推翻 |
| 2 | 在 task-spec 加「🔻 原型简化项」段（旧 v0 方案）| task spec 是 stage 6 执行合同，不是真实需求的归属地；真实需求在 PRD（v0 作废原因见 §7）|
| 3 | 算法自动识别"哪些是简化项" | 靠 task 作者 / close-task 主动登记；自动扫描误报率高（memory `judgment-pattern-not-mechanization`）|
| 4 | 与 `adjustment`「纠错偏差」/ §📁 历史档案「业务层偏差」合并 | 「纠错」= 文档写错了要改对；「原型简化」= 故意做少要保留真实需求 —— 二者的区分**正是本方案要新增的维度**，合并即取消方案 |
| 5 | 强 lint「正文出现简化词但没登记就报错」 | 误报风险（memory `judgment-pattern-not-mechanization`）；列入 §5 待验，不在 v1 强上 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**（除非 PM 显式更新 §0）

## §1 方案概述（v2）

**双家落点**（kind 1 / kind 2 分家，C1 决议）：

| kind | 触发 stage | 登记位 | 数据结构 |
|---|---|---|---|
| **kind 1**：功能在原型里、行为简化 | stage 5 `implementation-design.md`（拆 task 前已知）| `implementation-design.md` **「原型简化项」段** | `SIMP-ID` 表 |
| **kind 2**：整块功能原型不做 | stage 5 task-plan §4.2 验收 GAP 清单（任务拆分时发现）| `task-plan.md §4.2` GAP 行追加第三种处置 | `SIMP-ID` 反向引用进 `implementation-design.md` 简化项段 |

**为什么 kind 2 不能也直接进 implementation-design.md**：req-stage-gate 编排里 `implementation-design` 在 `task-plan` 之前；kind 2 是「task-plan 拆 task 时发现整块不立 task」—— 上游文档拿不到下游决策。所以 kind 2 在 task-plan §4.2 GAP 清单原地登记，反向写回 implementation-design.md 简化项段做汇总锚。

### §1.1 「原型简化项」段格式（在 implementation-design.md 内）

| SIMP-ID | PRD 锚点 | 真实需求 | 原型本次**计划**简化为 | 为什么简化 | 来源 |
|---|---|---|---|---|---|
| SIMP-01 | `§六 6.X` / `Story N`（章节号+功能名解析）| 见 PRD §六 6.X（引用、不重抄）| 原型实际计划做到什么；kind 2 整块不做写「本功能原型不实现」 | 原因 | kind 1（直接登记）/ kind 2（task-plan §4.2 反向写回）|

**字段说明**（决议来源）：

- **「原型本次计划简化为」**（C6）：stage 5 写时是计划、非 as-built 事实，字段名诚实命名。close-req 2a 时若实际偏离计划，走原 adjustment 路径再叠加。
- **「PRD 锚点」**（D5 / C5）：唯一 join 键（DRY，不加冗余 task 过滤列）。解析规则：按 PRD 第六章「一级/二级/三级功能名」+ Story 编号定位；解析失败 → close-req 2a 停下问 PM，不机械写错位。
- **「来源」**：标 kind 1 / kind 2，让 close-req 知道哪些是 task-plan 反向写回的。

### §1.2 PM 审定门（D1 决议）

stage-5 `implementation-design` PM 确认门**扩列**：原有的「架构决策表摘要」之外，加「原型简化项段摘要」。PM 单门审两块，scope 削减必须 PM 显式拍板。

### §1.3 下游消费链

```
PRD (WHAT 真相源，全程不被简化逻辑改)
  │
  ├─→ implementation-design.md 简化项段 (kind 1 直接登记 / kind 2 反向写回)
  │     │  ↑ PM stage-5 确认门审定 (§1.2)
  │     │  ↑ 产出后跑 PM-view lint (D2 源头约束)
  │     │  ↑ _shared/input-flow.md 承认 SIMP 行 (C7)
  │     │
  │     ├─→ task-spec (stage 6)：命中当前 task 的 SIMP → 实现规格 + PM 确认区按简化后写
  │     │     │  ↑ task 确认门受影响验收项行内标注 [SIMP-N] (D6)
  │     │     │  ↑ task.md.tmpl §文档偏差 carve-out：已标 SIMP 不算偏差 (C3)
  │     │
  │     └─→ close-req (stage 7) §2a：读简化项段，PRD 受影响行保留真实需求 + 追加标注
  │           │  ↑ 顺序：先全部 adjustment 覆盖、再全部 simplification 标注 (D4)
  │           │  ↑ 锚点解析失败 → 停下问 PM (C5)
  │           │  ↑ 标注写回后 PRD 再跑一次 PM-view lint (D2 后置)
  │           │  ↑ close-report 加「原型简化项」节 (C4)
  │
  └─→ task-plan §4.2 GAP 清单 (kind 2 原地登记)
        │  ↑ 第三种处置：原型不实现 → 写回 implementation-design.md simp 段 (kind 2)
        │  ↑ task-plan 输入契约补 implementation-design.md (C2)
        │  ↑ task-plan.md.tmpl 修 stale solution.md 引用 (C2)

执行期失控分支：
  task 执行中临时少做 → close-task promote 时分类 (D3)
    ├─ 纠错偏差 → adjustment 事件（原路径）
    └─ 计划外简化 → 停下问 PM、回填 implementation-design.md 简化项段
          ↑ 回填仅 close-time 触发；已完成 task 不重生成 (C9)
```

### §1.4 范围阈值（C8 决议）

「原型简化」是 PM-AI 工作流的常态，不是个例。**只登决策级简化** —— 即 PM 在 stage 5 / task-plan 主动决策「不做」的功能 / 边界。

路线默认（如「默认仅主路径，不实现 edge case」）由 `docs/工程结构约束-prototype.md` 给一句总体说明覆盖；不为每个略过的 edge case 立 SIMP 行。closed PRD 在 §六章节头部一次性引用该总体说明，避免 simp 段被低价值噪音淹没。

### §1.5 与 adjustment 事件 / close-req 覆盖逻辑的边界

- **完全不动** `scripts/req-events.py` —— 不新增事件类型，不 re-scope delta-7。
- **完全不动** close-req 2a 现有覆盖逻辑 —— simp 标注是**纯增量分支**，原 adjustment overwrite 跑完后追加。
- **同 PRD 锚点既有 adjustment 又有 simplification**（D4）：close-req 2a 先把所有 adjustment 一次性 overwrite，再读 simp 段一次性追加标注。顺序确定性，避免标注被后续 overwrite 抹掉。

## §5 风险与待验（v2）

### §5.1 漏登记简化项

**风险**：`implementation-design.md` 没识别出某个原型其实没全做的功能 → 简化项漏登 → close-req 扫不到 → closed PRD 该功能无「原型未实现」标注，走查仍分不清。

**已上的缓解**（v2）：
- T1：`implementation-design` skill 引导 + PM stage-5 审定门是主防线
- T5：simp 段产出后跑 PM-view lint
- T7：执行期发现的计划外简化由 close-task 拦下回填（D3 决议）

**待验**：是否要一条强 lint「正文出现简化词但没登记就报错」。v2 先不上（误报风险，memory `judgment-pattern-not-mechanization`）；新管线消费仓跑 3-5 个 req 后看漏登频率再定。
