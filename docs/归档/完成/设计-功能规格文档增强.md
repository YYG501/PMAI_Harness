# 功能规格文档增强 + 文档回写闭环

## Context

PM 在实际使用中遇到三个问题：

1. **功能规格文档太薄**：当前模块规格只有"接口定义、数据模型、依赖关系、约束条件"一行指导，没有功能表格，PM 无法在实现前确认具体功能需求
2. **文档回写缺失**：PM 根据原型/代码直接提出修改意见，迭代满意后，功能规格文档没有回写机制来反映最终实现
3. **实现 agent UI 质量差**：功能规格文档缺少实现指引（推荐组件、DESIGN.md 对齐、交互状态覆盖），agent 实现出来的界面样式和组件复用率很低
4. **规格过度约束扼杀 agent 美感**：功能规格如果把每个按钮位置、文案、布局都写死，agent 被迫逐条对标，反而失去了在 UI 细节上发挥的空间。需要区分"硬约束"（功能行为、数据规则）和"软指引"（布局、视觉细节），给 agent 留出创意自由度

参考：
- 旧仓库 `module-spec-writing` skill：成熟的 8-section 文档结构（定义→职责→边界→功能清单→页面状态→验收），借鉴结构但避免过度分层
- 实际功能规格文档：`Admin Console3/docs/功能规格文档/.../task-024-用户管理V4.1-功能清单与实现方案.md`

```markdown
### 步骤 2：生成模块规格

读取 `$REPO_ROOT/templates/module.md.tmpl`，为涉及的每个模块生成或更新 `docs/modules/<module>.md`：
```

### 3. 修改 `skills/task-execute/SKILL.md` — 步骤 2 明确读取实现指引

步骤 2 当前只读"模块规格和接口约定"。改为：

```markdown
### 步骤 2：读取必读文档

按「启动前必读」列表，逐个读取文档内容。理解：
- 模块规格中的功能清单（具体功能需求和规则 — 硬约束，必须严格遵循）
- 模块规格中的实现指引（推荐组件、DESIGN.md 对齐、交互状态覆盖 — 软指引，可在设计系统框架内自由发挥）
- 模块规格中的创意自由度（哪些维度可以自由发挥，哪些不可偏离）
- 设计系统规范（DESIGN.md）
- 项目背景（CONTEXT.md）

**硬软分离原则：** 功能清单定义"做什么"（不可偏离），实现指引建议"怎么做"（可灵活调整）。在满足功能行为和设计系统约束的前提下，追求最好的视觉效果和交互体验。
```

（步骤 3 的"实现前必做"行为指令已在上一轮 v0 改动中加入，保持不变）

### 4. 修改 `skills/doc-update/SKILL.md` — 增加模块规格对账模式

在现有 Workflow 的步骤 1 之后增加分流：

```markdown
### 步骤 1.5：判断更新模式

读取 task 文件的「PM 反馈」section，统计 PM 反馈轮数和偏差条数：

- **简单偏差**（1-2 条字段/数值变化，无 PM 反馈迭代）：使用现有最小修改模式（步骤 2-5）
- **显著偏差**（3+ 条，或有 PM 反馈迭代导致功能行为变化）：进入模块规格对账模式

### 模块规格对账模式

A. 读取偏差涉及的模块规格全文（docs/modules/<module>.md）
B. 读取最终实现的代码（task worktree 的关键文件）
C. 对照功能清单表格，逐行核对实际实现是否匹配
D. 生成修改方案：
   - 功能清单表格的行级更新（修改需求描述以匹配最终实现）
   - 实现指引 section 的更新（组件选择、状态处理变化）
   - 新增行（PM 迭代中追加的功能点）
   - 标记删除行（PM 确认不做的功能点）
E. 向 PM 展示对账结果，逐条确认
F. 执行修改

对账模式仍遵循最小修改原则：只改偏差涉及的行和 section，不重写整个模块规格。
```
