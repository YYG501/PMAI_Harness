## 一、视角和叙事的纠偏（§4 章节）

### 1.1 §4.1 问题陈述：用户视角，不是团队内部诱因

**优化方向：**
当前 skill §4.1 描述："直接来源于 `analysis.md`，保留关键原话"。这个规则没有约束**问题陈述的视角**——而 analysis.md 通常是 PM / 团队从内部诱因出发写的（"我们讲不清"、"规格交付卡住"），不是用户在使用产品时遇到的真实问题。

应在 skill §4.1 明示：

> 必须从**用户在使用产品时遇到的具体问题**出发（如：租户管理员误把员工调入部门来授予管理权、部门管理员遇到按钮禁用不知所措、业务方误以为主运营是租户超级管理员等）。
> 禁止以"PM 讲不清"、"团队内部规格交付卡住"、"我们要补一个 PRD"等团队内部诱因切入。
> 研发评审 PRD 不接受元叙事——读者不关心 PM 的内部困扰，只关心产品要解决什么用户问题。

**证据：**

- 第一版 §4.1 我写的开篇：

  > "PM 在向研发交付 V4.1 身份与权限模块的规格时讲不清楚，自己构造用户故事时逻辑接不上，规格交付被卡住"

- PM 反馈（原话）："这个视角不对，应该是从用户视角出发。"

- 第二版我写的 §4.1（仍不到位）：

  > "V4.1 模型已在原型中落地，但产品在多类用户的真实使用过程中暴露出共同问题..."

- PM 进一步反馈（原话）："整个需求描述部分，还是不合适，视角还是不对，应该是基于用户需求来分析这块功能应该如何设计。"

- 最终落地版本 §4.1 改为"业务诉求"段，列出 8 条具体业务场景（跨部门集中管理、调岗与权限独立处置、部门日常维护与租户级治理的清晰分层、治理边界与数据可见性分离、多平台并存下的租户自治、批量授权与显式授权兼顾、管辖范围多种形态、审计追溯完整性）。

---

### 1.2 §4.2 解决方案：写产品行为，不是文档元描述

**优化方向：**
当前 skill §4.2 描述："1-3 句话，说明本次做什么来解决上述问题。"——但没明示禁止"输出本 PRD..."这种自指元描述。

应在 skill §4.2 明示：

> 写产品做什么（具体行为 / 规则 / 能力组合），不是"本文档做什么"。
> 禁止任何对 PRD 自身的描述（"输出本 PRD 作为产品规格交付层文档"、"本 PRD 是规格交付层"、"本文档面向研发评审"）。
> 解决方案应承接 §4.1 的业务诉求推导出的设计原则集合（如本次的 8 条原则：角色与管辖范围分离 / 归属与权限相互独立 / 仅授予用户 / 默认窄边界 + 自定义扩展 / 治理边界与可见性分离 / 跨层身份隔离 / 管辖范围两种顶层形态 / 完整授权链与审计字段）。

**证据：**

- 第一版 §4.2 我写的：

  > "输出本 PRD，作为部门 / 用户 / 角色三实体的产品规格交付层文档：把三实体的产品定义、相互关系、各平台功能集合系统化呈现..."

- PM 反馈（原话）："里面包含了很多代码、路径信息、还有一些文档引用信息。不合适，要把这个 PRD 当作是一个用于给到研发评审的 PRD。"
（PM 明确指出含元描述）

- 修正后改写为基于业务诉求推导的 8 条设计原则表，第六章功能定义直接承接这些原则。

---

### 1.3 §4.3 成功指标：产品能力指标，不是文档质量指标

**优化方向：**
当前 skill §4.3 已写"使用'所有……均……''……后立即……'等句式；不写'提升体验'等无法验证的描述"——但没明示**指标的对象**应该是产品功能能力，不是文档覆盖度。

应在 skill §4.3 明示：

> 成功指标必须是"**产品能力是否达成**"的可验证指标（如"所有指定入口无 download 权限的普通成员，按钮均置灰且无法触发"），不是"**文档质量是否达成**"的覆盖度指标（禁止写"用户能从本 PRD 找到答案"、"PM 能直接引用本 PRD 给出回答"等指向 PRD 文档自身的指标）。

**证据：**

- 第二版 §4.3 我写的：

  > "1. 用户在使用过程中遇到非直观行为时，能从本 PRD 找到正面回答和下一步路径。
  > 2. 业务方提出常见误解类需求时，产品经理能直接引用本 PRD §6.5 给出标准回答。
  > 3. 部门管理员登录后能从本 PRD §6.4 自助查到完整的可用边界。"

- 这三条都是"PRD 文档作为答案库的覆盖度"，PM 在多轮反馈中（含 §4.4 整体反馈）让我整体重构第四章为正向逻辑。

- 最终版本 §4.3"设计验证标准"改为产品功能能力清单（人力业务伙伴等岗位的授权诉求能在第六章功能内完整完成、批量授权诉求通过用户列表的批量选择动作满足、默认部门管理员的权限点清单严格落在部门日常维护范围内等），完全脱离"PRD 文档质量"维度。

---

### 1.4 §4.4 方案价值：业务价值，不是文档治理价值

**优化方向：**
当前 skill §4.4 描述："说明此方案对业务/运营/商业化的价值，回答'为什么值得做'"——方向对，但没明示禁止文档治理类价值。

应在 skill §4.4 明示：

> 写产品对业务 / 用户 / 运营的实际价值（如"消除高价值内容外流风险"、"承载真实组织复杂度"、"保障租户自治"），禁止写文档治理类价值（"降低规格交付沟通成本"、"沉淀业务沟通的稳态版本"、"建立产品规格的稳态版本"等指向 PRD 文档自身或 PM / 团队内部协作的价值）。

**证据：**

- 第二版 §4.4 我写的：

  > "- 降低规格交付沟通成本：PM 一次性把模块产品规格交付给下游研发或外部 stakeholder，不需要每次现拼。
  > - 沉淀业务沟通的稳态版本：业务方反复提出的相同问题有产品级标准回答..."

- PM 在第四章整体反馈中要求"基于用户需求来分析这块功能应该如何设计"——本质是要把价值从"团队内部协作改善"扭转为"产品对业务的实际价值"。

- 最终落地版本 §4.4 改为业务价值导向：适配真实组织复杂度（人力业务伙伴等岗位无需妥协组织结构）、降低权限治理风险（默认窄边界机制阻断默认角色蔓延）、保障租户自治、支持完整审计追溯、支撑后续需求决策。

## 二、写作规则扩展（禁用清单）

**优化方向：**
当前 skill"写作规则"只有 4 条（先结论后规则 / 禁用"支持/优化/提升体验" / 同一信息只在一处主写 / 术语统一）。本轮反馈暴露大量需要明确禁用的措辞类型，应整合成一份完整的禁用清单。

应在 skill"写作规则"末尾追加完整禁用清单：

```markdown
### 禁用清单（必须遵守）

#### 禁用代码 / 实现层引用
- 代码常量名：`TENANT_ADMIN`、`DEPARTMENT_ADMIN`、`OPS_PRIMARY_ADMIN` 等 — 用产品语言对应名称（"租户管理员"、"部门管理员"、"主运营管理员"）
- 文件名 / 路径：`TenantRolesPage`、`prototypes/src/...` — PRD 不出现源码路径
- 文档章节交叉引用：`task-022 §1`、`V4.1 §十二.2`、`department-group-role-design.md §三` — PRD 自包含，不依赖外部文档章节号
- 数据库 / 数据模型字段名：`enabled`、`createdBy`、`includeDescendants`、`permissions[]` — 用产品行为描述（"角色启用状态"、"创建人字段"、"是否含子部门"）

#### 禁用 UI 实现术语
- "扁平区"、"摘要卡"、"Badge" — 改用"详情页顶部"、"摘要信息行"、"标识 / 标签"
- "按钮置灰"、"按钮级隐藏"、"按钮不展示" — 用"按钮处于禁用状态"、"按钮在界面上不展示"
- "统一渲染"、"悬浮"、"扁平化" — 用"按以下规则展示"、"鼠标悬停时"等产品形态描述

#### 禁用书面冷僻词
- 明示 / 暗中 / 链路 / 范畴 / 颗粒度 / 失控点 / 覆盖关系 / 隐式约定 / 落库
- 替换原则：用日常的、研发评审场景下不需要查字典的中文词

#### 禁用中英混杂
- review → 核对 / 评审
- CRUD → 创建 / 编辑 / 删除 / 启用停用（列全）
- scope → 管辖范围（首次定义后统一作为产品术语）

#### 禁用技术 jargon
- 死锁 / 互锁 / 悬挂引用 / 鉴权 / 三件套 — 改成业务语言
- 例："悬挂引用" → "管辖范围里仍引用了不存在的部门"

#### 禁用数学化表达
- "严格小于" / "严格更大于" / "⊊" / "⊆" — 改为产品语言
- 例："严格小于" → "完全包含在 X 之内（且至少少一个部门）"

#### 禁用元描述 / 自指
- "本 PRD 是产品规格交付层"
- "本文档面向研发评审"
- "如何使用本文档"
- "为了让 PM 讲清楚..."

#### 禁用兜底词
- "等"、"之类的"、"相关的" — 必须列全所有项
- 例："'编辑 / 启用停用 / 删除'等操作" → "'编辑'、'启用 / 停用'、'删除'三个操作"

#### 禁用主观词
- "清晰区分"、"清晰展示"、"明显标识" — 改为具体展示方式
- 例："默认角色清晰区分" → "默认角色行带'默认'标识"
```

**证据（按禁用类别给出本轮真实反馈）：**

| 禁用类别 | PM 原话反馈 | 我犯的具体错误 |
|---|---|---|
| 代码常量 | "Department——Admin" 这种代码常量不合适 | 写了 `DEPARTMENT_ADMIN` / `TENANT_ADMIN` / `OPS_PRIMARY_ADMIN` |
| 数据库字段名 | "'enabled 恒为 true' '记录 createdBy 字段' 这种描述不合适" | 写了"默认角色 enabled 恒为 true"、"记录 createdBy 字段（审计用，不参与鉴权）" |

## 三、原型与 task 文档的双向对齐

**优化方向：**
当前 skill `Workflow` 第 2 步说"读取原型代码作为依据"，但没明示**原型与 task 文档不一致时的处理规则**。本轮反馈暴露：task 文档原话直接搬到 PRD 时，可能与原型实际行为不符。

应在 skill `Workflow` 第 2 步补充：

> 读取原型代码后，必须用原型实际行为**反向校验** task 文档（或 module-spec）的描述。
> 若 task 文档与原型不一致，**以原型实际行为为准**写入 PRD，并在 PRD 章节末尾备注"task 文档此处与原型不一致，以原型为准"，让研发评审时同步修正 task 文档。
> 不允许仅复制 task 文档原话而不验证原型行为。

**证据：**

- task-022 §6 角色详情·顶部扁平区-标题行原话：

  > "左侧：角色名 + 类型 Badge（默认角色 / 自定义角色）+ 停用 Badge（若已停用）"

- 我把这段直接搬到 PRD §6.2.1：

  > "详情页顶部展示：角色名、角色类型标识（默认 / 自定义）、停用标识（若已停用）、描述。"

- PM 反馈（原话）："'停用 Badge（若已停用）'这个不对吧，启用状态的角色也会显示启用 Badge"

- 这是一个典型的"task 文档描述与原型实际行为不符"的例子——task-022 写的是"若已停用"，但原型实际是启用 / 停用都展示状态标识。

- 修正后 PRD 写法：

  > "详情页顶部展示：角色名、角色类型标识（默认 / 自定义）、角色状态标识（启用 / 停用）、描述。"

## 四、功能需求表格的层级实操规则

**优化方向：**
当前 skill 表格结构是 6 列（一级 / 二级 / 三级 / 优先级 / 使用角色 / 需求描述）。本轮反馈暴露三个具体问题：

- 章节标题已经标了一级功能时，表格里再填一遍是冗余
- 二级 / 三级功能必须按真实业务逻辑划分，不能简单复读章节标题，也不能"强行分级"
- 表格 cell 内有序列表换行需要用 `<br>`，飞书 docx 会正确渲染换行

应在 skill"功能需求表格写法"补充：

```markdown
### 表格层级处理规则

**列结构：**
- 当章节标题（如 `#### 6.2.1 角色管理`）已标明一级功能，表格内**不再保留"一级功能"列**，避免每行复读
- 实际表头：| 二级功能 | 三级功能 | 使用角色 | 功能描述 |（4 列）
- 必要时增加"优先级"列（如本次新增需求场景），但已发布功能的回溯型 PRD 通常不需要

**层级划分原则：**
- 二级 / 三级层级**来自该功能模块的真实业务逻辑**，参考已有 task 文档 / module-spec 的章节结构（如 task-022 的 §1 ~ §8 自然形成"角色列表 / 默认角色 / 创建自定义角色 / ..."的二级层级）
- **不得在 PRD 阶段拍脑袋分组**（例如把"角色列表 / 角色详情"硬归到"角色查看"组下，把"创建 / 编辑 / 启用停用 / 删除"硬归到"角色定义"组下，这种强行分级会让二级功能的逻辑变得做作）
- 同一二级功能下若三级功能 ≤ 2 个，可考虑不分级（避免强行分级）

**表格内换行：**
- 表格 cell 内多条规则必须用 `<br>` 换行（飞书 docx 表格 cell 渲染 `<br>` 为真实换行）
- 编号清单格式：`1. xxx<br>2. xxx<br>3. xxx`
- 注意：终端 markdown 渲染器不显示 `<br>` 换行，但飞书 docx 兼容；以飞书渲染效果为准

**相同内容单元格默认合并（视觉规范）：**
- 同一列下连续多行出现**相同内容**时，应按"合并单元格"的视觉效果呈现——只在第一行展示该值，后续相同的行该列留空
- 应用场景最典型：当二级功能列在相邻多行重复（如"角色列表"重复 5 行展示其下的 5 个三级功能），第一行展示"角色列表"，第 2-5 行该列留空
- 此规则对二级功能列、使用角色列同样适用——同一二级功能下多个三级功能的使用角色相同时，使用角色列也用留空写法
- **重要：飞书 docx 通过 markdown 写入时，留空 cell 不会自动合并**——只是视觉上空白格（行高小时看起来像合并，行高大时显出边框）。要真正合并必须用以下两种方式之一：
  - **方式 A（PM 手工）**：在飞书侧选中相邻 cell 合并；一次性操作即固化，但章节再次替换时合并丢失
  - **方式 B（AI 自动）**：通过飞书 docx 原生 blocks API 调 `merge_table_cells` 操作。每次 markdown 替换章节后，AI 重新拉取该 table block 的 `block_id` + 行数 + 每行第 0 列文本，按"连续相同二级功能"分组，逐次 PATCH 合并 cell。已在 req-002 PRD 落地中验证可行（5 张表共 41 次合并 PATCH 全部成功）
- **markdown 写法按"留空 cell"规范输出**——这样写最简洁、便于人工维护；飞书侧的真合并由 AI 在 markdown 替换后用方式 B 批量补齐
```

**证据：**

- PM 反馈（按时间顺序）：
  - 第一次："二级功能现在是重复标题说明了，不合理"（我把每行第一列都填"角色管理"——和章节标题 6.2.1 角色管理 重复）
  - 第二次："我不是说要删除二级功能，是应该按照逻辑来划分一、二级功能，角色管理已经是标题了，就不要再说了"（明确"章节标题已标 = 表格不再复读"）
  - 第三次："现在分的1/2级，有点强行分级的感觉了"（我尝试"角色查看 / 角色定义"分组被否决）

- 关于换行的反馈过程：

## 五、按钮 / 弹窗 / 提示文案的指代规则

**优化方向：**
当前 skill 没有专门约束 UI 元素描述时的指代精确度。本轮反馈暴露：写"按钮处于禁用状态"而不说哪个按钮、写"提示原因"而不给出具体提示文案，会让研发无法实现，PM 也无法验收。

应在 skill"写作规则"补充：

```markdown
### UI 元素指代规则

涉及按钮 / 弹窗 / 提示行为的描述，必须明确：

- **按钮名**：用引号引出按钮上的具体文字（如"添加用户"按钮、"编辑基本信息"按钮）
- **弹窗场景**：弹窗在哪个页面 / 哪个动作触发（如"移出归属确认弹窗"、"删除自定义角色二次确认弹窗"）
- **具体提示文案**：用引号给出实际显示的文字（如鼠标悬停时提示"该角色已停用，不能新增分配"）

错误示例：
> "按钮处于禁用状态，提示原因"
> "弹窗中提示用户将失去权限"

正确示例：
> "'添加用户'按钮处于禁用状态，鼠标悬停时提示'该角色已停用，不能新增分配'"
> "停用前需二次确认，确认弹窗中提示'已分配该角色的用户将立即失去该角色带来的权限'"
```

**证据：**

- 我写的："已停用角色不能被新分配（按钮处于禁用状态，提示原因）。"
- PM 反馈（原话）："'已停用角色不能被新分配（按钮处于禁用状态，提示原因）。' 这种文案没有和按钮对齐，按钮是添加用户"
- 修正后："当前角色若已停用，'添加用户'按钮处于禁用状态，鼠标悬停时提示'该角色已停用，不能新增分配'。"

## 六、cross-reference 不友好

**优化方向：**
当前 skill 没禁止 PRD 内章节交叉引用（"详见 §6.X"）。本轮反馈暴露：让读者跳到另一章再读，对研发评审不友好——PRD 应该自包含。

应在 skill"写作规则"补充：

```markdown
### cross-reference 处理规则

- 禁止用"详见 §6.X" / "见 §X.Y" 让读者跳转
- 关键规则的简要说明应直接写在当前位置；如果同一规则在多处出现，可在多处都简要描述（约 1-2 句）
- "详见 §6.X" 仅在引用本 PRD 之外的文档（如设计规范 DESIGN.md）时使用
```

**证据：**

- 我写的："添加 / 移除受自提权防护与管理员保护规则约束（详见 §6.4）。"
- PM 反馈（原话）："'添加 / 移除受自提权防护与管理员保护规则约束（详见 §6.4）。' 不要详见，直接简要说清楚规则。"
- 修正后改为两条独立规则（约束直接展开）：
  > "5. 添加用户时受自提权防护约束：操作者只能分配权限点不超过自身的角色，且目标管辖范围不能超出自身管辖范围。
  > 6. 移除用户时受管理员保护规则约束：当被移除对象持有'管理类角色'（含用户删除、移出成员、角色分配等权限点的角色）且其管辖范围等于操作者自身的管辖范围时，操作者不能移除，应交由租户管理员处理，避免同级管理员相互删除。"

## 七、模糊抽象动词的处理

**优化方向：**
当前 skill"写作规则"已禁"支持/优化/提升体验"等泛词，但没覆盖"更新 X 定义"、"保存后生效"、"立即生效"、"执行 X 操作"等抽象动词——这类动词没说清效果，读者不知道实际发生了什么。

应在 skill"写作规则"补充：

```markdown
### 抽象动词使用规则

以下动词使用时必须搭配具体效果，不能孤立出现：

- **"更新 X 定义"** → 必须写"更新后，X 对持有它的对象立即按新规则生效"
- **"保存后生效"** → 必须写生效后什么变化、对谁生效
- **"立即更新"** → 必须写更新的具体内容
- **"执行 X 操作"** → 必须写操作的具体步骤或结果

错误示例：
> "保存后立即更新角色定义"（"更新角色定义"等于"保存权限点变更"——重复表达，没说清效果）

正确示例：
> "保存生效后所有持有该角色的启用用户立即按新权限点鉴权"（具体效果 + 对象 + 时机）
```

**证据：**

- 我写的（两处）：
  > "1. 支持调整权限点集合，**保存后立即更新角色定义**。"
  > "4. **保存后立即更新角色定义**；启用状态下所有已分配用户实时按新权限生效。"

- PM 反馈（原话）："'保存后立即更新角色定义'，更新角色定义，这种说法也不明确"

- 修正后两处：
  > "1. 支持调整角色的权限点集合，保存生效后所有持有该角色的启用用户立即按新权限点鉴权。"
  > "4. 权限点保存后，所有持有该角色的启用用户立即按新权限点鉴权。"

## 八、依赖与约束章节的元描述

**优化方向：**
当前 skill 没有"依赖与约束"作为独立章节（§8 是非功能性需求）。但实际产品级 PRD 中常会有这个章节。本轮反馈暴露：依赖与约束章节里容易塞元描述（"本 PRD 是产品规格交付层"、"本 PRD 不依赖任何外部系统"）。

如果 skill 未来增加"依赖与约束"章节，应在该章节描述中明示：

> 仅写产品级约束（如"本模块依赖租户许可证授权"、"产品访问额度由许可证决定"），不写文档级元约束（"本 PRD 是产品规格交付层"、"本 PRD 不修改既有规则"）。

**证据：**

- 我在第二版 §8 写的：

  > - ..."

- 最终落地版本删除"本 PRD 是..."，仅保留"关键问题的产品承诺已写明，具体的界面即时提醒由后续界面优化需求按反馈触发"等产品级约束。

## 九、PRD 质检 prompt 补充

**优化方向：**
当前 skill 末尾的 PRD 质检 prompt 检查 5 项（逻辑矛盾 / 边界遗漏 / 验收模糊 / 泛词 / scope 不一致）。本轮反馈暴露至少 7 项新检查应纳入。

```text

1. 逻辑矛盾或自相冲突的地方
2. 遗漏的边界情况（error state、empty state、权限边界、异常流）
3. 验收标准模糊、无法测量的条目
4. 功能需求描述里有"支持/优化/提升体验"等无法执行的泛词
5. prd.md 与 analysis.md 的"In Scope"不一致的地方
6. 是否包含代码常量名（如 TENANT_ADMIN）/ 文件路径（如 prototypes/src/...）/ 文档章节引用（如 task-022 §1）/ 数据库字段名（如 enabled、createdBy）/ UI 实现术语（如扁平区、Badge、按钮置灰）

9. 是否含 cross-reference（"详见 §X"）让读者跳转
10. 是否含书面冷僻词（明示 / 暗中 / 链路 / 范畴 / 颗粒度）/ 中英混杂（review / CRUD）/ 数学化表达（严格小于 / ⊊）
11. 是否含元描述 / 自指（"本 PRD 是..." / "本文档面向..."）
12. 表格中按钮 / 弹窗 / 提示是否明确指代（按钮名用引号 / 弹窗场景明示 / 具体提示文案用引号）
13. 抽象动词（"更新 X 定义" / "保存后生效"）是否搭配具体效果

以编号 list 格式输出问题，每条附上建议修改方向。
不要直接修改文件，只给出审查意见。
```

**证据：**
