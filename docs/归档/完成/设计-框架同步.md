## 0. 分发机制 trade study

> v1.1 新增（2026-04-26 双 voice CEO review F1/F9/C1/C4/C5 接纳）
> 目的：在写"rsync + manifest"实施代码前，明确为什么不是 symlink / git subtree / git submodule / Claude Code plugin / npm package。补这一段是为了 6 个月后回头看时有书面答案，不是事后合理化。

### 0.1 候选机制

| 机制 | 一句话定义 |
|---|---|
| **symlink** | consumer 仓里 `.claude/scripts` 等是符号链接，指向本机 generator clone。生成器一改，consumer 立刻看到 |
| **git subtree** | consumer 仓通过 `git subtree pull --squash` 把生成器的目录 merge 进来。每次 sync = 一次 squash commit |
| **git submodule** | consumer 仓注册 generator 为子模块。`git submodule update` 拉新版 |
| **Claude Code plugin** | 把框架打包成 Claude Code 官方 plugin / marketplace 条目，消费者通过 plugin 安装机制接入 |
| **npm / pip package** | 把框架发布成包，消费者 `npm install` / `pip install` |
| **rsync + manifest（本设计）** | 生成器侧脚本读 manifest，rsync 推送目录到 consumer，PM 在 consumer 仓 commit |

### 0.2 维度对比

评分：✅ 满足 / ⚠️ 部分满足 / ❌ 不满足 / N/A 不适用

| 维度 | symlink | subtree | submodule | plugin | npm/pip | rsync |
|---|---|---|---|---|---|---|
| **跨机器可复现**（PM 在公司 / 家 / iCloud 同步） | ❌ symlink 路径硬编码本机 | ✅ subtree commit 跟着 git 走 | ✅ submodule 状态在 git | ✅ plugin 走官方分发 | ✅ package 在仓库 | ✅ 文件物理拷贝在 git |
| **CI 可工作**（consumer 仓在 CI 里 clone 后能跑） | ❌ symlink 目标缺失 | ✅ | ✅（`--recursive`）| ✅ | ✅ | ✅ |
| **worktree 兼容**（每个 worktree 独立工作树） | ⚠️ 每个 worktree 单独建 symlink | ✅ | ✅ | ✅ | ✅ | ✅ |
| **版本锚点**（consumer 知道在用哪个版本） | ❌ 永远是 generator HEAD | ✅ squash commit | ✅ submodule SHA | ✅ plugin version | ✅ package version | ⚠️ 靠 trailer / lockfile 自维护 |
| **回滚到旧版本**（consumer 单方面降级） | ❌ generator 一退 consumer 也退 | ✅ revert commit | ✅ submodule checkout | ⚠️ 看 plugin 版本 | ✅ | ✅ git revert |
| **本地覆盖安全**（consumer 自己改过 .claude/scripts/xx 不被覆盖） | ❌ 改的就是 generator 自身 | ⚠️ merge conflict | ⚠️ 在 submodule 里改不算 consumer commit | N/A 走 plugin 扩展点 | N/A | ⚠️ 靠 manifest exclude / git status precheck |
| **PM onboarding 成本**（学新工具） | ✅ 0（`ln -s`） | ⚠️ 中（`git subtree` 子命令） | ⚠️ 中（submodule 状态机易错） | ❌ 高（plugin 打包 + marketplace） | ❌ 高（账号 + 发布流程） | ✅ 0（rsync 内置） |
| **rename 处理** | ✅ 自动跟随 | ⚠️ 有时被识别成 add+delete | ⚠️ 同上 | ⚠️ 看 plugin 机制 | ⚠️ | ⚠️ 靠 manifest RENAMES |
| **删除安全**（generator 删文件不带走 consumer 多余文件） | N/A symlink 直接看到 | ⚠️ subtree merge 行为复杂 | ✅ submodule 隔离 | ✅ | ✅ | ⚠️ `--delete` 风险（C6/F5） |
| **生成器侧工作量**（实施 + 维护） | ✅ 几乎为 0 | ✅ 几乎为 0 | ✅ 几乎为 0 | ❌ 高（marketplace 接入） | ❌ 高（npm/pip 包打包） | ❌ 高（manifest + 脚本 + 测试 ≈ 12-18 小时实施） |

### 0.3 各机制的致命缺陷

| 机制 | 卡点 |
|---|---|
| symlink | **跨机器不可复现**：PM 在两台机器之间同步 consumer 仓时，symlink 目标路径不存在 / 路径不一致；Conductor / iCloud 同步会破坏 symlink；CI 上 100% 不工作。**worktree 倍数问题**：当前 AC4 有 3 个活跃 worktree，每个都要单独维护 4 条 symlink |
| git subtree | **PM 学习成本 + history 膨胀**：subtree 在 squash 模式下行为可控但 PM 要记 4-5 个子命令；rename 不被天然识别 |
| git submodule | **状态机复杂**：忘了 `git submodule update --init --recursive` 会得到空目录；PM 在 submodule 里直接编辑提交不会被 consumer 仓追踪 |
| Claude Code plugin | **机制不熟 + scope 不匹配**：plugin marketplace 主要分发 SKILL，本框架还含 templates / agents / scripts 三类 non-skill 内容；私有 plugin 部署机制本身要研究；过度工程 |
| npm/pip | **跨语言混合内容**：框架是 markdown + shell + python 混合，不属于任何单一包生态；single-PM 项目搞 npm 发布是 over-engineering |
| rsync + manifest | **自维护成本**：manifest / RENAMES / 锚点都需要 PM 手工 / AI 辅助维护；首次实施 12-18 小时 |

### 0.4 选择 rsync 的理由

按 PM 单人 + 多机器（公司 / 家）+ AC4 现有 3 worktree + 未来可能进 CI 的实际约束：

1. **跨机器可复现 + worktree 兼容 + CI 友好** 是硬约束，直接淘汰 symlink
2. **避免引入新工具学习成本**（subtree / submodule / plugin / npm）—— PM 已经在维护一个完整框架，不再加新工具栈
3. **保留 PM 完全控制**（看到具体改了哪些文件再 commit）— rsync 是唯一能让 PM 在 commit 前完全 inspect diff 的方案
4. **manifest 自维护成本可控** —— RENAMES 表预计每年新增 1-3 条，append-only 的腐烂问题用 §4.3 加 prune 规则化解（接纳 F7）

**淘汰但保留 fallback**：如果未来 PM 接受"只在单机用 + 永不进 CI + worktree 退化为单一工作目录"，symlink 是 ROI 最高的方案，可降级到 30 行实施。当前 AC4 实际有 3 worktree + 未来可能上 CI，不满足这个限定，故不选。

### 0.5 一票否决项

下面任一情况发生，必须重新走本 trade study：

- AC4 进入 CI 流水线，且 CI 跑得通则需要 sync 工具（plugin 替代）
- PM 永久退出多机器场景，confirms 单机使用（symlink 替代）
- 第三个消费者出现，且 PM 接受 git subtree 命令成本（subtree 替代）

## 2. 定位

**`scripts/sync-to-consumer.sh` 是生成器主动 push 模型的同步工具**：

- 在生成器仓里跑，传入消费者路径作为参数
- 单向：generator → consumer，**不反向**
- 不读消费者侧的"想要什么"，只按 manifest 推
- 不自动 commit / 不自动 push，只 rsync + 暂存 + 给出 commit message 草稿

**不做的事**：

- 不搞"消费者注册表"（PM 单人，多消费者用 wrapper for 循环即可）
- 不做"生成器订阅 / 推送给所有下游"
- 不做"消费者主动 pull"
- 不替 PM 决定改动是否安全（worktree impact 只列清单 + 建议，不阻断）

## 4. S1: manifest 结构

### 4.1 文件位置 / 格式

`framework-manifest.py`，**生成器仓根目录**（与 README.md 同级）。

**为何选 python module 而非 yaml/toml/json**（决议见 §13）：

- 零依赖。macOS 默认 python 没装 PyYAML；tomllib 要 python 3.11+；json 不能写注释
- 和 `scripts/*.py` 风格一致，sync 脚本里 `import framework_manifest as m` 即可，不需要解析器
- PM 改起来就是改顶层变量赋值（dict / list），缩进语义和 yaml 几乎一样
- 后期如要加条件逻辑（如「针对某 consumer 跳过某条 rename」）有路径

### 4.2 字段

```python
# framework-manifest.py
"""框架同步 manifest。每次生成器加新 sync 路径 / 做 rename 时同 commit 改这里。
sync-to-consumer.sh 通过 import 读取这些常量。"""

SCHEMA_VERSION = 1

# 同步路径映射：generator 路径 → consumer 路径
# rsync -a --delete 语义；trailing slash 必带（rsync 行为约定）
SYNC_PATHS = {
    "scripts/":   ".claude/scripts/",
    "skills/":    ".claude/skills/",
    "templates/": "templates/",
    "agents/":    ".claude/agents/",
}

# 历史 rename。sync 时如果 consumer 上 from 路径还在、to 不在，自动 git mv
# rename 不会"跨 sync_paths"，from/to 都是 consumer 侧路径
RENAMES = [
    {
        "from":   ".claude/skills/status",
        "to":     ".claude/skills/task-status",
        "since":  "d429bd3",
        "reason": "codex plugin /status 冲突",
    },
]

# 注：消费者本地自定义（exclude / mount_mode）不放在这里。
# 那是 consumer policy，应该放在 consumer 仓的 .framework-overrides.json
# 见 §4.2.1（C7 接纳）

# 生成器自身资产，永远不进入 sync 集
# 用 generator 侧 glob，匹配的文件 sync 时跳过
NEVER_SYNC = [
    "INVARIANTS.md",
    "TODOS.md",
    "README.md",
    "CLAUDE.md",
    "设计-*.md",
    "需求-*.md",
    "实施计划-*.md",
    "tests/",
    ".git/",
    "EXIT",
    ".worktrees/",
]
```

bash 侧通过小辅助 `scripts/_manifest-parser.py` 暴露这些常量给 sh（`--get sync_paths` 输出 `key1=val1\nkey2=val2`），见 §9 实现清单。

### 4.2.1 consumer-side override（C7 接纳）

> v1.1 新增。原设计把 `EXCLUDE_FROM_CONSUMER` 放在 generator manifest 里，问题：consumer 的本地自定义不该让 generator 全局知道，且 ExampleConsumerB 以后会被 AC4 的 exclude 污染。拆成两层。

每个 consumer 仓根目录维护 `.framework-overrides.json`（**入库**，consumer policy）：

```json
{
  "schema_version": 1,
  "exclude_from_sync": [
    ".claude/skills/prd-writing"
  ],
  "local_skills": [
    ".claude/skills/my-custom-skill"
  ],
  "mount_mode": "copy"
}
```

字段：

- `exclude_from_sync`：sync 时不被 `--delete` 清理的 consumer 侧路径（原 `EXCLUDE_FROM_CONSUMER` 搬到这里）
- `local_skills`：consumer 自己写的 skill / scripts / templates，不希望被生成器同步覆盖
- `mount_mode`：默认 `"copy"`（rsync 拷贝）。预留 `"symlink"`（symlink 模式 — 见 §0.5 一票否决条件）/ `"subtree"`（git subtree 模式）。当前实现只支持 `"copy"`，其他报错

sync 脚本读取 consumer 的 `.framework-overrides.json`，合并到 rsync 的 `--exclude` 列表中。如果 consumer 没有这个文件，按全默认（无 exclude，mount_mode=copy）。

### 4.3 manifest 维护规则

- 生成器加新 sync 路径（如未来加 `hooks/`） → 加一行 `sync_paths`
- 生成器做 rename → 同 commit 加一条 `renames`
- 消费者本地自定义新 skill → PM 在 consumer 仓的 `.framework-overrides.json` 加 `exclude_from_sync`（v1.1 改用 consumer-side policy，§4.2.1）
- 生成器加根目录的新设计文档 → glob `设计-*.md` 已覆盖，无需改 manifest

## 5. S1: sync 脚本流程

### 5.1 调用形式

```bash
# 仓根目录跑
scripts/sync-to-consumer.sh <consumer-path> [--apply] [--from-sha <sha>] [--force]

# 默认 dry-run，只输出 plan，不动文件
scripts/sync-to-consumer.sh ~/Projects/ExampleConsumerApp

# 实际执行（修改文件 + git add，不 commit）
scripts/sync-to-consumer.sh ~/Projects/ExampleConsumerApp --apply

# 显式指定上次同步 sha（首次 sync 或锚点丢失时用）
scripts/sync-to-consumer.sh ~/Projects/ExampleConsumerApp --from-sha 476bc75 --apply

# 跳过 consumer 工作树干净检查（不推荐，仅救急）
scripts/sync-to-consumer.sh ~/Projects/ExampleConsumerApp --apply --force
```

### 5.2 步骤

```
[1/9] 校验
  - consumer-path 存在 + 是 git repo
  - consumer 当前在 main 分支（避免污染 worktree 分支）
  - consumer 工作树干净（除非 --force）
  - 生成器工作树干净（保证 source 一致）

[2/9] 读 manifest
  - 找不到 → 报错
  - schema_version 不支持 → 报错

[3/9] 定位上次 sync 状态  (v1.1: 改用 consumer-side lockfile，C6/F6 接纳)
  优先级：
  a. --from-sha 显式参数（覆盖 lockfile）
  b. consumer 仓根读 .framework-sync-state.json
     → 拿到 generator_sha（lockfile 直接存）+ consumer 上次 sync commit SHA（git log 派生，见 step 5）
  c. consumer 仓根没 lockfile + commit message grep "framework-sync:" trailer
     → 回退路径，仅 v0 升级期使用，建好 lockfile 后不再用
  d. 全失败 → 要求 --from-sha 显式传

[4/9] 列上游变化  (用 generator_sha 查 generator log，正确域)
  cd generator && git log --oneline <generator_sha>..HEAD -- $(取 SYNC_PATHS keys)
  按 conventional commit type 分组：
    feat: / fix: / refactor: / chore: / docs:
  输出文件总数 + insertions/deletions（git diff --shortstat）

[5/9] 本地修改保护（P4 + C6 + C-E2 fix）
  ⚠️ v1.1 修订：原 v1 用 generator SHA 查 consumer log（C6 bug）；
  v1.1 草案存 consumer_sha_at_sync 进 lockfile（C-E2 chicken-and-egg）；
  最终方案：从 git log 派生。

  consumer_sha_at_sync=$(git -C consumer log -1 --format=%H -- .framework-sync-state.json)

  对每条 SYNC_PATHS.values()（consumer 侧路径）：
    a. git -C consumer diff --stat <consumer-path>
       → 有未提交改动 → 列文件 + 报错停下
    a.1 git -C consumer ls-files --others --exclude-standard <consumer-path>
       → 有 untracked 文件 → 列文件 + 报错停下
       (F3/C-E5 修复：避免 rsync --delete 静默删除 PM 临时调试文件)
    b. git -C consumer log <consumer_sha_at_sync>..HEAD -- <consumer-path>
       → 用 consumer 自己 lockfile commit SHA 查 consumer log
       → 有 commit = consumer 自己改过 sync 范围（如手动 patch），列 commit + 警告
       → 要求 --force 跳过 OR 先把这些改动 PR 回 generator 再同步

[6/9] 应用 renames
  对每条 renames：
    if consumer/<from> 存在 and consumer/<to> 不存在:
      git mv from to
    else:
      skip + log

[7/9] rsync
  对每条 SYNC_PATHS：
    rsync -a --delete \
      $(for ex in <consumer .framework-overrides.json :: exclude_from_sync>: --exclude=$ex) \
      generator/<src>/ consumer/<dst>/

  对 NEVER_SYNC 的 glob：rsync 默认不会进入（因 SYNC_PATHS 不含它们），
  但如果将来 SYNC_PATHS 扩到根（不推荐），在这里加 --exclude

[8/9] worktree impact 报告（S2，§6 详）
  生成 framework-sync-impact.md 写到 consumer 仓根目录（gitignore 不要它）

[9/9] commit message 草稿
  写到 stdout + .git/SYNC_COMMIT_MSG（让 PM 直接 git commit -F .git/SYNC_COMMIT_MSG）
  格式：
    chore: 同步框架 — <自动按 type 分组的 1-2 句概括>
    
    从 PM-AI-Workflow 同步自上次 sync (<from-sha>, <date>) 以来
    <N> 个上游 commit，覆盖 <M> 大工作线。
    
    1) <type>: <commit subject>
    2) <type>: <commit subject>
    ...
    
    ⚠️ <如有 worktree>，列 worktree 影响概要
    
    framework-sync: <generator HEAD sha>
```

### 5.3 锚点机制（v1.1：lockfile 主，trailer 辅）

> 原 v1 只有 commit trailer。F6/C8 评审指出 trailer 第一次忘写就 rot（squash / cherry-pick / 手动改 commit message 都可能丢）。改成 lockfile 主导。

**主锚点：consumer 仓根目录的 `.framework-sync-state.json`（入库，git tracked）**

```json
{
  "schema_version": 1,
  "last_synced": {
    "generator_sha": "5a39159",
    "generator_repo": "PM-AI-Workflow",
    "synced_at": "2026-04-26T12:00:00Z",
    "manifest_schema": 1
  }
}
```

每次 sync 完成后由脚本写入。git tracked，不会因为 commit message 操作而丢。

**关键：lockfile 不存 `consumer_sha_at_sync`**（v1.1 修订，C-E2 真 bug 修复）

原 v1.1 草案打算把 consumer 上次 sync commit 的 SHA 写进 lockfile。这有个 chicken-and-egg 矛盾：lockfile 是被本次 sync commit 包含的文件，commit SHA 由 lockfile 内容算出，无法在 lockfile 里预先写自己所在 commit 的 SHA（除非引入 finalize commit 二段提交，过度复杂）。

改为**派生**：sync 脚本在 step 5 需要 consumer 上次 sync commit SHA 时，跑：

```bash
consumer_sha_at_sync=$(git -C consumer log -1 --format=%H -- .framework-sync-state.json)
```

这个 SHA = "lockfile 文件最后一次被改的 commit" = "上次 sync commit"。零额外存储，零矛盾。

**辅锚点：commit trailer**

每次 sync commit 也带 trailer 作为人类可读副本：

```
framework-sync: 5a39159
```

trailer 丢了不影响功能（lockfile 是真相源），但保留对 PM 一眼看到 sync commit 的可读性。

**v0 锚点（AC4）**：

1. 在 AC4 commit `d0aa6c1` 之上写一个新 commit `chore: 建立 framework-sync v0 锚点`，内容是新增 `.framework-sync-state.json`（只含 `generator_sha = 5a39159` + `synced_at` + `manifest_schema`，**不含** consumer SHA — 派生自 git log）
2. 同时在 `d0aa6c1` 加 commit trailer（amend）作为人类可读副本
3. 之后所有 sync 都自动维护 lockfile

为什么不直接 amend lockfile 进 d0aa6c1：amend 会改 commit hash，破坏 d0aa6c1 这个 SHA 已经被本设计文档引用的事实。新建一个 v0 锚点 commit 更干净。

**推荐：sync 脚本提供 `--init <consumer-path> --from-sha <generator-sha>` 子命令自动化整个 v0 流程**（D-S1 接纳）。PM 不应手动构造 JSON 文件。

## 7. S3: module 规格 lazy migration

### 7.1 问题

template 改了，但 `docs/modules/<module>.md` 已经写过了。下次 doc-update sink 时，沉淀位置可能找不到对应 H2 / 表格列。

### 7.2 触发时机

doc-update skill 运行时。**不在 sync 流程内执行**——sync 只更新 template，迁移在使用 template 时再做。

### 7.3 检测机制

新增 `scripts/check-module-template.py <module-md-path>`：

- 解析 `templates/module.md.tmpl` 提取期望的 H2 段落 + 关键表格列名集合
- 解析目标 module.md，比对结构
- 输出：
  - `OK`：结构匹配，doc-update 直接 sink
  - `NEEDS_MIGRATION`：缺 H2 段 / 缺表格列，附 diff
  - `INCOMPATIBLE`：解析失败 / 不像 module.md，要 PM 手动处理

### 7.4 doc-update 集成

在 doc-update SKILL.md 加一段「前置：模板对齐」step：

```
0. 模板对齐
   对涉及的每个 module.md 跑 check-module-template.py
   - OK → 继续
   - NEEDS_MIGRATION → 走 reorganize 子流程：
       a. 把旧内容映射到新模板的 section
       b. 缺失 section 留 placeholder + 注释 "<!-- migrated from old template, fill in -->"
       c. 加 commit "chore(modules): align <module> to template v<N>"
       d. 然后再做正常 sink
   - INCOMPATIBLE → 停下，要 PM 手动处理
```

### 7.5 模板版本号

`templates/module.md.tmpl` 头部加注释行：

```markdown
<!-- template-version: 2 -->
# {{module_name}}
...
```

每次 module.md.tmpl 大改（H2 增删、关键表格列增删）→ 版本号 +1。
check-module-template.py 比对 module.md 顶部记录的 template-version 与当前 tmpl 版本。

不需要 semver；只是个递增整数。

## 8. 边界与红线

### 8.1 不会被 sync 改的（硬规则）

- consumer 仓根目录的 `CLAUDE.md` / `INVARIANTS.md` / 任何 `*.md`（除非显式在 sync_paths 里）
- consumer 仓的 `requirements/` `prototypes/` `docs/` 等业务目录
- consumer 仓的 `.git/` `.runs/` `.dev-port` `.worktrees/`
- consumer 仓任何 worktree 的工作树（sync 只改主 worktree / main）
- 生成器侧 `never_sync` glob 命中的文件

### 8.2 sync 出错时的恢复

sync 脚本不自动 commit。失败 / 不满意时：

```bash
cd consumer
git restore .         # 恢复未 add 的改动
git restore --staged . # 取消暂存
# rsync 已删除的文件靠 git 恢复（因为还没 commit）
```

### 8.3 不支持的场景

- consumer 不是 git repo → 报错（依赖 git 做 rollback / 锚点）
- consumer 在非 main 分支 → 报错（避免污染 worktree 分支；用户要在 main 上 sync）
- 生成器在非 main 分支 → 报错（锚点必须从 main commit 来）

## 11. 已决问题（原未决，2026-04-26 由 PM 全权委托决议）

### Q1: manifest 用什么格式？→ **python**

零依赖（macOS 默认 python 没 PyYAML；tomllib 要 3.11+），和 scripts/*.py 风格一致，`import framework_manifest` 即用，PM 改起来就是改 dict。详见 §4.1。

### Q2: 多消费者怎么管？→ **YAGNI**

当前只有 AC4。第二个消费者（ExampleConsumerB）首次迁移单独开 req，不进常规 sync 队列。多消费者批量同步用 PM 自己写的 wrapper：

```bash
for path in ~/Projects/ExampleConsumerApp ~/Projects/ExampleConsumerB; do
  scripts/sync-to-consumer.sh $path --apply
done
```

遇到第三个消费者再考虑 manifest 加 `CONSUMERS = [...]` 或 `--all` 命令。

### Q3: ExampleConsumerB 这种 v1 项目首次迁移？→ **本设计不覆盖**

ExampleConsumerB 可能没 `agents/`、可能 skill 集合差很多、可能 module.md 结构完全是 v1。直接走 sync 脚本会触发大量 rename / delete，不安全。

策略：先把 sync 脚本用 AC4 跑稳；之后**单独开 req**设计 v1→v4 的一次性迁移脚本（不复用 sync-to-consumer.sh，因为迁移是一次性的、要做大量 ad-hoc 转换）。迁移完成后 ExampleConsumerB 进入常规 sync 队列。

### Q4: framework-sync trailer 是 amend 到 d0aa6c1 还是从下次开始？→ **amend**

建立锚点 v0，否则下次还要 grep 反推。AC4 main 未 push，amend 安全。amend 步骤纳入 §9 实现清单（第 9 项）。

### Q5: sync 脚本要不要支持 `--no-worktree-impact`？→ **不加，YAGNI**

worktree 报告轻量（只读 git worktree list + status-view），先不加 opt-out。

### Q6: doc-update 的 lazy migration 谁触发？→ **PM 走 stage 6 时自然触发**

不主动触发。模板升级后已沉淀的 module.md 暂时无害（无人读），等下次有 req 进 stage 6 → doc-update 跑 → 检测到旧结构 → reorganize → sink。符合 TODO "lazy" 本意。
