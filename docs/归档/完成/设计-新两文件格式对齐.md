# 设计 — 新两文件格式对齐

> 本文是骨架版。详细实施细节（具体函数签名、迁移步骤、测试用例）留待专门讨论会展开。

## 一、背景与问题

### 现状

框架在 PR 2 系列 commit（d4024eb / 0496e9e 等）完成 "task PM 视图 + `.engineering.md` 工程合同" 的双文件拆分。新模板的关键格式变化：

- **状态字段**：`**状态：** 待确认` → `| **状态** | 待确认 |`（表格行）
- **分支字段**：同上变成表格行
- **worktree 字段**：同上
- **文档偏差 / 自审记录 section**：从 PM 视图（`task.md`）搬到工程合同（`task.engineering.md`）的 `§10` / `§11`

### 痛点

模板演进了，但 scripts / hooks / tests 的解析仍按**旧单文件 grep**。这些 grep 散落在 5 个文件，**没有共享解析层**——所以模板再演进时无法集中迁移。

### 现实后果

5 条 P0/P1 bug 已经在 main 上活跃，会破坏 task 闭环：

- 新 task 卡在「执行中→待验收」（`task-transition.py`）
- hook 拦截被绕过（`check-branch.sh`）
- close/cancel 漏掉新 task（`close-req.sh` / `cancel-req.sh`）
- 外部执行器拿错 worktree（`build-execution-prompt.py`）
- 测试覆盖不到新格式（`tests/helpers/fixture.sh`）

详细证据见 §二。

## 二、Bug 清单（已 sanity-check 验证）

| # | 文件 | 当前症状 | 严重度 |
|---|---|---|---|
| P0-1 | `scripts/task-transition.py:200` | `re.search(r"^## 文档偏差", text)` 找不到——section 已搬到 `task.engineering.md §10`；且第 266 行 `text = read_text(task_file)` 只读 PM 视图、不读工程合同 | P0+ |
| P0-2 | `scripts/check-branch.sh:178` | `pat = r'\*\*状态：\*\*'` 不识别新表格 `\| **状态** \|`，PM/AI 直接改表格状态值会绕过拦截 | P0 |
| P0-3 | `scripts/close-req.sh:38` / `scripts/cancel-req.sh:53` | `grep '^\*\*状态：\*\*'` / `grep '^\*\*分支：\*\*'` 找不到新格式 task → 漏 open task / 留 worktree/branch | P0 |
| P1-5 | `scripts/build-execution-prompt.py:23` | `FIELD_RE = re.compile(r"^\*\*(.+?)：\*\*\s*(.*)$")` 抓不到表格内 worktree 字段；fallback 到 `pm_view.parent.parent.parent` 给 codex/cursor-agent 错的 worktree | P1 |
| P1-7 | `tests/helpers/fixture.sh:131` | `make_task` 仍生成旧单文件（`**状态：** $status` / 无 `.engineering.md`），新格式真实路径无测试覆盖 | P1 |

**P0-1 比表面诊断更严重**：不只是标题前缀变了（`## 文档偏差` → `## 10. 文档偏差`），section 还跨文件了。修复需要让 transition 同时读 PM 视图与工程合同。

---

## 三、根因

5 条 bug 共有同一根因：**框架缺少"task 元数据解析层"**。

每个 script / hook 自己写 grep / 正则，模板演进时无法集中迁移。任何"散点 grep + 模板字段直读"的设计都会重复这个故事——下次模板再改，仍会出现 N 处漂移。

修复策略不是"5 处独立打补丁"，而是**集中收口到一个 shared parser**，让模板演进只需改一处。

---

## 四、改造方案

### 4.1 新增 shared task parser

新增 `scripts/_lib/task_parser.py`（python 版）+ `scripts/_lib/task_parser.sh`（bash helper 版）。

最小接口（具体签名待实施时定）：

```
get_task_status(task_file)        → 状态字符串
get_task_branch(task_file)        → 分支名
get_task_worktree(task_file)      → worktree 路径
get_task_meta(task_file)          → 一次性返回所有字段
read_section(pm_file, eng_file, section_name) → section 内容
```

**实现要求**：
- 双兼容：新表格格式 + 旧 `**字段：**` 格式都能解析（通过自动探测）
- 跨文件：`read_section` 自动在 PM 视图 + 工程合同里找
- 容错：工程合同不存在 → 退化到 PM 视图（兼容旧格式 task）
- 单元测试：覆盖两种格式 + 跨文件 + 退化

### 4.2 5 处解析点替换

| 文件 | 原始解析 | 改为 |
|---|---|---|
| `task-transition.py` | 直接 regex 找 `## 文档偏差` | `task_parser.read_section(pm, eng, "文档偏差")` |
| `check-branch.sh` | `r'\*\*状态：\*\*'` | `task_parser.get_task_status` |
| `close-req.sh` | `grep '^\*\*状态：\*\*'` | `task_parser.get_task_status` |
| `cancel-req.sh` | `grep '^\*\*分支：\*\*'` | `task_parser.get_task_branch` |
| `build-execution-prompt.py` | `FIELD_RE` 直读 | `task_parser.get_task_meta` |

### 4.3 fixture 重写

`tests/helpers/fixture.sh` 改成生成新两文件格式：

- `make_task_v2`（默认）：生成 `task.md` 表格格式 + `task.engineering.md` 含 §10 / §11 占位
- `make_task_v1`（兼容性测试用）：保留旧单文件格式，用于验证 parser 双兼容

## 五、不做的事（边界）

- 不改模板（`task.md.tmpl` / `task.engineering.md.tmpl` 已是事实标准）
- 不改 stage / skill 流程
- 不引入"格式版本号"字段（用"是否存在 .engineering.md"足够区分新旧）
- 不重写 transition / hook 的核心逻辑——**只替换解析点**

## 六、验证方式

1. `tests/run-all.sh` 全绿（包括 fixture v1/v2 双覆盖）
2. 跑一次真实 task 全流程（new-req → new-task → execute → submit → close-task → close-req），状态机不卡
3. 验证 quick-fix 等横切流程对新格式 task 也工作

## 七、与双模式改造的关系

**本设计是双模式改造的前置依赖。**

落地顺序：

```
本设计（格式对齐）
    ↓
设计-原型与系统双模式 §四块 0（worktree 文档同步）
    ↓
设计-原型与系统双模式 §四块 A → B → D → C → E
```

理由：
- 块 0 验证步骤要求 task 能从「执行中」转「待验收」，但 P0-1 让转换卡死
- 块 0 的 audit 事件依赖 close/cancel 正确处理 task，但 P0-3 让它们漏 task
- 双模式建立在不稳的 task 闭环上没有意义

详见 `设计-原型与系统双模式.md` §六落地顺序中的"前置稳定性依赖"段。

## 八、决议记录

实施前的 4 个待回答问题已全部决议。决定与理由摘要如下，作为后续实施的参考依据。

| # | 问题 | 决议 | 理由 |
|---|---|---|---|
| Q1 | parser 形态：单 python 还是 python + bash 双版本 | **python 主体 + bash thin wrapper**：bash 调用方通过 `python3 -m _lib.task_parser get_status <file>` 调用 python 实现，**不写独立 bash parser** | 避免"两套实现漂移"—— 5 条 bug 的根因正是散点解析重复，bash 重写一遍只会重演这个故事；python 单实现可以单测覆盖 |
| Q2 | 格式自动探测的主信号 | **`.engineering.md` 文件是否存在**：`pm_view.with_suffix(".engineering.md").exists()` → 新格式 | 文件级别的"有 vs 无"最稳；探测表格行内容会被未来字段名变化拖死，需要重写探测信号 |
| Q3 | fixture v1 / v2 双轨保留多久 | **保留到双模式全部上线后统一清理**，加进 `TODOS.md` | v1 fixture 服务现阶段兼容性测试（parser 在生产旧 task 上仍工作）；删 v1 = 删 parser 旧格式分支，是一次完整重构，不在本设计范围 |
| Q4 | `read_section` 跨文件查找的语义 | parser 返回 `(found: bool, content: str \| None)`，**不在 parser 内报错**；caller 决定 `found=False` 怎么处理 | parser 不背 caller 的业务语义——同一 section "必须有内容" vs "可选" 的判定属于 caller；分层最小责任边界 |

### 实施起点

4 条决议已落到 §四改造方案。落地顺序：

```
4.1 新增 shared task parser（python + bash thin wrapper）
    ↓
4.2 5 处解析点替换（task-transition / check-branch / close-req / cancel-req / build-execution-prompt）
    ↓
4.3 fixture 重写（make_task_v2 默认 + make_task_v1 兼容性测试）
    ↓
跑 §六 验证
```

完成后进入 `设计-原型与系统双模式.md` 块 0 的 worktree 文档同步实施。
