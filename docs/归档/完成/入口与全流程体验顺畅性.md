#### §0.1.M1 init-project 入口三步分裂（已锁 2026-05-24）

PM 第一次开新项目时，要先在终端跑 `bash scripts/init-project.sh ...`（脚手架），再在 Claude Code 里发 `/project-solution`（定方向），再发 `/new-req`（起需求）——三步靠 echo / README 文案串接。其中 `/project-solution` 在 4 处用户入口（init 脚本 --help / init 脚本末尾 echo / README §1 / README §2）的"下一步"提示里**全部漏写**，导致 AI 和 PM 都把流程当两步（init → /new-req）。即使 `/new-req` 步骤 3.5 有 mini-fill 兜底把 PROJECT.md 补上，`roadmap.md` 永远不被填，项目级方向讨论缺失。

**触发场景**：

| # | 场景 | 实证 |
|---|---|---|
| 1 | AI 答"框架使用流程"漏 `/project-solution` | 本次对话（2026-05-24）；PM 追问才补正 |
| 2 | PM 跑完 init-project.sh 终端只看"下一步：/new-req" | `scripts/init-project.sh:38, 275`；`README.md:63, 65` |
| 3 | gsd 一个命令把骨架+方向+多份文档全跑完，我们三步分裂 | PM 提供 gsd ChatBuilder 对话(2026-05-24) |
| 4 | mini-fill 兜底 PROJECT.md 但 roadmap.md 永远漏 | `skills/new-req/SKILL.md:68-102` 只查 PROJECT 6 节 |

**根因**：`init-project.sh` 是 shell 脚本，跑完即返回终端，**没有跟 PM 对话的能力**——所以方向讨论必须拆出独立 skill，两段中间靠 echo / README 文案粘合 → 文案就会漂。修法：把入口改成 **agent 化 skill**，agent 内部串起「骨架 → 方向讨论 → 落档 → 下一步」全流程。

#### §0.1.M4 AskUserQuestion 答题规则散乱（PM 锁 2026-05-25）

PM 答题门规则散在各 skill 各处：

- "未决问题闸门"在 stage 1→2（已落 memory `feedback_open_questions_gate`）
- task-spec 步骤 10"执行前确认"在 task-spec 内部
- task-execute 验收呈交在 task-execute 内部
- 每处自定义答题分支、自定义"PM 没答怎么办"

**没统一规则**："PM 没答怎么办 / 空答案怎么办 / 二选一怎么强制 / 是否禁止默认落盘"。gsd 通过一条全局 `#3018` 规则统一约束（AskUserQuestion 空答 → STOP wait next message，不重试不默认；没拿到答案禁止落盘 artifact）。

**触发场景**（初稿，PM 校验）：

| # | 场景 | 实证 |
|---|---|---|
| 1 | task-spec 步骤 10 vs req-stage-gate stage 1→2 闸门答题规则不一致 | grep `skills/task-spec/SKILL.md` + `skills/req-stage-gate/SKILL.md` 验证 |
| 2 | PM 没答 AI 默认走 "通过"分支导致 task 跳过 PM 拍板（历史 commit 07a3a09 处理）| memory `feedback_close_default_flow.md` |
| 3 | gsd 一条 `#3018 failure mode` 通用规则跨所有 workflow 引用 | gsd `discuss-phase.md:95-102` / SKILL.md:29-35 |

**根因**：没有 `_shared/pm-view/askuser-rules.md` 这种统一约束文件，每 skill 各自实现答题分支 → 规则漂移、PM 体验不一致。修法：把 gsd `#3018` 规则照搬，落到 `_shared/pm-view/askuser-rules.md`，所有用 AskUserQuestion 的 skill 顶部加指针引用。

#### §0.1.M5 session 起始 AI 不主动播报工作进度（PM 锁 2026-05-25）

> **v2 重定义**（PM 2026-05-25 主动决策更新 §0）：原 v1 痛点（"半成品续接 / Resume 闸门"借鉴 gsd #7）PM 实证 NULL —— PM 用 Claude Code conversation history 恢复机制已兜底"半成品"问题。真痛点是 v2：**session 起始 AI 不主动结构化播报工作进度**。

PM 切窗口 / 隔天回来 / 开新 chat session 时，Claude Code 恢复了 **对话历史** 但 AI 不**主动结构化播报工作进度**。PM 要么记住自己在哪，要么主动问"我在哪"，要么主动跑 `/status-view`。希望的体验：**PM 发出第一条 message 后**（任何内容），AI 在回应该请求**前**先播报一句进度："上次你做到 req-003 stage 3，最近 commit 在 prd.md，下一步是 gap-check 闸门"；然后再处理 PM 的具体请求。

> **机制边界澄清**（codex Round 1 C-3）：AI 在 PM 没说话前**不会自动响应**（这是 LLM chat 模型固有限制）。CLAUDE.md 规则**只能让 AI 在响应 PM 第一条 message 时先播报**，不是"PM 一开窗口 AI 就说话"。这个体验差异仍有价值：PM 一句"继续昨天的"也能立刻拿到进度上下文。

**触发场景**：

| # | 场景 | 实证 |
|---|---|---|
| 1 | PM 开新窗口 conversation history 已恢复，AI 第一句不主动说"上次你在 stage X"，要 PM 主动问 | PM 2026-05-25 confirm 痛点真实 |
| 2 | gsd `progress.md` workflow 提供"phase.complete / disk_status / roadmap checkbox"聚合，用户敲一个命令看全 | gsd `progress.md` |

**根因**：我们 `status-view.py` 已经做了进度聚合，**但只在 PM 敲 skill 时由 `skill-preamble.sh` 触发**；PM 不敲 skill 直接聊天 → AI 没自动播报。`.req-meta.json` 数据齐备，缺的是**"session 起始就播报"的触发点**+ **AI 可直接念的 narrative 输出格式**。修法：① `status-view.py` 加 `--narrative` 模式（list → 段落叙述，AI 直接念给 PM 听）② `CLAUDE.md` 加章程规则「session 起始 AI 必须先跑 `status-view.py --narrative` 并播报」。

**与 M2 banner 关系**：M2 = 过程中位置感（每 stage 转换打 banner）；M5(v2) = session 起始位置感（开窗口时 AI 主动播报）；互补。

## §1 方案概述（4 模块综合）

> M3 砍后 4 模块共同指向**"PM 看到的是一条直线，框架在背后做所有状态判断"**（gsd punchline）。模块间关系：

```
M1 (init-project 一气呵成)     ←── 入口体验
                              ↓
M2 (Banner + Next Up + Decision gate label) ←── 视觉锚点 + 闸门 label 规范 [横切，所有 skill]
                              ↓
M4 (AskUser 严格化)            ←── 答题规则 [横切，所有用 AskUser 的 skill]
                              ↓
M5 (session 播报)             ←── 回来即知 [PM 发第一条 message 后 AI 主动播报]
```

**实施分两批**：

- **批 1：init-project 闭环（M1）** —— 修 init-project skill + `_shared/project-questioning.md` shared reference；**6 个 vp + vp-5 拆 vp-5a/5b**，~4.85h
- **批 2：横切普推（M2 + M4 + M5）** —— 全仓扩散 banner / label 规范 / askuser 严格化 / session 播报；**5 个 vp**（vp-9 砍后），~4h
