## 1. 顶层架构：三层分层 [v1]

### 1.1 三层定义

系统所有 artifact 和工作流必须落在以下三层之一：

- **产品层**：长生命周期，跨需求累积。描述"产品是什么、长什么样"。包含文档（模块规格、视觉规范、项目背景等）、代码（原型 app）、以及仓库级经验。
- **需求层**：per-requirement workspace，从 open 到 close。描述"这次要改什么、为什么、怎么改"。req/task 执行中产生的经验记录在需求层，沉淀后提升到产品层。
- **Task 层**：per-task execution，状态机驱动。描述"具体在写什么代码、改到什么程度"。

### 1.2 层间依赖方向（强制单向）

- task 可以读 req 和产品层
- req 可以读产品层
- **task 和 req 不允许直接修改 main 分支上的任何文件**（通过分支隔离，req close 时统一合并）
- 产品层不依赖任何 req 或 task

## 2. 项目接入与初始化

### 2.1 两种开始方式

系统支持两种开始工作的方式：

- **新产品启动** [v1]：产品层从零开始，init-project 创建空骨架并建立视觉基准，然后 first req 带着 PM 完整跑一遍
- **已有产品接入框架** [v2+]：独立的导入流程（见 §2.4），不走 req 流程

### 2.2 项目启动入口的职责 [v1]

系统提供"项目启动入口"，作用是：

- 检测并验证 gstack 已安装且可用（gstack 是 hard dependency，未通过则启动失败）
- 检测 gstack 版本，不是最新版给出警告但不阻塞
- 在指定位置建立新项目目录
- 创建产品层骨架文件
- 创建视觉规范空骨架（DESIGN.md，等 first req stage 4 填充）
- 创建需求层空目录
- 初始化新项目的 git 仓库
- 不做任何需求分析，不创建 req

启动完成后产品层文件均为空骨架，等待第一个 req 填充。具体的启动方式（命令名、调用形式、是否带参数）在设计阶段决定。

**体验约束**：PM 从 clone 框架仓库到创建第一个 req，步骤不超过 3 步。

### 2.3 分发与框架更新

**分发** [v1]：框架本身托管在公开 git 仓库，用户通过标准 git 方式获取。

**框架更新** [v2+]：已有项目可以通过**框架自带的"框架更新入口"**把当前项目里的框架部分刷到最新版本。该入口必须：

- 从框架仓库拉取最新版本
- **只更新框架范畴的文件**（脚本、规则、模板、skill 等），**不动业务范畴的文件**（产品层 docs / requirements / tasks / experience 等）
- 明确报告本次更新带入了哪些变化
- 永远不静默修改业务内容
- 业务范畴文件如果与新框架版本有结构性冲突，必须**报告冲突**而不是自动迁移

**约束**：

- 项目启动入口和框架更新入口必须由**框架本身**提供
- 启动入口和更新入口的具体调用形态在设计阶段决定
- v1 → v2 不保证平滑升级，**接受断代升级**

### 2.4 已有产品接入框架 [v2+]

当 PM 有一个已存在的产品要接入框架时，走独立的导入流程（不是一个 req）：

1. PM 上传外部材料（PRD、设计稿、截图、现有原型代码等）
2. 框架从外部材料中反向梳理出产品层文档：
   - **CONTEXT.md**：项目背景、约束、技术栈（从 PM 描述、已有 PRD、代码仓梳理）
   - **DESIGN.md**：视觉规范基线（从设计稿、截图、已有原型代码反推）
   - **模块规格文档**：各模块的工作规格（从已有 PRD、代码结构反推）
   - **prd.md**：产品整体说明（综合以上梳理结果生成）
3. 如果 PM 有原型代码，迁入 prototypes/；如果没有代码但有生产页面，可选用 live-align 反向还原（不强制）
4. PM 确认产品层内容
5. 导入完成，之后按正常 req 流程走

## 3. 产品层 [v1]

### 3.1 产品层包含两类内容

- **文档类**：描述产品长什么样（模块工作规格、视觉规范、项目背景、仓库级经验等）
- **代码类**：产品的原型 app 代码

**约束**：每个项目只有**一个** prototype app，不允许多个独立 app 并存。

产品层的具体文件清单和目录结构在设计阶段决定。

### 3.2 隔离机制

产品层在 main 分支上，不允许任何 agent 直接修改 main。所有修改通过 req 分支隔离：

- req 开始时从 main 创建 req 分支（在独立 worktree 中）
- 所有文档类和代码类的修改都在 req 分支及其子分支（task 分支）上进行
- req close 时 req 分支整体 merge 回 main
- req 被砍时不 merge，main 零污染

### 3.3 prd.md

- prd.md 持续维护，是产品当前状态的累积说明
- 当需要更新时，运行 `/prd-writing` 更新

## 4. 需求层 [v1]

### 4.1 目录结构

每个 req 有独立工作目录，包含：原始需求、分析、方案设计（按需）、task 拆分计划、收口报告、该 req 下的所有 task。

具体文件名和目录结构在设计阶段决定。

### 4.2 req 内部流程

每个 req 内部按 stage 1 → 7 的顺序推进：

| stage | 职责 | 可否跳过 |
|---|---|---|
| 1 感受问题 | 写原始需求：这次要做什么 | 不能 |
| 2 需求分析 | 从第一性原理出发分析问题、用户、关键决策 | 不能 |
| 3 方案设计 | 系统分层、模块边界、阶段路线 | **可跳过**（非 first req） |
| 4 设计系统建立 | 建立或更新视觉规范（DESIGN.md） | DESIGN.md 不存在时必选；**已有内容时问 PM** 是否需要更新 |
| 5 模块规格 + task 拆分 | 写/更新模块规格文档，拆 task | 不能 |
| 6 task 执行 | 各 task 串行在 worktree 中实现（v1 一次一个 task） | 不能 |
| 7 req close | 收口报告，合并 req 分支到 main | 不能 |

**跳过规则**：
- **first req**：stage 1-4 全部必选（产品层和设计系统都要建立），stage 3 不可跳
- **后续 req**：stage 3 可由 PM 在确认门显式跳过；stage 4 由 PM 决定是否需要更新设计系统
- 跳过由 **PM 在阶段确认门显式决定**（stage 3 和 stage 4），AI 不能自行跳过其他 stage

**回退规则**：
- PM 可从当前 stage 回退到之前任意 stage
- 回退时保留已产出的文件（PM 可在回退后修改或重写）
- **stage 6（task 执行）回退到 stage 5 或更早**：所有 task 必须先关闭或取消
- **stage 7（close）不可回退**：merge 到 main 后不可逆

### 4.3 阶段确认门

每个 stage 结束时，系统必须**显式询问 PM 是否进入下一 stage**，得到确认后才能继续。AI 不允许自动跨 stage。

对于可跳过的 stage，系统在该 stage 开始前询问 PM 是否需要进入，PM 可选择跳过。

## 5. Task 层 [v1]

### 5.1 task 文件位置

每个 task 是 req 的子物，不存在游离于 req 之外的 task。

### 5.2 task 文件内容

task 文件需记录：所属 req、任务目标、执行范围、验收标准、依赖、审查工具、当前状态、执行环境信息（worktree 路径、分支名、端口等）、审查记录、反馈记录。

具体字段在设计阶段决定。

### 5.3 状态总览

系统需提供以下状态总览能力：

- **全局状态总览**：PM 随时可查看当前活跃 req 所在的 stage、该 req 下所有 task 的状态、以及下一步该做什么
- **req 内 task 状态总览**：PM 和 agent 能快速了解当前 req 下所有 task 的状态

具体形态（静态文件 vs 动态生成）在设计阶段决定。

### 5.4 状态机

**4 状态**：`待确认 → 执行中 → 待验收 → 已完成`

状态转换规则：

- `待确认 →(PM 确认)→ 执行中`
- `执行中 →(实现 + 自审完成)→ 待验收`
- `待验收 →(PM 通过)→ 已完成`
- `待验收 →(PM 打回)→ 执行中`

**受控入口约束**：状态变更必须经过受控入口，**禁止 agent 直接编辑状态字段**。受控入口的具体形态在设计阶段决定。

每个状态限制可执行动作：

- **待确认**：可只读代码（preflight），不得写代码。
- **执行中**：可在 worktree 内写代码。实现完成后由 suborchestrator 自动进入自审。
- **待验收**：等 PM 显式通过/打回。
- **已完成**：不可改。

### 5.5 关闭与重开

- task 状态变成"已完成"且 PM 通过验收后，task 分支 merge 回 req 分支、清 worktree、归档 task 文件
- 已关闭的 task 可以重开（重开的具体机制在设计阶段决定）

### 5.6 归档产物

task close 时归档以下内容（具体物理位置在设计阶段决定）：

- task 快照（含完整审查记录、PM 反馈、文档偏差）
- 执行日志
- 事件流（状态变更时间线）

## 6. Worktree 隔离 [v1]

### 6.1 两级分支结构

```
main（主仓，永远不切分支）
  └── req-NNN 分支（req 的 worktree，从 main 创建）
        ├── task-001 分支（task 的 worktree，从 req 分支创建）
        ├── task-002 分支（同上）
        └── ...
```

- 主仓永远停在 main 分支
- 每个 req 一个独立 worktree + 分支
- 每个 task 一个独立 worktree + 分支，从所属 req 的分支创建
- task 完成后 merge 回 req 分支
- req close 时 req 分支整体 merge 回 main

### 6.2 主 Orchestrator 工作位置

- req 活跃期间，主 Orchestrator 在 req worktree 中工作
- 没有活跃 req 时，主 Orchestrator 在主仓 main 分支工作
- task 执行由 suborchestrator 在 task worktree 中完成

### 6.3 依赖与端口

- 依赖目录（如 `node_modules`）通过 symlink 共享到 worktree，不重复安装
- 每个 task 有**确定性的开发端口**，同项目不同 task 不冲突，不同项目之间也不冲突
- PM 验收时直接打开 task 文件里记录的端口

### 6.4 并行执行 [v2+]

- 多个 task 可以同时存在于不同 worktree，互不干扰
- task 之间**没有自动调度**——PM 显式启动哪个就跑哪个
- 系统需提供**并行冲突防护能力**，避免多个 task 同时修改同一文件导致冲突。具体机制在设计阶段决定

**v1 约束**：v1 只支持串行执行，一次只有一个 task 在执行中。但数据结构上允许多个 task 同时存在（为 v2 并行预留）。

## 7. 文档驱动协作 [v1]

- 所有 agent 之间的上下文传递必须**通过结构化文件**，不依赖对话窗口的压缩内容
- task 文件**只引用文档**（路径或锚点），不复制原文
- 任何信息只在一个地方有真相源，跨 artifact 之间通过引用建立关系
- execution agent 必须直接读原始文件，不能只靠 task 描述里的摘要

## 8. 角色分工 [v1]

系统区分四类角色：

### 8.1 PM

- 决策、确认、验收
- 不写代码

### 8.2 主 Orchestrator

- req 活跃时在 req worktree 中工作，没有 req 时在主仓
- 流程推进、文档维护、向 PM 呈交验收
- **不直接承担标准 task 的实现**
- 即使 PM 说"你直接改"，也必须在 req/task 分支内操作，不能直接修改 main

### 8.3 Suborchestrator

- 单 task owner
- 在 task worktree 内工作
- 负责该 task 的：preflight、实现推进（自己写或委托 execution agent）、自审、收口

### 8.4 Execution Agent

- 只是写代码的执行器
- 可被替换（Cursor / Gemini / 其他）

---

## 9. Review 与验收 [v1]

### 9.1 自审

- suborchestrator 在实现完成后**自动**进入自审，不等 PM
- 自审**必须在 worktree 中执行**
- 自审工具按 task 文件声明的"审查工具"字段执行（不写死）
- 自审发现的问题由 suborchestrator 自行修复或再次委托 execution agent
- 自审记录写入 task 文件
- 自审通过后才能向 PM 呈交验收

### 9.2 PM 验收呈交

`待验收` 状态时，主 orchestrator 必须向 PM 提供完整的验收信息，按 task 类型调整内容：

- **UI 类 task**：具体验收地址（URL）、实现内容摘要、自审结果摘要、重点检查项、验收标准对照清单、文档偏差摘要
- **非 UI 类 task**（文档更新、脚本、CLI、纯重构、配置等）：对应的验收证据（如 diff、测试结果、命令输出等）、实现内容摘要、自审结果摘要、验收标准对照清单

**"QA 通过，请确认" 不算合法呈交**——必须给 PM 足够具体的信息让 PM 能真正验收。

### 9.3 PM 决策

- PM 必须做**显式**通过 / 打回决策
- "看起来不错"、"先继续吧" 等模糊表达不算决策
- PM 打回 → task 回到"执行中"状态，PM 反馈追加到 task 文件，suborchestrator 修复后重新走自审

## 10. 收尾与关闭 [v1]

### 10.1 task close

PM 通过验收后，系统自动完成 close：

- 合并 task 分支到 req 分支
- 删除 task 分支
- 清理 task worktree
- 清理所有运行态残留（开发服务器进程、临时文件、缓存等）
- 归档 task 文件（含 §5.6 的全部归档产物）

### 10.2 反向文档更新

- task 实现过程中如发现产品层文档与实际不一致，必须记录到 task 的"文档偏差" section
- task close **之前**由 `/doc-update` 处理偏差：读取记录、生成最小修改方案、PM 确认后写入 req 分支
- 修改在 req close 时随 req 分支一起合入 main

### 10.3 req close

- 该 req 下**所有 task 必须都已关闭**才能 close
- close 步骤（在 req 分支上完成前 3 步，最后再 merge）：
  1. 写收口报告（收口总结 + 文档变更摘要）
  2. 更新 prd.md（如有变化）
  3. 移动整个 req 目录到 closed 区
  4. req 分支整体 merge 回 main
  5. 清理 req worktree

## 11. 经验层 [v2+]

经验不是独立的第四层，而是跨产品层和需求层的能力。

### 11.1 经验类型

- **仓库级经验**：属于产品层，跟项目走，进版本库
  - 包含 lessons（有效的做法）和 anti-patterns（已踩过的坑）
- **用户级偏好**：跟当前 PM 走，不进版本库
  - 只记录 PM 明确确认过的长期偏好

### 11.2 经验生命周期

- req/task 执行中产生的经验记录在需求层（跟 req 走）
- task close 时沉淀：PM 通过 → 提炼 lesson；PM 打回 → 提炼 anti-pattern
- 沉淀后的仓库级经验提升到产品层

### 11.3 召回机制

- **自动召回**：在 task 开始时自动注入相关经验到 agent context
- 不依赖 agent 主动调用 skill 或命令
- 召回筛选维度：当前模块、当前 task 类型、当前阶段

---

## 12. 框架问题反馈 [v2+]

### 12.1 issue 提交

- 业务项目使用过程中发现的**框架本身问题**（脚本 bug、规则缺失、误拦等）可以提交到框架 issue 系统
- 提交通过受控入口（具体形态在设计阶段决定）

### 12.2 框架维护闭环

- 框架维护会话能读取 issue、修复代码、关闭 issue
- 框架修复后，业务项目通过 §2.3 定义的"框架更新入口"拉取

### 12.3 区分

"框架问题"和"项目自身问题"必须明确区分：

- 涉及框架文件 → 框架 issue
- 项目自身问题 → 项目内部沉淀经验

## 13. 必须保留的能力

- **`/doc-update`**：反向文档更新 [v1]
- **`/prd-writing`**：prd 更新 [v1]
- **视觉基准建立能力**：在 first req 的 stage 4（设计系统建立）时触发，产出 DESIGN.md [v1]
- **框架 issue + upgrade 链路**：见 §12 [v2+]

### 13.1 可选能力 [v2+]

- **原型反向还原能力（live-align）**：AI 根据真实页面（URL / 截图）反向构建原型代码。依赖浏览器自动化能力。**v1 作为可选辅助能力**，不作为硬依赖——真实页面可能存在登录态、反爬、动态数据等障碍。

---

## 14. 明确砍掉的功能

- **材料层**（materials/ 目录 + index）
- **多 backend / 多 orchestrator 抽象**（Codex/Cursor 互通）
- **共享文件 hook 防并发编辑**（单 PM 用不到）
- **"自审中"作为独立状态**（自审降级为执行中里的动作）
- **stage 0 与"项目初始化"的绑定**（初始化和 stage 分离）

---

## 15. 待设计阶段决定的事项

- 受控入口的具体形态（CLI / hook / tool boundary / 混合）
- 产品层的具体文件清单和目录结构
- req 目录的具体文件名
- task 文件的具体字段
- 全局状态总览和 task 状态总览的具体形态
- task 重开的具体机制（恢复旧分支 vs 新开补丁分支、task 文件处理方式）
- 并行冲突防护的具体机制（文件持有申请/释放、粒度等）[v2+]
- 自动召回的具体注入机制 [v2+]
- gstack 检测的版本下限和"是否最新"的判断方式
- 框架 issue 系统的具体接入方式 [v2+]
- task 归档的具体物理位置
- close-task / reopen-task / report-issue / upgrade 等命令的具体调用形态
- 框架更新所需的元数据（framework version / 文件清单）[v2+]
- merge 后的回滚策略
- 执行中状态的可观测性（sub-status 或事件字段）
- 错误恢复策略（agent 崩溃、merge 冲突、worktree 创建失败等中断场景的恢复机制）

## 16. v2+ 计划能力

- **Codex 做主 Orchestrator**：v1 运行在 Claude Code 上。v2+ 支持 PM 选择用 Codex 等其他 AI CLI 做主 Orchestrator。核心逻辑已在脚本中实现（不依赖 Claude Code 特有能力），v2 只需加 Codex 的入口封装（prompt 规则替代 skill，system instruction 替代 CLAUDE.md 自动加载）

## 17. 未来可借鉴的能力（来自 gstack 源码分析）

以下能力已在 gstack 框架中验证有效，可在 v2+ 中按需引入：

- **SKILL.md 模板生成系统**：用 `.tmpl` 模板 + 构建脚本自动生成 SKILL.md，避免手工维护 preamble 重复。当 skill 数量超过 20 个时引入
- **学习系统置信度衰减**：跨会话经验的 confidence 每 30 天降 1 分，防止陈旧信息持久化。引入经验层（v2+）时一并加入
- **跨项目学习查询**：查询其他项目的经验应用到当前项目。需要经验层支持
- **分层测试成本策略**：区分免费静态验证（lint/typecheck）和付费 E2E 测试（claude -p），按成本分配测试预算
- **遥测与使用分析**：skill 使用频率、耗时、成功率的本地统计，用于优化框架
- **Compiled binary 分发**：用 bun build --compile 为关键工具生成单文件可执行文件，简化安装
