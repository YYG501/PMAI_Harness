## 项目本质（关键认知）

PM-AI-Workflow 服务的项目是**重需求分析、重文档**的：

- 最终交付 = **完整 PRD + 实际系统**
- 原型是"为了更清楚说明需求"的工具，**不是最终交付物**
- task-spec 的 **PM 视图最终汇集成 PRD** 给团队
- 实现程度只影响"本轮 AI 做哪些 + 做到什么程度"，**不影响文档链质量**
- PM 想直接做完整系统时框架也要支持——只需在 solution.md 写"完整系统"

## 实现程度的作用范围（关键不变量）

| 文档 / 阶段 | 实现程度是否影响内容深度 |
|---|---|
| `brief.md` | ❌ 完整（PM 可在末尾选填预期实现程度） |
| `analysis.md` | ❌ 完整（AI 可在末尾建议实现程度） |
| `solution.md` | ❌ 完整（含「本轮实现程度」段作为决策落地） |
| **`task-plan.md`** | ✅ **影响拆分粒度** |
| **task-spec PM 视图（`task.md`）** | ❌ **永远 PRD 等级、完整、详细** |
| **task-spec 工程合同（`task.engineering.md`）** | ✅ **按程度写"本次实际做什么"** |
| 实现代码 | ✅ 按工程合同走 |
| 最终 PRD（汇集 PM 视图）| ❌ 完整 |

**实现程度仅作用于两处**：

1. **task-plan 拆分粒度**
2. **工程合同内容深度**

绝不能让实现程度降级 PM 视图、PRD、brief、analysis、solution。

## 阶段 4 — 块 0 worktree 文档同步（**Eng review 修正：git show 绕 index**）

> **Eng review 修正点**：原方案用 `git checkout <branch> -- <path>` 会写主 repo `.git/index.lock`，多 worktree 并发 task-execute 时会抢锁退化串行甚至失败。改用 `git show <branch>:<path> > <dest>` **完全绕过 index**——worktree 同步本来就不需要进 index。

### 4.1 sync 白名单

```
第一层：req 级（必同步）
  requirements/active/<req-id>/   (递归同步目录下所有文件)

第二层：项目级
  DESIGN.md
  CLAUDE.md
```

### 4.2 sync-req-docs 实现

`scripts/sync-req-docs.sh`：

```bash
#!/usr/bin/env bash
# 从 req 分支同步需求与项目级文档到 task worktree（不写 git index）
set -euo pipefail

WORKTREE="$1"
REQ_BRANCH="$2"
REQ_ID="$3"

# 项目级单文件
PROJECT_FILES=("DESIGN.md" "CLAUDE.md")
for p in "${PROJECT_FILES[@]}"; do
  if git -C "$WORKTREE" cat-file -e "$REQ_BRANCH:$p" 2>/dev/null; then
    mkdir -p "$WORKTREE/$(dirname "$p")"
    git -C "$WORKTREE" show "$REQ_BRANCH:$p" > "$WORKTREE/$p"
  fi
done

# req 级目录递归
REQ_PATH="requirements/active/$REQ_ID"
git -C "$WORKTREE" ls-tree -r --name-only "$REQ_BRANCH" -- "$REQ_PATH" 2>/dev/null | while read -r f; do
  mkdir -p "$WORKTREE/$(dirname "$f")"
  git -C "$WORKTREE" show "$REQ_BRANCH:$f" > "$WORKTREE/$f"
done
```

**为什么 git show 比 git checkout 更对**：
- 不写 `.git/index.lock`，N 个 task worktree 并发 sync 互不干扰
- 不修改 git index，文件在 worktree 显示为 untracked / modified（这正是想要的——task 分支不应该 commit 这些）
- 配合 `check-task-scope.py` 阻断 commit 即可

### 4.5.1 detect-project-structure.py（**Eng A1 / C1 / C3 / P1 综合修正**）

新增 `scripts/detect-project-structure.py`：

```python
def detect(repo_path: Path, schema: dict) -> dict:
    """
    扫描项目，判定 prototype / system / hybrid / unknown，输出多维度报告 + 置信度。
    """
    # P1: 默认 exclude + 限定扫描根（性能）
    scan_roots = schema["scan_roots_default"]
    excludes = schema["scan_excludes"]
    
    # C1: glob 多 fallback + 输出实际匹配证据
    signal_results = {}
    for signal_id, signal_def in schema["signals"].items():
        matches = []
        for pattern in signal_def["globs"]:
            matches.extend(glob_with_excludes(repo_path, pattern, excludes, scan_roots))
        signal_results[signal_id] = {
            "present": len(matches) > 0,
            "matches": matches[:5],  # 前 5 个证据
            "implies": signal_def["implies"],
        }
    
    # A1: 多维度报告 + 总判定 + 置信度
    judgment, confidence = compute_judgment(signal_results)
    
    return {
        "judgment": judgment,           # prototype / system / hybrid / unknown
        "confidence": confidence,       # 0-1
        "signals": signal_results,
        "scan_roots_used": scan_roots,
        "recommendation": format_recommendation(judgment, confidence),
    }
```

**性能目标**：< 1s（小项目）/ < 5s（< 10000 文件）/ < 30s（极大项目）。

### 6.1 新增 `scripts/derive-task-types.py`

输出：本 req 应生成的 task 类型列表（JSON）

```python
# 伪代码
def derive_task_types(solution_md: Path) -> list[dict]:
    """读 solution.md 结构化字段表，返回应生成的 task 类型。
    
    每个 task 类型形如：
    {
      "kind": "ui-path" | "data-layer" | "api-contract" | "test" | "permission" | "boundary-state" | "edge-replicate",
      "scope": "tenant" | "ops" | "main-ops" | "all",
      "details": {...}
    }
    """
    fields = parse_structured_fields(solution_md)
    
    task_types = []
    
    # UI path tasks
    if fields["path_coverage"] == "仅主路径":
        task_types.extend([{"kind": "ui-path", "scope": fields["edge_coverage_scope"]}])
    elif ...:
        ...
    
    # data layer
    if fields["data_layer"] != "mock 静态数据":
        task_types.append({"kind": "data-layer", "details": {...}})
    
    # api contract
    ...
    
    # test
    if fields["test_coverage"] != "无":
        task_types.append({"kind": "test", "level": fields["test_coverage"]})
    
    # permission
    if fields["permission"] != "不做":
        task_types.append({"kind": "permission", "level": fields["permission"]})
    
    # boundary states
    if fields["boundary_state"] == "全部边界态":
        task_types.append({"kind": "boundary-state"})
    
    # multi-edge replication
    if fields["edge_coverage"] in ["双端", "三端齐全"]:
        task_types.append({"kind": "edge-replicate", "edges": [...]})
    
    return task_types
```

### 8.3 防漂移 + 字段级 stale + 批量决策（**PM-DX 修正**）

> **PM-DX 修正点**：原全段 hash → 5 个 task 同时 stale，PM 必须为每个写 override 才能继续——这是 PM-DX 评 3/10 的根因。改成：①字段级 hash（哪个字段变只影响相关 task）②批量决策 prompt ③一行命令 override。

**字段级 hash**：

每个 task PM 视图元数据存一个映射：
```
**solution-fields-hash**:
  implementation_intent: a1b2
  edge_coverage: c3d4
  permission_layer: e5f6
  ...
```

每次 PM 改 solution.md 字段，只有该字段相关的 task 显示 stale：
- `permission_layer` 字段变 → 仅 task-plan 中 `kind: permission` 的 task stale
- `edge_coverage` 字段变 → 仅 `kind: edge-replicate` 的 task stale
- `implementation_intent` 字段变 → **全 stale**（这是大改，应当全部 review）

**批量决策**：

PM 改 solution.md 后下次 task-execute / task-status 启动：

```
⚠️ Solution 实现程度字段变化：
  - permission_layer: 不做 → 简化
  - 影响 3 个已 confirmed task: task-002, task-005, task-007

如何处理？
  [1] 全部重生成（同步最新 solution，丢历史 review 痕迹）
  [2] 全部 override（接受新 solution，本轮 task 不变）
  [3] 逐个看 diff 决定
  [4] 取消改动（恢复 solution.md）

选择: _
```

**一行 override**：

`scripts/ack-stale.sh`：

```bash
#!/usr/bin/env bash
# 用法：bash ack-stale.sh <task-id>           # 单 task
#       bash ack-stale.sh --all <req-id>      # 整 req 批量
# 自动把 task 元数据的 solution-fields-hash 更新到当前 solution.md 的 hash
```
