# 设计 — 工程视图档位深度治理（v2，最小改动实验路径）

> **核心**：原型档下 `solution.engineering.md` 1220 行的膨胀，先用最小改动（prompt + lint）验证能否压到 ≤400 行。**不动结构、不删模板、不改 7 skill**。基于实证再决定下一步。

---

## 一、背景与问题

### 现状

框架自 v3.5 起把 PM 视图与工程视图分两份文件：
- req 级：`solution.md` + `solution.engineering.md`
- task 级：`task-NNN.md` + `task-NNN.engineering.md`

### 触发现实问题

PM 在原型档下推进一个 req 时观察：solution 写完后到 task-001 落地速度极慢——AI 把工程合同写得像生产代码规范（1220 行），与"原型档不用太精细"的档位精神矛盾。

### v1 → v2 的 reframe（autoplan CEO review 后）

v1 的反应是"分离设计本身在 req 级失控 → 删除分离"。autoplan CEO 双视角 review 一致反对——单点证据不能推出结构定律，且替代根因（prompt 边界规则缺失 / 档位深度指引未传播）未排除。

**reframe 后的真问题**：不是"是否物理分离"，而是"工程信息何时生成、多少、避免重复、AI 怎么消费"。

---

## 二、实证

### req-003（本仓新流程跑出，档位 prototype）

| 文件 | 行数 |
|------|------|
| solution.md | 846 |
| **solution.engineering.md** | **1220** ← 膨胀 |
| task-001.md | 339 |
| **task-001.engineering.md** | **150** ← 同样独立分离，不膨胀 |

### 关键观察（v2 新增——v1 忽略）

**同一个 req-003、同一个 AI、同一个档位、同样的"独立工程视图文件"——req 级 1220 行，task 级 150 行**。

这反证 v1 的核心 premise（"独立工程文件必膨胀"）。真实差异不是结构存在与否，而是：
- `task.engineering.md` 模板里有"参见 solution.engineering.md §X.Y"的强制引用规则
- `solution.engineering.md` 模板没有等价边界规则——AI 把 solution.md 已写过的内容又抄了一遍

### 替代根因候选（v1 未排除）

1. **req-solution skill 的 prompt 缺"什么不写"边界**——AI 把 PM 视图已有的内容重抄进工程合同
2. **档位深度指引（DEPTH_GUIDANCE）只覆盖代码，没覆盖文档输出**——AI 在工程模板里没接收到"原型档别写完整签名"的信号
3. **PM-VIEW-RULES 诱导对齐**——派生章节驱动让 AI 把 PM 视图的章节结构 1:1 映射到工程视图，造成结构性重复

只要任一为真，最小改动（修 prompt + 加 lint）就能解决，**不需要动结构**。

## 三、新方向（v2）

### 核心判断

> **先做最小改动实验。结构不变，只修边界规则与硬约束。如果实验证明输出仍膨胀，再讨论结构改动（届时再写 v3）。**

### 三个最小改动

#### 1. 改 `req-solution/SKILL.md` 的 prompt——加边界规则

仿照 `task-spec/SKILL.md` 的强制引用规则，给 `solution.engineering.md` 加：

> **§3 输入流强制规则**：本文件**只写 PM 视图未涵盖的工程信息**——具体类型签名、算法实现、文件层组织、Mock 数据 schema、跨 task 工程契约。
>
> **禁止重写**：solution.md 已写过的"产品行为 / 用户场景 / 弹窗规范 / 验收标准 / 模块职责文字描述"——直接写"参见 solution.md §X.Y"。
>
> **目标行数（原型档）≤300 行**——超过即视为重复 PM 视图，必须裁剪。

工作量：~15 分钟。

#### 2. 扩 `工程结构约束-{prototype,custom,system}.md` 的「文档输出深度指引」段

在现有"代码实现深度指引"对称位置加「文档输出深度指引」（已在 v1 的初始建议里）：

```
### 文档输出深度指引（原型档）

- solution.engineering.md 目标 ≤300 行；超过 lint 报错
- 上游已定义的类型/接口/函数签名禁止重写——用「参见 solution.md §X.Y」引用
- §4 功能清单工程版：只列「差异点 / 复用点」，不再贴完整签名
- §7 plan-*-review 沉淀、§8 a11y/视口/视觉规范：默认 N/A 一行带过
- §9 工程层验收清单：只列主路径 happy path
```

通过 `derive-structure-templates.py` 派生到三个档位变体。

工作量：~30 分钟（schema 扩段 + 派生脚本调一下）。

#### 3. 加 lint——原型档下 `.engineering.md` 行数硬上限

新增 `scripts/check-engineering-doc-size.py`：

- 输入：req-NNN/ 目录
- 行为：读 CLAUDE.md 档位 → prototype 档下 `solution.engineering.md` >300 行报错；`task-*.engineering.md` >200 行报错
- 挂到 `req-stage-gate` 的 stage 3→5 闸门 + `task-confirm` 的确认门

工作量：~30 分钟。

### 实证步骤（重要）

最小改动落地后，**用 req-003 的 brief.md / analysis.md 重新跑一次 stage 3** （不破坏现有 req-003，新建一个 req-003-rerun 实验分支）：

- 期望：`solution.engineering.md` ≤300 行（vs 现 1220 行，压缩 ~75%）
- 实际：以实测为准

### 三种实证结果对应的下一步

| 结果 | 含义 | 下一步 |
|------|------|--------|
| **≤300 行** | prompt + lint 是真根因；结构本身没问题 | 不动结构。新规则正式纳入；监控 3 个真实 req 后回看 |
| **300-600 行** | 改善但未达标；可能 lint 太严或边界规则不够清 | 调 lint 阈值或加额外强制引用条款；再跑一轮 |
| **>600 行** | 结构性问题坐实；最小改动不够 | 启动 v3 设计——讨论结构改动（含原 v1 的合并方案，但带实证支撑） |

## 五、风险与未决

### 1. 实证可能反向坐实 v1（即结构本身有问题）

**风险**：实证后 `solution.engineering.md` 仍 >600 行——证明 prompt + lint 不够，要回到结构改动。

**应对**：v2 接受这个风险。最小改动失败 = 结构性问题被实证证明，那时启动 v3 才有数据支撑。**v1 的方向被推翻不是"v1 错了"，是"v1 太早"——证据不够、替代未排除**。

### 2. lint 太严会让 AI 砍掉关键工程信息

**风险**：300 行 hard limit 可能逼 AI 删掉本该保留的派生算法、Mock schema 等。

**应对**：lint 是 warning + gate，不是 hard reject——超限时走人工 review，PM 决定是放行还是要 AI 重写。3 个 req 后看是否要调阈值。

### 3. req-003 现状如何处理

**v1 建议** B（freeze）。**Codex 反对**：长期两套流是最糟状态。

**v2 决策**：req-003 不动，但 v2 落地后**不为它兼容**——req-003 后续 task-spec 仍按当前格式（已有 1220 行 .engineering.md），新 req 走新规则。区别于 v1 的 freeze：v2 不在 skill / 脚本里加 legacy 分支；req-003 自己消化到 close。

### 4. custom / system 档完全不做规则承诺

**v1 给了 custom/system 档明确规则（task 级保留分离）**。**Codex 指出无证据**。

**v2 决策**：custom/system 档**不做规则承诺**。`工程结构约束-custom.md / -system.md` 的「文档输出深度指引」段先留空（PM 手填），等到第一个真实 custom 项目跑出来再基于实证写规则。

### 5. 我会不会再被推翻

第三次了。但 v2 比 v1/v0 都更保守：
- v0：加约束文字（被否决——文字提醒不够强）
- v1：删除分离 + 大改（被 autoplan 否决——单点证据 + 未排除替代根因）
- **v2：先做最小改动实验，结果导向决定下一步**

如果 v2 也错——大概率是"`req-solution` skill 的根本问题不在 prompt 而在 PM-VIEW-RULES 的派生章节驱动机制"，那时回看 review-input-bundle / pm-view-rules，是新一轮独立调查，不是继续打补丁。

## 六、实施顺序

### 阶段 A — 最小改动落地（~1.5 小时）

1. 改 `skills/req-solution/SKILL.md` prompt（加 §3 强制引用规则 + 目标行数）—— ~15 分钟
2. 改 `templates/工程结构约束.schema.json` 加 `DOC_DEPTH_GUIDANCE`，跑 `derive-structure-templates.py` 派生三档位—— ~30 分钟
3. 加 `scripts/check-engineering-doc-size.py` + 挂到 `req-stage-gate` / `task-confirm` 闸门—— ~30 分钟
4. 加 1-2 个 lint 测试到 `tests/`—— ~15 分钟

### 阶段 B — 实证（依赖第一个新 req 实战）

5. 用 req-003 的 brief.md / analysis.md 在新 worktree 跑 stage 3，量 `solution.engineering.md` 行数
6. 按 §三 三种结果分支决定下一步

### 阶段 C — 监控（被动，3 个真实 req 后回看）

7. 跑完 3 个真实 req 后，看 `solution.engineering.md` 行数分布是否稳定 ≤300 行
8. 如稳定：v2 正式纳入框架，关闭本 plan
9. 如反复超限：启动 v3

## 七、PM 决策点

进入实施前需要 PM 拍板：

1. ✅ **核心方向**（§三，最小改动实验）—— 同意？
2. ❓ **lint 阈值**：原型档 `solution.engineering.md` 300 行（推荐）/ 200 行（更严）/ 400 行（宽松）
3. ❓ **实证用什么 req**：req-003 重跑（依赖现有 brief/analysis，但要新建 worktree）/ 等下一个真实 req（自然实证，但等待时间不可控）
4. ❓ **custom / system 档处理**：完全不做承诺（推荐）/ 沿用 v1 的 task 级分离 + 强制引用（保留作为 default 但加 hypothesis 标记）

我建议：阈值 300、用 req-003 重跑、custom/system 完全不做承诺。
