## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

> ⚠️ 任何后续 review / autoplan 都**不能**给本节加东西、不能重定义痛点。
> 新发现的痛点要么开新设计文档，要么 PM 主动决策更新 §0 并重置版本号。

### §0.1 痛点（1-3 句）

母文档的运行模型（六步：现状 → 范围确认 → build → 覆盖审计 → 迭代 → **沉淀**）把"把产出写进脊柱"这个**沉淀动作只挂在最后一步（≈ close）**，且假设每个产出都走完整六步。但 PM 的真实用法是**分档的**——大量工作是"聊定 → 直接在 main / prototype 上改、不进 req"这种最轻档，它**一次都不经过沉淀那个开火点**。结果这些轻档产出全部漏沉淀：真相源乱、脊柱入口看不到、讨论决策不进库、mock 变体找不回（PM 原话四痛）。

### §0.2 触发场景（每条要能回答"PM 实际遇到过吗 / 在哪个 req"）

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | 高频"聊定→直落 main/prototype、不进 req"的轻档，不经过任何沉淀点 | 消费仓 `ExampleAgentProject` `docs/TODO.md` L34/L38 PM 自述"直落 main…**未正式 close 沉淀** PRODUCT-RULES"；git log 大量 `docs:` / `feat(prototype):` 直接落 main 未经 req（混合航道：req-002 确实 close 过，但轻档那股从不沉淀）|

### §0.3 根因（解决什么底层 mechanism）

**沉淀（写入脊柱）在框架里只有一个机器开火点 = full-req 末尾**（防腐铁律：`close-req/SKILL.md:90` 钉死"产品现状只在这一刻被写…沉淀是它唯一的写入口"；grep 全 skill，其它提 PRODUCT-STATE 的全是"读"）。母文档运行模型（六步）假设产出都走到第⑥步。但真实工作是**分档**的，最轻那档（main 直接改 / 聊定直落原型）根本不走到第⑥步 → 这一整档的产出全部绕过唯一的沉淀开火点 = **结构性失明**（不是 PM 不自律——母文档 §1.2 自己已证"维护活文档的纪律对单人 PM 会腐烂"，所以才把写入绑死在沉淀这一原子动作；问题是这个原子动作在轻档不触发）。叠加第二根因：母文档上坡路③**生成** mock 变体，但模型只"挑定回清单"，**没有变体持久化 / 找回 / 退役机制** → 探索变体集体孤儿。

### §0.4 不解决什么（显式列衍生 / 假设场景，防 review 拉进来）

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|

| 2 | 100% 全自动从对话提取沉淀 | 人在环：AI **提议** + PM **确认**，非自动写。沿用文档治理 §0.4.2（排"全自动"、不排"触发式提议"）；本设计补的是**触发点**，机制本就既定，非新增 |
| 3 | build 段本身怎么变轻（转写链 / 信封 / 对抗网）| 归 [`build直建轻车道.md`](./build直建轻车道.md)；本文只管"沉淀在哪些时刻开火"，不碰 build 内部 |
| 4 | 重复 PRD 去重 / 冗余 zip 清理 / 框架改名迁移 | 二阶清理，主航道沉淀时刻定调后再扫；本设计不碰 |

## §1 方案主体（草案，待 §0 锁后与 PM 抠细节）

### §1.1 分档运行模型（给母文档六步补一个轻档谱）

母文档的"六步"是**最重那一档**。把它放进一个按事情大小分的谱：

| 档 | 什么时候 | 在哪做 | 走多少 |
|---|---|---|---|
| **轻 · main 直接改** | 小改 / 一段讨论顺手定的 / 纯文档调整 | main，不开 worktree | 跳过 req，**只保留沉淀** |
| **中 · 轻 req 直建** | 一个完整功能、要并行隔离 | req worktree | 范围确认 → 直建（不拆 task）→ 覆盖审计 → 沉淀 |
| **重 · 完整 req** | 多块大需求 | req worktree + 拆 task | 完整六步 |

走哪档由 PM 按当下挑，AI 不卡。**三档是同一条流程的伸缩，不是三套机制。**

### §1.2 沉淀层：每一档都有一个开火点（解痛①②③的根）

**机制不新造**——"AI 提议 → PM 确认 → 分流四类 → 挂脊柱索引"在子设计里都有（决策记录 §1 触发点①顺手冻、文档治理 F-G1 主动展开+索引）。本设计只把**触发点从"只有 full-req 末尾"扩到每一档各一个**：

```
轻档：main 改完 / 讨论收敛   → 轻沉淀（最待抠：见 §1.4）
中档：直建完                  → 中沉淀（≈ 现覆盖审计后顺手沉淀）
重档：close-req               → 现六步⑥（不动）
```

每个开火点做同一件事，按四类分流（沿用子设计的出口）：

```
① 耐久事实（现状/规则/术语）→ 脊柱（PRODUCT-STATE/RULES）
② 为什么·理路              → 决策记录冻结档
③ 遗留待办                 → TODO（自包含一句话）
④ 原型/mock                → 主原型 + 变体档 + 看版导航（§1.3 新）
并同步把新文档挂进 PRODUCT-STATE 索引（治入口失真 / index lag）
```

**防腐铁律不破**：轻沉淀仍是"原子动作触发写入"，是 close 的轻量同构，不是退回"随手改活文档"。需要 PM 把"轻档沉淀时刻"显式拉进本 §0（母文档与子设计现都把它留在真空：既不解也不排除）。

### §1.3 mock 变体治理（解痛④，子设计零覆盖的新格 · 逐叉抠定中）

变体不是"文档"也不是"单一主原型"，是探索期并行原型集（母文档上坡路③**生成**了它们却不留存），要自己的家。由沉淀出口④在每档维护。

**病灶**（`ExampleAgentProject`）：三个 nav 打架（`_board`/`_view`/`index`）、`_view` 是 v1 死复制品、最新 4 个 mock 谁都不列——**手维护的看版必腐**。

| 叉 | 决议 | 日期 |
|---|---|---|
| **keystone：清单 vs 手维护** | ✅ **一份结构化「变体清单」(manifest) 当唯一真相源，看版导航页从它生成**（不手写）→ 永不 stale/互撞/漏、单一入口、从脊柱（PRODUCT-STATE 索引）可达。沉淀出口④每有新变体往清单加一条、顺手重生成看版。同 §1.4 逻辑：别靠手/记性，绑机器动作 | 2026-06-02 |
| **什么算变体 / 何时进清单** | ✅ **拆两层**：① **存（不丢）** 所有生成的独立 mock 一律落规范变体目录、tracked（含当场否掉的草图）→ 治"找不回" ② **清单 featured（干净）** 上坡路③收敛(PM 挑定)时沉淀提议把值得留的几版登记(探了什么/好东西/为何没选)，AI 提议+PM confirm；没 featured 的仍在目录可翻、看版不高亮。多攒的一次性草图由"退役"叉清 | 2026-06-02 |
| **存哪 / 字段 / 谁填** | ✅ **存**：独立变体目录 **`mocks/`**（PM 拍名，与 prototype/ 分开——主原型是单一真相源、跑着的 app，静态 mock 不塞进去；manifest + 生成的看版页都在此，init 脚手架建）。**字段**：路径(可点开)/探索什么(一句)/好东西(可合并候选)/状态(活跃·待合并·已退役)/出自哪轮。**谁填**：AI 登记时自动写注解(mock 它生成的)，PM 改/确认 | 2026-06-02 |
| **退役 / 合并后** | ✅ **谁触发**：好东西并进主原型时沉淀提议把源变体标 `已退役`、记一句"已并入主原型(位置/commit)"，PM 确认。**留还是删**：**留不删**——标 `已退役` → 看版默认折叠/灰掉(不进活跃高亮)，仍在 `mocks/`+清单可翻(治找回)；PM 真要清理手动删。退役=状态翻转+看版过滤，非销毁 | 2026-06-02 |

### §1.4 轻档（main 直接改）的"轻沉淀"形态（逐叉抠定中）

这是落地能不能成的关键，也是本设计唯一真正的新机制面。

**硬约束**：chat 里 AI 没法在 PM 不说话时自己动（LLM chat 固有限制，同 session 起始播报）。所以"AI 自动记录" = AI 在**回 PM 的那一轮里**识别收敛、顺手提议沉淀，**不是后台守护进程**。

| 叉 | 决议 | 日期 |
|---|---|---|
| **触发** | ✅ **AI 主动提议 + PM 显式"沉淀一下"兜底**。纯你主动→靠记性必腐（解不了痛③）；逢改必问→烦到再绕开（R1）。故 AI 主动 | 2026-06-02 |
| **边界（何时提）** | ✅ **两道闸：① 只在"聊定/改完"收敛点提（非逐条）② 只在真有耐久产出（新事实/决策/新变体）时提，纯文字微调不提**。判断准度做不到 100%，§0.4.2 已划范围外（人在环、不追全自动）| 2026-06-02 |
| **重量（问多重）** | ✅ **AI 按默认分流直接写好 + 末尾一行路径回执，PM 不对再调**（不预先问"打算怎么分"）。套现框架惯例：确认门只给路径（[[feedback_confirmation_gates]]）+ close 默认走完总审 diff（[[feedback_close_default_flow]]）。**重量随产出缩放**：多数 main 轻档只"PRODUCT-STATE 补一句 + 索引挂新文档"，只有真有理路才碰决策记录、真有新变体才碰看版；回执只列动过的 | 2026-06-02 |
| **落盘** | ✅ **写各自规范家**（PRODUCT-STATE/decisions/TODO/看版，同 close 落点、从 main 触发）+ **AI 把沉淀单独 commit**（只 `git add` 沉淀动过的文档、不卷入 PM 其它 WIP，单独 `沉淀:` commit）→ 回执给 commit+路径 → PM 总审 diff，不对 amend/revert。保证落地即 tracked（治"飘着没进库"）。配套 vp：防腐铁律段加"轻沉淀也是合法原子写入口" | 2026-06-02 |

## §2 与现有机制的关系

- **母文档（重构方向）**：六步 = 重档；§2.1 沉淀层概念**保留并扩**（从单开火点 → 每档开火点）；§2.3.1 三上坡路不动（探索仍那样发生），但上坡路③产出的 mock 由 §1.3 接住留存。
- **build直建轻车道**：本文给它补"轻档/中档的沉淀时刻"前提；它管 build 怎么变轻，本文管沉淀何时开火。两者在中档（轻 req 直建）交汇。
- **文档治理 + 决策记录**：出口①②③的落点不变，本文把它们的**触发从 close-only 扩到每档**。
- **防腐铁律**：不动语义，只新增"轻沉淀也是合法原子写入口"的说明（待 vp）。
