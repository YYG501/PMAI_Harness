## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

> ⚠️ 任何后续 review / autoplan / dual voice 都**不能**给本节加东西、不能重新定义痛点。
> 新发现的痛点要么开新 D-* 文档，要么 PM 主动决策更新 §0 并重置版本号。

### §0.1 痛点（1-3 句）

项目奠基轮（`init-project` / `project-solution` 的方向讨论，或像 req-001 这种首个 req 的范围确认）会产出一层**「为什么这么拼」的理路**——护城河论证、交互理念的咬合推导、跨功能机制的整体设计意图、v2 演进故事。这层理路在框架的脊柱文档里**没有任何归宿**（脊柱按"AI build/审各自要读的消费切面"切，只装离散事实，不装跨文件理路），PM 只能自建野文档承载，而野文档作为**活的并行真相源必然漂**。

### §0.2 触发场景（每条要能回答"PM 实际遇到过吗 / 在哪个 req"）

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | 业务仓首个 req 范围确认产出大量项目级理路，脊柱接不住 → PM 自建野文档 | 业务仓 `ExampleAgentProject` req-001：24 字段 ontology + Q1–Q7 交互理念 + owner颜色/E列/就绪度机制 + 护城河叙事 → 自建 `${CONSUMER_REPO_ROOT}/docs/产品梳理.md` |
| 2 | 野文档作为活真相源已经漂 | 同一份文件名写成 `PROJECT.md`，但框架 commit `32e92b7` 已改名 `PRODUCT.md`；且漏了 Q6/Q7/布局（本 session 调查 `wspt82z5n`）|
| 3 | 4 份真相源 + req-plan 合起来无损接不住理路层 | 本 session 四路调查 `wf_b56f66f2-bd8` 角度 A：6 类孤儿内容（护城河论证 / Q1–Q7 咬合推理链 / 字段+owner+E列+就绪度 的机制整体 / v2 演进故事 / IA 功能分工语义；待定项可进 TODO 不算孤儿）|

### §0.3 根因（解决什么底层 mechanism）

框架有 **req 级**冻结决策记录（`requirements/closed/<req>/req-plan.md` 决策页 + `scripts/req-events.py` 的 `decision` 事件 + prd decision 摘要），**但没有项目奠基级的**。所有 `decision` 概念都是 per-req、事件化、随 req 归档。同时 `close-req` 防腐铁律（正确地）禁止"活的并行综合稿"。结果：项目级理路被夹在「不能当活文档」（铁律禁）和「没有冻结档可放」（机制缺）之间 → 逃逸成野文档。

### §0.4 不解决什么（显式列衍生 / 假设场景，防 review 拉进来）

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 做"活的第五份脊柱"（持续维护的理路活文档）| PM 已在 2026-06-01 决策门否掉；理路活文档触防腐铁律，本设计走**冻结**不走活文档 |
| 2 | per-req 决策的归宿 | 已有 req-plan 决策页 + req-events，本设计不碰 |
| 3 | "从对话自动提取决策即时落档" | 决策记录由 project-solution / close-req 在**已有讨论产出**时顺手冻，不新增"即时落档"机制；从对话提取本质是 AI 判断，做不到 100% 自动，属另一话题 |
| 4 | 维护 / 更新已冻结的记录 | 冻结档写一次就不动；方向变（pivot）写**新的一份**，旧的留作历史坐标 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**（除非 PM 显式接受拉进 §0）

## §1 方案概述

新增一个**文档类**：「项目级决策记录（冻结档）」。

```
docs/decisions/<日期>-<slug>.md      ← 写一次 · 带日期 · 归档不维护
   ├─ 理路节   只装"为什么这么拼"（护城河论证 / 交互咬合 / 机制整体设计意图 / 演进故事）
   └─ 事实节   不复述事实，一律用指针「以 PRODUCT-STATE / PRODUCT.md 为准 →」
```

- **WHAT-now 看脊柱，WHY-then 看 decisions**：脊柱仍是当前真相；决策记录是带日期的历史快照。
- **为什么不触防腐铁律**：它**从不假装是现状**。哪怕某个指针指向的文件将来改了名，读者看到的是"这是 <日期> 那时的判断"——是历史，不是谎。结构上它无法和脊柱竞争"当前真相"的名分，所以铁律杀不到它。和 `requirements/closed/<req>/req-plan.md` 同构，只是尺度从单 req 抬到项目奠基。

**两个产出触发点**：
1. `project-solution` / `init-project`(step C) 的方向讨论确认门后——讨论本就产出理路，顺手冻一份。
2. `close-req` 步骤 2——若本 req 产出了**项目级理路**（不是单条规则、不是模块规格），冻进决策记录。

## §2 与现有机制的关系

### 保留（不动）
- 脊柱五件套（PRODUCT / PRODUCT-STATE / PRODUCT-RULES / DESIGN / 主原型）职责不变。
- req-plan 决策页 / `req-events.py` decision 事件 / prd decision 摘要——per-req 决策的归宿，不碰。
- **防腐铁律不动**——只在铁律旁加一句说明冻结档为何是例外（见 vp-6）。

### 改
| 改点 | 现状 | 改成 |
|---|---|---|
| `project-solution` SKILL + `init-project` step C | 方向讨论确认门后写 `PRODUCT.md` + `TODO.md` | 同上 + 冻一份 `docs/decisions/<日期>-<slug>.md` 装本轮理路（仅当本轮有实质理路；纯微调不冻，见 §5 风险 3）|
| `close-req` 步骤 2 候选清单 | 沉淀目标推断 `docs/modules/` 或 `PRODUCT-RULES.md`；AskUser 3 选项（沉淀进规格 / 不沉淀 / 推下个需求）| 候选新增**理路类**识别（护城河 / 机制整体 / 交互理念，非单条规则非模块规格）；AskUser 加第 4 选项「冻结进决策记录」|
| `PRODUCT-STATE.md.tmpl` 索引节 + 各 SKILL"读什么"清单 | 索引指向 PRODUCT / RULES / DESIGN / prototype | 加一条指向 `docs/decisions/`——让后续 AI 能读到理路。**读取模型（对齐文档治理 F4）：决策记录属脊柱「索引展开层」，查"为什么"时按需读、非每次全载** |
| 防腐铁律段（`close-req/SKILL.md` + `PRODUCT-STATE.md.tmpl`）| 只说"现状只在沉淀写" | 加一句：冻结档（带日期、不维护）不在铁律约束内，因其不声称是现状 |

### 砍
无。本设计不删任何现有机制。
