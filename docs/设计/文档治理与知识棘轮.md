## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

### §0.1 痛点（1-3 句）

PMAI 的**文档治理**——文档分几类 / 各存哪 / AI 何时读哪些 / 讨论与决策落哪——是**隐式的**（散在 `init-project` + `CLAUDE.md.tmpl` + `deliverables-INDEX` + `docs/INDEX` 四处），**没有一份成文模型**。后果：没有明确家的内容（尤其「理路」）逃成野文档；而且**跨 req / 跨 close 的"知识棘轮"漏**——后面的 req/close 读不到前面的关键讨论、决策、遗留。直接让元目标「聊天时 AI 知道产品 + 产出积累」兑现不了。

### §0.2 触发场景（实证，引 file:line）

| # | 场景 | 实证 |
|---|---|---|
| 1 | 内容无家 / PM 不知该放哪 → 野文档 | 消费仓 `ExampleAgentProject`：`docs/产品梳理.md`、`docs/v2-interaction-design.md`、根目录 `会议讨论.md` 都游离在脊柱外 |
| 2 | close-report「推下个需求」遗留**孤儿** | `close-req/SKILL.md:120-121,192` 记遗留，但 `new-req/SKILL.md:213,285` 明令"不主动翻 closed（RAG 噪声）"→ 下个 req **读不到**，推了个寂寞 |
| 3 | 跨 close 只走脊柱单通道 | `close-req/SKILL.md:76,100` 只读 `git diff main..HEAD` + 主原型 + 脊柱，**不读任何 closed req** |
| 4 | 理路无脊柱家 | 本 session 决策记录线已证（脊柱五件套无"为什么这么拼"的节）|

### §0.3 根因

没有一份**成文的文档治理模型**（类别 + 存放 + 读取策略 + 决策落点）；脊柱（项目底座）是铺好的但**"什么够格当脊柱"无定义、无扩展规则**；跨 req 知识**仅靠脊柱单通道传，且蒸馏有损**——耐久事实能传，理路 / 遗留传不过去。

### §0.4 不解决什么

| # | 不在范围 | 理由 |
|---|---|---|
| 1 | build 流程本身 | 归 `build直建轻车道.md` |
| 2 | 即时落档 100% 自动 | 从对话提取本质 AI 判断，做不到全自动；本设计立纪律 + 兜底，不追全自动 |
| 3 | 引入 RAG 全文检索 closed | 框架明确反 RAG 噪声（`new-req:213`）；棘轮靠**蒸馏进脊柱**，不靠检索旧档 |

## §1 方案（草稿，待讨论）

### §1.1 写成一份「文档地图」（堵 G3：治理无成文模型）

把现在隐式的分类写成**一份成文模型**，并分发给消费仓（让消费仓 AI 也按它判断）。**落点（F2 折中）**：读取策略「AI 读哪几份」进 `CLAUDE.md.tmpl`（每次必见）；完整文档地图（下表 + 生命周期）独立成 `templates/文档地图.md`，CLAUDE 放指针。

| 类别 | 存哪 | AI 读取 | 生命周期 |
|---|---|---|---|
| **脊柱·必读核心**（F4①，要小）PRODUCT-STATE 现状 hub | `docs/PRODUCT-STATE.md` | **每次必读**（"先读项目底座"入口）| 长期真相源，每档沉淀写（轻量同构；close-req + /pmai-deposit） |
| **脊柱·索引展开**（F4②，被 hub 索引、按需读）PRODUCT / DESIGN / PRODUCT-RULES / modules / **决策记录** + 主原型 | `docs/` + `docs/modules` + `docs/decisions` + `prototype/` | **按需**（查到才读）| 长期真相源，每档沉淀写（轻量同构；close-req + /pmai-deposit） |
| **参考资料** 导出 / 调研 / xlsx | `docs/inputs/<子目录>` | 按需 | 一次性留档 |
| **过程（在途）** 实现方案 / 信封 / events | `requirements/active/<req>/` | 仅本 req 读 | close 后归档 |
| **归档** | `requirements/closed/<req>/` | **不主动翻** | 留底 |
| **产物** PRD 等 | `requirements/active/<req>/` / `docs/独立PRD` | 按需 | 按需 |
| **待办** | `docs/TODO.md` | new-req 起步提醒 | PM 增删 + 遗留自动入（见 §1.2）|

并定一条**"什么够格当脊柱"**规则 + 扩展口（决策记录据此正式入脊柱）。

### §1.2 知识棘轮 = close 的**三个出口**（堵 G1/G2，每个 close 必须给下一个留下"读得到的"增量）

```
一个 req close 时，把残留按"类型"分流到三个会被后面读到的地方：
  ① 耐久事实（现状/规则/术语/模块规格）→ 脊柱            【已有】
  ② 为什么/理路（护城河/咬合/演进）     → 决策记录冻结档   【G1，联动那份设计】
  ③ 待办/遗留（推下个需求）             → TODO 待办池      【G2，新 wiring】
```
- **③ 是新的一条线**：close-report「推下个需求」**自动写进 `docs/TODO.md`**——TODO 本就是 new-req 起步时提醒 PM 的池子（TODO 模板自述），所以遗留进 TODO = 下个 req 起步**自动浮出来**，不再孤儿。
- 三个出口覆盖"残留"的三种类型：**事实 / 为什么 / 待办**。close 后没有任何关键信息只躺在 closed/ 里没人读。

### §1.3 决策落点收敛成**一条管道**（堵决策散落）

现在决策散在 6 处（req-plan 决策页 / req-events / prd 摘要 / task 反馈 / close-report / PRODUCT-RULES）让人猜该写哪。收敛成**两个固定的家**：
```
在途两个家（PM 永不用猜）：
  · 定范围拍的    → 实现方案 · 决策节
  · build 期反馈  → 信封 · 反馈段
  → close 时自动按 §1.2 三出口分流（耐久→脊柱 / 理路→决策记录 / 遗留→TODO）
（req-events 事件流作为后台审计模态保留，非 PM 面对的落点）
```

### §1.4 底料保真（堵 G4，联动 build轻车道）
结构化底料当数据进脊柱（实现方案契约当数据 + 对抗网），脊柱存的不是 prose 降级版。

## §2 与现有机制的关系
- **保留**：脊柱 + "先读项目底座"读取规则（`CLAUDE.md.tmpl:265`）+ "不主动翻 closed"（棘轮靠蒸馏不靠检索）+ inputs 参考归档 + TODO 池。
- **改**：把隐式分类写成成文文档地图；决策落点收敛成一条管道。
- **建**：close-report 遗留 → TODO 的 wiring；"什么够格当脊柱"规则 + 决策记录入脊柱。
- **联动**：决策记录冻结档（出口②）、build直建轻车道（出口①的底料保真）。
