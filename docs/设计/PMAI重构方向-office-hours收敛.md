## §0 起点（PM 原话，锁定，后续不可反向改写）

- 框架用着**不顺、慢**；它出的第一版原型**不如我直接给 AI**。
- 我喜欢用 gstack / Claude Design，但**不知道怎么结合**：我想跟它聊**完整的、真要落地生产的需求**，但实现时只要**原型**——最终 PRD 指导真实产品，原型是我**检查 / 说明需求**的手段。
- 我想明确自己的工作流：可以是框架 + 其他工具混合，但**最好框架直接服务，不想全部自研**。

## §1 诊断（真实证据，不可反向改写）

### §1.1 根因

> **框架的重量几乎全压在"想"和"建原型"这两段——它在这两段又重又弱，而 PM 早就绕开它用别的工具做了；它真正该重、别人不做的后半段（产品上下文 / 沉淀 / 留痕 / 跨 req 继承）反而被流程噪音淹没。**

### §1.2 取证关键数字（消费仓 ExampleConsumerApp，5 周 / 9 个 req / 469 commit）

| 发现 | 数据 |
|---|---|
| 产品代码占比极低 | 真碰 `prototypes/` 的 commit 只有 **21.5%（101/469）**，近 80% 是文档/流程/返工 |
| 文档税不随复杂度伸缩 | "挪菜单换图标"的琐碎 req **2404 行**文档 ≈ "重做整个权限模型"的架构 req **2778 行** |
| 同一决策反复重述 | 一个 icon 避让决策在 brief→analysis→prd→impl-design→task 链条上重复 **5-7 遍** |
| 想都在框架外发生 | req-009 权限模型在 **ChatGPT** 推演定稿、stage2 是逐字快照、**连 analysis.md 都没有**；req-007 brief 地基是语音会议转录；代码在 codex/cursor、QA 在 gstack |
| 维护纪律已失败过一次 | 旧仓 `prototypes/` 跑完一整个真实项目后**只剩一个 README** —— "维护一份活文档"的纪律对单人 PM 会腐烂 |

### §1.3 原型差距根因（ExampleAgentProject，对照实验）

- **不是模型、不是执行器、不是输入模态。** 执行器其实是 Claude Code（不是 Codex，那个 `*-codex.txt` 文件名是误导残留）；PM 给 Claude Design 的输入更少（3 份访谈 + 1 份 research，纯文本、无图）却赢了。
- 根因 = **框架管线把同一个 Claude 摁进了"规格执行"模式**：丰富输入被压成纯文字契约（12 条禁止项 + ASCII 线框当事实上的视觉真相 + impl-design 的 SIMP 把交互裁成占位壳）+ **全流水线没有任何"用眼睛看渲染"的环节**。Claude 越忠实照建，视觉上限越低。
- **spike 实证**（2026-05-29）：给 Claude Code **完全相同的输入**、在 Next.js 栈里独立建一版（`ExampleAgentProject-pathB`），结论见 §X-C —— **视觉布局 Claude Design 略胜，交互完整度 Claude Code 更强，覆盖范围 / 产品判断打平，整体相近**。证明 Claude Code 在栈内建可达到与 Claude Design 相近的水平，差距只在"视觉布局"一处，且可用设计约定补。

## §2 最终模型

### §2.1 一句话

**PMAI = 围绕"产品现状 + 主原型"的【上下文脊柱 + 范围确认 + 沉淀】层。** 想和建原型直接用 Claude Code（在你自己的栈里），框架不抢这两段，只做它们不做、且 Claude Design / ChatGPT 给不了的事：让 AI 不失忆、原型不漏项、确认后能沉淀成可评审 PRD。

### §2.2 三类文档（最关键的区分 —— "砍文档"指的只是第三类）

| 类型 | 是什么 | 处理 |
|---|---|---|
| **① 产品上下文** | `PRODUCT-STATE.md` / `DESIGN.md` / 主原型说明 —— AI 每次进项目**必读** | **留，且是框架的心脏**（治"每次重新解释产品"） |
| **② 交付 PRD** | 给决策者评审的 PRD + 确认的原型 | **留，是终点交付物** |
| **③ 过程文档税** | 同一范围重复 7 遍 / PM 不读的工程双合同 / `.term-skip.json` 类机器废气 / 琐碎 req 也走全套的固定开销 | **只砍这一类** |

### §2.3 六步流程

```
① 产品现状（PRODUCT-STATE.md + DESIGN.md + 主原型说明）   ← AI 必读，心脏，治失忆
        ↓  想：直接跟 Claude Code 聊（框架不抢）
② 确认【范围层】：界面 / 弹窗 / 字段 / 按钮 / tab / 做不做   ← build 前，防残版（PM 的强项）
        ↓
③ build：直接在 prototype/ 用 Claude Code 建（你的栈）       ← 配 design 约定 + 产品化 demo 目标 + 看渲染的视觉门
        ↓                                                      Claude Design 只当"只看不导"的视觉参考
④ 覆盖审计：AI 对照范围逐项 diff、自报"建了/丢了/降级占位"   ← 治工具偷丢字段
        ↓
⑤ 迭代【体验层】：看渲染调交互 / 信息密度 / 层次            ← build 后，看图才发现
        ↓
⑥ 沉淀：反向出可评审 PRD + 更新产品现状                     ← 终点（PRD 恒按真实系统口径，权限/审批规则从 brief 锁）
```

### §2.3.1 第②步「范围确认」的内部结构（一个目的地、三条上坡路）

第②步不是"AI 出张清单、PM 点确认"那么单薄。它是**一个目的地、三条上坡路**——走哪条由 AI 按 PM 当下状态临场判断。

**目的地**：一份**详细范围清单 + 一页关键决策**（合起来 = PM 说的"实现文档"，**落盘为 per-req 的 `req-plan.md`**，两节：范围清单 + 决策页）。
- **范围清单** = 结构化的 WHAT：分区 / 块 / 字段 / tab / 状态 / 交互形式（"有什么"）/ 做不做。同时是第 ④ 步覆盖审计的锚点。
- **关键决策页** = 薄薄一页"关键岔路 + 拍了什么 + 为什么"（decision packet 雏形）。它是第 ⑥ 步反向出 PRD 的决策依据，**必须落盘留底**（区别于被砍的过程税——它有下游用途）。

**三条上坡路**（殊途同归到上面的目的地）：

| 上坡路 | 触发 | AI 做什么 |
|---|---|---|
| **直奔清单** | PM 思路很清 | PM 口述 → AI 结构化成清单 → PM 确认。快，不抛岔路口。 |
| **收范围对话** | 有概念岔路 / PM 思路未定 | `@读 PRODUCT-STATE + 主原型` 找 delta（"这是新东西、当前原型没有"）→ 抛结构化岔路口（A/B/C，**画 ASCII 把每个选择的后果摆出来**）→ PM 答 → 综合成具体结构图复确认 → 一致性检查 → 收敛后结晶成清单 |
| **视觉变体探** | 文字岔路掰不清 / PM 想用眼睛挑 | 先出几版**便宜的静态视觉草图**（mock，不动真原型代码）给 PM 挑 → 挑定方向回到清单。= 夹在"文字清单"与"真 build"之间的第三档视觉探针；Claude Design / gstack `design-shotgun`「只看不导」在此承接 |

**内部弧**：探索 / 收缩（任一上坡路）→ **选定一个方向** → 深化成完整**实现文档**（详细清单 + 决策页）→ 交第 ③ 步 build → 第 ④/⑤ 步复审。

**"实现文档"装什么 / 不装什么**（卡死，防工程文档复活）：
- ✅ **装**：详细范围清单（WHAT）+ 关键决策页（为什么）——**产品口径，PM 拍板**。治 PM 老痛点"不确认修改方案就让 AI 出、出错了花巨多时间调"。
- ❌ **不装**：工程 HOW（组件怎么拆 / 状态怎么管 / mock 数据结构 / 调用怎么 mock）——**AI 后台，PM 不逐行确认**。旧 `implementation-design` 这个独立工程文档由此坐实"降后台 / 砍"。

**护栏（防机械化）**：何时抛岔路口、抛几个、何时画 ASCII、何时改走视觉草图——**全是 AI 临场判断，不得写成"每个 req 必跑 N 个岔路口"的硬流程**，否则思路清的简单需求被强行拖一遍 = 又长回流程税。框架在第②步只管两头（**上下文进场 + 清单/决策落盘**），中间收敛对话交给判断。这段对话之所以能接住，靠的就是第①步上下文脊柱——AI 知道当前原型长什么样，才指得出 delta（§1.3 spike：同一个 Claude 加载了产品现状就接得住）。

### §2.3.2 第④⑤⑥步的内部结构（复审 → 沉淀）

后半截脊梁：

```
③ build（栈内建）
   ↓
④+⑤ 复审 = 三道机器审（自动）→ 一道人审（体验迭代）→ demo 呈交闸门（PM 一句话验收，唯一拍板）
   ↓
⑥ 沉淀 = 每 req 必做（更新 PRODUCT-STATE + merge 主原型回 main）+ 按需交付（反向 PRD）
```

**framing：PM 那个"AI 出一版、我花巨多时间一点点调"的痛，其实是两种病，各给一个药：**

| 病 | 例子（用户管理） | 谁治 |
|---|---|---|
| **残版**（WHAT 缺了） | 字段不全、按钮不全、没详情页、tab 漏建 | **④ 覆盖审计** |
| **体验差**（HOW 不顺） | 信息太杂、交互不顺、tab 层次乱 | **⑤ 体验迭代** |

（"tab 分不清"横跨两边：② 清单先定**有哪几个 tab**、④ 查**都建了没**、⑤ 调**层次清不清**——三层兜死这个老坑。）

**④ 三道机器审（build 完自动跑，结果合成一份给 PM）：**

| 道 | 查什么 | 怎么做 |
|---|---|---|
| **覆盖审计** | 建全了没（**存在**） | **独立新鲜视角 agent**（不参与 build），只拿「范围清单 + build 出的代码」两边硬 diff，报"建了 / 丢了 / 降级占位"。**对标已有 analysis-reviewer 模式，不让 builder 自审**（丢字段的 AI 审不出自己丢字段）。非 gstack。 |
| **视觉门** | 长得对不对（**外观**） | gstack `/design-review`，**只截图 + 挑问题、不自动改**；产出截图 + 视觉发现。 |
| **行为审** | 跑得通不通（**行为**） | 拿第②步范围清单派生的**验收流程**驱动 gstack `/browse` 走一遍（步骤定死、每次同路径 = 确定性验收门；PM 既有机制，背后本就是 gstack browser）。区别于 `/qa` 的 AI 探索（那是另一种驱动、手动按需找没想到的 bug）。 |

**⑤ 体验迭代（人审，三个收口防"调整地狱"）：**
1. **AI 主动批量扫、PM 拍**：视觉门 findings 当 AI 的眼睛，AI 先开口"这 5 处体验有问题、要不要改、改哪几个"，PM 勾要改的。**AI 主动提，但不自作主张改。**
2. **停止条件 = demo 成功标准 + PM 闸门**：原型不磨像素级；达标 + PM 一句"行"。**不设"AI 觉得够好自己过"**。
3. **磨不动上抛**：几轮不收敛，AI 喊停"这可能是②方向错、不是细节"，拉回第②步重选——不在错地基上无限抛光（根因优先）。

**呈交闸门**：PM 一句话 pass / 打回 = 唯一拍板点（落在现 `task-verify` 位置）。行为审是它下面"自动产证据"的一环；闸门是 PM 架在三道审证据上的决策——两件事，别混。

**⑥ 沉淀：**
- **反向 PRD = 多源合成，不是"代码翻译成文档"**：结构 / 字段 / 交互 ← 最终原型 + 范围清单（WHAT）；业务规则 / 权限语义 ← brief + 决策页（WHY）。**铁律（不变量 B）：哪怕这版是 mock 壳，PRD 也按真实系统口径写，绝不从 mock 随手实现反推规则。**§2.3.1 留的决策页在此兑现价值（供 PRD 的"为什么"）。
- **防腐铁律：PRODUCT-STATE 只在沉淀这一刻被写**（别处随手更新必漂，见 §5 腐烂教训）。
- **节奏两档**：① **每 req 必做**（保持脊柱最新）= 更新 PRODUCT-STATE + merge 主原型回 main；② **按需交付**（PM 真要拿去评审时才合成，可一次覆盖多个 req）= 反向 PRD。**避免每个琐碎 req 都硬产一份没人看的 PRD = 文档税。**

### §2.4 两条不变量

**不变量 A —— 范围层在前、体验层在后（两层不同时序，化解"先确认范围 vs 看图才发现"的矛盾）**
- **范围层（WHAT：界面/弹窗/字段/按钮/tab/做不做）**：build **前**用文档确认，防残版。PM 本来就能做、做得好。（注：范围层也会漏**关系态/派生态**——见 §2.5.1，PM 写时也想不全；靠第 ④ 步覆盖审计 + 看原型兜底。"范围层确认"≠"一次定全"。）
- **体验层（HOW 的感觉：交互顺不顺、信息杂不杂、密度、层次）**：build **后**看渲染才发现、才迭代。这才是 PRODUCT.md"很多决策是看着原型才发现的"真正所指。

**不变量 B —— 实现深度可调，PRD 深度恒定**
- **实现深度**靠现有「实现程度控制参数」调：同一个 `prototype/`，可做原型（大量 mock）也可做真实系统（打通真后端/数据/权限）。
- **PRD 永远按"真实系统"口径写**：哪怕这轮原型是 mock 壳，PRD 的需求/业务规则/权限语义都面向生产系统，**不从 mock 原型里随手的实现反推**。
- **两者解耦**：原型是验证/演示需求的手段（深浅可变），PRD 是面向决策者和真实落地的产物（始终真系统口径）。**把"原型从 mock 加深到真系统"当成 PM 显式拍的决策点**（"这轮我要把权限地基从 mock 换成真 RBAC"）——那一步是**在同一个主原型里原地结构性重写**（符合前稿《产品现状与主原型》§0.4 #4 锁定的"绝对单一主原型、不留 fork"，**不另开分叉**），不是悄悄演进。**（2026-05-29 D9：这种层级深化默认走独立 req——跨多页/改地基、要重走范围确认 + 沉淀，最好专门 req 别混"加功能"；真·localized 的单点 mock→真 才当 task。）**
- **mode 承接位置（§5.8，2026-05-29 D4 已拍）**：按层走、三层挂靠——详细深度指引留现成 `工程结构约束-{prototype,system,custom}` ／当前 mock-真状态进 PRODUCT-STATE 状态位 ／本轮深化哪层的决策在第②步决策页。mode 只改 build 深度，不动本条"PRD 恒真系统口径"。
- **标签 mode 中立（2026-05-29 PM 补）**：六步 / 单元名按 mode 中立取——`task` 不改成"demo"（mode=system 时建的是真实功能、不是 demo），主原型 / build / 确认门同理对两种 mode 都成立。常见叙述里的"原型 / demo"只因 prototype 是常态，**不代表流程只服务原型**。

### §2.5 关键机制澄清（来自 5 视角对抗审 + spike，修正前两稿）

1. **"范围合同"= 验收清单，不是生成保证。** 视觉工具按"页面看起来合理"优化、不按"字段矩阵逐项覆盖"优化，所以会丢字段/合并 tab/详情页占位。真正治残版的是 **build-then-check 覆盖审计**（第 ④ 步），不是 build 前的清单。尤其**关系态/派生态**（删最后一个管理员该不该拦、停用用户的悬空审批流）PM 写范围时也想不全，靠看原型 + 覆盖审计兜。
2. **"无损录入"是幻觉，已规避。** Claude Design 出的是它那套静态 React-UMD/Babel，主原型是 Next.js —— 跨栈"录入"= AI 重写一遍 = 引入新残版 + 视觉失真。**解法：不跨栈，build 直接在 `prototype/` 用 Claude Code 干；Claude Design 只当"只看不导"的视觉参考板**（用它赢的"布局"给 Claude Code 当灵感，代码仍在栈内建）。这正是"怎么结合 Claude Design"的答案。
3. **PRD 不从 mock 代码反推业务规则。** 权限/审批等"为什么"类规则代码反映不出，反推必失真 —— 从 brief 阶段就锁，对应不变量 B。

### §2.6 三个新机制的最小可操作定义（否则会塌回口号）

这三个是本稿补 Claude Code 视觉短板 + 防残版的**全部承重机制**，必须可操作：

| 机制 | 最小可操作定义 |
|---|---|
| **design 约定** | = `DESIGN.md` 里 **N 条正向视觉约束**（不是"禁止项清单"）+ 产品化 demo 目标（首屏见价值 / 每个主按钮最低可用闭环）；build skill **强制 `@读 DESIGN.md`** 后再动手。 |
| **视觉门** | = build 后 **AI 必跑已存在的 gstack `/design-review`** + 截图贴给 PM，**PM 一句话 pass / 打回**。不是抽象"看一眼"，是一个固定动作 + 明确 pass/fail 出口。 |
| **覆盖审计** | = 第 ② 步"确认范围层"**必须产出一份结构化范围清单 + 一页关键决策**（清单 = markdown 表：页面/字段/按钮/tab/状态/做不做；决策页见 §2.3.1）；build 完由**独立新鲜视角 agent**（非 builder 自审，见 §2.3.2）拿这张表**逐项打勾**（建了/丢了/降级占位）。**没有结构化清单，逐项 diff 就没有锚点。** |

## §3 保留 / 砍 / 入口收敛

**保留**：产品上下文脊柱（PRODUCT-STATE + 主原型 + DESIGN）；PRD 反向沉淀；worktree 隔离（后台化，不进 PM 视图）；跨 req 上下文继承；"不和 Claude Design 比首版原型"的定位。

**砍**：过程文档税（§2.2 第三类）；7-stage 前置重门；ASCII 当视觉真相源；"默认禁止项清单"当唯一视觉指引（要换成正向的 design 约定 + 产品化 demo 目标 + 视觉门）。

**入口收敛（2026-05-29 D7 已拍）**：PM 主循环收敛到 **4 条**——`init`（起项目）/ `new-req`（起需求）/ **`next`**（推进六步，**接管被砍的 stage-gate 推进引擎**；护栏：先说"要做 X / 要你确认 Y"再动，不闷头跑）/ `status`（我在哪 + 产品现状）。**按需 PRD = `prd-writing` skill standalone 调**（PM 要拿去评审时触发，不进主循环、不新造命令）。情景命令保留但不进主循环：`quick-fix` / `cancel-req` / `publish-to-lark` / `codebase-audit` / `pmai-upgrade`。不暴露 stage / worktree / task-spec 细节。

## §4 落地顺序（评审强调：别一次建全、先证伪）

| 阶段 | 内容 | 性质 |
|---|---|---|
| **阶段 0（先 ship）** | 砍冗余（工程双合同 / 同范围重复 / 琐碎 req 全套 / 机器废气）+ worktree **PM 视图不显示**（播报/banner 文案，轻量）+ **worktree 自动托管**（AI 自动建/merge/删 task worktree，PM 零窗口切换——2026-05-29 PM 拍：早上、不押后）+ 入口收敛只定方向 | 砍冗余/藏显示 = 纯收益、可独立落；**自动托管随本批早上，但必须 spike 验证再固化**（动 merge/删/residue + dispatch-clean 事故区） |
| **阶段 1（薄脊柱）** | `PRODUCT-STATE.md`（手写、AI 必读）+ 主原型说明 + `DESIGN.md`；**更新绑死在沉淀那一刻**（防腐：别加必读 hook 去管一份注定漂移的文档——漂移的现状档比没有更危险） | 心脏，零机制成本起步 |
| **阶段 2（build 纪律）** | Claude Code 在栈内建 + design 约定 / skill（frontend-design 原则 + 产品化 demo 目标"首屏见价值 / 每个主按钮最低可用闭环" + 看渲染的视觉门）+ 覆盖审计 | 补 Claude Code 唯一短板（视觉布局） |
| **阶段 3（沉淀）** | 原型确认后反向 PRD + 更新产品现状（PRD 按真系统、权限从 brief 锁） | 终点交付物 |

> 注：worktree **自动托管** 是前稿《task执行自动化》VP4 的重改动——**2026-05-29 PM 拍板早上、随阶段 0 一起做**（窗口切换是 PM 最烦的体感税，藏显示只是半截 fix）。代价：阶段 0 不再是纯零风险 ship——自动托管动 merge/删/residue + "dispatch 前 working tree 必须 clean"那条事故区，**先用一个真实 req spike 验证再固化、这步不能省**。砍冗余 + 藏显示仍是纯收益、可独立先落。**澄清**：自动的是 worktree 机器（fork/merge/删/切窗口）；**PM 的呈交闸门验收（pass/打回）保留、绝不自动**。

**纪律**：每个新机制**先用一个真实 req 跑一遍验证（spike）再固化**，别在证伪前先建脚手架（旧仓 prototypes/ 只剩 README = 教训）。

**下一步（assignment）**：① 先把"阶段 0 砍冗余 + worktree 后台化"作为第一个独立 ship；② 下一个真实 req 用新 build 路径（Claude Code 在栈内 + design 约定 + 覆盖审计）跑一遍，当作新机制的 spike。

## §5 待定 / 风险

- **`prototype/` 单一性（前稿《产品现状与主原型》§0.4 #4，PM 已锁定：绝对单一、不留 fork / 变体 / 逃生舱）**：⚠️ 评审曾提"探索期想并排比 A/B 方向"可能受此约束。但这是 PM 拍板的 **binding 决策**——本稿**默认严格按"绝对单一"执行，不擅自加 fork 逃生舱**。若未来真撞到 A/B 探索受限，这是一个**需 PM 重新拍板**才能动的点，在 PM 改口前不变。（mock→真系统的结构性重写按不变量 B：在单一主原型内**原地重写**，不是 fork。）

## §X 证据留档

### A. 取证扫描（2 仓，文件级）
见 §1.2 / §1.3 关键数字。完整 6 维（ExampleConsumerApp）+ 3 维（ExampleAgentProject）取证结论：框架在"想/建"段又重又弱、后半段（跨团队规格、审计留痕、三段式 PRD）真有价值但被淹没；原型差距根因在"输入契约 + 无视觉门"，不在模型/执行器。

### B. 5 视角对抗审（裁决一致：补漏后成立）

| 视角 | biggest_risk（最可能错的承重假设） |
|---|---|
| 资深后台 PM | 把复杂后台核心难度（关系态/派生态/权限联动）误当成"字段清单完整性问题" |
| 怀疑论工程师 | "无损录入"这个词本身——跨栈不存在的操作，必坍缩成重写+失真 |
| CEO 值不值 | 范围合同 + 无损录入两个 high 级单点故障串联，且都是"静默"失败，下个 req 才爆 → 误导出"需要更厚框架"的负反馈 |
| 专职证伪 | "scope-first 防残版"和方案自己的根因诊断（spec-first 是病）正面打架 |
| Codex（跨模型） | 把"范围合同"和"无损录入"当成可靠能力，实际只是人工验收 + 二次实现的包装 |

**三刀补丁**（已并入 §2.5）：① 范围合同→验收清单+覆盖审计 ② 无损录入→不跨栈、Claude Code 在栈内建 ③ build 前确认范围→两层时序（范围层前/体验层后）。
**Codex 另两点（采纳）**：保留一个薄"判断继承"接口、别变纯文档机器人；最小版本 = 几个模板 + 几条命令，别上 state-machine。**（Codex 的"默认不产文档/交易系统"提法被 PM 否决——文档恰恰是 AI 认识产品的方式，见 §2.2。）**

### C. A/B spike 分维裁决（2026-05-29，PM 亲判）

| 维度 | 赢家 |
|---|---|
| 视觉 / 布局设计 | **Claude Design** |
| 交互完整度 | **Claude Code** |
| 覆盖范围 | 平 |
| 产品判断 | 平 |

**结论**：整体相近、各擅胜场；Claude Code 唯一明确短板 = 视觉布局 → 用 design 约定 + Claude Design 当只看不导的视觉参考补。**最大叉口"build 接谁"拍板：默认 Claude Code 在栈内建，零录入。**（产物：`ExampleAgentProject-pathB`，对照 Claude Design 产物 `ExampleAgentProject/src/`。）

**回退点（写进基线，不藏在风险表）**：阶段 2 的 design 约定若 spike 不达标 → build 路径回退 = **加大 Claude Design 视觉参考权重 / 重评是否需要有限录入**。即"默认 Claude Code"是一个**押在 1 次 spike 上、带回退点的赌注**，不是已证实的定论。
