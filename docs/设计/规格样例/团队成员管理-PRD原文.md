# 团队成员与角色权限管理 PRD（prd-writing 重风格 · agent 原文）

**摘要：** 本模块是 SaaS 产品后台的成员管理中心，面向团队的所有者、管理员与普通成员。它解决"谁在团队里、谁能管谁、最高权限怎么安全交接"三件事：维护一份完整的成员列表，提供基于邮件邀请的加入流程，并约束成员角色变更、成员移除、所有权转移这三类涉及权限边界的敏感操作。范围限定在单个团队内部的成员构成与角色权限管理，不含团队的创建与删除、不含计费与席位购买、不含成员对业务数据的具体操作权限。

## 三、名词解释

| 术语 | 说明 |
| --- | --- |
| 团队 | 共享同一份产品数据与协作空间的成员集合；本模块所有操作都在单个团队范围内进行，不跨团队。 |
| 成员 | 已接受邀请并正式加入团队的人；只描述已正式加入的人，不描述仅收到邀请尚未接受的人。 |
| 所有者 | 团队唯一的最高权限角色。**一个团队有且仅有一个所有者。** 所有者能执行本模块的全部操作，包括转移所有权；不可被移除、不可被降级。 |
| 管理员 | 拥有成员管理权限的角色：可邀请成员、移除成员、改成员角色、查看全部成员；不能对所有者执行任何管理操作。 |
| 普通成员 | 只拥有查看权限的角色：能看成员列表，不能执行任何管理操作。 |
| 角色 | 成员在团队内的权限身份，取值为所有者、管理员、普通成员三者之一；是权限的来源，不是岗位或职级的描述。 |
| 邀请 | 由所有者或管理员向一个邮箱地址发出的加入请求；邀请不是成员，被邀请人接受邀请后才成为成员。 |
| 邀请状态 | 一条邀请所处的环节，取值为待接受、已过期两者之一；只描述邀请本身的处理进度，不描述接受邀请后那个人的成员状态。 |
| 成员状态 | 一个成员当前是否能正常使用团队的标志；只描述已正式加入的成员，不描述邀请。 |
| 所有权转移 | 所有者把最高权限完整交给一名管理员的操作：**原所有者降为管理员，目标管理员升为所有者。** 转移是身份的整体交接，不是给目标加一份所有者权限。 |
| 自提权 | 一名管理员通过改角色操作，把别人或自己的权限抬到超过自身的行为；本模块**不允许**自提权。 |

## 四、需求分析

### 4.1 业务诉求

**团队得有一份能信的成员名册。** 谁在团队、各自什么角色、是否还在用、什么时候进来的，要在一个地方一次看全。如果名册散在邀请记录、登录日志、付费席位等多处，管理员就无法回答"现在到底谁能进我们团队"这个最基本的问题，敏感数据的知情范围就失控。所以本模块要把"已正式加入的人"和"还在路上的邀请"都收进同一个可检索、可筛选的视图。

**加入团队必须本人同意。** 把一个邮箱直接拉进团队、不经对方确认，等于替别人决定了他的归属，也无法保证那个邮箱真由本人掌握。不应通过"管理员填邮箱即生效"来表达加入，否则填错一个字母就会把陌生人放进团队，或把数据暴露给一个无人认领的邮箱。所以加入走"邀请—接受"两步：管理员发出邀请，被邀请人本人接受后才正式成为成员。

**权限只能向下授予，不能向上夺取。** 管理员的职责是替所有者打理团队，不是给自己扩权。如果管理员能把别人或自己提到超过自身的权限，授权链条就被绕过了——上级的权限边界形同虚设。不应通过"管理员可以自由设置任意角色"来表达改角色能力，否则任何一个管理员都能一步把自己变成实际上的最高权限者。所以改角色的能力被框死在"不超过操作者自身权限"的范围内，且所有者的角色不经转移所有权不可改动。

**最高权限的交接要重、要慢、要不可误触。** 所有权是团队里唯一的最高权限，一旦交出去就拿不回来。如果转移所有权和改个普通角色一样点一下就完成，一次误操作就可能把团队拱手让人。不应通过"一次点击直接转移"来表达这个操作，否则代价与门槛严重不匹配。所以所有权转移要二次确认、要手动输入指定文字确认意图，让操作者必须刻意才能完成。

**团队不能没有人能管。** 如果所有者被移除、或团队里最后一个能管理的人退出，剩下的人就再也无法邀请、无法调整角色，团队进入无人可管的死局。不应通过"允许任意移除、任意退出"来表达成员流动，否则团队会被一步操作锁死。所以所有者不可被移除、不可被降级（除非先把所有权转走），团队始终保留至少一个能管理的人。

### 4.2 设计原则

| 编号 | 原则 | 内容 | 对应诉求 |
| --- | --- | --- | --- |
| 1 | 名册唯一且完整 | 成员与邀请收进同一个视图集中呈现；只呈现本团队范围内的人，不混入其他团队。 | 团队得有一份能信的成员名册 |
| 2 | 加入需本人接受 | 邀请只产生一条待接受记录，不直接生成成员；只有被邀请人本人接受，才把这条记录转为正式成员。 | 加入团队必须本人同意 |
| 3 | 权限只降不升 | 改角色操作只能把目标设为不高于操作者自身的角色；不能借此给自己或他人提权。 | 权限只能向下授予，不能向上夺取 |
| 4 | 敏感操作分级设防 | 移除成员需二次确认，所有权转移需二次确认加手动输入指定文字；普通查看与筛选不设确认。 | 最高权限的交接要重、要慢、要不可误触 |
| 5 | 始终保留管理能力 | 所有者不可被移除、不可被降级；任何操作都不能使团队进入无人可管的状态。 | 团队不能没有人能管 |
| 6 | 角色即权限来源 | 一个成员能做什么，只由其角色决定；不存在脱离角色的单独授权。 | 权限只能向下授予，不能向上夺取 |

### 4.3 方案价值

**管理员能一眼回答"谁能进我们团队"。** 成员与待处理邀请收在同一视图，配合搜索与筛选，管理员无需在多处记录间拼凑，就能掌握当前团队的真实构成与知情范围。反过来，若名册不全或散落，管理员只能凭印象判断，敏感数据的暴露面就成了盲区，事后追责也无据可依。

**加入团队不会出现"被加入"。** 经由邀请—接受两步，每个成员都是本人确认后才进来的，填错邮箱最多产生一条无人接受的待处理邀请，过期即作废，不会把陌生人放进团队。反过来，若允许直接拉人入团，一次手误就可能造成数据外泄，且这种错误难以被及时发现。

**提权这条路被堵死。** 改角色能力被约束在"不高于操作者自身"，加上所有者角色受转移所有权保护，任何管理员都无法靠自己一步登顶。反过来，若改角色不设上限，团队的权限结构就失去了稳定性，谁是管理员谁就可能是潜在的最高权限者。

**最高权限交接安全且明确。** 转移所有权的二次确认与输入指定文字防呆，把这个不可逆操作的门槛抬到与其代价相称；转移后原所有者明确降为管理员、新所有者明确获得全部权限，交接结果不含糊。反过来，若交接轻率，一次误触就可能让团队失控，且无法挽回。

## 五、用户与场景

### 5.1 用户角色

| 角色 | 描述 | 在本模块的核心诉求 |
| --- | --- | --- |
| 所有者 | 团队唯一的最高权限持有者，通常是团队的建立者或当前负责人。 | 掌握全员构成；安全地把团队日常管理交给管理员；在需要时把最高权限交接给可信的管理员。 |
| 管理员 | 受所有者委托打理团队的人。 | 邀请新成员、移除离开的成员、调整成员角色、随时查看全员；在不越权的前提下高效管理团队。 |
| 普通成员 | 团队的一般使用者。 | 知道团队里都有谁、各自是什么角色、如何联系；不需要也不应拥有管理能力。 |

### 5.2 用户故事

**Story 1：** 作为管理员，我想在一个列表里看到团队的全部成员和待处理邀请，并能按姓名、邮箱搜索、按角色、状态筛选，以便快速找到我要处理的人。

**Story 2：** 作为管理员，我想给一个新同事的邮箱发出带指定角色的邀请，让他本人接受后加入团队，以便把合适的人以合适的角色引入团队。

**Story 3：** 作为管理员，我想对一条待接受的邀请重发或撤销，并在对方已是成员或已有待接受邀请时被拦住，以便不产生重复或失效的邀请。

**Story 4：** 作为管理员，我想在普通成员与管理员之间调整某人的角色，同时被系统挡住任何把别人或自己提到超过我权限的操作，以便在不越权的前提下调整团队分工。

**Story 5：** 作为管理员，我想移除一名不再属于团队的成员，并在移除前得到一次明确的二次确认，以便避免误操作把人踢出团队。

**Story 6：** 作为成员，我想主动退出我不再参与的团队，以便不再占用名额、不再持有访问权。

**Story 7：** 作为所有者，我想把团队的最高权限转交给一名管理员，并通过二次确认和输入指定文字来防止误操作，以便安全地完成团队负责人的交接。

**Story 8：** 作为普通成员，我想查看成员列表了解团队都有谁，同时看不到任何管理操作入口，以便清楚自己的权限边界。

### 5.3 非目标

1. 不含团队本身的建立与解散。
2. 不含计费、席位数量限制与席位购买。
3. 不含成员对业务数据、功能页面的具体操作权限设置（本模块只管理员管理、移除、改角色、转移所有权四类权限，不管业务级权限）。
4. 不含跨团队的成员管理与一人多团队的切换。
5. 不含登录、注册、找回密码等账户体系功能。
6. 不含自定义角色与权限自由组合，角色固定为所有者、管理员、普通成员三种。
7. 不含批量邀请、批量移除、批量改角色。

## 六、功能需求

> 表格内关键约束与默认行为加粗。需求描述每条编号并穷举边界。

| 二级功能 | 三级功能 | 使用角色 | 需求描述 |
| --- | --- | --- | --- |
| 成员列表 | 列表展示 | 所有者 / 管理员 / 普通成员 | 1. 进入成员管理页面，**默认**展示本团队的全部成员，每行展示姓名、邮箱、角色、状态、加入时间五项。<br>2. 角色一列展示"所有者""管理员""普通成员"三种之一。<br>3. 状态一列对成员展示"正常"或"已禁用"，对尚未接受的邀请展示"待接受"或"已过期"。<br>4. 加入时间对成员展示其接受邀请的日期，对邀请展示该邀请的发出日期。<br>5. 列表把成员与待处理邀请收在同一视图，**默认**把成员排在前、待处理邀请排在后。<br>6. 所有者一行始终展示，**不允许**对其展示任何管理操作入口（详见各操作行的可见性差异）。 |
| 成员列表 | 搜索 | 所有者 / 管理员 / 普通成员 | 1. 页面提供一个搜索框，占位文案为 "搜索姓名或邮箱"。<br>2. 输入内容时按姓名、邮箱两项做匹配，**只**匹配这两项，不匹配角色与状态。<br>3. 搜索对成员与待处理邀请同时生效。<br>4. 无匹配结果时，列表区域展示空状态文案 "没有匹配的成员或邀请"。<br>5. 清空搜索框后恢复展示全部。 |
| 成员列表 | 筛选 | 所有者 / 管理员 / 普通成员 | 1. 页面提供"角色"筛选与"状态"筛选两个入口。<br>2. 角色筛选可选"全部""所有者""管理员""普通成员"，**默认**选中"全部"。<br>3. 状态筛选可选"全部""正常""已禁用""待接受""已过期"，**默认**选中"全部"。<br>4. 角色筛选、状态筛选与搜索可同时作用，结果取三者的交集。<br>5. 三种角色都能使用搜索与筛选，**普通成员可看可筛，但每一行都不展示任何管理操作入口。** |
| 邀请成员 | 发起邀请 | 所有者 / 管理员 | 1. 列表页右上角提供 [邀请成员] 按钮，**普通成员不展示**此按钮。<br>2. 点击后在当前页面弹出"邀请成员"弹窗，含一个邮箱输入框与一个角色选择项，底部为 [发送邀请] 与 [取消] 两个按钮。<br>3. 角色选择项可选"管理员"与"普通成员"，**不允许**选择"所有者"。<br>4. **管理员发起邀请时只能选"普通成员"**，"管理员"一项对管理员置为不可选；所有者发起邀请时"管理员"与"普通成员"均可选。<br>5. 邮箱为空或格式不符合邮箱规则时，[发送邀请] 保持禁用，并在输入框下方提示 "请输入有效的邮箱地址"。<br>6. 该邮箱**已是本团队成员**时，拦截发送并提示 "该邮箱已是团队成员"。<br>7. 该邮箱**已有一条待接受的邀请**时，拦截发送并提示 "该邮箱已有待接受的邀请，可在列表中重发或撤销"。<br>8. 该邮箱此前的邀请已过期或已撤销时，**允许**重新发起新邀请。<br>9. 发送成功后关闭弹窗，列表新增一条状态为"待接受"的邀请记录，并提示 "邀请已发送"。 |
| 邀请成员 | 接受邀请 | 被邀请人 | 1. 被邀请人通过邀请中的入口确认接受后，该邀请记录转为正式成员，角色取邀请时指定的角色。<br>2. 接受成功前，被邀请人**不是**团队成员，不占用成员名册中的成员条目，仅作为待接受邀请存在。<br>3. 邀请超过有效期未被接受时，状态由"待接受"变为"已过期"，**已过期的邀请不可被接受**。 |
| 邀请成员 | 重发邀请 | 所有者 / 管理员 | 1. 对一条状态为"待接受"的邀请，其所在行提供 [重发] 操作。<br>2. 点击 [重发] 后重新向该邮箱发出邀请，并提示 "邀请已重新发送"。<br>3. **只有"待接受"状态的邀请展示 [重发]**；"已过期"的邀请行改为展示 [重新邀请]，点击后等同于对该邮箱发起一条新邀请。<br>4. 对已是成员的行**不展示** [重发]。 |
| 邀请成员 | 撤销邀请 | 所有者 / 管理员 | 1. 对一条状态为"待接受"的邀请，其所在行提供 [撤销] 操作。<br>2. 点击 [撤销] 后弹出二次确认，文案为 "撤销后该邀请立即失效，对方将无法再通过此邀请加入。"，按钮为 [确认撤销] 与 [取消]。<br>3. 确认后该邀请记录从列表移除，并提示 "邀请已撤销"。<br>4. 撤销后该邮箱**允许**被重新邀请。<br>5. **只有"待接受"状态的邀请展示 [撤销]。** |
| 改成员角色 | 调整角色 | 所有者 / 管理员 | 1. 在一名成员所在行提供"角色"调整入口，**普通成员不展示**此入口。<br>2. 可调整的目标角色范围为"管理员"与"普通成员"两者之间互改。<br>3. **不允许**把任何人的角色改为"所有者"，提权到所有者只能通过转移所有权完成。<br>4. **不允许**改动所有者的角色，所有者一行的角色调整入口**不展示**。<br>5. 自提权防护：**管理员不能把任何人的角色改到高于管理员自身**，因此对管理员而言"所有者"不可作为目标；**管理员不能给自己提权**，管理员对自己一行不展示角色调整入口。<br>6. 所有者可在"管理员"与"普通成员"之间调整任意非所有者成员的角色。<br>7. 调整成功后该行角色一列立即更新，并提示 "角色已更新"。 |
| 移除成员 | 移除他人 | 所有者 / 管理员 | 1. 在一名成员所在行提供 [移除] 操作，**普通成员不展示**此操作。<br>2. 点击 [移除] 后弹出二次确认弹窗，文案为 "移除后该成员将立即失去对本团队的访问。此操作不可撤销。"，按钮为 [确认移除] 与 [取消]。<br>3. 确认后该成员从名册移除，并提示 "成员已移除"。<br>4. **所有者不可被移除**，所有者一行**不展示** [移除]。<br>5. **管理员不能移除所有者，也不能移除其他管理员**——管理员仅能移除普通成员（管理员对其他管理员一行不展示 [移除]）；所有者可移除任意管理员与普通成员。<br>6. 被移除的成员若此前有正在使用的访问，移除生效后立即失去对本团队的访问。 |
| 移除成员 | 退出团队 | 管理员 / 普通成员 | 1. 在当前登录者自己一行提供 [退出团队] 操作（即移除自己）。<br>2. 点击后弹出二次确认弹窗，文案为 "退出后你将立即失去对本团队的访问。此操作不可撤销。"，按钮为 [确认退出] 与 [取消]。<br>3. 确认后当前登录者从名册移除，立即失去对本团队的访问。<br>4. **所有者不展示 [退出团队]**：所有者要离开团队，必须先转移所有权降为管理员后再退出。<br>5. 退出操作不需要其他人审批，由本人确认即生效。 |
| 转移所有权 | 转移最高权限 | 所有者 | 1. 该操作**仅所有者**可见可用，入口为列表页的 [转移所有权] 按钮，**管理员与普通成员不展示**此按钮。<br>2. 点击后弹出"转移所有权"弹窗，提供一个目标人选择项，**只能从当前团队的管理员中选择**，普通成员不出现在可选范围。<br>3. 团队内没有任何管理员时，[转移所有权] 按钮置为禁用，悬停提示 "请先把一名成员设为管理员，再转移所有权"。<br>4. 选定目标后，弹窗展示警示文案 "转移后你将降为管理员，对方将获得团队的全部权限，包括再次转移所有权。此操作不可撤销。"。<br>5. 防呆校验：弹窗要求在输入框中手动输入指定文字 "转移所有权" 才能继续，输入不一致时 [确认转移] 保持禁用。<br>6. [确认转移] 与 [取消] 为弹窗底部两个按钮，输入一致后 [确认转移] 方可点击。<br>7. 确认后完成交接：**原所有者角色变为"管理员"，目标管理员角色变为"所有者"**，团队仍只有一个所有者。<br>8. 转移成功后关闭弹窗，列表中两人的角色一列立即更新，并提示 "所有权已转移给（目标姓名）"。<br>9. 转移完成后，原所有者**立即失去**所有者专属能力（转移所有权按钮不再展示），按管理员权限继续使用团队。 |

## 七、验收标准

**Story 1：成员列表与搜索、筛选**
- [ ] 进入页面，列表展示全部成员，每行含姓名、邮箱、角色、状态、加入时间五项
- [ ] 待处理邀请与成员展示在同一列表，成员在前、待处理邀请在后
- [ ] 在搜索框输入姓名片段，列表只保留姓名匹配的行；输入邮箱片段，只保留邮箱匹配的行
- [ ] 搜索不匹配角色与状态文字
- [ ] 无匹配时展示空状态文案 "没有匹配的成员或邀请"，清空搜索后恢复全部
- [ ] 角色筛选默认"全部"，切到"管理员"后只展示管理员
- [ ] 状态筛选默认"全部"，切到"待接受"后只展示待接受邀请
- [ ] 搜索与两个筛选同时作用时，结果为三者交集
- [ ] 普通成员可使用搜索与筛选，且任意行都不展示管理操作入口

**Story 2：发起邀请并由本人接受加入**
- [ ] 所有者与管理员在列表页可见 [邀请成员] 按钮，普通成员不可见
- [ ] 弹窗中所有者可选"管理员"与"普通成员"，管理员只能选"普通成员"，两者都无法选"所有者"
- [ ] 邮箱为空或格式不符时，[发送邀请] 禁用并提示 "请输入有效的邮箱地址"
- [ ] 发送成功后列表新增一条"待接受"邀请，提示 "邀请已发送"
- [ ] 被邀请人本人接受前不是成员、不占成员条目
- [ ] 被邀请人接受后成为成员，角色为邀请时指定的角色

**Story 3：重发、撤销邀请与重复邀请拦截**
- [ ] 对"待接受"邀请行可见 [重发] 与 [撤销]
- [ ] 点击 [重发] 后提示 "邀请已重新发送"
- [ ] 点击 [撤销] 弹出二次确认，确认后邀请从列表移除并提示 "邀请已撤销"
- [ ] 对已是成员的邮箱发起邀请，被拦截并提示 "该邮箱已是团队成员"
- [ ] 对已有待接受邀请的邮箱再次邀请，被拦截并提示 "该邮箱已有待接受的邀请，可在列表中重发或撤销"
- [ ] 邀请超期后状态变为"已过期"，该行展示 [重新邀请]，不展示 [重发] 与 [撤销]
- [ ] 已过期的邀请不能被接受
- [ ] 已撤销或已过期的邮箱可被重新邀请

**Story 4：改成员角色与自提权防护**
- [ ] 成员行可见角色调整入口，普通成员不可见该入口
- [ ] 角色目标范围为"管理员"与"普通成员"互改
- [ ] 任何人都无法被改为"所有者"
- [ ] 所有者一行不展示角色调整入口
- [ ] 管理员对自己一行不展示角色调整入口（不能自我提权）
- [ ] 管理员的角色目标项中不出现"所有者"（不能把他人提到超过自身）
- [ ] 所有者可在"管理员"与"普通成员"之间调整任意非所有者成员
- [ ] 调整成功后该行角色一列即时更新并提示 "角色已更新"

**Story 5：移除他人**
- [ ] 成员行可见 [移除]，普通成员不可见
- [ ] 所有者一行不展示 [移除]
- [ ] 管理员对其他管理员一行不展示 [移除]，仅能移除普通成员
- [ ] 所有者可移除任意管理员与普通成员
- [ ] 点击 [移除] 弹出二次确认，文案含 "移除后该成员将立即失去对本团队的访问。此操作不可撤销。"
- [ ] 确认后成员从名册移除，提示 "成员已移除"，被移除者立即失去对本团队的访问

**Story 6：退出团队**
- [ ] 管理员与普通成员在自己一行可见 [退出团队]
- [ ] 所有者一行不展示 [退出团队]
- [ ] 点击后弹出二次确认，文案含 "退出后你将立即失去对本团队的访问。此操作不可撤销。"
- [ ] 确认后本人从名册移除并立即失去访问，无需他人审批

**Story 7：转移所有权**
- [ ] [转移所有权] 按钮仅所有者可见，管理员与普通成员不可见
- [ ] 目标人选择项只列出当前团队的管理员，普通成员不在可选范围
- [ ] 团队内无管理员时 [转移所有权] 禁用，提示 "请先把一名成员设为管理员，再转移所有权"
- [ ] 选定目标后展示警示文案 "转移后你将降为管理员，对方将获得团队的全部权限，包括再次转移所有权。此操作不可撤销。"
- [ ] 必须手动输入 "转移所有权" 才能启用 [确认转移]，输入不一致时按钮保持禁用
- [ ] 确认后原所有者变为"管理员"、目标变为"所有者"，团队仍只有一个所有者
- [ ] 转移后两人角色即时更新，提示 "所有权已转移给（目标姓名）"
- [ ] 转移后原所有者不再展示 [转移所有权] 按钮

**Story 8：普通成员只读**
- [ ] 普通成员可进入成员管理页面并查看完整列表
- [ ] 普通成员可使用搜索与筛选
- [ ] 普通成员看不到 [邀请成员]、[转移所有权]、[移除]、角色调整入口、[重发]、[撤销] 等任何管理操作入口
- [ ] 普通成员自己一行可见 [退出团队]

## 八、非功能性需求

| 类别 | 要求 |
| --- | --- |
| 数据一致性 | 角色变更、成员移除、所有权转移生效后，成员列表、各行操作入口的可见性、权限判定三者状态保持一致；同一时刻团队有且仅有一个所有者，任何操作不得产生零个或多个所有者。 |
| 并发安全 | 两名管理员同时对同一对象操作（同时移除同一成员、同时改同一成员角色）时，以先生效的一次为准，后一次基于失效前提的操作给出失败提示并刷新该行最新状态，不产生相互矛盾的结果。 |
| 权限即时性 | 成员被移除、退出、降级后，立即失去对应权限与对本团队的访问；提权后立即获得新权限，无需重新进入页面。 |
| 操作可逆性提示 | 移除成员、撤销邀请、转移所有权三类不可撤销操作，均在二次确认文案中明确写出 "此操作不可撤销" 或等义表述。 |
| 响应时延 | 列表加载、搜索、筛选的结果在常规网络下一秒内返回；邀请发送、角色调整、移除、转移所有权的操作结果在两秒内返回并更新界面。 |
| 可访问性 | 所有操作按钮与弹窗可用键盘逐项聚焦与触发；禁用状态的按钮通过视觉与可被辅助技术读取的方式同时表达不可用；弹窗打开时焦点进入弹窗内，关闭后焦点回到触发它的按钮。 |
| 失败可见 | 任何被拦截或失败的操作都给出明确的文字提示，提示直接说明被拦截的原因（如 "该邮箱已是团队成员"），不使用仅"操作失败"一类无信息的提示。 |
| 术语一致性 | 全篇与界面统一使用所有者、管理员、普通成员、成员、邀请、所有权转移、角色这一组称呼，同一概念不换用其他叫法。 |
| 空与边界状态 | 团队仅有所有者一人时，列表正常展示且不出现可移除所有者的入口；无任何待处理邀请时，列表只展示成员，不展示空的邀请分区标题。 |
