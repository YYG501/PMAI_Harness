### §0.1 痛点（1-3 句）

当 close-task 的 I-CT7 / I-CT8 挡下一个 work 真实完成、但审计证据（事件流）以已知原因不全或有误的 task 时，框架没有任何受支持的修复入口。唯一办法是手改 `.runs/events/*.jsonl` —— 不留痕、不强制理由、易错、且不受约束（谁都能改成任何样子）。

### §0.2 触发场景

| # | 场景 | 实证证据 |
|---|---|---|
| 1 | task work 真实完成，但执行期未走 `/task-execute`、事件流缺 execution 事件，close-task I-CT7 BLOCK，只能手工 append 事件解封 | ExampleConsumerApp req-006 `task-001-ops-log-pages`：靠手工 `task-events.py append execution_manual_completed` + retroactive note 才放行 |

### §0.3 根因

框架对"审计证据不全 / 有误"没有受支持、受约束、留痕的修复入口；手改 jsonl 是唯一办法。

### §0.4 不解决什么

| # | 衍生 / 假设场景 | 为什么不在范围 |
|---|---|---|
| 1 | 甲 / reopen 状态机回退 /「已完成」task 真返工 | 2026-05-21 PM 拍板选乙。零实证 —— task-001 是证据修复、不是返工；真要返工有"新开 revert task"兜底（`cmd_discard` 对已完成 task 的报错文案已指向）。真出现实证再单立 D-task |
| 2 | v2 状态物化重做 | TODOS.md 独立条目 |
| 3 | 改 I-CT7 / I-CT8 的判定逻辑 | 不动审计判定本身；本命令只受控地补对证据 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**。

## §1 方案（已实施）

`task-transition.py` 新增 `--repair-evidence` flag + `cmd_repair_evidence()`：

- **入口**：`task-transition.py <task-file> --repair-evidence --reason "<为何 work 真实完成>"`，非交互场景加 `--yes`。
- **前置校验**：① 状态须为「已完成」（否则报错并引导「执行中」走 `/task-execute`）；② `--reason` 必填；③ 事件流已有 execution 事件则报错"无需 repair"。
- **PM 认定**：交互 confirm（输入 yes），`--yes` 跳过。
- **动作**：经 `task-events.py append` 补一条 `execution_manual_completed`，带 `--note`（含 retroactive + reason）+ `--payload '{"repaired": true}'` 永久标记；不改状态。
- **integrity（§5 约束落地）**：强制 reason + PM 认定 + `repaired:true` 永久可辨标记 + 收窄到只补 `execution_manual_completed` 一种（不做任意事件合成）+ 仅「已完成」可用。

## §5 设计约束（方案必须解掉 —— §0 锁定前 PM 须知）

**核心难题 —— integrity surface**：乙 本质是"一个让审计通过的受支持命令"。设计不当 = I-CT7 被架空（每次 repair 一下就过，闸门白做）。方案必须满足：

- 强制 `--reason`；强制 PM 显式认定（"这个 task 的 work 真实完成"）。
- 修复事件带永久可辨标记（如 `"repaired": true` + retroactive note）—— 事件流里一眼看出是事后补的、不是运行时发的。
- 大声留痕（stderr 警示，可选独立 audit log）。
- **收窄能力面**：只允许补"已知合法缺口"（首选：补一条 `execution_manual_completed`），不做任意事件合成。允许集合在 §1 定。
- 适用窗口：仅 close-task 审计 BLOCK、task 尚未 merge 时（merge 后无审计可修）。

**reason 可见性**（codex finding 5）：修复理由除进 event note，方案需评估是否也写进 task 文档 section —— 事件流会被 close-task 归档 / 清理，PM 日后翻 task 文件应看得到。

**codex outside-voice 的 6 条 reopen 复杂度在乙 下基本消解**（佐证选乙正确）：

| codex 点（原针对甲 / reopen）| 乙 下 |
|---|---|
| ① epoch 语义 / ② I-CT8 基线 / ⑥ reopen 后旧完成条件失效 | **MOOT** —— 乙 不回退状态、无第二 epoch |
| ④ task 文件 split-brain | **MOOT** —— 乙 改事件流 jsonl（单一位置 `.runs/`），不碰 task `.md` |
| ③ close-task 失败窗口 | **简化** —— 乙 只在 pre-merge 审计 BLOCK 窗口用 |
| ⑤ reason 可见性 | **仍相关** —— 见上 |
