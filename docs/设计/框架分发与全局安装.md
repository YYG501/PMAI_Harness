## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

### §0.1 痛点（1-3 句）

PM 起新消费仓时必须 `cd ~/Projects/PM-AI-Workflow`（生成器仓）才能跑 `/init-project`——把"框架开发仓"和"消费仓启动器"两个角色塞进同一个仓库。心智模型反直觉、不可分发给他人、框架仓 dirty working tree 时还要兼任 launcher，状态管理混乱。

### §0.2 触发场景

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | PM 想在桌面任意位置起新消费仓时不知道入口 | 2026-05-26 PM 对话："我要新开一个消费仓，怎么处理" → AI 回"先 cd PM-AI-Workflow 跑 /init-project" → PM 回"感觉整体不合理" |
| 2 | 一次性 `init-project.sh` 假设 `cwd = 生成器仓`，跨机器 / 跨人不可用 | `scripts/init-project.sh` 硬依赖相对路径找 `templates/scripts/skills/agents/` |
| 3 | 框架仓 working tree dirty（PM 正在改框架）时不应当兼任 launcher | 当前无机制阻止；PM 操作纪律承担风险 |
| 4 | 已有消费仓（example-consumer-app 等）升级框架靠 `框架同步-SOP.md` 手动 rsync 4 块，错漏率高 | 2026-05-08 / 05-10 两次实战均踩坑（参见 `框架同步-SOP.md` §5 实战记录）|

### §0.3 根因

生成器仓与消费仓启动器**物理路径强耦合**——`/init-project` skill 只能通过 `cwd = 生成器仓` 被 Claude Code 识别加载；`init-project.sh` 通过相对路径找模板源。两层共同绑死了"入口位置"。

参照对比：GSD 是 npm 包形态，源代码住 `~/gstack/`，通过 `~/.claude/skills/gstack-*` symlink 注册到 Claude Code 全局——**源代码位置和入口位置完全解耦**。

### §0.4 不解决什么

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 跨语言 / 跨平台分发（Windows / Linux）| PM 单人 Mac，本设计只解 Mac；其他平台未来需求触发 |
| 2 | 多用户 / 团队场景下的权限隔离 | 框架定位单人工具（[[GSD-参考调研]] §一），不为团队 SOP 设计 |
| 3 | 消费仓 `.claude/` 副本完全淘汰 | gstack 留了 `--local` 模式做向后兼容；本设计保留同样退路 |
| 4 | 公共 registry 发布（npm publish / brew tap）| 不属于"装到本机"环节，未来对外推广再说 |
| 5 | 框架内部资产的版本兼容矩阵 | 当前仓 + 消费仓基本同步推进，不存在大版本分叉 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**（除非 PM 显式接受拉进 §0）

## §1 候选方案对比

PM 起新消费仓的入口形态，3 个候选：

| 模式 | 怎么用 | 工作量 | 直观度 |
|---|---|---|---|
| **A. 全局安装 + 任意位置 init** | `pmai install` 装到 `~/.pmai/` → 任意 cwd 跑 `/init-project` 或 `pmai init <dir>` | 中（参考 gstack 几乎现成）| 高 |
| **B. install.sh 一行拉到目标目录** | `cd <new-dir>` → `curl <url>/install.sh \| bash` → cwd 加载 skill 跑 `/init-project` | 中（要托管 install 脚本 + 升级机制）| 中 |
| **C. 当前 hack（cd 框架仓）** | `cd ~/Projects/PM-AI-Workflow` → `/init-project` | 0 | 低（PM 当前痛点）|

**推荐 A**。理由：gstack 实战已验证全套机制可行（见 §2 POC），工作量比想象的小；B 模式要解决脚本托管 / 升级通道与 A 几乎一样的问题，不如直接 A；C 不解决根因。

| 层 | 物理位置 | 角色 |

| 卸载脚本 | `gstack-uninstall`（清单明确）| 干净卸载 |

## §3 A 路线技术架构（参考 gstack）

### §3.1 物理布局

```
~/.pmai/                                 # 源代码（独立 git clone PM-AI-Workflow）
├── scripts/                            # 框架脚本（原 PM-AI-Workflow/scripts/）
├── skills/                             # 框架 skill（原 PM-AI-Workflow/skills/）
├── templates/                          # 模板源
├── agents/                             # 自定义 subagent
├── hooks/                              # hook 脚本
├── bin/
│   ├── pmai                            # 主 CLI 入口
│   ├── pmai-install
│   ├── pmai-upgrade
│   └── pmai-uninstall
└── VERSION                             # 版本号

~/.claude/skills/                       # Claude Code 全局 skill 目录
├── init-project       → symlink to ~/.pmai/skills/init-project
├── new-req            → symlink to ~/.pmai/skills/new-req
└── ...                                 # 19 个 skill 全部 symlink

~/.claude/settings.json                 # 全局 hook 注册（绝对路径指向 ~/.pmai/hooks/）

~/.pmai-state/                          # 全局状态（如果需要；当前框架几乎无全局状态，可能跳过）
```

**消费仓内（默认模式）**：

```
<consumer>/
├── .claude/
│   ├── settings.json                   # 项目级 hook 注册（指向 ~/.pmai/hooks/ 绝对路径）
│   └── （不再需要 scripts/skills/agents/ 副本，依赖全局）
├── docs/PROJECT.md
├── docs/DESIGN.md
├── docs/ROADMAP.md
├── templates/                          # 业务实例的模板（如果需要）
└── .framework-sync-state.json          # 记 ~/.pmai/ 版本号（替代 generator_sha）
```

**消费仓内（`--local` 兼容模式）**：保留 `.claude/scripts/skills/agents/` 实体副本（现状）；用 `pmai sync` 从 `~/.pmai/` 拷贝过去。给现有消费仓 / 团队场景留退路。

### §3.2 CLI 入口

```bash
pmai install              # 首次安装（git clone + symlink + PATH 提示）
pmai upgrade              # cd ~/.pmai && git pull && pmai install --relink
pmai uninstall            # 清理 symlink + 状态（参考 gstack-uninstall）
pmai init <target-dir>    # 在 target-dir 初始化新消费仓（取代当前 init-project.sh）
pmai sync <consumer>      # 同步框架到消费仓（取代 框架同步-SOP.md）—— --local 模式才需要
pmai status               # 显示当前安装版本 + 消费仓 link 状态
```

或者：保留 Claude Code `/init-project` skill 作为入口（不引入 `pmai` 命令），全局 skill 内部用 `$PMAI_HOME=~/.pmai` 找模板源。轻量得多。

**§7.1 待 PM 决策**：要不要 CLI 命令，还是只走 skill。

### §3.3 `init-project.sh` 改造

当前：

```bash
# scripts/init-project.sh 现状（假设 cwd = 生成器仓）
cp -r templates/ "$TARGET_DIR/templates/"
cp -r scripts/ "$TARGET_DIR/.claude/scripts/"
...
```

改造后：

```bash
# 改读 PMAI_HOME（symlink 模式默认 ~/.pmai/）
PMAI_HOME="${PMAI_HOME:-$HOME/.pmai}"
cp -r "$PMAI_HOME/templates/" "$TARGET_DIR/templates/"
# .claude/scripts/skills/agents/ 不再拷贝实体，改 symlink 或省略（依赖全局）
ln -s "$PMAI_HOME/scripts" "$TARGET_DIR/.claude/scripts"
ln -s "$PMAI_HOME/skills"  "$TARGET_DIR/.claude/skills"
ln -s "$PMAI_HOME/agents"  "$TARGET_DIR/.claude/agents"
```

**§7.2 待 PM 决策**：消费仓 `.claude/scripts/skills/agents/` 是 symlink 还是实体副本？symlink 更轻但跟现有消费仓不兼容；实体副本兼容但要 `pmai sync` 维护。

## §5 现有消费仓迁移策略（最痛环节）

现状：example-consumer-app 等消费仓**自带** `.claude/scripts/skills/agents/` 完整实体副本，跟全局 `~/.pmai/` 形成双份维护。

**3 个候选迁移策略**：

| 策略 | 做法 | Pros | Cons |
|---|---|---|---|
| **5.1 切 symlink** | 删消费仓 `.claude/scripts/skills/agents/` 实体 → 全部 symlink 到 `~/.pmai/` | 一份维护；升级自动 | 消费仓 git 历史看不到框架代码；其他人 clone 该消费仓时打不开 |
| **5.2 保留实体 + `pmai sync` 维护** | 实体副本保留（`--local` 模式）；用 `pmai sync` 推送框架升级 | git 历史完整；clone 即用；跟现状几乎兼容 | 双份维护痛点没消除（只是工具化）|
| **5.3 混合：新仓 symlink + 老仓保留** | 新消费仓默认 symlink；example-consumer-app 等老仓继续 `pmai sync` | 老仓零迁移成本 | 长期维护两种模式 |

**推荐 5.3 混合**：example-consumer-app 当前正在跑 active req（不能动），保留 `--local`；未来新起的消费仓默认 symlink；存量消费仓在合适时机（无 active req 时）切 symlink。

**§7.3 待 PM 决策**：迁移策略选哪个？
