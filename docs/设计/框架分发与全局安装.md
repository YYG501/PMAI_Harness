## §0 原始痛点（PM + AI 共写，后续 review **不可反向修改**）

### §0.1 痛点（1-3 句）

PM 起新消费仓时必须 `cd ~/Projects/PM-AI-Workflow`（生成器仓）才能跑 `/pmai-init-project`——把"框架开发仓"和"消费仓启动器"两个角色塞进同一个仓库。心智模型反直觉、不可分发给他人、框架仓 dirty working tree 时还要兼任 launcher，状态管理混乱。

### §0.2 触发场景

| # | 场景描述 | 实证证据 |
|---|---|---|
| 1 | PM 想在桌面任意位置起新消费仓时不知道入口 | 2026-05-26 PM 对话："我要新开一个消费仓，怎么处理" → AI 回"先 cd PM-AI-Workflow 跑 /pmai-init-project" → PM 回"感觉整体不合理" |
| 2 | 一次性 `init-project.sh` 假设 `cwd = 生成器仓`，跨机器 / 跨人不可用 | `scripts/init-project.sh` 硬依赖相对路径找 `templates/scripts/skills/agents/` |
| 3 | 框架仓 working tree dirty（PM 正在改框架）时不应当兼任 launcher | 当前无机制阻止；PM 操作纪律承担风险 |
| 4 | 已有消费仓（example-consumer-app 等）升级框架靠 `框架同步-SOP.md` 手动 rsync 4 块，错漏率高 | 2026-05-08 / 05-10 两次实战均踩坑（参见 `框架同步-SOP.md` §5 实战记录）|

### §0.3 根因

生成器仓与消费仓启动器**物理路径强耦合**——`/pmai-init-project` skill 只能通过 `cwd = 生成器仓` 被 Claude Code 识别加载；`init-project.sh` 通过相对路径找模板源。两层共同绑死了"入口位置"。

参照对比：GSD 是 npm 包形态，源代码住 `~/gstack/`，通过 `~/.claude/skills/gstack-*` symlink 注册到 Claude Code 全局——**源代码位置和入口位置完全解耦**。

### §0.4 不解决什么

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 跨语言 / 跨平台分发（Windows / Linux）| PM 单人 Mac，本设计只解 Mac；其他平台未来需求触发 |
| 2 | 多用户 / 团队场景下的权限隔离 | 框架定位单人工具（[[GSD-参考调研]] §一），不为团队 SOP 设计 |
| 3 | 消费仓 `.claude/` 副本完全淘汰 | gstack 留了 `--local` 模式做向后兼容；本设计保留同样退路 |
| 4 | 公共 registry 发布（npm publish / brew tap）| 不属于"装到本机"环节，未来对外推广再说 |
| 5 | 框架内部资产的版本兼容矩阵 | 当前仓 + 消费仓基本同步推进，不存在大版本分叉 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**（除非 PM 显式接受拉进 §0）

## §1 候选方案对比

PM 起新消费仓的入口形态，3 个候选：

| 模式 | 怎么用 | 工作量 | 直观度 |
|---|---|---|---|
| **A. 全局安装 + 任意位置 init** | `pmai install` 装到 `~/.pmai/` → 任意 cwd 跑 `/pmai-init-project` 或 `pmai init <dir>` | 中（参考 gstack 几乎现成）| 高 |
| **B. install.sh 一行拉到目标目录** | `cd <new-dir>` → `curl <url>/install.sh \| bash` → cwd 加载 skill 跑 `/pmai-init-project` | 中（要托管 install 脚本 + 升级机制）| 中 |
| **C. 当前 hack（cd 框架仓）** | `cd ~/Projects/PM-AI-Workflow` → `/pmai-init-project` | 0 | 低（PM 当前痛点）|

**推荐 A**。理由：gstack 实战已验证全套机制可行（见 §2 POC），工作量比想象的小；B 模式要解决脚本托管 / 升级通道与 A 几乎一样的问题，不如直接 A；C 不解决根因。

## §3 A 路线技术架构（参考 gstack）

### §3.1 物理布局

```
~/.pmai/                                 # 源代码（独立 git clone PM-AI-Workflow）
├── scripts/                            # 框架脚本（原 PM-AI-Workflow/scripts/）
├── skills/                             # 框架 skill（原 PM-AI-Workflow/skills/）
├── templates/                          # 模板源
├── agents/                             # 自定义 subagent
├── hooks/                              # hook 脚本
├── bin/
│   ├── pmai                            # 主 CLI 入口
│   ├── pmai-install
│   ├── pmai-upgrade
│   └── pmai-uninstall
└── VERSION                             # 版本号

~/.claude/skills/                       # Claude Code 全局 skill 目录（19 skill 全 pmai- 前缀，review F-ARCH-2）
├── pmai-init-project   → symlink to ~/.pmai/skills/init-project
├── pmai-new-req        → symlink to ~/.pmai/skills/new-req
└── ...                                 # 19 个 skill 全部 symlink，pmai- 前缀

# 注：~/.claude/settings.json 全局 hook **不注册** PM-AI-Workflow 的 hook（review F-ARCH-1 决议）。
# 消费仓 .claude/settings.json 自己写绝对路径指 ~/.pmai/hooks/，避免污染用户其他项目。
```

**Skill 暴露范围（2 种安装模式，砍掉中间态 v1.1 简化）**：

```
模式 1：default（全局）
  pmai install
  └── git clone <remote> ~/.pmai/
      └── 建 ~/.claude/skills/pmai-* symlink（所有项目都能调 /pmai-*）

模式 2：--local <dir>（项目自带完整副本，无全局依赖）
  pmai install --local ~/Desktop/Projects/some-project
  └── 不依赖 ~/.pmai/
      └── 拷实体到 <dir>/.claude/{scripts,skills,agents}/  ← 实体进项目
       <dir>/.claude/skills/pmai-* 只在该项目可调
       适用：clone 到没装 pmai 的机器；兼容现有消费仓（example-consumer-app 现状）
```

**为什么不要中间态**（v1.1 砍掉 v1 设计的 `--project` flag）：
- 原 `--project`（框架在 `~/.pmai/` + 项目级 symlink）= 优雅的中间态，但 PM 心智多一档
- PM 当前实战只有 example-consumer-app 一个真消费仓，不会出现"5 个项目都要框架但只 2 个暴露 skill"的场景
- 砍后心智：**全局共享 = default；任何例外 = --local**
- 未来真需要"框架共享 + 限制 skill 暴露"时加 `--project` 回来不破坏 backward compat

**消费仓内（默认全局模式）**：

```
<consumer>/
├── .claude/
│   ├── settings.json                   # 项目级 hook 注册（指向 ~/.pmai/hooks/ 绝对路径，review F-ARCH-1）
│   └── （不再需要 scripts/skills/agents/ 副本，依赖 ~/.claude/skills/pmai-* 全局 symlink）
├── docs/PROJECT.md
├── docs/DESIGN.md
├── docs/ROADMAP.md
├── templates/                          # 业务实例的模板（如果需要）
└── .framework-sync-state.json          # 记 ~/.pmai/ 版本号（schema_version=2 加 pmai_version 字段，保留 generator_sha 兼容，review F-ARCH-4）
```

**消费仓内（`--local` 兼容模式）**：保留 `.claude/scripts/skills/agents/` 实体副本（现状）；将来 T3 `pmai sync` 维护（**T3/T5 PM 2026-05-26 决议暂缓**）。给现有消费仓 / clone 到其他机器场景留退路。

### §3.2 CLI 入口（命令清单 + flag 完整列表）

PM 决议 §7.1：**CLI 命令体系**（与 Claude Code skill 互补；CLI 给 PM 一次性操作，skill 给 Claude Code 内交互流）。

```bash
# === 安装 / 卸载 ===
pmai install                              # 默认全局：git clone → ~/.pmai/ + ~/.claude/skills/pmai-* symlink
pmai install --local <dir>                # 不依赖 ~/.pmai/，<dir> 自带实体副本（兼容老消费仓 / clone 场景）
pmai uninstall                            # 清 ~/.pmai/ + ~/.claude/skills/pmai-* + 所有 --local 项目副本
pmai uninstall --force                    # 跳确认
pmai uninstall --local <dir>              # 只清 <dir> 的实体副本，~/.pmai/ 全局不动

# === 升级 / 版本（档 2：VERSION + git tag）===
pmai upgrade                              # cd ~/.pmai && git pull origin main（默认吃 main 最新）
pmai upgrade --stable                     # 跳到最新 git tag（PM 打的稳定标记）
pmai upgrade --to v0.3.0                  # 跳到指定 tag（回滚 / 锁定特定版本）
pmai update-check                         # 比对本地 VERSION vs 远程最新 tag，过期提示（≥ 7 天）

# === 状态 / 诊断 ===
pmai status                               # 当前安装模式 + VERSION + main HEAD diff + skill 链接清单
pmai doctor                               # 完整性自检（兜底 §8 critical gaps，详 §3.4 + T6）

# === 消费仓 init（取代 scripts/init-project.sh）===
pmai init <target-dir>                    # 任意 cwd 调用，等价 /pmai-init-project skill 的 bash 路径

# === 同步（T3 暂缓，PM 5/26 决议）===
# pmai sync <consumer>                    # 把 ~/.pmai/ 内容推到消费仓 .claude/（--local 模式用）
# pmai migrate <consumer>                 # 现有消费仓从实体副本切 symlink（5.3 混合策略）
```

**主 dispatcher 设计**：`bin/pmai` 是主入口，路由到 `bin/pmai-install` / `bin/pmai-upgrade` / 等子脚本。`pmai --help` 列子命令；`pmai --version` 读 `VERSION` 文件。这跟 git / gstack 一致（`git status` 实际跑 `git-status`）。

### §3.3 `init-project.sh` 改造

当前：

```bash
# scripts/init-project.sh 现状（假设 cwd = 生成器仓）
cp -r templates/ "$TARGET_DIR/templates/"
cp -r scripts/ "$TARGET_DIR/.claude/scripts/"
...
```

改造后：

```bash
# 改读 PMAI_HOME（symlink 模式默认 ~/.pmai/）
PMAI_HOME="${PMAI_HOME:-$HOME/.pmai}"
cp -r "$PMAI_HOME/templates/" "$TARGET_DIR/templates/"
# .claude/scripts/skills/agents/ 不再拷贝实体，改 symlink 或省略（依赖全局）
ln -s "$PMAI_HOME/scripts" "$TARGET_DIR/.claude/scripts"
ln -s "$PMAI_HOME/skills"  "$TARGET_DIR/.claude/skills"
ln -s "$PMAI_HOME/agents"  "$TARGET_DIR/.claude/agents"
```

**§7.2 决议**：双模式可配（default symlink 全局；可选 `--local` 实体副本）。default 走 symlink，老消费仓兼容用 `--local`。

### §3.4 版本管理（档 2：VERSION + git tag + update-check）

PM 决议：起步采用档 2（VERSION 文件 + git tag），不打 GitHub Release 仪式。

**版本号源**：

```
~/Desktop/Projects/PM-AI-Workflow/VERSION    ← 文本文件存当前版本号，如 "0.1.0"
~/.pmai/VERSION                              ← clone 后跟随
```

**PM 工作流**（手动打 tag）：

```bash
# 在本仓做了一批改动 + commit，觉得是 stable baseline 时：
cd ~/Desktop/Projects/PM-AI-Workflow
echo "0.2.0" > VERSION         # 改版本号
git add VERSION
git commit -m "release: v0.2.0 — <一行摘要>"
git tag v0.2.0
git push origin main --tags    # tag + commit 一起推
```

**消费方升级路径**：

```bash
pmai upgrade                   # 默认吃 main 最新（不锁 tag，跟 PM 开发节奏）
pmai upgrade --stable          # 跳到 latest tag（PM 打过的最新 stable）
pmai upgrade --to v0.1.0       # 锁定指定版本（回滚 / 固定某 baseline）
```

**`pmai update-check` 行为**（参考 `~/gstack/bin/gstack-update-check`）：

```bash
LOCAL_VER=$(cat ~/.pmai/VERSION)
REMOTE_VER=$(git -C ~/.pmai ls-remote --tags origin | grep -oE 'v[0-9.]+$' | sort -V | tail -1)
if [ "$LOCAL_VER" != "${REMOTE_VER#v}" ]; then
  echo "UPGRADE_AVAILABLE $LOCAL_VER → $REMOTE_VER"
fi
```

**何时升档 3（GitHub Release）**：

- 对外有第二人用框架 → 需要 release notes 仪式
- CHANGELOG.md 内容已经稳定到能当 release notes 模板
- 现在 PM 单人 + 密集迭代，**不升**

**版本号语义**（标准 semver 但精简）：

| 改动类型 | bump | 例子 |
|---|---|---|
| 砍掉 skill / 改了消费仓不兼容的 schema | major (1.x.0 → 2.0.0) | task 文件格式重构 |
| 新增 skill / 新增 hook / 重大新机制 | minor (0.1.0 → 0.2.0) | 框架分发与全局安装本设计 |
| bugfix / 文档 / 小补丁 | patch (0.1.0 → 0.1.1) | hook 路径 typo 修 |

起步：`VERSION = "0.1.0"`（本设计实施完成后打 `v0.1.0` 作为框架分发与全局安装的 baseline）。

## §5 现有消费仓迁移策略（最痛环节）

| **5.1 切 symlink** | 删消费仓 `.claude/scripts/skills/agents/` 实体 → 全部 symlink 到 `~/.pmai/` | 一份维护；升级自动 | 消费仓 git 历史看不到框架代码；其他人 clone 该消费仓时打不开 |
