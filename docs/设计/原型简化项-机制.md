### §0.1 痛点（1-3 句）

task spec 既要描述**原型实际行为**，又要承载「原型故意不做、但真实产品要做」的**需求意图** —— 框架没给后者一个结构位，只能把它塞进 §🎯 决策 / §📋 功能清单的正文，再加「需求层意图见…」旁注。同一条边界因此在 5-6 处复述，简化时漏改一处就自相矛盾。

| # | 场景描述 | 实证证据（消费仓 req / commit）|
|---|---|---|
| 1 | task spec 同一条边界多处复述，简化时漏改一处 → 自相矛盾 | ExampleConsumerApp `req-007-login-entry-rework` / `task-002-product-deeplink-ops-login.md`：§📋 功能清单（line 219）「外部地址拒绝 → 回该产品首页」与 §🎯 决策 #2 / §🚦 #7 / §📓 速查 / §✅ 验收 / §🧪 流程 3（共 5 处）+ `.engineering.md` 全文「→ 回工作台」直接打架 |

| 3 | "原型不做、但真实产品要做"的条目无渠道传到 stage 6 的 req PRD | `solution.md` stage 3 已闭合；stage 5 写 task spec 时才发现的简化项无处可放，回写 solution 是自指坑 |

**没填实证证据的场景标 `[ASSUMED]`，后续过滤时优先 DEFER**。（本节 3 条均有实证）

### §0.3 根因（解决什么底层 mechanism）

task spec（stage 5，**搭原型**用）与 req PRD（stage 6，给研发**做真实产品**用）是两个目的、两个受众的文档。「原型故意做得比真实需求少」的条目，正是这两份文档的 **delta**。框架从未给这个 delta 一个结构化归属 —— 它只能寄生在 task spec 正文里，与原型行为描述混写，于是出现「一处描述原型、一处描述需求、再用旁注互相打补丁」的局面。

### §0.4 不解决什么（显式列衍生场景 / 假设场景，防 review 把这些拉进来）

| # | 衍生 / 假设场景 | 为什么不在 §0 范围 |
|---|---|---|
| 1 | 算法自动识别"哪些是简化项" | 靠 task 作者主动登记；自动扫描误报率高（参 memory `judgment-pattern-not-mechanization`）|
| 2 | 把简化项回写 `solution.md` | solution stage 3 已闭合，回写闭合基准 = 自指坑（memory `reconcile-no-self-reference`）|
| 3 | 改 `req-prd.md.tmpl` 章节结构 | 模板是给研发的成品格式（`PRD-体系收敛.md` §0.4.2 已锁"不改模板"）；本方案只加 `/prd-writing` 的读取逻辑 |
| 4 | "原型做得比真实需求多"的反向场景 | 原型是真实需求的子集，反向场景不存在 |
| 5 | 与 §📁 历史档案「业务层偏差」段合并 | 「业务层偏差」是"task 实证发现 req/项目文档**写错了**需修订"；原型简化项是"**故意**做少了"，性质不同，不合并 |

→ **review 中任何 finding 指向以上场景的，默认 DEFER**（除非 PM 显式接受拉进 §0）

## §1 方案概述

task spec 新增一个固定段 `## 🔻 原型简化项`：每条登记「真实需求 / 原型简化为什么 / 为什么简化」。task spec 正文（§🎯 决策、§📋 功能清单、§✅ 验收、§🧪 自测）从此**只写原型实际行为**，所有「需求层意图见…」旁注收进这个段。`/prd-writing`（stage 6）读所有 task 的 🔻 段，让 req PRD 写**真实需求**、并在受影响的功能行标注原型简化。

一句话归属规则：

| 内容 | 归属 |
|---|---|
| 原型实际行为 | task spec 正文 |
| 真实需求（stage 3 就知道的）| `solution.md` |
| 真实需求（stage 5 写 task spec 时才发现要简化的）| task spec `## 🔻 原型简化项` |
| 给研发的真实需求 + 原型差异标注 | req PRD（`/prd-writing` 在 stage 6 汇总）|

效果：边界**一处声明** → 不再自相矛盾；**每个 task 都有这个段** → 通用；它同时是 stage 5 发现 → stage 6 写 PRD 的**传递通道**。

### §2.1 `## 🔻 原型简化项` 段格式

**位置**：`templates/task.md.tmpl` 中 §📦 范围 之后、§✅ 验收清单 之前（都属"边界"语义；PM 可调整）。

**格式**：

```markdown
## 🔻 原型简化项

> 本 task 原型故意做得比真实需求少的地方。每条登记后，正文（决策/功能清单/验收/自测）
> 只描述原型行为；真实需求由 /prd-writing 在 stage 6 收进 req PRD。
> 本 task 无简化项则写"无"。

### 简化项 1 · <一句话标题>

- **真实需求**：<完整的真实产品行为>（已在 solution 的写「见 solution.md §🎯 #N」，不复制原文）
- **原型简化为**：<原型实际做什么>
- **为什么简化**：<原因>
```

**填 task-002 后长这样**（示例，非本设计交付物）：

```markdown
### 简化项 1 · 外部地址 redirect 拒绝后的回跳目标

- **真实需求**：redirect 解析失败时，按 rawRedirect 内识别的产品标识降级到该产品首页（见 solution.md §🎯 #7）
- **原型简化为**：解析不到当前租户内有效页面时，一律回工作台
- **为什么简化**：纯外部地址里没有产品标识可恢复；按产品标识降级需要 redirect 链额外携带产品上下文，原型阶段不做
```

### §2.2 `/prd-writing` 改动

1. 输入清单增加：读本 req 下所有 task spec 的 `## 🔻 原型简化项` 段
2. req PRD §六功能需求 / §七验收按 **真实需求** 写（不继承原型简化行为）
3. 受影响的功能行，在「需求描述」末尾加一句轻量标注：`（原型 v<N> 暂简化为：<原型行为>）`，让研发知道原型与 PRD 的差异点
4. 不改 `req-prd.md.tmpl`；以上是 skill 话术 / 规则层改动

## §5 风险与待验

### §5.1 task 作者漏登记 🔻 段

**风险**：有简化决策但忘了填 🔻 段 → 简化项漏入 PRD，研发拿到的是原型行为而非真实需求。

**缓解**：`task-spec` skill 引导（vp-2）是主防线。

**待验**：是否需要一条 lint —— task spec 正文出现「暂不 / 简化 / 原型层 / 需求层意图」等词、但 🔻 段为「无」时提示。**v0 先不上**（误报风险，参 memory `judgment-pattern-not-mechanization`）；消费仓真实跑几个 req 后看漏登记频率再定。

### §5.2 段名 `🔻 原型简化项` 待 PM 确认

「简化」是否准确 —— 也包含"原型完全不做该场景"。备选：`原型未覆盖项` / `原型与 PRD 差异`。PM 锁 §0 时一并定。

### §5.3 🔻 段与 solution.md 的引用关系

🔻 段的「真实需求」字段，已在 solution 的**只引用 §N 不复制原文**，避免双写漂移。stage 5 才发现的则原文写在 🔻 段，由 PRD 兜底 —— 这种条目 solution.md 里没有，不构成双写。
