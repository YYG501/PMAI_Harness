## 一、工作方法论（内核）

从两边实战反复验证、**跨需求类型都成立**的核心原则。每条说清：是什么、为什么是内核、适用边界——边界尤其重要，上次的错就是没标边界。

### 内核 1 · 对抗三问：任何"简化/合并/dormant"的强制自检
**是什么**：每做一个减法决策，当场答三问——(a) 丢了什么 (b) 对所有需求类型都成立吗 (c) 是不是把内核当仪式砍了。答不全不许落盘。配**对称判别尺**：砍掉后"补丁消失/流程更顺/能力不减"=仪式税（砍对）；砍掉后"能力消失"=内核（别砍）。
**为什么是内核**：这正是 reshape 全程缺的那一步。要写进每个减法决策本身——像 supersede 一样在 decisions 里留三行自答。
**适用边界**：覆盖所有 dormant/合并/collapse/迁移。正面对照——7-stage 流水线、逐层转写链、task 状态机、requirements/ 目录树、工程双合同，这些 dormant 是**对的**（砍掉补丁消失、能力不减），别因矫枉过正捞回来。判别尺两边都要用。

### 内核 2 · 先懂问题再设计：探索⊥信息设计是两个正交阶段
**是什么**："要解决什么真问题"（探索）和"怎么把信息摆清楚"（信息设计）是两件事，前者必须在后者之前独立做完。探索不是问"谁看"，是问"这需求是不是伪需求、现状怎么凑合的、有没有更简的路、方案背后真正的痛点是什么"。
**为什么是内核**：ExampleAgentProject 反复踩的坑（待办"去删除机制"、"通知与待办分家"）全是**方向错了，信息设计得再精致也是把错的东西做精致**。对单 PM 内部产品，最贵的不是建错原型，是建了根本不该做的功能；单 PM 没有真实用户、没有同事 review，**探索段是他唯一的外部对抗源**，砍掉=在回音壁里裸奔。
**适用边界**：所有需求都该过探索，但**深度自适应**（内核 6）。形态借 office-hours 的诊断内核（反拍马屁/逼到具体/push once then again/现状是真竞品/给方向选项+代价），但**砍掉依赖外部 demand 的三问**（有人掏钱吗/哪个客户被炒鱿鱼/坐用户后面看过吗）——单 PM 内部产品问不出真答案，强问只会逼 PM 编。

### 内核 3 · 派生信息 4 环：唯一真正跨类型的设计抽象
**是什么**：每类 AI 派生/计算信息过四环——**①来源**（录入/引用/计算三分，只标"计算"不给逻辑=没说清）→**②生成**（复合/AI判定要写出完整可落 prompt）→**③变更**（人发现不对怎么定位根因层）→**④重算影响**（人工拍过的 AI 不许静默覆盖）。
**为什么是内核**：ExampleAgentProject 趟出来、框架自认"以前最薄、最值钱"的一步。硬证：它**不是 UI 专属**——grep 商机专家AgentV2/spec.md，"触发/重算"出现 47 次，整份规格围绕③④环组织。
**适用边界**：**从"§六信息密集才写"提级到"真通用内核"**。上次把它挂"信息密集才写"是错位——纯后端 Agent 没有信息密集卡反而可省，但 Agent 最需要的恰恰是"何时重算/人改完会不会被盖"。

### 内核 4 · 根因优先：补丁消失是设计正确的最强信号
**是什么**：PM 说"不对/不合理/没明白"就立刻停、回信息模型重想，**绝不在表面加提示文字打补丁**。判据：方向改对了，**伴生复杂度会消失而不是再加一层**。
**为什么是内核**：全局最高铁律，也是 ExampleAgentProject 挖出"去删除机制""通知与待办分家"的方法。元用法——**reshape 病本身就是它的反例**：用"深度自适应护栏（运行时临场判断）"去盖"方法论结构性偏 UI"这个根因，正是在症状上打补丁。根因是"没有按类型分流的方法库"，正解是重建分类层，不是加运行时开关。
**适用边界**：贯穿探索/设计/收口全程，无例外。

### 内核 5 · 真相源治理 + 三件套零重叠：一块内容只有一个出处
**是什么**：discussion（收集信息+未决，含本需求相关现状切片）/ decisions（结论+为什么+否过什么+supersede 留痕）/ spec（唯一真相源）三者**维度正交、零重叠**；规格是权威定义、原型只是草稿；事实以文档真相源+inputs 原文为准、代码不是真相源；方法论正本落 _shared 单一真相源。
**为什么是内核**：整个体系的地基。supersede+删除线留痕防返工——能力匹配卡 9 版、待办类型三改靠它记住"为什么否决过这条"。
**适用边界 + 要补的洞**（这条铁律正被 reshape 自己破例，先修自己）：
- **决策落点真相源打架**（high，已核实）：`close/SKILL.md:40` 写"`decision-record.md`/`deposit-routing.md` 仍写旧 docs/decisions/ 落点……遇冲突以本 skill 为准"，而 `decision-record.md` 仍被 5 个 skill 读。"以我为准"是创可贴。**瘦身落地前必须清掉，不能带病交付**。
- **PRODUCT-RULES 双重身份**（high）：既是"活档·随产品演进维护"，又承接"写一次不维护的冻结理路"。一份文档背两个互斥生命周期契约。要么物理分两节写死各自契约，要么理路别折进活档。
- **discussion 读侧断链**（high）：写侧有家，但**下一轮没有任何 skill 读它**。必须给进场场景（最低：重做同模块时 /design 必读自己的 discussion）。

### 内核 6 · 深度自适应：必须有默认档 + 触发器 + 反向逃生阀，不能是口号
**是什么**：跑多深由 AI 提议、PM 拍。风险：现在 `info-design.md` 写"5 问任何需求都过、每问缺一项不算想清楚"，这**激励 AI 求稳走全套**（LLM sycophancy 偏好就是多做多问）。护栏该防过度走流程，文本却激励过度走流程。
**为什么是内核**：整个瘦身防机械化的承重墙。落成"AI 默认走全套求稳"，7 步法就偷偷变回"每需求必跑的硬流程"，要治的病原地复活。空话护栏比没有护栏更危险。
**适用边界 + 补法**：补成可执行三件套——(a) **默认档=轻过**（删掉激励走全套的措辞）；(b) AI 提议拖深必须附**具体理由**+PM 显式同意；(c) **反向逃生阀**："PM 任何时候说别问了直接干→立即降到最轻档"。管设计深度，也管探索段追问、记忆加载深度、mock 要不要出。

### 内核 7 · 隔离与可逆：分档触发，不是每事必隔离
**是什么**：worktree 隔离（真实 build 的并行隔离）和 dormant（保留代码/测试/不变量、默认不用、可激活）都是真资产，但**分档**——讨论/小改在 main 直接动（无 worktree），大需求才开 worktree；用不上的 skill 进 dormant 而非删。
**为什么是内核**：脱离框架后 ExampleAgentProject 丢了 worktree 隔离，11 天工作堆 main 未提交——隔离价值被反向证明。但"每改动都开 worktree"是仪式。dormant 让 28→~7 瘦身不破坏隔离/真相源/三道审/不变量。
**适用边界 + 警告**：**dormant 一个 skill 前必须先核清活跃 skill 对它底层无状态资产的依赖**——/build 仍复用 task 底下的 exec-adapter + build-audits.py，脚本必须可达、锚点从 req-plan.md 改成 spec.md 并参数化敲死。**分档还要推广到读侧**：记忆加载也分档（小改只读模块自己那套，别无条件全量吞 PRODUCT-RULES）。

## 二、工作流（从需求到落地的完整链路）

端到端：**探索 → 设计 →（mock 确认）→ build → close**。核心修正是把 /design 从"步骤2读记忆直接跳步骤3理结构"改成**显式三段式**，物理对齐三件套自然顺序。

```
①探索 ───────────→ ②设计 ──────→（mock 确认）──→ ③写规格 ──→ build ──→ close
对话式诊断          按需求类型选方法   多变体让PM挑     统一灵活骨架  (大需求才走) 沉淀回写
↓产物               ↓产物                            ↓产物
discussion.md       决策上移 decisions              spec.md
(含内部现状切片+     (含"这是X类需求"判定)
 真问题+岔路)
```

### 阶段 ① 探索（reshape 砍没了、现在补回来的一整段）
**干什么**：PM 拿"想要的方案"来，AI 先借 office-hours 式对话诊断还原成"要解决的真问题"。诊断内核：每个回答要表态+说明什么证据能改判（**反拍马屁**，禁"这思路不错/可以考虑"）；逼到具体（要名字/数字/具体后果）；**push once then push again**；**现状是真对手**（逼问"现在不做你怎么凑合的"）；有岔路给 PM 几个方向+代价让选。**砍掉创业三问**。
**深度自适应**：**escape-hatch 优先**——思路清一句话放行，只在闻到"伪需求/方案先行"味才 push。绝不能变成"每次开工被追问三遍"的新仪式。设计窗口很窄：做没了=裸奔，做满=仪式税，两个坑都通向 PM 弃用。
**产物**：`discussion.md`（第一阶段产物）：内部现状整理 + 探索出的真问题 + 排除过哪些岔路 + 外部材料。
**和真相源关系**：内部现状整理**切片化**——只装"为本需求收集/核实的相关现状切片"，明写"全局现状看 PRODUCT-STATE"。探索收尾 AI 必须说一句**"这是 X 类需求，所以打算用 Y 套设计问题"**，PM 拍——**定类型是②的前提，必须在动手理结构之前完成**。

### 阶段 ② 设计（7步法降级为"信息密集类"的工具之一）
**干什么**：按①定的类型选对应方法理清结构。**不再是"一套主干5问+UI特化2问套到所有需求"，而是"一个很小的真通用内核 + 每类一套特化问题集"**。

**真通用内核（只有三条，grep 实证所有类型都成立）**：
1. 真问题/谁因此能做成什么决策（①探索已答）
2. **派生信息 4 环**（提级到这里）
3. 状态别只画正常态（空/计算中/基于旧数据待重算/冲突待澄清/人工已锁定）

**七类需求 + 各配特化问题集**：

| 需求类型 | 特化问题集（除三条通用内核外） | 专属硬自检 |
|---|---|---|
| 信息密集 UI 卡 | 一行原子粒度 + 卡面vs抽屉 + **三身份界面可区分**（三身份归这里、非UI规格0出现） | 卡面是否只答漏斗前1-2层 |
| 多对象管理页 | CRUD 全列 + 列表/详情/批量 + 权限边界 + 空态 | 动作列写全没（别"等操作"） |
| 后端规则 | 触发前置 + 判定（可落prompt）+ 默认值 + 冲突兜底 + 对谁可见 | 判定写得出 prompt 吗 |
| 纯算法 | 输入域与边界 + 判定逻辑（完整prompt）+ 输出精度（档位vs数值、不给假精确）+ 回归怎么验 | 换批数据漂不漂、精度档位定了吗 |
| 业务流程/状态机 | 全状态枚举 + 分支 + 异常路径 + 在场/不在场两套 + 回退 | 异常路径和回退画了吗 |
| Agent/引擎 | 触发时序（攒批/防抖/上限）+ 重算依赖传播 + 人机权威 + 静默还是提醒 + 输出落哪几张卡 | 人改完会被静默盖吗、触发会风暴吗 |
| 数据产物（如报价BOM Excel） | 字段schema/列定义 + 命名规则 + 版本与覆盖策略 + 可信度继承 + 预览即文件不前端重建 | 多版本会互相覆盖吗、字段有真相源吗 |

**为什么这么分**：`info-design.md §八`（写规格阶段）已按"卡片/管理页/Agent/纯算法"四类自适应——它隐约知道对象分多类，却只在最表层（章节排版）落实。**最小改动、最自洽的修法就是把 §八 已有四类补全成七类、前移成"选方法层"分类骨架**，让"理结构问什么"和"写规格§八怎么排"用同一套类型。
**深度自适应**：默认轻过，拖深附理由+PM 拍。**删掉 `info-design.md:23` 的"5问对任何需求成立"**。
**产物**：设计结论上移 `decisions.md`（含"这是X类需求"判定）。

### 阶段 ②.5 mock 确认（降回"可选第三档"，不是信息密集类默认动作）
视觉/布局靠文字掰不清时才调 /mock 借 design-shotgun 出多变体让 PM 挑。**修正**：现在 SKILL 把它写成信息密集类默认动作（"不要省"）是把可选探针默认化、又一笔不随复杂度伸缩的税。对齐 office-hours 收敛原意——视觉变体是"文字/ASCII 掰不清视觉岔路时才上"的可选档。mock 是探索草稿，建 `mocks/`、和 prototype/ 分开，规格不嵌 ASCII 只引用路径。

### 阶段 ③ 写规格（理结构+写骨架+磨文字+冷读，统一在 /design）
**统一灵活骨架=菜单不是死模板**：10 章是菜单、§六信息模型按需、§八核心动作按七类自适应；顶部钉权威声明、不嵌 ASCII、术语 grep 收口。收口三道：磨文字（只动文字不动结构，发现要改结构就停回②）+ subagent 冷读自检 + 一致性扫描（flag 给 PM，不静默吞不自动改）。
**产物**：`spec.md`（唯一真相源）。
**要补的洞**：
- **decisions↔spec 同模块漂移**（medium，最高频返工）：能力匹配卡9版全栽这。`check-state-index-drift.py` 实测只扫顶层、对 modules/ 子文档零覆盖。至少补一条机械检查：同模块 decisions 里被 supersede 的旧口径，grep 确认 spec 已不再出现。
- **spec 正文能否带演进痕迹**（low）：明确 spec 正文=纯最终事实（变更日志一行说改了什么，正文不留删除线/迭代语）；"为什么从A改B"完整留痕只在 decisions.md。消除"就地升版要留痕"和磨文字"只写最终事实"的指令冲突。

### 阶段 build（大需求才走）
对着定稿 spec.md 在 prototype/ 建。**分档**：讨论=改文档；小改=直接改 prototype/（main 无 worktree）；大需求才 /build。建完 review loop + 三道审，merge 回 main。
**并行/worktree/切窗口**：worktree=真实 build 的并行隔离；会话窗口与 worktree 解耦（主窗口 `git -C` 远程改 / 也可副本窗口就地干）；worktree 从 main 拉天然带 spec/PRODUCT/DESIGN；起原型复用 pnpm store + 端口探测错开。
**要补的洞**：
- **锚点悬空先解再放行**（high）：build-audits.py 的 `_range_list()` 锚点参数化（指向 spec.md + 按模块名定 audit-dir），第一次真跑大需求前把"实施时择一"敲死。覆盖审计是防"工具偷丢字段"的承重墙，不能带病上线。
- **决策门别每次问**：build 两道 AskUserQuestion（要不要 worktree / 用什么工具）对单 PM 90% 答案固定，给 settings 可配记忆默认值。

### 阶段 close（沉淀+回写，跨需求记忆"写侧"）
决策/术语回写基线、文档归位、有 worktree 则 merge 回 main、自动 cd 回主仓。
**要补的洞**：
- **跨需求记忆要写读两侧闭环**（medium）：回写侧已做实（决策→decisions/PRODUCT-RULES、术语→PRODUCT.md），但**进场侧 /design 步骤2 不读 TODO（遗留浮出）、不按需读理路**——这俩进场动作躺在已 dormant 的 new-req 里，是 dormant 错依赖。把进场职责迁进 /design 步骤2 加载清单。回写做实了进场没接住=存了不取。

- **探索段真落地**：在 `_shared/` 建一份 req 级诊断真相源（暂名 `req-questioning.md`），从 office-hours 抽诊断内核、砍创业三问。**req-analysis 不继续 dormant 后谎称"并入主干①②"**——要么真激活成探索段调用方，要么明确删除并把诊断内核搬进 req-questioning。当前"认可了但没接"的空位比假并入更危险。
- **discussion 是探索段第一产物**，不是步骤5笔记；给它进场读取通道。

### 该 dormant / 该合并的（对抗三问验证：砍后补丁消失、能力不减）

- **prd-writing/spec-polish 合并进 /design 是对的**，但要给"理结构⊥磨文字"边界加机制。

### 瘦身落地的元风险：清漂移是前置闸门
对单 PM，文档是他认识自己工作流的唯一界面。现在方向真相源（office-hours收敛.md §3 还写"4条入口 init/new-req/next/status"）、不变量（INVARIANTS I-RT2/I-RT5 旧 stage 措辞）、共享方法论（decision-record/deposit-routing 旧 docs/decisions/ 落点）**分别停在三个不同时代版本**，PM 读到自相矛盾的指引会对整套框架失去信任。**瘦身落地前必须把这些对齐到同一版本**——这是"缺陷会不会被 PM 感知"的总闸门。
