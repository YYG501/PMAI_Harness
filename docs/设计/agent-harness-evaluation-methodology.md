# Agent Harness 真实场景评测方法论

> 状态：活跃设计，尚未完整实现。
>
> 适用范围：评测「PMAI Harness + Agent + 宿主」在消费仓中的真实任务效果，不替代现有确定性测试，也不默认监控 PM 正在使用的业务仓。
>
> 本轮实施顺序和验收条件见 [`harness-hardening-execution-plan.md`](./harness-hardening-execution-plan.md)；实际进度和验证结果统一见 [`RUNTIME.md`](../../RUNTIME.md)。

## 1. 为什么需要这一层

传统软件测试主要回答：给定输入后，确定性代码是否产生预期输出。

Agent 工作流需要回答一个更完整的问题：

> 在明确的业务状态下，当 PM 表达某个意图时，Agent 能否稳定理解、正确行动、遵守边界，并把真实消费仓推进到正确终点？

最终结果不是只由模型决定，而是由整套协作系统共同产生：

```text
PM 表达
  x 模型能力
  x Prompt / Skill
  x 工具与权限
  x 消费仓状态和历史
  x Harness 合同与脚本
  x 判定规则
= 真实任务结果
```

因此，评测对象不是一段模型回复，也不是某个独立脚本，而是端到端的人机协作系统。

## 2. 与现有 Harness 的关系

PMAI 需要区分三层验证：

| 层次 | 回答的问题 |
|---|---|
| 确定性测试 | 脚本、合同、状态机和写入护栏本身是否正确 |
| Session eval | Agent 使用这些能力时，真实任务是否成功 |
| Release gate | 当前框架、宿主和模型组合是否达到可发布的稳定程度 |

现有确定性 Harness 擅长证明「不该发生的事情被阻止」，例如越界写入、陈旧证据、错误生命周期和不完整测试摘要。

真实场景评测补充证明「应该发生的事情确实完成」，例如 PM 说「可以提交了」之后，Agent 是否真的完成验收、合入主线和文档同步。

这不是重做现有 Harness，而是为它增加真实效果的观测、评测和发布证明。

## 3. 场景合同

每个真实场景都应被描述为一个业务合同，而不是固定关键词测试。

| 要素 | 要回答的问题 |
|---|---|
| 初始状态 | 任务开始前，消费仓处于什么状态 |
| PM 意图 | PM 真正希望完成什么，不限定唯一说法 |
| 行为边界 | Agent 可以和不可以做什么 |
| 目标结果 | 最终哪些业务事实必须成立 |
| 禁止结果 | 哪些情况即使表面完成也必须失败 |
| 停止条件 | Agent 应继续、等待 PM 还是结束 |

例如「可以提交了」「就这样吧」「这个版本定了」文字不同，但在满足相同前置条件时，可以表达同一个定稿意图。评测应验证意图和结果，不应只匹配某句话。

一个合格场景还必须固定环境身份，包括消费仓基线、初始 commit、框架版本、宿主、模型、权限和超时。没有共同起点的两次运行不可直接比较。

## 4. 真实但可控的消费仓

真实场景评测不应直接在 PM 长期使用的业务仓里做实验，也不应只构造脱离真实目录和合同的玩具环境。

平衡点是：

> 从已有消费仓的固定、脱敏基线创建一次性隔离副本，在副本中运行真实 Agent。

这个环境需要同时满足：

- **代表性**：保留真实消费仓结构、Git、合同、Skill 和生命周期。
- **可重置**：每次运行从同一个已提交基线开始。
- **隔离性**：失败不能污染真实业务仓或其它 case。
- **可追溯**：知道本次运行基于哪个消费仓、commit 和框架版本。
- **可清理**：结束后可安全销毁；失败时只保留必要的脱敏证据。

所谓消费仓 fixture，是已有消费仓状态的可重复测试副本，不是再建设一个长期业务仓。

## 5. 独立观测原则

最重要的原则是：

> 被测 Agent 负责行动，Harness 负责观测；不能只依据 Agent 对自己的描述判定成功。

需要区分三类证据：

| 证据 | 例子 | 用途 |
|---|---|---|
| 表达证据 | Agent 回复、解释和结论 | 判断沟通与意图理解 |
| 过程证据 | 工具事件、命令日志、状态变化 | 判断 Agent 实际采取了什么行动 |
| 结果证据 | Git diff、commit、文件快照、审计产物 | 判断外部世界最终发生了什么 |

Agent 说「已经提交」只能证明它表达了这句话。Harness 必须独立检查 commit、分支关系和最终文件，才能证明提交真实存在。

建议由 Harness 直接采集：

- 运行前后的 Git status、diff、commit graph 和 ancestor 关系。
- 关键合同、正式文档和审计文件的前后快照。
- 测试、构建、浏览器验收、landing 和文档同步的命令日志。
- 宿主原生的工具调用事件和退出状态。
- 生命周期的追加式事件记录，避免最终状态文件清理后丢失过程。

## 6. 事实判定与语义判定

Agent 任务包含两类不同问题，必须分开处理。

### 6.1 确定性事实

机器可以直接验证：

- 文件是否存在，是否只修改批准路径。
- 测试、typecheck 和 build 是否真实通过。
- source hash 与 implementation commit 是否匹配。
- 实现是否真的进入 main。
- 生命周期是否经过允许的状态顺序。
- 文档是否只在 landed 后同步。

这类事实由 Harness 判定，任何失败都不能由 Judge 覆盖。

### 6.2 语义质量

需要结合上下文判断：

- Agent 是否准确理解 PM 意图。
- 是否重复询问已经确认的问题。
- Proposal 是否完整、有判断力，而不是机械填模板。
- 是否把内部命令和状态管理负担转嫁给 PM。
- 最终回复是否准确表达真实结果和剩余问题。

这类问题由独立 Judge 按 rubric 评审。

完整通过条件是：

```text
确定性事实通过
AND
语义质量通过
= 任务通过
```

## 7. Runner 与 Judge 的职责边界

Runner adapter 是 Harness 与具体宿主之间的适配层，负责在指定消费仓副本中启动 Agent、传入 PM 指令、设置权限和超时，并捕获宿主原生事件。

Runner 不负责宣布 case 是否通过，也不应自行生成 Git diff、生命周期和 observations 作为唯一事实来源。

Judge adapter 只读接收场景合同和已经冻结的证据，负责语义判断。Judge 不修改消费仓，也不能推翻确定性失败。

仓内应提供经过 review 和测试的真实 adapter，使其随框架一起版本化。运行时凭证和本机路径可以通过环境提供，但不能沉淀进框架规则。

## 8. 证据绑定与可追溯性

每次运行应形成一份完整证据包，至少回答：

- 测了什么场景。
- 使用了哪个框架和消费仓基线。
- 使用了哪个 Runner、Judge、宿主和模型。
- Agent 实际做了什么。
- 最终状态是什么。
- 依据哪些规则判定。

对 case、adapter、transcript、工具事件、Git diff、文件快照和命令日志分别计算内容 hash，再生成整包 evidence digest。Judge 结果必须绑定同一个 digest。

内容 hash 不能单独证明证据真实。真实性来自 Harness 独立采集；hash 用来证明采集后没有被替换，且发布门、Judge 和事后复盘使用的是同一份证据。

`run_id` 可以继续用于检索运行记录，但两个不同字符串不能证明 Runner 和 Judge 真正独立，也不能替代内容绑定。

## 9. 从单点场景到端到端旅程

优先覆盖用户价值最高、上游影响最大的场景。

### 9.1 Proposal

- 背景不足时提出必要问题，不提前进入模块设计。
- 方向确认后形成完整 Proposal，并同步产品基线。
- 产品方向变化时创建新版本并明确 supersede。
- 只做完整性复核时保持只读，不产生新版本。

### 9.2 Build 与定稿

- 自然语言续接 active build，不重新打开已关闭问题。
- 多轮反馈保持批准范围和 prototype / product 深度。
- PM 定稿后自动完成 final check、landing 和文档同步。
- 中断恢复不重复验收、merge 或文档提交。

### 9.3 完整主链

```text
init
  -> proposal
  -> design
  -> spec-writing
  -> build
  -> PM 多轮反馈
  -> finalize
  -> landed
  -> docs complete
```

完整主链主要验证跨阶段继承：上游决定是否进入下游，已经确认的问题是否被重复打开，最终实现和文档是否仍绑定同一份产品依据。

## 10. 稳定性而不是单次成功

LLM 行为存在随机性，单次通过不能证明能力稳定。评测结果需要从 PASS / FAIL 扩展为：

- 确定性硬门通过率。
- Judge 语义通过率。
- 同一 case 多次运行的成功率和方差。
- 按宿主、模型和版本拆分的变化趋势。
- 时长、token 和费用。
- 失败属于产品行为、Agent 不稳定还是基础设施故障。

评测强度按风险分层：

| 场景 | 建议标准 |
|---|---|
| 越权写入、错误合并、陈旧证据等硬安全场景 | 必须全部通过 |
| Proposal、Build、定稿等核心旅程 | 多次运行并达到预设成功率 |
| 表达质量和轻微步骤差异 | 作为趋势指标和改进输入 |

普通 PR 可以只运行受影响的关键 case；定时回归运行多次；稳定发布运行完整 Golden Path。

## 11. Artifact 与发布治理

每次运行应归档：

- 运行 manifest 与 evidence digest。
- Git patch 和关键文件快照。
- 脱敏 transcript 与工具事件。
- 命令日志和确定性判定结果。
- Judge 结果及其绑定的证据 digest。

发布门应发生在创建稳定版本之前：

```text
候选 commit
  -> 确定性测试
  -> Golden Session eval
  -> 稳定性门槛
  -> 证据归档
  -> 创建 tag / release
```

这样「稳定版本」表达的是已经有证据的质量结论，而不是 tag 创建后才开始验证。

## 12. 使用方式

这层能力不应增加 PM 的日常操作负担。

| 使用场景 | 使用者如何使用 |
|---|---|
| 正常使用 PMAI | 无新增步骤，Session eval 不默认监控真实业务仓 |
| 修改框架 | 运行受影响的单个 case 或 Golden Path |
| 比较宿主 / 模型 | 在相同消费仓基线和 case 上重复运行 |
| 准备稳定发布 | 触发完整 release gate |
| 复现真实问题 | 从真实消费仓创建脱敏隔离快照并重放 |

失败报告应优先说明业务结果，例如「Agent 重复询问合并确认」「实现没有进入 main」「生命周期停在 final_check」，而不是只展示底层协议字段。

## 13. 最小落地顺序

不要一开始建设完整评测平台。先建立一条可信闭环：

1. 选取现有消费仓的脱敏、已提交基线。
2. 先跑通一个高价值场景，例如自然语言定稿。
3. 让 Harness 创建隔离副本并独立采集 Git、文件、命令和生命周期证据。
4. 把确定性事实从 Runner 自报中移出。
5. 提供首个真实 Runner adapter 和只读 Judge adapter。
6. 用内容 hash 绑定整套证据，并增加伪造、篡改和无实际修改的反例测试。
7. 再增加 Proposal、完整主链、重复执行、artifact 归档和正式发布规则。

第一条闭环应满足以下验收条件：

- Runner 声称成功但消费仓没有实际变化时，必须失败。
- Agent 修改禁止路径、使用陈旧依据或停在错误生命周期时，必须失败。
- Judge 没有读取当前证据包或证据被修改时，必须失败。
- 真实完成任务时，可以从证据恢复完整执行事实和判定原因。
- 运行结束后不污染长期消费仓，也不泄露凭证和未脱敏业务数据。

## 14. 方法论总结

一个成熟的 Agent Harness 由六个闭环组成：

> 场景定义、环境控制、独立观测、分层判定、稳定性测量、发布治理。

它最终要证明的不是「Agent 看起来很聪明」，而是：

> 在明确的业务条件下，这套系统能够以可接受的成功率，持续完成 PM 真正关心的任务，并且失败时可发现、可解释、可复现。
