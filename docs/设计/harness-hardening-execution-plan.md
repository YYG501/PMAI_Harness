# PMAI Harness 增强执行计划

> 本文定义实施顺序、交付物和验收条件，不代表功能已经实现或发布。
> 当前批次、验证结果和下一步统一记录在 [`RUNTIME.md`](../../RUNTIME.md)。
> 产品边界以 [`PRODUCT.md`](../../PRODUCT.md) 为准；评测原则沿用 [`agent-harness-evaluation-methodology.md`](./agent-harness-evaluation-methodology.md)，宿主范围沿用 [`host-capability-current-and-target-matrix.md`](./host-capability-current-and-target-matrix.md)。

## 1. 要交付的结果

保留 PMAI 的产品上下文、决定授权、Build 合同、验收与落地主链，完成三个可验证的增强：

1. 宿主或工具发生异常时，框架能正确阻断、解释并保留恢复点。
2. PM 能通过自然语言完成真实产品旅程，同一版本重复执行有独立证据。
3. 日常 Build 发生重复失败或中断时，主控能定位、恢复或形成框架修复交接，PM 不需要整理日志。

在这些证据建立后，再针对实际读取热点优化上下文。整轮不包含底座迁移、通用 Policy Engine、Capability Registry、第二套生命周期、后台监控服务或自动修改已安装框架的机制。

## 2. 分批与依赖

| 批次 | 工作 | 主要交付物 | 进入条件 | 完成标准 |
|---|---|---|---|---|
| H1 | 修护栏异常处理、对齐发布门配置 | 有效的阻断结果、CI 配置与能力预检、明确用例清单 | 核对仓内与安装态基线 | 异常正确阻断；缺少 Runner / Judge 不能通过 |
| H2 | 验证真实宿主能力 | 带版本与证据的宿主验收记录、可解释的降级 | H1 对应护栏修复完成 | 受测宿主能证明工具拦截、角色边界和恢复；未知项明确保留 |
| H3 | 建立真实旅程与重复运行入口 | PM 首轮走查、三类旅程、受约束的多轮驱动与汇总 | 一个真实主控环境通过 H2 | 单次旅程从自然语言进入，跨阶段继承真实产物；驱动不替 Agent 补状态 |
| H4 | 增加 Build 最小诊断与反馈 | 本地诊断记录、两条识别规则、status 摘要、feedback 交接 | H3 首轮暴露的问题与采样点明确 | 能识别、解释、分流；观测失败不改变验收结论 |
| H5 | 重复评测并形成候选发布证据 | 固定组合的重复结果、失败归因、候选 revision 对应报告 | H3/H4 可用，环境和预算明确 | 核心旅程达到下述放行条件；缺失、跳过和救场不得算通过 |
| H6 | 按证据优化上下文 | 一项明确热点的改动及前后对照 | H5 有可比较基线 | 读取成本下降，产品语义、授权和恢复验证不退步 |

默认依次推进 H1 → H2 → H3 → H4 → H5；H6 由测量结果决定是否需要。H1 的 CI 配置修复、H2 的脚本验收、H3 的驱动实现可以分别交付；真实模型或宿主暂不可用时，其验证项保持未完成，不阻塞其它不依赖它的本地工作。

每批按“实现与针对性验证 → 相关完整回归 → 更新证据与 RUNTIME → 按已有授权提交和分发”交付。最终稳定候选需要在同一 revision 上跑发布门，不能拼接不同版本的通过结果。

批次功能验收与提交、CI、发布分开记录。H1 验收护栏异常处理和发布门配置，不以真实模型发布运行作为完成条件；实际宿主拦截与角色恢复由 H2 验证，真实旅程与固定配置重复评测分别由 H3、H5 承担。实际发布仍须满足发布门，不能因 H1 完成而豁免。

## 3. H1：先修护栏异常路径和发布门

### 3.1 开工核对

- 记录 checkout revision、工作区改动、宿主和解释器版本。
- 核对 RUNTIME 中此前版本的提交、远端分发与全局安装待办；仓内完成不能推导为用户安装已升级。
- 区分本仓 CLI source、实际 `PMAI_HOME` 和消费仓 audit target。首次检查只读；既有升级授权按原范围执行，不从本计划推导全局升级或迁移授权。

### 3.2 护栏任务

重点入口为 [`decision-gate-guard.cjs`](../../hooks/decision-gate-guard.cjs) 和 [`finalize-route-guard.cjs`](../../hooks/finalize-route-guard.cjs)。两者存在坏输入、超限或超时后退出而未输出阻断的路径；这说明单个 Hook 的异常处理有缺口，尚不能据此宣称整个授权链已经被绕过。

实现前先写明异常行为表：

| 情况 | 目标行为 |
|---|---|
| 已确认是 PMAI 消费仓，关键校验输入损坏、跨根或校验器失败 | 停止受保护动作，说明失败原因和恢复办法 |
| 普通非 PMAI 仓 | 保持 no-op，不因无 PMAI 元数据阻断用户工作 |
| 生成器仓 | 按生成器开发规则处理，不套消费仓 lifecycle |
| 仓库身份无法判定 | 使用已有三态身份模型，结合可信调用位置判定；不能只信 payload，也不能全局一律放行或一律阻断 |
| 宿主自身杀死 Hook、未加载 Hook 或忽略阻断协议 | 记录为宿主能力问题，由 H2 真实验证；脚本输出不能冒充已拦住工具 |

复用 [`repo_identity.py`](../../scripts/_lib/repo_identity.py) 的身份合同，避免每个 Hook 发明一套判定。覆盖坏 JSON、错误形态、超限、超时、依赖缺失、跨根 payload、合法请求，以及普通仓不误伤。恢复后允许合法重试，不能靠关闭 Hook 解决阻断。

### 3.3 发布门任务

[`run-release-gate.sh`](../../tests/run-release-gate.sh) 要求 runner、证据 Judge 和语义 Judge；[`harness-release-gate.yml`](../../.github/workflows/harness-release-gate.yml) 需要与该要求对齐。

- 补齐语义 Judge 配置传递，核验实际 Runner/Judge CLI、版本、凭据与执行环境 readiness；只定义命令字符串不算能力可用。
- 明确仓内维护的核心用例清单，不能只凭默认单个 finalize 案例宣称验证完整旅程。H3/H5 完成后再纳入旅程，未实现前不声称已经覆盖。
- 缺配置、空用例、运行失败、Judge 失败、必要证据缺失或必测用例 skip 均阻断；fake runner 只能证明测试编排。
- CI 先核验确定性合同，再执行明确选中的真实场景；保留失败产物和框架 revision。
- 明确“候选 revision 通过 gate → 发布相同 revision”的流程。现有 tag 触发检查发生在 tag 创建后，本身不等于发布前门禁；后续 tag 检查可作为复核。

仓内 H1 发布配置使用固定的 `evals/release-suite.json`。以下以仓内 Codex 适配器为例；三个适配器命令均须配置，CLI 与认证依赖按实际选择准备：

| 配置 | 内容 |
|---|---|
| `PMAI_CODEX_VERSION` | 仅选择默认 `codex` 执行器时需要的固定 CLI 版本（`x.y.z`），不自动使用 latest |
| `PMAI_SKILL_EVAL_RUNNER` | `python3 scripts/skill-eval-codex-runner.py` |
| `PMAI_SKILL_EVAL_JUDGE` | `python3 scripts/skill-eval-readonly-judge.py` |
| `PMAI_SKILL_EVAL_SEMANTIC_JUDGE` | `python3 scripts/skill-eval-semantic-judge.py` |
| `PMAI_CODEX_COMMAND` / `PMAI_JUDGE_CODEX_COMMAND` | 可选的已准备执行器或包装命令；未指定时为 `codex` |
| `OPENAI_API_KEY` Secret | 使用该认证方式时提供，实际评测步骤按原合同传递；默认 Codex 通过 stdin 登录，不是所有适配器的必填项 |

候选提交先通过 `workflow_dispatch` 在对应分支运行 gate；核对产物中的 revision、必测用例和独立 Judge 结果后，才发布同一提交。当前工作流不自动创建 tag 或 Release，也不把 tag 创建后的补测当作发布前批准。本地可先执行 `python3 scripts/release-gate-preflight.py --cases-only` 检查用例，再配置三个命令并执行完整预检。预检不调用模型；通过预检也不代表真实评测已通过。

CLI 安装与凭据入口分别依据 [官方 CLI 源码说明](https://github.com/openai/codex#installing-and-running-codex-cli) 和 [官方认证文档](https://developers.openai.com/codex/auth/)。CI 先按配置生成依赖计划：只有所选仓内适配器使用默认 `codex` 时才通过 npm 安装固定版本，并在提供 Key 时登录。自定义适配器或执行器须在工作流中准备其真实依赖及认证，不会借此跳过后续检查；仓内 Codex 适配器仍检查其实际执行器的 CLI flags 和登录状态，不兼容或未认证时阻断。

**H1 验收**：用护栏、skill-eval 和发布编排回归证明异常正确阻断，配置缺少 Runner、证据 Judge 或语义 Judge 时不能通过，并核对 CI 配置与脚本要求一致。真实模型运行和远端 CI 的执行结果分别记录，不追加为 H1 的完成条件；也不能把 H1 回归通过称为真实发布验证通过。

## 4. H2：真实宿主验收

在既有宿主矩阵中增加“宿主版本、OS、调用方式、验证时间、证据位置”，不新增运行时能力注册系统。

| 验收项 | 必须看到的事实 |
|---|---|
| Skill 与项目入口 | 真实会话读到正确来源；仓内候选与用户全局安装不混用 |
| 工具拦截 | 实际文件修改或命令被阻断；生成了配置或打印 deny 不算完成 |
| 用户答复绑定 | 确认对应当前展示问题；旧答复、恢复后的摘要不能替代本轮授权 |
| Builder / Verifier / Judge | 任务和实际执行身份、候选 commit、证据引用一致；降级准确报告 |
| 续接与恢复 | 换会话或中断后从真实 checkpoint 继续，不重做已落地主线动作 |
| 环境能力缺失 | 缺解释器、锁原语、Hook、child 或浏览器时，说明具体受限动作 |

先验证当前可用的完整主控组合，再验证另一完整主控。Claude Code 和 Codex 的实现及验证结果分别记录；OpenCode 保持 Builder 范围，不扩为主控。`main-fallback` 必须明确非独立，不能用任务 ID 或不同目录冒充执行隔离。

平台验收按 OS 分开。PM 已要求本轮适配 Windows：采用 PowerShell 入口和 Windows 本地 Cygwin 兼容运行时，验证文件锁、目录绑定、不可覆盖重命名、Node/Python 路径、初始化与恢复；不依赖 WSL 或远端机器。兼容运行时与原生 Windows Python 是不同执行环境，支持结论分别记录，不能从脚本存在推导全部宿主已通过。

宿主验证优先覆盖 PM 实际使用环境。PM 主要使用 Mac：Windows 兼容运行时用于本地开发与回归，Windows 原生宿主验证暂停；后续在 Mac 的真实业务使用中完成 H2 核验并开展 H3 走查，旅程通过仍须满足对应的宿主能力前提。

## 5. H3：先走通，再固定旅程和驱动

### 5.1 PM 首轮走查

选择一个小而可信的业务任务，在隔离消费仓里由真实 PM 走完首轮。开局只给背景和产品意图；产品决定由 PM 作出，不为评测提前填好 Proposal、规格或批准收据。记录原始对话、实际产物、需要 PM 额外解释的地方和最终验收结果。

PM 在此阶段只需给业务方向、回答产品取舍并验收结果。Runner、日志、Git 隔离、重复统计由框架工程承担。

### 5.2 三类核心旅程

| 旅程 | 自然语言过程 | 关键验收 |
|---|---|---|
| J1 完整交付 | 初始化 → Proposal → Design → Spec → Build → PM 修改意见 → 明确定稿 → main → 文档 | 方向未漂移；代码确实可用；规格、现状、主线一致；PM 不必提示内部命令 |
| J2 后续模块继承 | 在本次运行真实完成的首模块上提出第二模块需求 | 复用对象、权限和规则；不重复询问已确认事实；方向变更与模块变更正确分流 |
| J3 中断恢复 | 在明确事件点中断，再让主控继续 | 保留 WIP；识别当前阶段；不重复 landing；文档未完成时从 docs_pending 续接 |

J2/J3 使用该次运行实际生成的前序产物；冻结中间状态可以用于单点回归，但不能冒充完整旅程。J3 采用可验证事件触发，例如已落地主线但文档尚未完成，不采用“睡固定秒数再随机杀进程”。故障注入只作用于隔离测试环境。

J1 设置 Web product 和非 Web product 两个变体：Web 验证真实浏览器交互，非 Web 验证无浏览器、无 dev port 也能按项目定义合法完成。

### 5.3 多轮与重复驱动

扩展 [`skill-eval.py`](../../scripts/skill-eval.py) 和现有 Runner adapter，增加 journey、多轮用户输入、session 恢复、repeat 和汇总能力，复用独立文件/Git 采集和只读 Judge。

- 根据真实走查冻结业务背景、PM 已确认取舍和允许回答的分支，形成受约束的 PM 应答脚本。
- 脚本通过宿主正常用户输入接口回应；不直接写决定收据、规格、lifecycle 或验收成功。
- 未覆盖问题标为脚本覆盖缺口，不能随意替 PM 发明决定，也不能把该轮算通过。
- 被测 Agent 只看到业务输入和正常项目上下文。隐藏 rubric、精确下一步 Skill、评分证据不能作为额外提示。
- 同一旅程保留真实阶段连续性；不同重复使用全新 workspace/session，并隔离个人记忆，防止前一次答案泄漏。
- 框架、fixture、宿主、模型/provider、reasoning、权限、依赖和 Judge 配置共同冻结；敏感凭据不写进产物。

**验收**：先证明一次端到端运行可追溯，再运行小批量；驱动无法继续时必须报告原始失败，不允许评测器补好状态后继续宣称成功。

## 6. H4：Build 最小诊断与反馈闭环

### 6.1 采什么、放哪里

首版只采 Build 开始/结束、步骤结果、耗时、失败原因、重试和恢复引用。沿用 [`build-timing.py`](../../scripts/build-timing.py) 与现有 evidence 中可复用的信息，但不修改已封存验收产物。

拟采用独立的本地 `.runs/diagnostics/<work_id>/<run_id>.jsonl`，写入 Git 本地 exclude；每个 run 使用独立文件，明确部分写入、并发与大小上限。它只是可丢弃诊断数据，不是新的产品决定日志或 lifecycle 真相源。

最小字段为：`work_id / run_id / session_id / attempt_id / step / input_digest / outcome / reason_code / duration_ms / evidence_ref`。宿主 ID 仅使用可核验值，缺失记 unknown；不复制业务正文、凭据或完整对话。输入指纹须覆盖本步骤实际使用的 authority、实现内容及相关配置，不能只看 HEAD 而漏掉未提交修改。

现有 `timing.json` 参与 finalization 校验，不能以“观测不阻断”为由弱化该合同。新诊断写入失败只报告“观测不完整”，实际验收失败仍按原规则阻断。

### 6.2 自动识别的两条规则

| 规则 | 识别条件 | 主控收到后的动作 |
|---|---|---|
| 同输入连续失败 | 同 work、step、实际输入指纹和 reason 连续失败 3 次；成功或输入改变重置 | 停止机械重复，检查证据并分流；3 次是首版待实测校准的阈值 |
| 有开始、无结束 | 发现未闭合步骤，再核验宿主/进程与 checkpoint | 区分仍在运行、确认中断、等待 PM 和未知；确认中断后按原 checkpoint 恢复 |

识别在执行结果返回、恢复和 status 读取时触发；没有常驻进程，关闭会话后不会承诺主动告警。长时间没有新日志不能单独证明卡死。相同异常摘要应去重，已解决事项不反复提示。

诊断汇总通过 [`_lib/state.py`](../../scripts/_lib/state.py) 的共享读取入口提供，[`status-view.py`](../../scripts/status-view.py) 继续只做展示，不自行复制扫描逻辑。PM 看到问题、影响和下一步；原始诊断只在定位时展开。

### 6.3 识别之后谁修

| 归属 | 消费仓主控 | 框架仓 |
|---|---|---|
| 业务实现或本项目依赖 | 在已有授权内修复、验证、继续 | 仅在发现共性框架缺口时介入 |
| PMAI Skill、Hook、合同、恢复脚本 | 保留 checkpoint，整理最小证据和复现；不得修改全局框架或绕过门禁 | 复现、修复框架源资产、补回归、形成可分发版本 |
| 宿主、网络、权限或环境 | 明确缺失能力；执行已授权的重试或恢复 | 修适配缺陷，不替宿主宣称支持 |
| 证据不足 | 继续采集最小证据，不武断定责 | 根据交接材料复核归因 |

扩展 [`feedback/SKILL.md`](../../skills/feedback/SKILL.md) 时，先读取关联诊断和引用，再按需核对固定原始会话快照；仍保持只读交接职责。没有精确 session locator 的宿主，不靠“最近会话”降级。

交接至少包含：框架与宿主版本、失败步骤、预期与实际、输入指纹、证据范围、checkpoint、已尝试处理及其结果。流程为“消费仓发现 → 框架仓复现修复 → 版本验证与分发 → 按授权升级 → 消费仓恢复”。自动识别不等于自动跨任务发送、升级或自修改框架。

**验收**：模拟同输入重复失败、WIP 变化、确认中断、仍在运行、等待 PM、证据不足及诊断写入失败，验证正确分流、无误报阻断、无状态污染；用真实问题验证交接足以让框架仓复现。

## 7. H5：重复评测与放行

先跑一次校准运行，确认业务脚本、工具能力和 Judge 可用，再冻结候选组合。核心 J1/J2/J3 各重复 5 次；J1 的 Web 与非 Web 变体分别验收和统计，不能用一个变体替代另一个。每次 J2/J3 所需的前序旅程成本也计入预算。

每条旅程同时报告：硬约束是否守住、独立语义判断、业务完成率、非计划人工救场次数、耗时、模型报告的 token 用量，以及具体失败类别。正常产品问答不是人工救场；手工修状态或提示内部命令属于额外干预。工具或宿主不提供 token 时记不可得，不用文本字节数伪装 token。

首版候选放行标准：

- 必测组合没有硬约束违规、证据缺失、skip 或未解决的异常。
- 同一候选上，每个必测旅程/变体的 5 次运行均通过机器事实与独立语义验收，没有非计划人工救场。
- 环境失败、Judge 失败和脚本缺口单独列出，不能计为通过。补跑保留原始失败；若框架或脚本发生变化，应按新 revision 重新形成受影响的完整批次。
- 小样本通过只作为初始回归门，不宣称已经证明高可靠性，也不从单一宿主/模型结果外推其它组合。

普通改动先跑受影响的确定性测试和关键旅程；共享脚本、Hook、评测编排或跨入口行为变更按仓规跑完整回归。稳定候选再执行完整必测清单，不在日常每次 PM 操作时启动昂贵评测。

**资源估算方法**：首轮测得各旅程的耗时与 token 后，按“单次实测成本 × 必测重复数 + 前序链路 + 故障定位补跑”给出范围，再安排批次。未测量前不承诺日历工期或固定模型费用；使用已有预算授权，超出范围时在启动相应批次前明确处理。

## 8. H6：有证据再优化上下文

以 H3/H5 的真实读文件和工具记录定位重复加载、无关引用或过大必读文件，先选一个明确热点。优先评估 Design 的规则加载与 context pack 来源选择，但不能仅凭文件长就裁剪。

- 保留必需产品事实、授权合同和恢复规则；摘要要能定位权威原文，不能成为新的决定真相源。
- 区分可复用内容与必须因文件变化、会话恢复或模型切换重新读取的内容，不牺牲 currentness 换取读取量下降。
- 在相同旅程、宿主/模型、权限和 Judge 下做前后重复对照；同时看输入量、工具调用、耗时与语义结果。
- 实施前根据热点冻结具体优化目标；达标且无产品质量、边界或恢复回归才保留。信号不足时保留基线，不扩大重构。

## 9. 交付与回退

框架工程在本仓处理实现、测试和文档；消费仓承担真实体验与问题证据；PM 负责产品选择、结果验收及超出现有授权范围的动作。计划不会把工程日志整理或内部命令编排推给 PM。

每个实现批次应能独立审阅：说明解决的具体失败、修改的入口、验证证据、尚未验证的环境，以及回退办法。涉及 `skills/ / scripts/ / templates/ / hooks/` 时同步更新 CHANGELOG 未发布段；当前进度和测试数字只写 RUNTIME。

代码回退不覆盖消费仓 WIP，也不重置已落地主线事实。运行问题从现有 checkpoint 恢复；需要退回框架版本时先核验活动合同兼容性，再使用既有升级/固定版本路径。已完成的设计按仓规归档，并更新导航。
